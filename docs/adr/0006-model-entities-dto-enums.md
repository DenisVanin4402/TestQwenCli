# ADR-006. Внутренние модели, DTO и сущности

**Статус:** Принят. **Редакция:** 04.10.2026.

## Причина

Модель описывает необходимые данные сценария. Дублирующие объекты, идентификаторы без потребителя и дополнительные версии увеличивают количество состояний, которые приходится согласовывать.

## Решение

Внутренние модели располагаются в agent-model; generated wire DTO — в соответствующих API-модулях. Используются обычные Lombok POJO с нужными `@Getter`, `@Setter`, `@NoArgsConstructor`, `@AllArgsConstructor`, а не Java records. DTO именуются с суффиксом DTO; согласованные имена OperationContext/WorkflowManager сохраняются. Конструкторы не выполняют бизнес-валидацию или скрытое копирование. Предметные перечисления заменяют строки там, где набор значений известен.

| Группа | Назначение и содержание |
|---|---|
| Вход use case | Команда/намерение, идентификаторы входа и переданные предметные данные; не ACL DTO и не заранее вычисленное целевое состояние. |
| Контекст и подготовка | Принадлежность организации/пользователю/платежу, снимок данных операции, идентичность подготовки и отдельное согласие именно на неё. Новый черновик требует нового согласия. |
| Предметный результат | Исход выполнения, код и типизированные данные для оркестратора; без текста, templateId, HTTP и полей GA. Это результат Action/FSM и данные для persistence. |
| Подготовленный ответ | Содержание и признак завершения для входного адаптера. Создаётся оркестратором вне FSM, не сохраняется в ExtendedState. Существующие ResultDTO/TurnOutDTO переиспользуются, если их смысл соответствует этой границе. |
| Контекст внешней операции | OperationContext: UUID operationId, String epkId, digitalUserId, paymentId, необязательный PaymentDetailsChangesDTO changes. Передаёт подтверждённый снимок данных менеджеру. |
| Persistence | SessionEntity как постоянный семафор и носитель formatId; native-модель принадлежит библиотеке SSM. JPA entities доступны DB-реализации, а не бизнес-потребителям. |

PaymentDetailsChangesDTO предусматривает строковые recipientInn, recipientAccount, recipientName, paymentPurpose. Для STATUS changes отсутствует. В будущей операции уточнения передаётся непустое подмножество изменений: null означает отсутствие изменения, пустая строка не означает очистку. Наличие модели не разрешает реализовывать RECALL/DETAILS до их этапа и внешних контрактов.

operationId идентифицирует логическую внешнюю операцию, не попытку или внутреннюю команду FSM. В контексте не нужны sessionId/requestId для обратной доставки: результата менеджер не возвращает. Данные подтверждённой операции не перечитываются из изменяемого черновика.

Не создаются domain entities поверх DTO без самостоятельной обязанности. Удаляются FsmBindingEntity, журнал команд, модели владельцев/попыток corr и поля без потребителей. Счётчик представления или идентификатор подготовки сохраняется только при реальном потребителе; это не основание сохранять expectedRevision старого раздельного load/apply.

По [task02](../tasks/task02/impl_design.md) нормализованный вход использует один SessionEvent. Ответ TurnOutDTO содержит result, terminal, confirmation и availableOperations напрямую; SessionViewOutDTO/PreparationViewDTO удалены. Внутренний запрос читает SessionSnapshotDTO. Сохранённые типы status-v3 не изменяются.

## Проверка

После согласованного ревью внутренние причины представлены `ResultCode`; сохраняемый `TurnOutcome` связан с ним явно. Именованные mapper-методы и Lombok builder исключают позиционное копирование длинных DTO. `TurnOutDTO.terminal` передаёт достоверно установленную завершённость независимо от наличия полной проекции: контролируемая ошибка после восстановления COMPLETED не теряет финальность и не требует повторного чтения FSM.

Review проверяет назначение каждой группы и отсутствие текста/протокола в результате FSM. Смысл полей и enum документируется по [ADR-011](0011-russian-code-documentation.md). Принадлежность, согласие и допустимость перехода проверяются на своей границе один раз, без каскада одинаковых проверок в DTO, mapper, Action и persistence.
