# ADR-007. Роль LLM и пределы её полномочий

**Статус:** Принят. **Редакция:** 07.10.2026. Task03/04 задают технический клиент и классификацию STATUS. В task05 выбран RAG вне транзакции; [дизайн реализации](../tasks/task05/impl_design.md) и [задачи](../tasks/task05/tasks.md) явно согласованы 06.10.2026; реализация и [валидация task05](../tasks/task05/validation.md) завершены. Запрет справки после завершения пока только клиентский.

## Решение

**Принятое уточнение task08, 07.10.2026:** пользователь требует хранить описания доступных операций в самой базе знаний и расширять их вместе с операциями. Справочный provider передаёт полный текст ресурса без добавления каталога и требований к Markdown-заголовкам. Источник найденного ответа обязателен: конкретный раздел с меткой вроде KB-01; `found/answer/sourceIds` сохраняется. Формат метки допустимо проверять; [согласованный дизайн task08](../tasks/task08/impl_design.md) предусматривает также проверять наличие полной метки в ресурсе без фиксированного списка разделов и зарезервированной KB-00. Это заменяет требования task05/07 к форме KB-заголовков, синтетической KB-00 и справочному каталогу, но сохраняет одну попытку, ответы только по знаниям и каталог исполняемых команд в классификаторе. Архитектура, дизайн реализации и [задачи](../tasks/task08/tasks.md) явно согласованы 07.10.2026; реализация и [независимая валидация](../tasks/task08/validation.md) завершены. Предложение review удалить sourceIds отменено уточнением пользователя.

**Task07, 07.10.2026, последнее уточнение:** пользователь поручил заменить списки отсутствующих знаний/возможностей положительной справкой о комиссиях, сроках, графике и валютах. Наименование — «Банк», стиль — профессиональная банковская справка для обычных клиентов; оговорки об учебных, демонстрационных или вымышленных условиях в знаниях и ответах убираются. Комиссия за запрос по RUB — 50 рублей. Ответы «Что делает агент?»/«Что ты можешь?» перечисляют зарегистрированные операции и темы справки. Это заменяет содержание task05 об отсутствии тарифов/сроков, но сохраняет запрет модели дополнять источник произвольными фактами или выполнять действия через справку. Передача каталога операций в существующий REFERENCE и новые статьи согласованы в [impl_design.md task07](../tasks/task07/impl_design.md) и [knowledge.md](../tasks/task07/knowledge.md); дизайн реализации и [задачи](../tasks/task07/tasks.md) явно согласованы пользователем 07.10.2026; код реализован, автоматические проверки пройдены; браузерная приёмка task07 открыта.

**Принятое уточнение task06 от 06.10.2026:** пользователь выбрал [A — представление текущего шага по снимку](../tasks/task06/arch_design.md). Справка, отсутствие сведений, уточнения и недопустимая команда получают серверную навигацию: на старте доступные операции, на активном шаге вопрос о продолжении и «Да»/«Нет», после завершения без действий. Для этого используется снимок текущего хода либо короткое чтение после LLM по ADR-010; прежний запрет чтения task04/05 в этой области заменён. Справка/уточнение не изменяют FSM. Кнопки продолжения/сброса не вызывают LLM; «Да» не подтверждает операцию. Архитектура принята, [дизайн реализации](../tasks/task06/impl_design.md) и [задачи](../tasks/task06/tasks.md) явно согласованы 07.10.2026; код реализован, автоматические проверки пройдены; браузерная приёмка открыта.

**Уточнение task05 от 06.10.2026, последняя редакция:** [вариант A](../tasks/task05/arch_design.md): LLM вне транзакции, справка в любом нетерминальном состоянии, включая confirmation с активным текстом. Первый разбор определяет справку, второй отвечает по полному тексту знаний на 2–3 страницы. Отдельного поиска/embeddings/векторной БД нет. Кнопка с непустым user_input отклоняется до LLM с просьбой выбрать один источник. Действие с вопросом, несколько действий или неоднозначные смыслы текста ничего не выполняют и требуют выбора/уточнения одного. Несколько справочных вопросов допустимы. Для справки одна попытка, затем HTTP 500 при сбое; для разбора — до трёх одинаковых попыток.

Это заменяет приоритет кнопки над текстом task04 и прежний запрет ввода на confirmation; отдельное подтверждение/отказ сохраняются. Справка не меняет статус, подготовку и сохранённый результат; projectionVersion не сравнивается и LLM не повторяется из-за смены шага. В реализованной task05 чтения нет; выбранная task06 добавляет чтение для навигации после LLM. Предварительный серверный запрет справки после завершения не вводится: ввод закрывает UI, а обнаруженное при оформлении ответа завершение отражается в terminal. JSON разбора содержит route=COMMAND/REFERENCE/MIXED/UNCLEAR и actionCode только для COMMAND. Справка содержит found/answer/sourceIds; источник метки проверяется по KB-разделам. Валидные информационные маршруты не повторяются. По уточнению пользователя корректный справочный ответ без меток источников преобразуется в «нет сведений», его текст отбрасывается; остальные нарушения контракта остаются технической ошибкой. Реализация и [валидация task05](../tasks/task05/validation.md) завершены, но не являются проверкой task06.

По прямому уточнению пользователя в task04 общий клиент пишет на INFO полный system/user-промпт и текст ответа, связывая их callId. Авторизационные ключи, токены и заголовки не логируются. Это заменяет прежнее ограничение task03 на логирование содержимого.

05.10.2026 пользователь выбрал вариант A [task03](../tasks/task03/arch_design.md): штатная автоконфигурация GigaChat и синхронный Spring AI ChatClient уже в текущем этапе POC/тестового UI. Это клиент и отдельный smoke, без текстового маршрута ACL, RAG, tools и вызовов из FSM. Один технический вызов генерации выполняется без автоматических повторов; OAuth-обмен учитывается отдельно. Локальный запуск без включения клиента не требует credentials. Дизайн реализации и задачи явно согласованы 05.10.2026; реализация проверяется.

05.10.2026 пользователь выбрал вариант A [task04](../tasks/task04/arch_design.md): классификация самостоятельного текста до семафора/транзакции через существующий ChatClient. Ответ — строгий JSON модели MessageAnalysisDTO с actionCode. Код проверяется по общему каталогу операций, приложение формирует тот же SELECT, что и для саджеста; допустимость определяет SSM. Сейчас поддерживается STATUS выбранного платежа без извлечения реквизитов. Будущий DETAILS расширит модель существующим PaymentDetailsChangesDTO; RAG пока не реализуется.

Непонятый текст возвращает вежливое уточнение из файла шаблонов без создания FSM, обеспечения семафора и второго вызова LLM. Task06 добавляет чтение для выбора навигации, заменяя прежнее правило task04 об отсутствии чтения. Это успешная обработка сообщения, а не технический сбой. System/user-промпты полностью хранятся в YAML; JSON Schema формируется из прикладной модели. Подтверждение и отказ поступают только через специальный механизм GA, текст не создаёт CONFIRM/CANCEL.

Task05 добавляет определение необходимости справки к основному разбору; второй логический вызов отвечает по полному тексту знаний. Извлечение изменений остаётся последующим расширением. Отдельная дополнительная классификация для справки не требуется.

LLM не выбирает переход FSM, не изменяет полномочия, не подтверждает операцию вместо пользователя и не вызывает corr. Результат разбора проверяется приложением; окончательная допустимость события определяется guards SSM. Обновление данных подготовки требует нового подтверждения. Операционные сводки и ответы готовит оркестратор по локальным шаблонам, без генерации моделью.

## Число вызовов

| Вход | Лимит логических вызовов |
|---|---|
| Единственная команда/клик; либо конфликт кнопки с текстом | 0; конфликт ничего не выполняет и просит выбрать один источник |
| Обычный текст | Не более 1 для разбора |
| Разбор выявил вопрос, требующий RAG | Не более 2 всего: разбор и справочный ответ; в task05 весь текст знаний передаётся второму вызову |

Логический вызов — уникальная комбинация полного промпта и параметров. Дополнительная классификация, переформулирование поиска, ранжирование, исправление JSON новым промптом или оформление операционного ответа не разрешают превысить лимит. Второй вызов зарезервирован для RAG. Если материалов нет или намерение неоднозначно, возвращается предусмотренное уточнение, без дополнительных генераций для угадывания.

Для разбора сохраняется согласованная политика технических попыток: исходный вызов и не более двух повторов после сбоя, включая невалидный структурированный ответ. Повтор использует тот же снимок входа, полный промпт и параметры; после успеха прекращается. Добавление просьбы «исправить JSON» или изменение параметров считается новым логическим вызовом.

Эта политика применяется к структурированному разбору task04 и будущего MVP. Повторы локальны для классификатора; общий технический клиент task03, WorkflowManager и corr не получают автоматических повторов. Валидный null не повторяется. Повтор входящего сообщения должен отсекаться входной библиотекой после её подключения; текущий маркер не даёт такой гарантии по [ADR-012](0012-method-idempotency-and-resilience4j-retry.md).

## Проверка

На этапе текстового ввода проверяются лимиты промптов и попыток, неизменность параметров при техническом повторе, короткие ответы, невалидный разбор и отсутствие ложного согласия/submit. Stub проверяет протокол. По task04 отдельный прогон агента с реальным GigaChat на размеченном наборе до 10 сообщений считает TP/TN/FP/FN и технические ошибки отдельно; результаты остаются в target. Новая система оценивания общего назначения и отдельный слой для каждого вида генерации не требуются.
