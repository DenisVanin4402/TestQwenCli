# ADR-007. Роль LLM и пределы её полномочий

**Статус:** Принят. **Редакция:** 06.10.2026. Task03/04 задают технический клиент и классификацию STATUS. В task05 выбран RAG вне транзакции; детали обсуждаются до дизайна реализации, разрешения на код нет.

## Решение

**Уточнение task05 от 06.10.2026:** пользователь выбрал [вариант A](../tasks/task05/arch_design.md): короткие чтения состояния, LLM вне транзакции, справка только на выборе STATUS. Первый разбор определяет необходимость справки, второй ищет ответ в полном тексте знаний на 2–3 страницы. Отдельные поиск/embeddings/векторная БД не добавляются. Команду с самостоятельным вопросом попросить разделить без применения обеих частей. Для второго вызова одна попытка; сбой даёт HTTP 500. Первый разбор сохраняет до трёх одинаковых попыток. На confirmation и COMPLETED текст отклоняется до LLM; на confirmation свободный ввод запрещён и в UI.

Это частично заменяет правило task04 о разборе до любого чтения сессии и уточнении без чтения FSM: чтение нужно для допуска текста и актуальности ответа, справка не создаёт события/записи. Путь операций и полномочия LLM не расширяются. Подготовлены проекты знаний и промптов; они обсуждаются, код не изменён. Ниже описание task04 применяется с этим уточнением.

По прямому уточнению пользователя в task04 общий клиент пишет на INFO полный system/user-промпт и текст ответа, связывая их callId. Авторизационные ключи, токены и заголовки не логируются. Это заменяет прежнее ограничение task03 на логирование содержимого.

05.10.2026 пользователь выбрал вариант A [task03](../tasks/task03/arch_design.md): штатная автоконфигурация GigaChat и синхронный Spring AI ChatClient уже в текущем этапе POC/тестового UI. Это клиент и отдельный smoke, без текстового маршрута ACL, RAG, tools и вызовов из FSM. Один технический вызов генерации выполняется без автоматических повторов; OAuth-обмен учитывается отдельно. Локальный запуск без включения клиента не требует credentials. Дизайн реализации и задачи явно согласованы 05.10.2026; реализация проверяется.

05.10.2026 пользователь выбрал вариант A [task04](../tasks/task04/arch_design.md): классификация самостоятельного текста до семафора/транзакции через существующий ChatClient. Ответ — строгий JSON модели MessageAnalysisDTO с actionCode. Код проверяется по общему каталогу операций, приложение формирует тот же SELECT, что и для саджеста; допустимость определяет SSM. Сейчас поддерживается STATUS выбранного платежа без извлечения реквизитов. Будущий DETAILS расширит модель существующим PaymentDetailsChangesDTO; RAG пока не реализуется.

Валидный actionCode=null возвращает непосредственно в GA вежливое уточнение из файла шаблонов ответов, без чтения/создания FSM, обеспечения семафора и второго вызова LLM. Это успешная обработка сообщения, а не технический сбой. System/user-промпты полностью хранятся в YAML; JSON Schema формируется из прикладной модели. Подтверждение и отказ поступают только через специальный механизм GA, текст не создаёт CONFIRM/CANCEL.

Task05 добавляет определение необходимости справки к основному разбору; второй логический вызов отвечает по полному тексту знаний. Извлечение изменений остаётся последующим расширением. Отдельная дополнительная классификация для справки не требуется.

LLM не выбирает переход FSM, не изменяет полномочия, не подтверждает операцию вместо пользователя и не вызывает corr. Результат разбора проверяется приложением; окончательная допустимость события определяется guards SSM. Обновление данных подготовки требует нового подтверждения. Операционные сводки и ответы готовит оркестратор по локальным шаблонам, без генерации моделью.

## Число вызовов

| Вход | Лимит логических вызовов |
|---|---|
| Явная поддерживаемая команда/клик | 0 |
| Обычный текст | Не более 1 для разбора |
| Разбор выявил вопрос, требующий RAG | Не более 2 всего: разбор и справочный ответ; в task05 весь текст знаний передаётся второму вызову |

Логический вызов — уникальная комбинация полного промпта и параметров. Дополнительная классификация, переформулирование поиска, ранжирование, исправление JSON новым промптом или оформление операционного ответа не разрешают превысить лимит. Второй вызов зарезервирован для RAG. Если материалов нет или намерение неоднозначно, возвращается предусмотренное уточнение, без дополнительных генераций для угадывания.

Для разбора сохраняется согласованная политика технических попыток: исходный вызов и не более двух повторов после сбоя, включая невалидный структурированный ответ. Повтор использует тот же снимок входа, полный промпт и параметры; после успеха прекращается. Добавление просьбы «исправить JSON» или изменение параметров считается новым логическим вызовом.

Эта политика применяется к структурированному разбору task04 и будущего MVP. Повторы локальны для классификатора; общий технический клиент task03, WorkflowManager и corr не получают автоматических повторов. Валидный null не повторяется. Повтор входящего сообщения должен отсекаться входной библиотекой после её подключения; текущий маркер не даёт такой гарантии по [ADR-012](0012-method-idempotency-and-resilience4j-retry.md).

## Проверка

На этапе текстового ввода проверяются лимиты промптов и попыток, неизменность параметров при техническом повторе, короткие ответы, невалидный разбор и отсутствие ложного согласия/submit. Stub проверяет протокол. По task04 отдельный прогон агента с реальным GigaChat на размеченном наборе до 10 сообщений считает TP/TN/FP/FN и технические ошибки отдельно; результаты остаются в target. Новая система оценивания общего назначения и отдельный слой для каждого вида генерации не требуются.
