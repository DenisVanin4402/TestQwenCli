# ADR-008. SSM как единственный механизм переходов

**Статус:** Принят. **Редакция:** 06.10.2026. Заменяет прежнюю схему внешнего выбора переходов; task06 уточняет чтение текущего шага и навигационную отмену без новых состояний. Это целевое решение, не отчёт о готовом коде.

## Причина

В первоначальном решении внешний policy выбирал переход, а SSM подтверждала уже выбранную цель. Это дублировало сценарий и порождало модели согласования. Reactive API сам по себе не является основанием выносить бизнес-действия из перехода или дробить JPA-транзакцию.

## Решение

**Частичная замена 05.10.2026:** [ADR-021](0021-direct-spring-statemachine.md) отменяет заменяемую границу, FlowDefinition/FsmEngine и callback-протокол поверх SSM. Упоминания этого механизма ниже относятся к прежней реализации. SSM, отдельные guards/actions, схемы согласия, состояния, хранение и транзакционные гарантии сохраняются. Дизайн и задачи [task02](../tasks/task02/impl_design.md) согласованы 05.10.2026 с сохранением отдельных guards/actions.

- Сохраняем Spring Statemachine и штатный JPA persister. Исполнение напрямую использует SSM в agent-service; agent-db предоставляет штатный persister и репозитории по [ADR-005](0005-module-hierarchy.md).
- **SSM выбирает переход через guards и исполняет его через actions.** Внешний SessionTransitionPolicy, предварительный targetState и TransitionDecisionDTO удаляются. Оркестратор может нормализовать намерение входа, но не решает заново, какой переход допустим.
- Все бизнес-actions — синхронные **transition `.action(...)`**. Для этого пути не используются state `.doAction(...)`, переключение scheduler, фоновые действия и параллельные регионы. Завершение reactive-обработки ожидается до persistence и выхода из рабочей транзакции.
- По принятой [task01](../tasks/task01/arch_design.md) бизнес-логика находится в отдельных классах actions и guards. Общие guards — в guard.common. Конфигурация регистрирует упорядоченные цепочки: первый отказ запрещает последующие guards и action. SessionStateMachineConfiguration хранит определения и предоставляет каталог напрямую, без отдельного OperationRegistry и проверок бизнес-полей в каталоге. Техническая привязка выбирает компоненты операции, а source/event/target остаются переходами SSM. Нет отдельного EventChecks или конкурирующих CONFIRM-переходов по операциям.
- Action формирует предметный исход и данные, не текст ответа, шаблон, HTTP или ACL. Подготовка ответа находится в общем оркестраторе по [ADR-004](0004-api-domain-mapstruct.md).
- При подтверждённой операции Action **один раз** вызывает `WorkflowManager.callOperation(Operation, OperationContext)`. Обратного бизнес-результата, corr-result события или ожидания callback нет; подробности — [ADR-013](0013-outbound-retry-and-timeouts.md).

## Жизненный цикл и хранение

После захвата семафора в рабочей транзакции создаётся **один экземпляр** машины: восстанавливается native-состояние либо инициализируется отсутствующее для допустимого первого входа. На этом же экземпляре обрабатывается событие и выполняется native save. По согласованному уточнению от 05.10.2026 временный экземпляр останавливается в `finally` до выхода из транзакционного метода; затем Spring завершает commit/rollback. После обработки экземпляр не используется повторно. Нет предварительного load в другой транзакции, повторной сборки машины для save или общего кеша активных FSM.

`StateMachineEventResult.complete()` ожидает завершения обработки события до сохранения; `stopReactively().block()` отдельно ожидает остановки экземпляра. Машина создаётся через builder, без `StateMachineService.acquireStateMachine`, поэтому `releaseStateMachine` не требуется. Ошибка остановки без предшествующей ошибки вызывает rollback; при уже возникшей ошибке добавляется как suppressed и не подменяет основную причину. Перенос очистки в `afterCompletion` не нужен для согласованного синхронного пути.

Native ExtendedState хранит предметный контекст, подготовку, идентичность согласия и последний предметный результат. Task01 добавляет сохраняемый снимок подтверждаемых значений; схема операции едина для его подготовки и проверки. Согласие связывается с активной подготовкой по sessionId + preparationNo. Номер не переиспользуется после отказа; preparationId остаётся внутренним UUID. Готовые тексты и templateId не сохраняются. Идентификатор native-записи — строковое представление sessionId.

На технической SessionEntity хранится **один formatId** совместимости сохранённого формата. Для существующего снимка он проверяется до десериализации. Неизвестный/несовместимый формат, чужой sessionId или неожиданный тип данных означают ошибку восстановления, а не повод создать новую FSM. FsmBindingEntity и отдельные engineCode/bindingVersion/serializationVersion/flowVersion/contextSchemaVersion удаляются. Конкретное обновление formatId и обработка прежних локальных сессий определяются [дизайном task01](../tasks/task01/impl_design.md), который согласуется отдельно; принудительный сброс хранения не подразумевается.

Журнал команд, replay/hash, DUPLICATE, сканирование max revision и commandId без потребителя удаляются. Входная идемпотентность задаётся [ADR-012](0012-method-idempotency-and-resilience4j-retry.md), а сериализация работы сессии — [ADR-010](0010-session-execution.md). История действий и аудит отложены; listener или новая таблица взамен журнала не вводятся.

## Сценарий POC

**Категории состояний, уточнение пользователя в task06:** инициирующее (`INITIAL`), промежуточные (`INTERMEDIATE`), терминальное (`TERMINAL`). Сейчас это соответственно CHOOSING_REQUEST_TYPE, AWAITING_CONFIRM, COMPLETED. Категория задаётся явно у состояния, управляет общей навигацией и не является отдельным состоянием/сохранённым полем сессии. Будущий AWAITING_DETAILS и другие шаги подготовки из [MVP](../stages/03_mvp/requirements.md) — промежуточные: «Да» показывает их собственное представление, «Нет» идёт по их CANCEL-переходу с очисткой данных. Категория не выбирает переход вместо SSM и не отменяет guards. Конкретный способ описания категории и расширения renderer представлен в [impl_design task06](../tasks/task06/impl_design.md), явно согласованном 07.10.2026. Будущие шаги сейчас не добавляются.

**Уточнение task06 от 06.10.2026:** выбран [вариант A](../tasks/task06/arch_design.md). Представление текущего шага по «Да» читается без события, actions, записи или повторной подготовки. Навигационный «Нет» использует семантику CANCEL в одной транзакции, сохраняя исходный контекст и монотонный счётчик подготовок. Справка/уточнение не меняют FSM; при недопустимой команде показываются предусмотренные task06 навигационные кнопки. Ни новое состояние, ни сохранённый текст, ни изменение native-формата не требуются. Точные изменения [дизайна](../tasks/task06/impl_design.md)/[плана](../tasks/task06/tasks.md) явно согласованы 07.10.2026; код реализован, автоматические проверки пройдены; браузерная приёмка открыта.

Достаточны CHOOSING_REQUEST_TYPE → AWAITING_CONFIRM → COMPLETED. В AWAITING_CONFIRM допустимы только CONFIRM (отправить запрос) и CANCEL (удалить подготовку и вернуться к выбору). По решению пользователя от 04.10.2026 переход SELECT с напоминанием из этого состояния удалён: повторный выбор возвращает недопустимую команду без изменения подготовки и вызова менеджера. После отказа новый выбор создаёт новую подготовку и требует отдельного согласия. Самостоятельный перезапуск STATUS также удалён. Успешный вызов менеджера с успешным commit завершает сессию. SUBMITTING, SUBMIT_UNKNOWN, AWAITING_RETRY_CONFIRM и события внешних результатов в новый путь не переносятся. Новая операция после COMPLETED требует новой сессии.

## Проверка

Проверяются реальный guard, вызов Action, один экземпляр restore/execute/save, совместное сохранение и rollback с native persister. Для используемой конфигурации проверяется сохранение JPA-транзакции в transition Action и доведение ошибки SSM до её границы. Ранее проведённая локальная проба SSM 4.0.2 подтвердила этот путь в плоской машине; она не заменяет приёмку новой реализации и не распространяет гарантию на произвольные scheduler/regions.
