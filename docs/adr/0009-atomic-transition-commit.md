# ADR-009. Одна рабочая транзакция FSM и предметного результата

**Статус:** Принят. **Редакция:** 05.10.2026. Заменяет раздельные транзакции admission/apply/result и сохранение готового ответа в FSM.

## Решение

После отдельного обеспечения семафора по [ADR-010](0010-session-execution.md) SessionExecutionService в agent-service начинает одну рабочую JPA-транзакцию:

1. Захватывает семафор сессии через SELECT FOR UPDATE NOWAIT.
2. Читает formatId и восстанавливает либо создаёт один экземпляр FSM.
3. Передаёт событие SSM; guards выбирают переход, синхронный transition Action исполняет бизнес-действие.
4. Сохраняет native-состояние, предметный результат и необходимые прикладные данные в той же БД/транзакции.
5. В `finally` останавливает временный экземпляр FSM. Ошибка остановки вызывает rollback, если основной ошибки ещё нет; иначе сохраняется как дополнительная причина.
6. Spring завершает commit и освобождает блокировку. Только после успешного завершения транзакционной границы оркестратор получает результат. Возврат из тела `@Transactional`-метода ещё не означает успешной фиксации.

Граница должна охватывать полную обработку события, а не только отправку reactive-сигнала. Используются один поток исполнения и один JPA transaction manager для прикладного и native persistence. Вложенная транзакция для сохранения результата Action не вводится.

**Любая ошибка Action откатывает всю рабочую транзакцию**, независимо от места возникновения и типа исключения: бизнес-логика, mapping, БД или WorkflowManager. Ошибка, захваченная внутренним error channel/handler SSM, должна быть доведена до транзакционной границы; записать её в лог и закоммитить недостаточно. Штатный отказ guard — предметный отказ без внешнего вызова, не исключение Action.

При rollback сохраняется последнее закоммиченное состояние. Изменённый экземпляр FSM отбрасывается. Ошибка persistence/commit также не разрешает успешный ответ. Если соединение потеряно и факт commit неизвестен, нельзя утверждать, что операция точно откатилась.

## Ответ внешней системе

Атомарно сохраняется **предметный результат**, а не текст, ACL DTO или факт доставки. После commit общий SessionTurnOrchestrator выбирает/заполняет шаблон по возвращённому снимку; входной адаптер формирует wire-ответ. При ошибке Action содержание ошибки готовится после rollback. Сбой шаблона или отправки ответа после commit не запускает повторно Action/WorkflowManager и не меняет уже зафиксированный результат.

Границы транзакций, обработка ошибок и внутреннее чтение сессии описаны в [архитектуре реализации POC](../stages/01_poc/old/c4_architecture.md). HTTP GET сессии удалён по ADR-020. Подготовка ответа описана в [ADR-004](0004-api-domain-mapstruct.md).

## Необратимый внешний эффект

Во временном POC WorkflowManager непосредственно вызывает corr **внутри Action до commit и до ответа GA**. Пользователь явно принял риск: corr мог выполнить действие, а локальный commit, формирование или доставка ответа — завершиться ошибкой. Откат БД не откатывает corr; транспортный тайм-аут не доказывает отсутствие внешнего эффекта. Сообщение ошибки не утверждает, что операция точно не выполнена. Автоматический повтор запрещён.

Это временное допущение, а не распределённая атомарность. Будущий полноценный менеджер отвечает за Transactional Outbox/УСС и восстановление операций по ADR-013. Бизнес-приоритет «ответ GA перед необратимым действием» сохранён для его проектирования: успешная передача ответа GA считается доставкой клиенту. Один afterCommit обеспечивает лишь порядок относительно БД и не доказывает отправку ответа GA. Детали этого будущего протокола сейчас не реализуются.

## Проверка

Необходимы успешный commit и ошибка Action с проверкой совместного отката прикладных и native-данных, отсутствие успешного ACL-ответа при rollback, отсутствие повторного corr после ошибки. Тест не должен обещать rollback внешнего эффекта или работающий входной replay до подключения библиотеки.
