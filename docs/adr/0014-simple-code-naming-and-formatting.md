# ADR-014. Необходимый код и проверка простоты решения

**Статус:** Принят. **Редакция:** 04.10.2026.

## Причина

Первоначальная реализация проверялась на корректность принятых механизмов, но недостаточно — на необходимость самих механизмов. Разделённые транзакции породили защитные уровни, а их наличие затем использовалось как основание сохранить сложность. Новое решение должно начинаться с требуемого поведения и наиболее простого способа его обеспечить.

## Решение

Реализуется только то, что нужно текущему этапу и его критериям приёмки. Используются стандартные Spring/библиотечные механизмы, когда они сокращают ручной код и сохраняют необходимые гарантии. Универсальные конструкторы процессов, слои переадресации, запасные реализации и будущие расширения без задачи не создаются.

Перед добавлением слоя, сущности, версии или защитной проверки ответить:

1. Какой конкретный допустимый сценарий или реальный сбой требует этого механизма?
2. Какая уже выбранная граница отвечает за него? Нельзя ли устранить источник противоречия или проверить условие один раз на этой границе?
3. Почему недостаточно более простого решения? Если причина — предположение о поведении библиотеки, подтвердить его документацией используемой версии или минимальной проверкой.
4. Какое наблюдаемое поведение проверит необходимость механизма? Сам факт наличия класса, ADR или теста старой реализации не является отдельным требованием.

Это вопросы review, а не новый документ/комитет на каждый метод. При явном изменении требований пользователем фиксируется изменение гарантии, вместо скрытого сохранения старого протокола. Для временного corr принято ограничение ADR-009/013; его нельзя обходить незапрошенным outbox или выдавать за exactly-once.

Одна валидация имеет одного владельца: транспортная форма — адаптер; допустимость перехода и согласие — guards/actions; совместимость native-данных — DB/FSM; внешний контракт — исходящий адаптер. Сохраняются проверки реальных границ доверия. Не нужны повторные null/version/state проверки одного уже проверенного значения во всех слоях или два поля, независимо кодирующих один исход.

После замены **физически удаляются** старые реализации, модели без потребителей, wiring, настройки, зависимости и тесты только удалённого поведения. Не оставлять старый путь в выключенных beans, deprecated-классах, комментариях или feature flags. Исторические документы и применённые Liquibase changeset не являются runtime-кодом.

## Читаемость и инструменты

- Имена предметные: SessionState, SessionEvent, SessionTurnOrchestrator. Переименование сервиса в оркестратор не создаёт новый слой поверх старого. Префикс Poc не используется у общих бизнес-типов; допустим для настоящего профиля/контракта прототипа.
- Пакеты группируются по текущей ответственности; пустые пакеты для будущих сущностей не создаются. Слои определяются [ADR-005](0005-module-hierarchy.md), не количеством каталогов.
- В production Java нет `var`; тип локальной переменной явный. В тестах var разрешён.
- Spotless с Google Java Format AOSP: четыре пробела, порядок и очистка импортов. После изменения Java используется spotless:apply, check входит в verify. Generated-файлы исправляются через источник/шаблон.
- Документация на русском соответствует [ADR-011](0011-russian-code-documentation.md). Компактность не означает сжатый нечитаемый код.

## Проверка

Review проверяет необходимость и корректность, а не только работоспособность. ArchUnit, искусственные Good/Bad fixtures и тесты ради числа исключены. Для документации не запускается сборка приложения.
