# ADR-015. Ответственность при разработке и история этапа

**Статус:** Принят. **Редакция:** 05.10.2026. Уточнён процесс коротких доработок по поручению пользователя.

## Решение

Разработку этапа ведёт один оркестратор. Архитектор проверяет требования, границы и необходимость решения; при делегировании исполнители получают конкретную область файлов/ответственности и учитывают параллельные изменения. Делегирование не требует увеличивать число слоёв, документов или проверок приложения.

До изменения кода читаются индекс ADR, действующие решения и требования этапа. Краткая схема ответственности показывает путь входа, рабочую транзакцию, FSM, внешний эффект и подготовку ответа. Архитектор проверяет её до реализации; текущая схема POC находится в [C4](../stages/01_poc/old/c4_architecture.md), прежний план сохранён в [архиве](../stages/01_poc/old/README.md).

Постановка исполнителю:

> Покажи путь UI и GA к одному use case, ответственность классов и зависимости. Обоснуй каждый новый слой и защитный механизм конкретным требованием. Проверь более простой вариант. После реализации проверь общий путь и удали заменённый код.

Review включает два разных вопроса: правильно ли работает механизм и нужен ли он при принятых границах. Требования не выводятся из старых ADR или тестов, если пользователь уже заменил решение. Непроверенное предположение о библиотеке не оправдывает усложнение: сначала узкая проверка по ADR-014.

Схема будущей интеграции не означает её готовности. Документационная задача завершается согласованными документами; задача реализации — работающим кодом и необходимыми проверками по [ADR-017](0017-spring-http-and-database-acceptance.md). Дополнительного согласования уже разрешённой работы это решение не вводит.

## История и проверка

Новые короткие доработки ведутся через [реестр задач](../tasks/tasks.md) по [правилам проекта](../../AGENTS.md#короткие-доработки-функционала): arch_design.md с несколькими вариантами → выбор пользователя → impl_design.md и tasks.md → явное согласование обоих документов → реализация и тесты → отдельный валидатор-архитектор. Его заключение о соответствии плана и факта фиксируется в validation.md. Выбор архитектуры не разрешает начинать реализацию: пользователь должен отдельно явно согласовать дизайн реализации и задачи. После этого повторное разрешение на выполнение согласованного плана не требуется. До выбора рекомендация не считается утверждённой архитектурой.

Для таких задач документы taskNN заменяют отдельный подробный отчёт этапа; при необходимости в историю этапа добавляется ссылка. Прежние записи истории сохраняются. Это уточнение процесса не меняет архитектуру приложения.

В history.md соответствующего этапа кратко записываются задача, ответственность, принятое изменение, фактический результат и существенные проверки/препятствия. Заключение архитектора хранится рядом; историческое review не выдаётся за приёмку новой реализации.

При обновлении ADR меняются его файл, индекс и затронутые требования/планы. Действующий ADR содержит одно согласованное решение; последовательность обсуждения хранится в истории/реестре ответов, а не в противоречащих друг другу вставках.

История не содержит копий Maven-логов, XML, effective POM или dependency tree; результаты остаются в target. Не создавать дополнительные отчёты ради подтверждения отсутствия кода. Итог указывает сделанное, проверку и существенные ограничения.
