# ADR-018. Усечённый ACL 1.6 для первого этапа

**Статус:** Принят. **Редакция:** 04.10.2026. Заменяет самостоятельный локальный POST; не подтверждает интеграцию настоящей поверхности GA.

## Вход

POC использует POST /api/v1/ai/agents/{agent_code}. Формат {command, fixtureId} и POST /local-api/v1/sessions/{sessionId}/turns не возвращаются. В agent-ui-back остаётся только загрузка fixtures; GET сессии удалён по [ADR-020](0020-acl-chat-actions.md).

Уточнение второго этапа от 05.10.2026: браузерный UI использует локальное зеркало того же ACL в `agent-ui-back` по [ADR-019](0019-test-ui-acl-mirror.md). Прежнее ограничение единственным HTTP POST частично заменено; контракт и общий путь обработки сохранены.

Источник — [исходная OpenAPI-схема](../api/rest_api_acl_gigaasistant.02.013.02.yml). Производная agent-api-in/src/main/resources/openapi/acl-poc.yaml явно описывает сужение: version=1.6, обязательную UUID-корреляцию и final_message. Исходный внешний документ не переписывается ради прототипа. API/DTO генерируются Maven; tag Acl задаёт интерфейс AclApi.

Нужны Request-Id, Gigachat-Session-Id, message.version, performative, reply_with, conversation_id, sender, receiver, content.action_code; организация epk_id, пользователь digital_user_id и семь строковых полей платежа из metadata.additional_info по [требованиям POC](../stages/01_poc/old/requirements.md#3-исходные-данные-и-подготовка). Первый допустимый вход требует полного контекста. В последующих входах пропуски дополняются из сохранённых данных под семафором, явная подмена не меняет привязку сессии.

Транспортную форму, поддерживаемую версию и корреляцию проверяет адаптер один раз. Он не загружает FSM для выбора перехода. Общий оркестратор передаёт нормализованное намерение инфраструктуре; **SSM guards определяют его допустимость**. Отсутствие/повреждение FSM нельзя скрывать транспортным default.

Request-Id совпадает с reply_with; при несовпадении возвращается failure с корреляцией по ID заголовка без бизнес-перехода. Неизвестные JSON-поля игнорируются. Проверки корреляции и неизменной привязки не заменяются входной идемпотентностью и не отменяются её временным отсутствием.

Первоначальный выбор и выбор после отказа принимают request с status. В AWAITING_CONFIRM допустимы только accept_propose и reject_propose; request с status отклоняется машиной как недопустимое событие (400/failure). По решению пользователя от 04.10.2026 restart_status удалён из локального профиля: request с этим кодом возвращает 400/failure без обработки FSM. При accept/reject поля текста/действия нижнего приоритета не переопределяют явное намерение. Код status — временный код симуляции, не зарегистрированное действие GA. Остальные performative/action codes, свободный текст, proxy, LLM и полный канал добавляются только на своих этапах.

## Ответ

Action возвращает предметный результат без текста. После завершения рабочей транзакции SessionTurnOrchestrator выбирает и заполняет локальный шаблон; AclInputAdapter/AclMapper преобразуют подготовленный ответ в wire-форму по [ADR-004](0004-api-domain-mapstruct.md).

| Ситуация | Ответ |
|---|---|
| Подготовка сводки | propose с content.result и state CONFIRMATION; metadata.final_message=false по ADR-020. |
| Отказ от подготовки | inform с suggestions для нового выбора status. |
| Успешная операция и commit | HTTP 200; message.content.status_code="200"; message.performative="inform"; metadata.final_message=true; текст в content.result. |
| Ошибка | failure с content.reason и кодом по согласованному реестру; ошибка Action сначала откатывает транзакцию. Нет фиктивного успешного завершения. |

Код успеха задан [реестром кодов](../api/error_codes.md), завершение — metadata.final_message в [ACL 1.6](../api/api_contract_details_1.6.md). Отдельный «код завершения» и performative proxy для успеха не вводятся. Закрывается агентская сессия, а не весь внешний чат. WorkflowManager не возвращает бизнес-результат операции; отдельного позднего финального ответа нет.

Адресаты переставляются, conversation_id сохраняется, in_reply_to берётся из Request-Id. Оркестратор не импортирует generated ACL DTO; Action не знает этих полей. Успешная передача ответа GA считается доставкой клиенту по принятому допущению. Для временного прямого corr сохраняется риск, описанный в ADR-009/013.

## Проверка

Через настоящий ACL HTTP проверяются корреляция, полный первый контекст, запрет подмены, игнорирование неизвестных полей, подготовка, отдельное согласие, rollback и финальный ответ после commit по [ADR-017](0017-spring-http-and-database-acceptance.md). Runtime replay/конфликт payload отложены до библиотеки по [ADR-012](0012-method-idempotency-and-resilience4j-retry.md). Полные коды ошибок, платформенные шаблоны и зарегистрированные действия GA остаются внешними зависимостями соответствующего этапа.
