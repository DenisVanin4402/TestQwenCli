# ADR-020. Действия ACL и чат без API сессии

**Статус:** Принят. **Редакция:** 07.10.2026. Пользователь выбрал [task06, A](../tasks/task06/arch_design.md): серверная навигация и явные кнопки. [Дизайн реализации](../tasks/task06/impl_design.md) и [задачи](../tasks/task06/tasks.md) явно согласованы 07.10.2026; код реализован, автоматические проверки пройдены; браузерная приёмка открыта. Новые wire-поля в проекте дизайна не объявляются согласованным контрактом поверхности GA.

## Решение

**Принятое уточнение task08, 07.10.2026:** фраза «Есть незавершённая операция» применима только к активному промежуточному шагу. После отмены подготовки недопустимое подтверждение должно получать нейтральный отказ и прежние кнопки выбора операции. Это уточняет область применения текста task07; HTTP, события, guards, согласие и навигация не меняются. [Дизайн реализации](../tasks/task08/impl_design.md) и [задачи](../tasks/task08/tasks.md) явно согласованы 07.10.2026; реализация и [независимая валидация](../tasks/task08/validation.md) завершены.

**Task07, 07.10.2026:** пользователь выбрал [B — карточку подтверждения STATUS](../tasks/task07/arch_design.md): номер платежа, организация, дата, получатель из сохранённой подготовки. Локальный ACL передаёт структурированное представление и полный текст для клиентов без карточки; UI показывает одно представление. Согласие сохраняет paymentNumber/preparationNo и отдельный accept_propose. Заменяется также `INVALID_COMMAND.message` на «Сейчас это действие недоступно. Есть незавершённая операция.», с прежней навигацией task06. Конкретное поле `content.confirmation_view` и изменения UI согласованы в [дизайне реализации](../tasks/task07/impl_design.md); он и [задачи](../tasks/task07/tasks.md) явно согласованы пользователем 07.10.2026. Код реализован, автоматические проверки пройдены; браузерная приёмка task07 открыта; это локальный профиль, а не утверждённое расширение внешнего GA.

В task06 общая навигация определяется категорией состояния по [ADR-008](0008-replaceable-fsm.md): INITIAL — операции, INTERMEDIATE — вопрос и «Да»/«Нет», TERMINAL — без действий. Это распространяется на новые промежуточные шаги, например подготовку/ввод реквизитов; UI не получает собственный список состояний и не решает, является ли шаг подтверждением. По «Да» backend возвращает представление конкретного шага; не каждый промежуточный шаг выдаёт propose.

Агент определяет доступные действия локального ACL-профиля. После подготовки статуса возвращает `message.performative=propose`, текст сводки в `message.content.result`, `metadata.final_message=false` и `state[]` с `type=CONFIRMATION` и подтверждаемыми реквизитами. По task06 backend также явно передаёт кнопки «Подтвердить»/«Отклонить»; UI не создаёт их по одному propose. Отправляются прежние `accept_propose`/`reject_propose`; согласие остаётся отдельным сообщением. Значение final_message само по себе не означает подтверждение.

После отказа от подготовки агент возвращает `inform` и `suggestions[]` с `text`, `action_code=status`, `display_mode=BUTTON`, `message_text`, `is_posted_to_chat` и `guid`. После завершения/технической ошибки действий нет. Предметный `INVALID_COMMAND` по task06 получает явную навигацию, сохраняя смысл отказа; UI не подавляет эти кнопки только из-за failure/HTTP-ошибки. Начальные и последующие бизнес-саджесты берутся из одного каталога зарегистрированных операций; навигация и подтверждение определяются представлением ответа, а mapper структурно переносит их в общую OpenAPI-схему.

Источники: [YAML](../api/rest_api_acl_gigaasistant.02.013.02.yml), [1.5](../api/api_contract_details_1.5.md) и [1.6](../api/api_contract_details_1.6.md). Propose явно разрешён YAML и описан в примере подтверждения 1.5; таблица ответов 1.6 неполна. Для локального профиля принято поведение YAML/1.5. Локальный текст сводки не объявляется зарегистрированным шаблоном GA; поверхность GA подключается отдельно.

Основной ACL и зеркало в agent-ui-back используют общий AclInputAdapter/AclMapper. Внешние типы генерируются из YAML. По task01 STATUS подтверждает ровно paymentNumber и общий preparationNo в state типа CONFIRMATION. accept_propose допускается только после сравнения номера и полного набора по схеме с активной серверной подготовкой через последовательные guards. Входящий state не перезаписывает доверенные реквизиты. reject_propose не требует этого набора и не означает банковскую отмену. Транзакционные гарантии сохраняются; подключение проверок FSM изменяется по task01.

Это согласованное архитектурное уточнение, ещё не выполненная реализация. Дизайн и задачи task01 требуют отдельного явного согласования перед изменением кода.

## Удаление локального протокола

Удалён `GET /local-api/v1/sessions/{sessionId}`, его generated-модели и mapper/adapter. Из вспомогательных API остаётся `GET /local-api/v1/fixtures`. Ресурсы /test-ui/ и ACL-зеркало сохраняются. Внутреннее чтение сессии используется для проверки persistence и не публикуется через HTTP.

UI не использует availableCommands, projectionVersion, GET-восстановление или sessionStorage. Каждый ответ проверяется по conversation_id/in_reply_to; только кнопки последнего ответа активны. Пока запрос выполняется, повторный клик блокируется. После потери ответа повторного POST нет; диалог остаётся без активных действий. Новый диалог не отменяет внешний эффект старого.

После перезагрузки открывается новый локальный диалог без автоматического POST. Старые сообщения и сессия не восстанавливаются. Это явное изменение прежней гарантии восстановления, а не имитация чтения бизнес-командой.

## Экран

Лента сообщений с реквизитами тестового платежа, саджестами и подтверждением. Внизу поле ввода и кнопка «Отправить». До реализации task04 свободный текст вызывает локальное пояснение об отсутствии поддержки; текст «Подтверждаю» не считается согласием.

## Принятое расширение task04

05.10.2026 выбран вариант A [task04](../tasks/task04/arch_design.md); [дизайн реализации](../tasks/task04/impl_design.md) и [задачи](../tasks/task04/tasks.md) явно согласованы, реализация проходит проверку. request/content.user_input добавляет текстовый выбор STATUS через JSON-разбор GigaChat перед транзакцией. Приоритет — управляющий performative, затем явный action_code, затем текст. Подтверждение/отказ остаются accept_propose/reject_propose; на propose свободный ввод не предлагается.

Если команда не распознана, оркестратор возвращает HTTP 200 / inform и content.result с вежливым уточнением из файла шаблонов. По task06 ответ получает навигацию и терминальность по снимку без изменения/создания FSM; прежнее правило task04 о пустых suggestions и отсутствии чтения заменено. Это ответ по тому же ACL, без отдельной исходящей интеграции. Ошибка JSON/клиента после технических попыток даёт 500 / failure, а не ложное «не понял».

## Область замены и проверка

**Task05, последнее уточнение 06.10.2026:** RAG вне транзакции доступен по умолчанию во всех нетерминальных состояниях. **На confirmation текст активен.** Ради вопроса не нужно отклонять подготовку; справка не меняет подготовку, её номер или статус. Прежний запрет ввода отменён; текстовое подтверждение не добавляется.

**Область замены task06:** справка, отсутствие знаний, непонятный ввод, уточнение одного действия/источника и недопустимая команда оформляются по текущему снимку. На выборе/без FSM — доступные операции без вопроса; на активном шаге — пустая строка, «Хотите продолжить предыдущую операцию?» и ровно «Да»/«Нет»; после завершения — никаких действий. Снимок текущего хода либо чтение после LLM заменяют запрет чтения task04/05. Справка/уточнение не меняют FSM. «Да» показывает актуальный шаг без повторного события; «Нет» отменяет подготовку по ADR-008/010, не отменяя внешнюю операцию.

Каждый ответ содержит полный набор актуальных кнопок: пустые/отсутствующие suggestions очищают прежние, в том числе на propose/information/failure. Метка response_mode=information больше не разрешает хранить старые кнопки или параметры согласия. Подготовка остаётся на сервере; по «Да» UI получает новую сводку с её прежним номером и явными кнопками подтверждения. final_message=true всегда закрывает диалог; false не сбрасывает уже известное завершение. Потеря/несовпадение ответа снимает действия. Это заменяет прежнее поведение UI task05; сам факт реализации проверяется отдельно.

Кнопка/управляющее действие вместе с непустым user_input — конфликт: до LLM попросить выбрать одно, ничего не выполнять. Это заменяет приоритет кнопки над текстом. Два изменения состояния или изменение с вопросом внутри текста также ничего не выполняют; несколько справочных вопросов допустимы. Единственная кнопка работает без LLM. Запрет ввода после завершения остаётся клиентским: проверки COMPLETED до LLM не добавляется, но task06 отражает завершение, обнаруженное при оформлении навигации. GET, автоматические POST-повторы и текстовое согласие не добавляются.

Уточняет [ADR-018](0018-first-stage-acl-profile.md) в части propose/state/suggestions и заменяет часть [ADR-019](0019-test-ui-acl-mirror.md) о GET-проекции и availableCommands. Остальные модульные границы и общее исполнение сохраняются.

Проверки: HTTP обоих ACL-входов, отсутствие удалённого маршрута, клиентская доставка без GET/повторов, сохранение/rollback через внутренний сервис, запуск и перезапуск JAR.
