Точки встраивания

## 1\. Точки встраивания (Поверхности отображения)

Точки встраивания определяют **место** (пользовательский интерфейс или экран), где агент становится доступен пользователю. Для каждой поверхности могут действовать свои технические ограничения по доступным данным и функционалу.

### 1.1 Чат (Базовая точка встраивания)

-   **Код:** ASSISTANT
-   **Описание:** Основное пространство для диалога с ассистентом. Поддерживается полноценный текстовый диалог, обработка естественного языка и вывод сложных компонентов.
-   **Технические особенности:** Передаются все доступные идентификаторы пользователя. Поддерживаются все типы взаимодействий (текст, кнопки, интерактивные элементы).
-   **Ограничения:** Отсутствуют.
-    Пример

    !


### 1.2 Прелогин (СберБизнес, неавторизованная зона)

-   **Код:** PRELOGIN
-   **Описание:** Зона до авторизации пользователя в системе СберБизнес. Агенты, выводимые на эту поверхность, предназначены для помощи пользователям, которые еще не вошли в систему (например, ответы на общие вопросы, помощь при входе).
-   **Технические особенности:**
    -   Идентификаторы пользователя (epk\_id, digital\_id, и т.д.) и сессионные параметры не передаются
    -   Переходы не поддерживаются
-   **Требование к агентам:** Агент (common-экшен) должен корректно работать **без использования** идентификаторов пользователя и сессионных данных. Если логика агента требует авторизации, необходима доработка агента для работы в условиях анонимности.
-    Пример

    !


### 1.3 Поиск (СберБизнес)

-   **Код:** GLOBAL\_SEARCH
-   **Описание:** Поверхность, интегрированная с поисковой строкой СберБизнеса. Агент формирует ответ (или дополняет выдачу) непосредственно по поисковому запросу пользователя.
-   **Технические особенности:**
    -   **Ограничения:** На этой поверхности **не должны передаваться переходы и операции.**  Акцент делается на быстрый и информативный ответ, в основном, выводятся только COMMON экшены
-    Пример

    !

-   **Технические особенности:** Ограничений нет. Доступен полный функционал, аналогичный базовому Чату в Прелогине.

## 2\. Варианты вызова (Способы инициации диалога)

Точки входа определяют **способ**, которым пользователь или система инициируют работу агента.

### 2.1. Взаимодействие внутри чата

-   **Триггер:** Пользователь вводит текстовый запрос в поле ввода чата.
-   **Механизм:** Запрос обрабатывается внутренним классификатором, который определяет намерение (intent) и направляет запрос соответствующему агенту.
-   **Пример:** Пользователь пишет: *«Показать историю операций»* -> Классификатор вызывает агента «История операций».

### 2.2. Контекстный саджест

-   **Триггер:** Пользователь нажимает на кнопку-саджест, предложенную самой поверхностью (интерфейсом).
-   **Механизм:** Поверхность, учитывая контекст, предлагает пользователю возможные вариант продолжения диалога. При клике вызывается соответствующий агент.
-   **Пример:** Агент «Налоговый консультант» отвечает пользователю на вопрос по налогам, Giga-ассистент предлагает саджесты с продолжением общения по этой теме.

### 2.3. Саджест агента

-   **Триггер:** Пользователь нажимает на кнопку, предложенную агентом, которая вызывает внутренний сценарий или сценарий другого агента.
-   **Механизм:** Агент в ходе своего сценария передаёт в саджестах ссылку на свой экшен или на экшен смежного агента
-   **Пример (для экшена другого агента):** Агент «Выписка» в конце диалога показывает кнопку «Проверить лимиты». При клике управление передается агенту «Лимиты».

### 2.4. Компонент точки входа (UI Component)

-   **Триггер:** Пользователь взаимодействует со специальным UI-компонентом на экране приложения, не являющимся стандартным чатом.
-   **Механизм:** Выделенные элементы интерфейса служат прямым входом в определенный агентский сценарий.
-   **Пример:** Assistant Alert размещается на разделе с платежами,при  нажатии на компонент вызывается агент, консультирующий по конкретному платежу.

### 2.5. Межагентское взаимодействие

-   **Триггер:** Программный вызов агента другим агентом без прямого действия пользователя в момент вызова.
-   **Механизм:** Один агент в ходе выполнения своей логики может вызвать другого агента для получения данных или выполнения специфической задачи. Пользователь может быть не уведомлен о смене агента или видит результат его работы.
-   **Пример:** Агент «Оформление кредита» вызывает агента «Проверка паспорта» для валидации введенных данных.

### 2.6. Операции

-   **Триггер:** Пользователь нажимает на операцию.
-   **Механизм:** Контекстное меню документа содержит пункты, инициирующие агентские сценарии.
-   **Пример:** В сообщении про платежное поручение пользователь нажимает «···» на конкретном документе и выбирает пункт «Повторить платеж». Это действие запускает агента для создания нового платежа на основе шаблона.

Действия

**Действие** — это конкретное пользовательское намерение или задача, которую агент может выполнить или помочь выполнить в рамках диалога.

### **Типы действий:**

#### **СOMMON (Общая консультация)**

-   **Что это:** Общий диалог без выполнения конкретной бизнес-функции. Например: «расскажи о тарифах», «что такое ЭДО», «как подключить зарплатный проект».

-   **Особенности:** Не требует жесткого сценария


#### **Активное действие**

-   **Что это:** Действие, которое приводит к выполнению конкретной бизнес-функции или запускает строгий процесс. Например: «создать платеж», «открыть счет», «получить выписку».

-   **Типы действий:**
    -   Одношаговые (работает в формате запрос-ответ, не предусматривает уточнений у пользователей)
    -   Многошаговые (сценарное действие)
-   **Особенности:**

    -   Зачастую требует проверки полномочий пользователя для его выполнения.

    -   Может быть представлено в качестве саджеста, если соответствует контексту диалога. Возможность участия действия в подборе саджестов-действий (см. определение ниже), необходимо явно указать на странице присутствия.


#### **Сценарное действие (Подвид активного)**

-   **Что это:** Активное действие, которое запускает многошаговый сценарий общения с пользователем.

-   **Особенности:**

    -   Для завершения сценарного действия агенту требуется собрать у пользователя набор данных или получить ответы на вопросы.

    -   После вызова сценарного действия пользователь остается в диалоге с этим же агентом до завершения или отмены сценария. Агент сам решает, когда сценарий должен быть остановлен. Оркестрация на другого агента внутри сценария не происходит. 
        
    -   На время выполнения сценария генерация саджестов со стороны GigaАссистента приостанавливается.

    -   Агенту передается вся история переписки, которая была совершена в рамках этого экшена (в обычных активных действиях и COMMON - это 4 сообщения)

Переход

**Переход** — это элемент интерфейса, который позволяет агенту осуществлять навигацию пользователя внутри СберБизнеса или перенаправление на внешние ресурсы.

**Пример отображения в случае, если переход недоступен пользователю или если некорректно заполнен переход**

**!**

-   **Для чего:** Показ рекламного или информационного баннера.

-   **Реализация:** Требуется указать GUID контейнера отдельно для Web и Mobile.

-   **Обязательное условие:** GUID контейнера должен быть одинаковым на всех стендах (ИФТ, ПСИ, ПРОМ).

#### **Переход-источник**

-   **Для чего:** Ссылка на источник, данные которого необходимо кратко отобразить пользователю.

-   **Реализация:** Это новый вид отображения переходов. Для каждого типа перехода предусмотрен вариант источника:

    -   **Внешний переход-источник** — ссылка на внешний источник.

    -   **Внутренний переход-источник** — ссылка на внутренний источник.

-   **Параметры перехода источника:**
    -   Заголовок тултипа 
    -   Описание тултипа
    -   Текст источника
-   Используется, чтобы сослаться на какой-либо источник, данные которого необходимо кратко отобразить.

    Пример внутренней ссылки в ответе

    !

    Переход источник - это отдельный переход, который необходимо регистрировать на странице присутствия

    Если вы хотите использовать одну внешнюю ссылку и как обычный переход, и как переход-источник - то необходимо зарегистрировать 2 отдельных перехода


### **Порядок работы с переходами:**

1.  **Объявление:** Все переходы, которые агент планирует использовать в своем ответе, должны быть внесены в соответствующую таблицу на странице присутствия. Если для доступа к ресурсу нужна проверка полномочий, необходимо там же указать его.

2.  **Использование в ответе:**

    -   Агент в своем ответе указывает только **коды** зарегистрированных переходов, обернутые в отдельный Markdown-блок `transition-code`.

        Пример оформления блока transition\_code

        [?](#)

        | ` **Пример использования, если переход требует выделения на отдельной строке**\n\nТекст сообщения \\n\n ```transition-code\n    КОД_ПЕРЕХОДА\n``` \nТекст сообщения \\n\n```transition-code\nКОД_ПЕРЕХОДА\n```\n\n**Пример использования, если переход фигурирует в тексте сообщения (доступно для внешних ссылок)**\n\nТекст сообщения ```transition-code КОД_ПЕРЕХОДА ``` продолжается текст сообщения\n\n**Пример использования нескольких переходов одновременно**\n\nТекст сообщения \\n\n```transition-code\n    КОД_ПЕРЕХОДА_1\n``` \n```transition-code\n    КОД_ПЕРЕХОДА_2\n``` \n```transition-code\n    КОД_ПЕРЕХОДА_3\n``` ` |
        | --- |

    -   Необходимо передавать используемые переходы и их параметры в ответе агента в объекте `transitions   `

        [?](#)

        | `"transitions"``: [\n      {\n`        `"code"``:` `"PAYMENT_DONE"``,\n`        `"parameters"``: [\n          {\n`            `"key"``:` `"S_ATTR_1"``,\n`            `"value"``:` `"Тутурум"``\n          }\n        ]\n      }\n    ]` |
        | --- |

    -   Агент должен использовать в ответе только те переходы, которые пришли ему в массиве `available_transitions.` Это связано с тем, что:
        -   Часть переходов может не пройти проверку полномочий (если она необходима)
        -   GigaАссистент выведен в поверхностях, которые не поддерживают переходы.

Саджесты

**Саджест** — это подсказка, которая показывается пользователю после ответа агента. Цель — подтолкнуть пользователя к продолжению диалога и упростить его взаимодействие с GigaАсситентом. После каждого сообщения агента показывается **до 3 саджестов**.

### Типы саджестов по отображению

**Классические саджесты**

-   Максимальная длина саджеста для корректного отображения - 75 символов

-    Пример

    **!**


**Саджесты - кнопки**

-   Короткие - не более 2 слов
-   При клике на саджест-кнопку может быть осуществлен переход

-    Пример

    !


Одновременное использование саджестов-кнопок и классических саджестов после сообщения не допускается

#### **Агентские саджесты** 

-   **Что это:** Саджесты, которые явно возвращает сам агент в своем ответе.

-   **Кто формирует:** Команда агента.

-   **Использование:** Для навигации по ключевым сценариям или ответам внутри компетенции агента. Могут быть текстовыми или содержать ссылку на действие.

-   **Особенности**: Агент может предложить выполнить действие другого агента. Для этого 
    
    -   В сценарии на странице присутствия явно пропишите действия агентов, которые вы хотите использовать

-   После проверки полномочий пользователя все действия, доступные вашему агенту, придут в списке `available_actions.`


#### **Саджесты-действия**

-   **Что это:** Активные действия, которые подбираются из всех доступных действий агентов 
    
-   **Кто формирует:** Giga-ассистент на основе релевантности текущему контексту диалога.

-   **Основа:** Используются активные действия (включая сценарные), которые были корректно задекларированы командой.


#### **Текстовые саджесты**

-   **Что это:** Текстовые подсказки, которые генерируются на основе контекста диалога.

-   **Кто формирует:** Giga-ассистент


#### **Базовые саджесты агента** 

-   **Что это:** Набор из трёх статичных саджестов

-   **Кто формирует:** Команда агента на этапе заведения страницы присутствия
-   **Когда показываются:**

    -   При первом переходе по нейро-зацепке.

    -   Если агент не прислал свои саджесты, а GigaАссистент по какой-то причине не смог рассчитать их сам (например, получил ошибку от GigaChat)


**Статичные саджесты**

-   **Что это:** Список саджестов

-   **Кто формирует:** Команда агента на этапе заведения страницы присутствия
-   **Механизм**: После ответа агента, в случае если агент не прислал свои саджесты, выберутся саджесты из статичного списка. Если клиент кликает по такому саджесту - он больше не показывается в данном диалоге.

### **Правила:**

-   Есть возможность отключения саджестов от GigaАссистента в рамках общения с вашим агентом, но это должно быть аргументировано, проговаривается отдельно case by case.
-   Подбор саджестов работает по следующему алгоритму:
    -   Если агент прислал хотя бы один саджест, то пользователю будут предложены саджесты агента. GigaАссистент в таком случае не формирует свои саджесты (даже если агент прислал менее трех)
        -   (исключение) при переходе по нейро-зацепке - могут отображаются базовые саджесты, если агентских саджестов меньше трех
    -   Если агент прислал более трех саджестов (так делать не нужно),  в приоритете будут те, что имеют связь с действием
    -   Если агент не прислал саджесты - они формируются GigaАссистентом из саджестов-действий и текстовых саджестов.

Операции

Что должен сделать агент, чтобы использовать операции

1.  Отрисовать на UX-схеме сценарий использования операций
2.  Объявить на странице присутствия операции, которые планирует использовать
3.  Доработать ответ при API взаимодействии с Giga-ассистентом для сообщения, которому необходимы операции: 
    1.  Заполнять message.type
2.  Присылать все необходимые параметры для корректного отображения операций в объекте state с type = OPERATION

**Операция** — это интерактивный элемент, который появляется в истории диалога рядом с конкретным сообщением агента и позволяет пользователю выполнить дополнительные действия, связанные с результатом завершенного сценария (например, с созданным платежом, документом или выпиской).

### **Назначение**

-   Предоставить пользователю контекстные действия над результатом работы агента без необходимости ввода новых текстовых команд.

-   Обеспечить удобный доступ к часто используемым функциям: просмотр деталей, повторение операции, скачивание, отмена и т.п.


### **Как это работает**

1.  **Типизация сообщения:** Агент при отправке ответа присваивает ему определенный **тип** (например, `payment_created`, `statement_ready`, `document_signed`). Тип указывает, какой именно объект был создан или обработан.

2.  **Подбор операций:** GigaАссистент на основе этого типа автоматически подбирает соответствующие операции из числа заранее зарегистрированных для данного типа.

3.  **Отображение:**

    1.  Операции визуально привязываются к сообщению-результату в истории диалога

    2.  У операций есть текст, отображаемый в пуллере (короткий), и текст, который отобразиться пользователю в чате (если это необходимо). Второй текст может быть параметризован. *Пример: короткий текст Повторить платеж, текст для чата Повторить платеж {{КОМУ}} на сумму {{СУММА}}*

### **Отличие от саджестов**

-   **Саджесты** — это подсказки, что делать *дальше* после ответа агента (продолжить диалог, перейти к другому сценарию).

-   **Операции** — это действия, применяемые непосредственно к *результату*, отображенному в конкретном сообщении.


### **Объявление операций на странице присутствия**

Если ваш агент в ходе сценариев создает объекты, требующие последующих действий, необходимо:

-   Задекларировать все **типы сообщений**, которые может возвращать агент.

-   Для каждого типа указать список доступных **операций** (например, `view_details`, `repeat`, `download`, `cancel`).


Тестовая корзина

**Тестовая корзина** — это набор типовых вопросов, отражающих компетенцию вашего агента. Она выполняет две ключевые функции:

-   **оркестрация:** помогает системе определить, какому агенту направить запрос пользователя;
-   **валидация:** используется для проверки точности и полноты ответов агента перед запуском.

#### **Правила составления:**

1.  **Качество над количеством:** Включайте вопросы, отражающие основные сценарии и темы, которые должен покрывать агент. Не нужно создавать всевозможные лингвистические варианты (синонимы, изменения падежей, порядка слов и т.п.) одного и того же вопроса.

2.  **Репрезентативность:** Вопросы должны отражать реальные пользовательские интенты, которые агент призван обрабатывать.

3.  **Рекомендуемый объем:** Оптимальный размер — **от 50 до 150 вопросов**. Если в рамках компетенции набирается меньше — предоставьте то, что есть.

4.  **Формат предоставления:** Итоговый список вопросов должен быть оформлен в виде файла **Excel (.xlsx) или CSV** с одним столбцом, содержащим вопросы.


**Агент должен давать точные, полные и полезные ответы на все вопросы, представленные в его тестовой корзине.** Это обязательное требование для допуска агента в работу.
