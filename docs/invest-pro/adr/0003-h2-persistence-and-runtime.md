# ADR-003. H2 для тестов persistence и локального запуска

**Дата:** 28.09.2026. **Статус:** принято по прямому решению пользователя. **Реализация:** запланирована в P1.05; persistence FSM — в P1.06.

## Решение

Для тестов БД использовать H2 и поднимать Spring-окружение с настоящей персистентностью: DataSource, JPA repositories, транзакции и Liquibase. Хранилище не подменять mock/in-memory коллекциями. После реализации FSM её JPA persister работает в той же H2 и транзакционном контуре, что данные приложения.

Для запуска приложения добавить явный профиль `h2`. Он включает persistence, в отличие от `bootstrap`, который её отключает; эти профили не совмещаются. PostgreSQL остаётся поддерживаемым вариантом вне профиля H2. Автоматического fallback между БД нет. Выбор H2 не меняет режимы внешних клиентов из ADR-001.

Тесты используют изолированную H2 in-memory. Для проверки восстановления после перезапуска контекста база должна сохраняться между этими контекстами. Проверку перезапуска JVM выполнять с H2 file, а не с исчезающей при завершении процесса in-memory БД. При ручном запуске URL настраивается: in-memory для временного окружения, file для сохранения данных между запусками.

## Схема и конфигурация

Использовать тот же единственный `db.changelog-master.xml` и общий каталог `changeset/` по [ADR-002](./0002-liquibase-xml.md). Liquibase создаёт схему, Hibernate — только `validate`; `ddl-auto=create/update` не используется. Отличия SQL/типов СУБД при необходимости оформлять внутри общей XML-цепочки средствами Liquibase, без отдельной упрощённой тестовой схемы.

Драйвер H2 должен быть доступен при запуске приложения, а не только в test scope. JDBC URL, пользователь и пароль задаются конфигурацией. Владение persistence остаётся у `agent-db`, профиль приложения — у `agent-main`.

## Проверки и границы

На H2 проверять миграции, сохранение/чтение, ограничения, транзакции/rollback и восстановление состояния. В P1.05 добавить проверку запуска приложения с профилем `h2` и включённой persistence; команда запуска будет приведена после реализации. Docker/PostgreSQL не являются обязательным условием DB-тестов MVP.

Это решение заменяет прежнее требование обязательной PostgreSQL для всех DB-тестов. Успех H2 не доказывает PostgreSQL-специфичное поведение SQL, блокировок или LOB; отдельные проверки PostgreSQL добавляются при соответствующей необходимости. Остальные архитектурные границы и TDD сохраняются.
