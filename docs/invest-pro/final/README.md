# Итоговая архитектура агента по переписке

**Дата:** 28.09.2026. **Статус:** выбранная архитектура для реализации. Документы описывают проектное решение; код интеграций и проверки совместимости ещё предстоит реализовать.

Выбран вариант A с уточнениями заказчика:

**Модель P1.02 r8:** 10 простых Lombok DTO с getters/setters и no-args/all-args конструкторами. DTO не проверяют значения и не копируют списки; wire-валидация сохранена. Доменные и generated типы используют InDTO/OutDTO по направлению API, внутренние — DTO; enum без суффикса. Проверки — в [task](../plan/phase1_step02/task.md).

**Изменение входного контракта от 28.09.2026:** обязательны epkId (организация в едином профиле клиента), digitalUserId (пользователь), requestId (текущий запрос), sessionId и content. additionalInfo — необязательный массив уникальных key/value; paymentId передаётся произвольной строкой и пока не обрабатывается/не привязывает платёж. action_code сохраняется для клика, отсутствует при ручном вводе. Идемпотентность делегируется существующей внешней библиотеке: создана только временная @Idempotent в utils без исполняемого поведения. Краткая русская документация обязательна для OpenAPI, интерфейсов/методов и DTO/полей. Ответы внесены в [P1.02 design r4](../plan/phase1_step02/design.md), ревизия согласована и дореализована; 150 тестов прошли, реализация на пользовательской проверке.

- **Java 21** и синхронная обработка сообщения за **не более 10 секунд**.
- **ADR-003:** тесты БД на H2 с настоящей persistence; профиль "h2" для запуска приложения. PostgreSQL сохраняется как вариант БД. [Решение](../adr/0003-h2-persistence-and-runtime.md).
- **ADR-002:** схема PostgreSQL и native таблицы SSM управляются **Liquibase**, все changelog-файлы — **XML**, владелец — `agent-db`. [Полное решение](../adr/0002-liquibase-xml.md).
- **Spring Statemachine** за собственным заменяемым интерфейсом и тонким proxy. Встроенная JPA-персистентность FSM хранит состояние в **PostgreSQL** и заменяется вместе с движком. Данные операций и реестр отправок принадлежат приложению.
- **GigaChat 3 Ultra или 3.5 Ultra** через **`ai-forever/spring-ai-gigachat`**; максимум один вызов генерации на сообщение.
- Вход чата содержит **`epkId`, `digitalUserId`, `requestId`, `sessionId`, `content`**, при нажатии саджеста также **`action_code`**; `content` равен его `text`. Ответ содержит **`sessionId`, `content`, `suggestions: [{guid, action_code, text}]`**. При ручном вводе `action_code` отсутствует. LLM разбирает каждый допустимый текст, включая «Да»; код саджеста проверяет приложение и не превращает напрямую в событие FSM. Переданный paymentId пока сохраняется только как дополнительная информация; его бизнес-обработка не входит в P1.02.
- Полномочия, наименование организации по `epkId` и обработка трёх операций доступны через **Invest corr**. На первых этапах эти интеграции реализуются заглушками.
- **ADR-001:** у каждого out-клиента есть stub, включая GigaChat. Выбор задаётся `integrations.<integration>.stub=enabled/disabled`, адрес — `integrations.<integration>.url` в `application.yaml`. Реальные HTTP-вызовы выполняются через Feign; GigaChat использует выбранную библиотеку. [Полное решение](../adr/0001-outbound-clients-and-stubs.md).
- **Сведения о платеже и статусе исполнения заявок клиент получает SMS с номера 900 на личный телефон.** Агент запрашивает подтверждение и после достоверного приёма запроса сообщает о получении информации по SMS; банковские сведения/результаты в чат не выводятся. `COMPLETED` означает приём запроса, а не доставку SMS или исполнение платежа.
- LLM возвращает данные разбора. **Приложение формирует событие и ответ** по алгоритму «состояние + сохранённый контекст + исходный вход + проверенные данные LLM». Следующее состояние определяется FSM; выбор шага модели не поручается.
- Небольшая база знаний передаётся в контекст модели целиком; модель предлагает разделы, приложение формирует справку из утверждённых блоков. Решения об отправке и ФЛК контролирует Java-код.
- Maven-модули: `agent-api-in`, `agent-api-out`, `agent-common`, `agent-db`, `agent-main`, `agent-model`, `agent-service`, `agent-ui-back`. Внешние DTO изолированы по интеграциям; OpenAPI Generator и MapStruct обеспечивают их генерацию и преобразование в доменную модель.
- Зависимость доступа к данным: **`agent-service → agent-db`**. Только сервисы `agent-service` вызывают прикладной API БД; интеграции и UI обращаются к данным через сервисный слой. Обратной зависимости `agent-db → agent-service` нет.

## Приоритет решений

Основа бизнес-поведения — [docs/old/final.md](../old/final.md), включая матрицы M/D/S и критерии AC-01–AC-30. Решения заказчика из текущего этапа уточняют технологии и маршрут интеграций: проверки полномочий теперь выполняются через Invest corr; добавлен поиск наименования организации по `epkId`.

Текущий контракт использует `suggestions` в ответе и необязательный `action_code` во входе. GUID саджеста клиент обратно не передаёт; стабильный код действия не является ключом доставки или токеном конкретного подтверждения. Входной `requestId` предназначен для идемпотентности через внешнюю библиотеку; временная аннотация её не выполняет. Внутренний `turnId` служит учёту исполнения. Идемпотентность отправки подтверждённой операции обеспечивается отдельно реестром `submission` и контрактом corr. Классификация текста через LLM сохраняется.

Порядок работы и handoff описаны в `docs/plan/plans.md`, статусы 22 шагов — в трёх фазовых планах. На каждый шаг архитектор создаёт `phaseN_stepNN/design.md` и `task.md`, затем останавливается для согласования. После ответов документы дорабатываются и снова предъявляются пользователю. Отдельная команда запускает разработчика и implement через TDD. После обязательных тестов task/history обновляются, разработчик останавливается; `Выполнен` ставится только после пользовательской приёмки. Следующий шаг начинается новой командой с design.

[docs/old/architecture.md](../old/architecture.md) сохраняется как предыдущее сравнение вариантов. Его рекомендации о собственной FSM, прямом GigaChat Java SDK и Spring Boot 4 не являются целевыми для этой версии. Текущий комплект имеет приоритет по архитектуре.

Граница замены включает **движок, его persister, сериализацию, восстановление и техническую схему FSM**. Proxy не реализует собственное хранение состояний. Замена для уже существующих сессий требует явной миграции либо сохранения старой реализации до их завершения; прозрачная совместимость бинарных checkpoint разных движков не предполагается.

**Q-05 остаётся отложенным:** после неизвестного исхода corr сохраняются данные отправки и возвращается ошибка; фоновая сверка, компенсация и новые отправки не добавляются автоматически. Заглушки моделируют этот случай, но не определяют за бизнес дальнейшие переходы.

Версии библиотек и свойства API проверены по первичным источникам, указанным в документах. Временные бюджеты являются проектными настройками для испытаний, а не измеренным SLA внешних сервисов.
