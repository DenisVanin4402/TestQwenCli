# Интеграционные контракты и заглушки

**Уточнение P1.02 r4 (28.09.2026):** epkId — организация в едином профиле клиента, digitalUserId — пользователь; requestId — обязательный ID входного запроса. additionalInfo необязателен (можно []), содержит уникальные строковые key/value; paymentId — необязательная произвольная строка, сейчас только передаётся без обработки/привязки. Идемпотентность входа принадлежит существующей внешней библиотеке @Idempotent; в P1.02 только временный маркер без поведения. Собственный механизм входной дедупликации не разрабатывается. Платёжный контекст описанных ниже будущих workflow уточняется в их design и не реализуется в P1.02. Документация OpenAPI, интерфейсов/методов и DTO/полей — краткая, на русском; generated использует стандартные описания из OpenAPI.

Связанные документы: [архитектура](./architecture.md), [модули и mapping](./modules.md), [состояние](./state-machine.md), [обработка запросов](./execution.md).

Входящие интеграции находятся в `agent-api-in`, исходящие — в `agent-api-out`; тестовый UI выделен в `agent-ui-back`. Порты внешних интеграций объявлены в `agent-service`, их доменные DTO — в `agent-model`. Контракты БД объявлены отдельно в `agent-db.api`, и только сервисы `agent-service` обращаются к ним. API DTO каждой интеграции изолированы в `ru.sberbank.pprb.agent.<integration>.dto` и преобразуются MapStruct-мапперами из её `mapper`. Внешние DTO генерируются из OpenAPI Maven-плагином либо задаются вручную в том же интеграционном модуле до согласования спецификации.

## 0. Входящий контракт чата

Базовое сообщение содержит обязательные строковые `epkId`, `digitalUserId`, `requestId`, `sessionId`, `content`. При нажатии саджеста добавляется **`action_code`**, а в `content` передаётся его `text`. Для вручную набранной реплики `action_code` отсутствует; `null` или пустая строка вместо кода не используются. Предлагаемый endpoint: `POST /api/v1/gigaassistant/turns`; имя endpoint является проектным, не утверждённым API внешнего канала.

Пример нажатия стартового саджеста:

```json
{
  "epkId": "epk-demo-org",
  "digitalUserId": "digital-demo-user",
  "requestId": "chat-request-001",
  "sessionId": "session-status-001",
  "action_code": "REQUEST_STATUS",
  "content": "Статус"
}
```

| Поле | Обработка |
|---|---|
| `epkId` | Обязательный заявленный идентификатор организации в едином профиле клиента |
| `digitalUserId` | Обязательный заявленный идентификатор пользователя; тело запроса не доказывает аутентификацию |
| `requestId` | Обязательный идентификатор текущего входного запроса для внешней библиотеки идемпотентности; не turnId и не ID заявки corr |
| `additionalInfo` | Необязательный массив key/value с уникальными строковыми ключами; [] допустим, null запрещён; paymentId — произвольная строка, без обработки |
| `sessionId` | Идентификатор диалога; сервер находит привязанное состояние и контекст в пространстве этого канала |
| `content` | Текст пользователя либо `text` нажатого саджеста; классификацию и извлечение значений выполняет LLM |
| `action_code` | Необязательный для свободного текста, обязательный при клике код саджеста; проверяется приложением по каталогу и текущему контексту |

Саджест и ручной ввод различаются наличием `action_code`, но используют общий LLM-разбор `content`. Короткие «Да»/«Нет» также проходят модель. Код не является событием FSM и не позволяет обойти классификацию, подтверждение или guards. Адаптер проверяет JSON, обязательность/тип/длину полей и доступ; лингвистический смысл не определяет локальным словарём. Исходный текст сохраняется для проверки извлечённых фрагментов.

### 0.1. Ответ и suggestions

Каждый ответ на принятое сообщение содержит **`sessionId`, `content`, `suggestions`**. Массив обязателен; если действий нет, возвращается `[]`.

```json
{
  "sessionId": "session-status-001",
  "content": "Направить информацию о статусе платежа в SMS с номера 900 на ваш личный телефон?",
  "suggestions": [
    {
      "guid": "b2a11010-9849-4daf-8a20-270fdc602001",
      "action_code": "CONFIRM_REQUEST",
      "text": "Да"
    },
    {
      "guid": "b2a11010-9849-4daf-8a20-270fdc602002",
      "action_code": "CANCEL_REQUEST",
      "text": "Нет"
    }
  ]
}
```

| Поле саджеста | Значение |
|---|---|
| `guid` | UUID конкретного экземпляра саджеста в ответе, назначается сервером; используется UI как идентификатор элемента |
| `action_code` | Стабильный код действия из каталога приложения; повторяется у однотипных саджестов разных ответов |
| `text` | Отображаемый текст; при клике дословно копируется в `content` |

Состав массива, коды и тексты определяет `ResponsePolicy` по достигнутому состоянию и контексту. LLM их не генерирует. В одном ответе `guid` уникальны и `action_code` не повторяются, чтобы код однозначно определял предлагаемый текст. Новая публикация получает новые GUID; чтение уже сохранённого ответа повторно возвращает прежние GUID. Ответ с полным массивом фиксируется в `message_receipt` вместе с состоянием и контекстом до публикации. Доменные типы — `SuggestionSpecDTO`/`SuggestionOutDTO`, внешние DTO — в пакете интеграции, преобразование выполняет MapStruct.

Принятые для примера коды:

| `action_code` | Текст | Назначение |
|---|---|---|
| `REQUEST_STATUS` | Статус | Предложить подготовку запроса информации по SMS |
| `REQUEST_RECALL` | Отзыв | Предложить подготовку отзыва |
| `REQUEST_DETAILS` | Уточнение реквизитов | Предложить подготовку уточнения |
| `CONFIRM_REQUEST` | Да | Ответить согласием на текущий вопрос подтверждения |
| `CANCEL_REQUEST` | Нет | Отказаться от текущей подготовки, без отмены уже принятой заявки |

Это каталог UI-действий проекта, а не enum событий FSM или справочник реального API банка. Набор доступных действий ограничивает Java-политика, включая `statusOnly`.

При нажатии «Да» клиент отправляет:

```json
{
  "epkId": "epk-demo-org",
  "digitalUserId": "digital-demo-user",
  "requestId": "chat-request-002",
  "sessionId": "session-status-001",
  "action_code": "CONFIRM_REQUEST",
  "content": "Да"
}
```

При ручном вводе:

```json
{
  "epkId": "epk-demo-org",
  "digitalUserId": "digital-demo-user",
  "requestId": "chat-request-003",
  "sessionId": "session-status-001",
  "content": "Да"
}
```

**GUID саджеста во входном запросе не возвращается** — так задан текущий контракт. Не добавляем скрыто `suggestionId`, `replyTo` или `messageId`. Приложение проверяет код/текст относительно последнего актуального массива и текущего состояния. Для стартового саджеста канала, до первого ответа агента, допустимые код/текст берутся из серверного каталога выбора операции при `CHOOSING_REQUEST_TYPE`. Это отдельное начальное условие, а не разрешение использовать любой ранее показанный код.

Неизвестный код отклоняется; неактуальный код или несовпадение `content` с текстом текущего саджеста не дают перехода по этому коду. При противоречии с разбором LLM (например, код согласия и отрицание/вопрос в тексте) приложение возвращает уточнение и актуальные предложения без отправки. Прямого преобразования `action_code` в `DomainEvent` нет. Код проверяется как отдельный входной факт; в prompt он не передаётся, чтобы языковой разбор опирался на `content` и минимальный контекст диалога.

Состояния, события, внутренние банковские идентификаторы, реквизиты, банковский статус и факт доставки SMS в ответ не входят; `guid` идентифицирует только UI-элемент. Для повреждённого JSON/отказа в доступе используется транспортная ошибка; приведённый формат описывает ответ на принятое сообщение. HTTP-коды фиксируются в OpenAPI входной интеграции.

### 0.2. Серверный контекст сессии

Для текущего workflow принимаем условие: **до первого сообщения сессия уже привязана на сервере к конкретному платежу, пользователю и организации**. В тестовом контуре привязку создаёт fixture через use case `agent-service`; в промышленном источник начального контекста требует согласования с каналом. Это подготовка сессии, а не дополнительные поля каждого сообщения.

По одному `epkId` нельзя выбрать платёж; lookup названия организации и `action_code` также его не определяют. При неизвестной сессии, отсутствии платежа или несовпадении владельца агент не запускает операцию и не предлагает модели угадать привязку. Значения тела запроса сами по себе не являются аутентификацией.

### 0.3. Порядок и повторы сообщений

Канал отправляет следующий ход после получения ответа на предыдущий, сохраняет порядок и не делает автоматических повторов с неизвестным исходом. UI показывает активными только саджесты актуального ответа и блокирует их на время хода. Вход в занятую сессию получает контролируемый отказ без второго исполнителя; произвольная очередь не создаётся. Эти условия необходимо проверить на реальном канале.

Внутренние `turnId` и `commandId` учитывают исполнение и его шаги, но не отличают повтор HTTP-доставки от новой одинаковой фразы. Хеш `content` и стабильный `action_code` также не являются ключами дедупликации. Уникальность операции/версии сводки и `submission.idempotencyKey` защищают одну отправку corr отдельно от входной доставки.

Согласие относится к последнему сохранённому вопросу и текущей сводке. GUID в ответе не связывает согласие с показанной версией, поскольку клиент не возвращает его. Входной requestId предназначен для внешней библиотеки идемпотентности, однако сам не связывает клик с вопросом/версией. Гарантии повторов определит контракт библиотеки при подключении; временная аннотация не обеспечивает дедупликацию. До подключения сохраняется последовательный режим без автоматических повторов.

## 1. Граница Invest corr

Через Invest corr доступны три сервиса:

1. Проверка полномочий пользователя на отзыв/уточнение данного платежа.
2. Получение наименования организации по `epkId` с проверкой доверенной организационной привязки.
3. Приём подтверждённого запроса одного из трёх типов: `status`, `recall`, `details`.

В первой реализации все три сервиса представлены заглушками. Java-интерфейсы ниже — наши внутренние контракты. Имена реальных HTTP-методов, URL и wire DTO Invest corr остаются предметом интеграционного согласования; они не выводятся из этих примеров.

```java
public interface PermissionPort {
    PermissionResult check(PermissionQuery query, CallContext context);
}

public interface OrganizationPort {
    OrganizationResult resolveName(OrganizationQuery query,
                                   CallContext context);
}

public interface CorrespondencePort {
    SubmissionResult submit(SubmissionEnvelope request,
                            CallContext context);
}
```

Порты реализует `InvestCorrAdapter`, использующий `InvestCorrClient`. У него обязательны `StubInvestCorrClient` и `FeignInvestCorrClient`; транспорт второй реализации — `InvestCorrFeignApi`. Выбор выполняется по `integrations.invest-corr.stub=enabled/disabled`, адрес реального вызова — `integrations.invest-corr.url`. `CallContext` содержит correlation ID, deadline и номер попытки. Политикой повторов владеет оркестратор; независимые retries Feign/транспорта отключены. [ADR-001](../adr/0001-outbound-clients-and-stubs.md).

Физическое размещение — `agent-api-out`, пакет `ru.sberbank.pprb.agent.investcorr`: реализации портов в `service`, HTTP/stub-клиенты в `client`, внешний контракт в `dto`, преобразования в `mapper`, локальные ошибки в `exception`. Все три сервиса corr используют эту интеграцию. Интерфейсы выше и DTO их сигнатур остаются доменными; они не генерируются из OpenAPI corr.

Интеграционные результаты типизированы. Бизнес-отказ не передаётся как неразличимый `RuntimeException`, а ошибки преобразуются в доменные исходы. Клиент не меняет FSM и не пишет тексты пользователю.

## 2. Проверка полномочий

### Запрос

| Поле | Источник/смысл |
|---|---|
| `digitalUserId` | Доверенная идентификация пользователя из сессии |
| `organizationRef` | Привязка к организации в исходном контексте |
| `paymentRef` | Исходный платёж, не значение из пользовательского текста |
| `operationType` | Только `recall` или `details` |
| `operationId`, `expectedAggregateVersion` | Привязка ответа к актуальной подготовке и версии снимка, на которой начата проверка |

### Результат

| Исход | Действие агента |
|---|---|
| `ALLOWED` | Зафиксировать разрешение для этой подготовки; продолжить сценарий |
| `DENIED` | Завершить подготовку; сохранить `statusOnly=true` для диалога по платежу; запретить обе операции |
| `TECHNICAL_ERROR` | Один автоматический повтор; после второго сбоя завершить подготовку с технической ошибкой |

`status` не вызывает этот сервис. Возврат названия организации также не является доказательством полномочий. Разрешение не распространяется на новый `operationId` автоматически; ограничение «только статус» сохраняется при смене операции. Длительность действия разрешения и необходимость внешней ревалидации определяются контрактом; дополнительные синхронные проверки перед каждой отправкой не вводятся без соответствующего правила и бюджета.

Заглушка проверяет совпадение пользователя, организации и платежа по fixtures. Неизвестная связка не получает разрешение по умолчанию.

## 3. Получение названия организации по epkId

### 3.1. Организация и пользователь

По уточнению пользователя epkId обозначает организацию в едином профиле клиента; digitalUserId обозначает пользователя. Lookup использует организационный epkId; проверка личности использует отдельный digitalUserId. Прежняя трактовка epkId как пользователя заменена.

Внутренний запрос:

```java
public record OrganizationQuery(
        String epkId,
        DigitalUserId digitalUserId,
        OrganizationRef expectedOrganization,
        TrustedIdentityRef identityRef) {}
```

Адаптер вызывает lookup corr по организационному epkId и сверяет результат с expectedOrganization; digitalUserId сохраняется отдельно. Точные wire-поля реального corr согласуются при интеграции, но семантика входного epkId уже определена пользователем. Fixture будущего workflow явно связывает пользователя и организацию.

### 3.2. Ответ и использование

| Исход | Обработка |
|---|---|
| `FOUND` | Проверить привязку, сохранить `organizationRef`, название, источник и время получения |
| `NOT_FOUND` | Контролируемая ошибка подготовки контекста; не придумывать название |
| `AMBIGUOUS` / несовпадение организации | Не выбирать первую организацию; ошибка доверенного контекста |
| `TECHNICAL_ERROR` | Вернуть техническую ошибку обогащения; не трактовать как отсутствие полномочий |

Название получается при входе в новую сессию, если в ней ещё нет проверенного результата corr. В первом этапе оно является обязательным для внутренней сводки подтверждаемого запроса всех трёх типов. Его наличие в контексте не требует выводить банковские сведения в чат. Бюджет одного lookup — до 0,8 с, по умолчанию одна попытка; это **новая проектная настройка**, а не распространение бизнес-правила о двух попытках полномочий на все сервисы corr.

При ошибке первоначального обогащения операция не запускается. Валидный исходный контекст уже сохранён, FSM остаётся `CHOOSING_REQUEST_TYPE`. Новый принятый ход получает внутренний turnId и проходит общий разбор; обработка повтора requestId принадлежит внешней библиотеке после её подключения. Сервис не просит свободным текстом подменить организацию.

Полученный результат хранится в контексте сессии и не запрашивается заново из-за вопроса, отмены или смены операции. Он фиксируется в версии внутренней сводки и привязке показываемого подтверждения. Если появится правило обновления названия в активной подготовке, изменение сводки должно аннулировать прежнее подтверждение. Требования свежести/срока хранения пока относятся к интеграционному контракту; произвольный TTL, сбрасывающий бизнес-контекст, не вводится.

## 4. Приём запросов: три операции

| `type` | Состав значимых данных | Условие подготовки |
|---|---|---|
| `status` | Исходный платёж, пользователь и организация, подтверждённая сводка | Без специальной проверки полномочий, но с явным подтверждением |
| `recall` | Те же исходные данные, тип запроса отзыва | Разрешение corr и подтверждение текущей сводки |
| `details` | Исходные данные + непустое подмножество четырёх изменений | Разрешение, успешная локальная ФЛК данной версии, подтверждение |

Для `details` разрешены только `recipientInn`, `recipientAccount`, `recipientName`, `purpose`. Отсутствующее поле означает «не менять»; `null`/пустое значение не трактуется как разрешённая очистка. Точные форматы и ограничения — Q-06.

Логический envelope хранится до отправки и больше не изменяется:

```json
{
  "submissionId": "submission-demo-1",
  "operationId": "operation-demo-2",
  "summaryVersion": 2,
  "idempotencyKey": "a7d04a61-8375-4ac1-ad67-7f0375c53c11",
  "type": "details",
  "paymentRef": "payment-demo-42",
  "digitalUserId": "digital-demo-user",
  "organization": {
    "ref": "org-demo-7",
    "name": "ООО Пример"
  },
  "changes": {"purpose": "Оплата по договору 42"},
  "notificationPolicy": "SMS_900_PERSONAL_PHONE_V1",
  "payloadHash": "sha256:demo-hash"
}
```

Каноническое представление для хеша определяется один раз. Значения реквизитов — строки; начальные нули и текст не теряются. Подтверждение связывается с операцией, версией и этим набором значимых полей. Сетевые retries не меняют конверт и не создают новый ключ.

### Результаты

| Исход | Значение | Состояние |
|---|---|---|
| `ACCEPTED` | Corr достоверно подтвердил приём, вернул свой request ID | `COMPLETED` |
| `REJECTED` | Контракт гарантирует отсутствие принятого запроса | `FAILED` |
| `UNCERTAIN` | Timeout, потеря ответа либо ошибка без гарантии отсутствия приёма | Повторы по настройкам в рамках текущего хода; затем `SUBMIT_UNKNOWN` |
| `NOT_SENT` | Достоверно не начиналась передача, например не хватило времени до вызова | Технический исход без ложного утверждения об отправке |

HTTP 500 сам по себе не равен `REJECTED`; HTTP 200 без корректного признака приёма сам по себе не равен `ACCEPTED`.

### Канал выдачи банковской информации

Сведения о платеже и статусе исполнения заявок поступают клиенту **SMS с номера 900 на его личный телефон**. Банковский контур выполняет обработку и отправку SMS вне агента. Ответ `ACCEPTED` подтверждает только приём запроса corr, а не фактический статус платежа, отправку SMS или доставку на телефон.

Для успешного `status` шаблон чата: «Запрос принят. Информация о статусе выбранного платежа будет отправлена SMS с номера 900 на ваш личный телефон». Для отказа/неизвестного исхода используется соответствующий технический ответ без обещания SMS. В примерах контракта агента отсутствуют поля фактического `paymentStatus`, результата банковского исполнения или `smsDelivered`.

Номер телефона не вводится в чат и не извлекается LLM. Получателя определяет доверенный банковский контур по согласованной идентификации клиента; точный способ привязки контакта — часть Q-09/Q-10. Внутренняя политика `SMS_900_PERSONAL_PHONE_V1` фиксируется в подтверждаемом envelope. Наличие одноимённого поля в реальном API corr не предполагается: его mapping определяется спецификацией. Дополнительный SMS-клиент в `agent-api-out` не вводится.

## 5. Заглушки Invest corr

### 5.1. Режимы

**Автономный режим:** `integrations.invest-corr.stub=enabled`, цепочка `InvestCorrAdapter -> StubInvestCorrClient` внутри приложения, с теми же DTO/deadline, что у реального клиента. Заглушка исполняет только один вызов сервиса; retries остаются в оркестраторе. Реальный клиент не инициализируется.

**HTTP-контрактный режим:** `integrations.invest-corr.stub=disabled`, реальный Feign-клиент против локального HTTP-стенда/WireMock по тестовому `url`. Проверяются сериализация, статусы, заголовки, deadline и обрывы. Это не подключение настоящего corr. Для банковского хоста после согласования внешней спецификации используется тот же реальный клиент и соответствующий URL.

Сценарий задаётся fixture по `testScenarioId` и доверенной связке идентификаторов. Пользовательский текст не может переключать режим или ответ на `ALLOWED`/`ACCEPTED`. Stub выбирается единым свойством из ADR-001, без дополнительного `mode`; тестовые управляющие endpoints доступны только в локальном/тестовом UI-профиле. Политика промышленного допуска заглушек не входит в текущий прототип.

### 5.2. Обязательные сценарии

| Сервис | Сценарии |
|---|---|
| Полномочия | Разрешено; отказ; первый технический сбой и успех; два сбоя; запоздалый ответ для старой версии |
| Организация | Одно совпадение; нет результата; несколько организаций; неверная привязка; технический сбой; медленный ответ |
| Каждая из трёх операций | Приём; достоверный отказ; timeout до доказанного приёма; принятие с потерянным ответом; повтор того же ключа; тот же ключ с другим payload |
| Состояние тестового corr | Перезапуск клиента; перезапуск приложения; сохранённый ранее ключ; конкурентные повторы |

Часть тайм-аутов может быть неопределённой, даже если тест знает, что приёма не было. Возвращаемый агенту исход определяется наблюдаемым контрактом, а не скрытым знанием сценария.

### 5.3. Реестр принятых запросов заглушки

Ключ связывается с `payloadHash`, `type` и стабильным `corrRequestId`. Повтор одинакового ключа/хеша возвращает тот же результат. Тот же ключ с другим payload даёт конфликт, а не новую запись. Необходимо проверять число **логических банковских приёмов**, а не только количество HTTP-вызовов: retries могут увеличивать второе.

Для unit-тестов и первого in-process stub достаточно изолированного in-memory реестра. Для интеграционных тестов с устойчивым реестром используется отдельный HTTP stub-сервис corr со своим хранилищем, например PostgreSQL-схемой `stub_corr` с уникальным ключом. Его приём коммитится в отдельном тестовом контуре независимо от транзакции агента. `agent-api-out` обращается к нему по HTTP и не получает JDBC/repository для этой схемы. Так сохраняется правило доступа к БД через сервисный слой агента и воспроизводится окно «corr принял, агент упал» без общей транзакции.

В сценарии `ACCEPT_THEN_TIMEOUT` заглушка сначала устойчиво сохраняет приём, затем имитирует потерю ответа. Следующий запрос с тем же ключом получает прежний ID. Сценарий `ACCEPT_THEN_ALWAYS_TIMEOUT` сохраняет один приём, но скрывает ответ на все разрешённые попытки: агент должен завершить ход с `SUBMIT_UNKNOWN`.

Fake-clock используется в unit-тестах retry. На интеграционных/нагрузочных тестах задержки и обрывы воспроизводятся реально. Заглушка не должна выполнять эффект с задержкой уже после deadline только потому, что её sleep не был отменён.

## 6. GigaChat через spring-ai-gigachat

### 6.1. Граница адаптера

```text
TurnInterpreterPort
  -> SpringAiGigaChatAdapter
  -> GigaChatClient
       stub=enabled: StubGigaChatClient
       stub=disabled: SpringAiGigaChatClient
                        -> ChatModel из ai-forever/spring-ai-gigachat
                        -> согласованный endpoint Ultra
```

Используется именно выбранная библиотека. Прямой самостоятельный GigaChat Java SDK из предыдущего предложения не является основным путём интеграции. Внешние типы Spring AI/GigaChat не проходят в доменную модель.

По ADR-001 реальный клиент и `StubGigaChatClient` реализуют одинаковый прикладной клиентский контракт в пакете `gigachat`. Выбор — `integrations.gigachat.stub`; реальный адрес — `integrations.gigachat.url`. При `enabled` нет ChatModel/OAuth и сетевых вызовов, в том числе при старте. Stub возвращает фикстуры структурированного разбора/ошибок через тот же адаптер и валидацию; он не определяет бизнес-события. При `disabled` используется библиотека, без Feign и автоматического fallback на stub. Лимит одной генерации относится к реальной модели; один вызов stub проверяет форму обработки, но не качество и задержку Ultra.

Реализация находится в `agent-api-out`, пакет `ru.sberbank.pprb.agent.gigachat`, с теми же `client`, `dto`, `exception`, `mapper`, `service`, `utils`, `config`. Структура аргументов `interpret_turn` разбирается во внешний DTO этой интеграции и после проверки схемы преобразуется MapStruct-маппером в доменную `Interpretation`. Mapping не заменяет последующую валидацию и алгоритм `StateInputPolicy`.

```java
public interface TurnInterpreterPort {
    Interpretation interpret(InterpretationInput input, Deadline deadline);
}
```

`InterpretationInput`: текущее сообщение, минимальный контекст для понимания речи, последний вопрос агента, схема извлекаемых полей, версия prompt и полная БЗ. Список событий FSM и таблица переходов в контракт модели не входят. Из контекста можно передать, какие данные сейчас обсуждаются, но решение о допустимом действии остаётся в приложении.

`content="Статус"` также вызывает `TurnInterpreterPort`: модель выделяет просьбу и упоминание `status`. Для `content="Да"` она выделяет согласие. Java-алгоритм затем различает выбор операции, вопрос о ней, подтверждение актуального запроса и ответ вне контекста. Полный `ConversationSnapshot` и входные `epkId`/`sessionId` в prompt не нужны; минимальную смысловую проекцию строит сервис. `turnId`, версия чтения и deadline сопровождают вызов внутри приложения, а не заполняются моделью.

`Interpretation` — данные языкового разбора: признаки согласия/отрицания/вопроса/просьбы, упоминания типов операций, предполагаемые значения полей, исходные фрагменты, признаки цитирования/условного высказывания/неоднозначности и кандидаты разделов БЗ. Признак согласия означает только «в реплике есть согласие», а не «отправить запрос». Название операции в тексте также не является выбором операции, пока Java-правила не проверили смысл и контекст.

В результате **нет** `intent` со значением события FSM, `event`, `nextState`, `nextAction`, `toolCall`, `DomainPatch`, `EffectSpec`, `ResponseSpec` или готового ответа пользователю. Модель не заполняет доверенные `epkId`, версии, полномочия, `summaryPayloadHash` или ключ идемпотентности. Эти значения приложение получает из собственного контекста и сервисов.

После адаптера результат проходит `InputValidator`, затем `StateInputPolicy` вместе с текущим состоянием, его сохранённым контекстом и исходным входом. Только `StateInputPolicy` формирует событие пользовательского действия. Прямое преобразование строки модели через `DomainEvent.valueOf(...)` либо десериализацию в иерархию событий запрещается архитектурным контрактом.

`modelId` — конфигурация, ограниченная разрешёнными Ultra deployment. Точный ID 3.5 Ultra и endpoint подтверждаются в целевом контуре. Нельзя оставлять дефолт starter `GigaChat`, если он маршрутизирует в другой класс модели. Доступность корпоративного Ultra, квоты и задержки проверяются отдельно. [Публичная документация Ultra](https://developers.sber.ru/docs/ru/gigachat/models/gigachat-3-ultra).

### 6.2. Один вызов и структурированный результат

Основной режим для прототипа 1.1.x — **принудительное предложение функции `interpret_turn`**, аргументы которой соответствуют нашей схеме данных разбора. Функция задана конфигурацией приложения; модель не выбирает банковский инструмент или следующий шаг. Внутреннее выполнение tools отключено; приложение извлекает аргументы, проверяет их и не отправляет tool result обратно модели.

В `GigaChatOptions` версии 1.1.2 есть `FunctionCallMode.CUSTOM_FUNCTION`, `functionCallParam` и `internalToolExecutionEnabled(false)`. В проверенном классе этой версии нет `responseFormat`; поэтому поддержку native strict JSON Schema не обещаем как уже доступную настройку starter. Выбор режима проверяется контрактным тестом на целевой Ultra. [Исходник GigaChatOptions 1.1.2](https://github.com/ai-forever/spring-ai-gigachat/blob/v1.1.2/spring-ai-gigachat/src/main/java/chat/giga/springai/GigaChatOptions.java).

Если функции в конкретном контуре не поддерживаются, заранее выбирается режим `JSON_IN_TEXT` с инструкцией и локальной валидацией. Это настройка deployment, а не второй LLM-вызов после неудачи. Native schema можно подключить внутри того же адаптера после подтверждения поддержки библиотекой/API.

Никакие `PermissionPort`, `OrganizationPort`, `CorrespondencePort` не регистрируются в Spring AI как `@Tool`/`@GigaTool`. Автоматический цикл tools, ChatMemory advisor и JSON-repair retry для пользовательского хода не включаются. RetryTemplate/транспортные retries ограничиваются одной попыткой генерации; фактическое число HTTP-вызовов проверяется тестом.

### 6.3. Пример результата

```json
{
  "schemaVersion": 1,
  "speechActs": [
    {"kind": "AFFIRMATION", "usage": "DIRECT", "sourceText": "Да"},
    {"kind": "REQUEST", "usage": "DIRECT", "sourceText": "назначение замените на Оплата услуг"}
  ],
  "operationMentions": [],
  "fieldMentions": [
    {
      "field": "purpose",
      "valueText": "Оплата услуг",
      "role": "PROPOSED_VALUE",
      "usage": "DIRECT",
      "sourceText": "назначение замените на Оплата услуг"
    }
  ],
  "ambiguous": false,
  "knowledge": {"candidateSectionIds": []}
}
```

Это пример разбора «Да, но назначение замените на Оплата услуг». Модель выделила согласие и предложенное значение, но не вернула `CHANGE_DETAILS`. Если приложение находится в `AWAITING_CONFIRM` операции `details`, `StateInputPolicy` сформирует это событие после проверки контекста. В `AWAITING_DETAILS` из тех же данных получится `INPUT_DETAILS`. Отправка не выполняется: Java-правила создают новую версию, запускают ФЛК и запрашивают подтверждение обновлённой подготовки.

`speechActs.kind` и `usage` описывают язык; они не являются enum событий FSM. Элемент `operationMentions` содержит `operationType` (`status`, `recall`, `details`), `usage` и `sourceText`; это классификация упоминания, не команда открыть операцию. `fieldMentions` — предполагаемые значения, а не готовый patch: приложение проверяет принадлежность текущей операции, отличие от сохранённых данных и допустимость изменения. Нормализация и предметная ФЛК остаются Java-алгоритмами. Примеры «Статус» и «Да» приведены в [workflow-status.md](./workflow-status.md).

Схема закрытая: неизвестные свойства, в том числе попытка добавить `nextState` или `event`, отклоняют результат. Повреждённый JSON, неизвестные значения enum разбора, конфликтующие сведения, усечённый результат и отсутствие свидетельств приводят к уточнению/техническому ответу с сохранением подготовки. Второй запрос для исправления результата не выполняется. Корректность JSON и наличие цитаты не равны бизнес-валидности действия.

### 6.4. Тайм-ауты и конфигурация

У starter документированы отдельные connect/read timeout. Их значения по умолчанию не соответствуют бюджету этого проекта; нужен внешний deadline всего вызова, включая авторизацию, соединение, чтение полного ответа и парсинг. Connect и read timeout по 5 секунд не означают суммарные 5 секунд. [Конфигурация starter](https://github.com/ai-forever/spring-ai-gigachat#конфигурация).

Общий LLM-budget — до 5 секунд. OAuth-клиент и соединения переиспользуются, токен обновляется заранее. TLS проверяется с корпоративным truststore. Небезопасный SSL из демонстрационных примеров не применяется. Версии prompt/schema/model записываются в техническом аудите без секретов и полных реквизитов.

При недоступном GigaChat любое допустимое сообщение, в том числе «Статус» или «Да», получает контролируемый технический ответ без запуска операции/отправки. Подготовка сохраняется, неподтверждённые данные не меняются; технический ответ не выдаётся за новый вопрос согласия. Локального обхода интерпретатора и подмены Ultra более дешёвой моделью нет.

## 7. База знаний

Согласованные 2–3 страницы хранятся в версионированном Markdown/YAML и загружаются в память при публикации конфигурации. В одном ходе используется единый snapshot БЗ. Embeddings, внешнее хранилище векторов и сетевой поиск не нужны.

Модель за один вызов распознаёт вопрос и предлагает `candidateSectionIds`. Приложение проверяет существование и соответствие разделов вопросу, затем формирует справку из утверждённых ответных блоков БЗ. В выбранном контракте LLM не пишет полный пользовательский ответ. При неоднозначном подборе приложение уточняет вопрос; отсутствие статьи и техническая недоступность БЗ дают разные ответы.

`ResponsePolicy` отдельно определяет напоминание текущего шага и `suggestions` по сохранённому состоянию/контексту. Даже подходящий раздел БЗ не разрешает переход или отправку. После справки рабочие реквизиты и сводка сохраняются; `lastAssistantAct` соответствует сформированному ответу. Если ответ снова просит подтвердить, вопрос и suggestions согласия/отказа привязываются к текущей сводке; иначе следующее «Да» не становится подтверждением отправки и саджест согласия не предлагается.

В prompt не попадают OAuth, полная идентификация, история отменённых черновиков и не относящиеся к текущему шагу сообщения другого агента. Справка не меняет текущую операцию и не запускает corr.
