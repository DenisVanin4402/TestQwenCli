## 2. Артефакты шага и роли

При фактическом запуске шага создаётся папка **`docs/plan/phaseN_stepNN/`**, например для P1.01:

```text
docs/plan/phase1_step01/
  design.md
  task.md
  reports/             # только при появлении фактических отчётов
```

До запуска шага папка не создаётся для видимости прогресса. Для P1.01 подготовлены [design.md](./phase1_step01/design.md) и [task.md](./phase1_step01/task.md), ревизия 2; исходные шаблоны: [шаблон design.md](./templates/design.md), [шаблон task.md](./templates/task.md). Главный журнал всех существенных изменений — [корневой history.md](../../history.md); отдельные конкурирующие журналы по фазам не вводятся.

**Координатор** читает план, ADR, history и `git status`, выбирает только разрешённый шаг, обновляет WBS/handoff и передаёт работу соответствующему агенту. **Агент-архитектор** отвечает за подробные `design.md`/`task.md` стадии design. **Отдельно запускаемый агент-разработчик** отвечает за implement утверждённой ревизии, TDD, код и фактические отметки task. Для Java-кода используется Java-разработчик. У агента явно ограничиваются шаг и файлы; пользовательские и чужие изменения не откатываются. Конкурирующие записи в одни документы не допускаются.

На design допускаются исследование существующего кода/контрактов и создание проектных документов. Production-код, миграции и реализационные тестовые исходники пишутся после явного согласования design, которое разрешает implement. Критерии и дизайн тестов описываются архитектором заранее.

### Что обязательно содержит design.md

- Фаза/шаг, ревизия, требования/ADR, объём и конкретные критерии приёмки.
- Детальные контракты, модули/пакеты/классы, файлы, данные и mapping, состояния/события и последовательность обработки; диаграммы и JSON по применимости.
- Транзакции, конкуренция, ошибки/восстановление, deadline/retries, stub/real конфигурация; Liquibase XML changeset при изменении схемы.
- Тестовая матрица «AC → test ID → уровень → исходные данные → ожидаемый RED → GREEN», применимость integration/e2e и регрессия.
- Варианты решения и вопросы с ID, рекомендациями и последствиями; ответы пользователя и журнал ревизий.
- Порядок реализации, риски, ограничения и критерий готовности к implement.

### Что обязательно содержит task.md

- Ссылка на design и его ревизию, текущая стадия, отметки согласования и запуска implement.
- Checkpoints реализации и тестов, связанные с AC/test IDs; фактические состояния и свидетельства закрытия.
- RED/GREEN с датой/временем, командами, результатом и ссылками на отчёты; отдельно unit, integration и e2e.
- Вопросы/замечания/блокировки, принятые решения, способ воспроизведения пользователем.
- Раздельные поля «разработка готова к проверке» и «пользователь принял шаг».

## 3. Порядок остановок и согласований

1. **Новый шаг → design.** Команда «продолжаем следующий шаг» запускает дизайн следующей разрешённой строки. Координатор сначала проверяет, нет ли незакрытых замечаний/непринятого результата предыдущего шага. Создаёт папку и запускает архитектора; статус строки — `Design`.
2. **Первый пакет документов → остановка.** Архитектор заполняет design/task, фиксирует вопросы и варианты, переводит шаг в `Design на согласовании`, обновляет history/handoff и останавливается. Код не пишется.
3. **Ответы и актуализация документов.** Архитектор фиксирует ответы и обновляет ревизию. Если пользователь явно согласовал представленное решение, техническая фиксация ответа без новых решений не требует повторного согласования. Иначе — остановка на согласовании.
4. **Согласование разрешает implement.** «Согласовано», «принимаю» или однозначный эквивалент означает приёмку представленного design и разрешение немедленно начать реализацию текущего шага, если пользователь не ограничил согласие. Решение и ревизия фиксируются в design/task/WBS.
5. **Запуск разработчика.** Координатор сразу передаёт согласованные документы отдельному разработчику; для Java — Java-разработчику. Отдельная команда implement не нужна.
6. **TDD и развилки.** Изменения поведения выполняются через TDD. Новая существенная развилка останавливает зависимую работу до согласования. Архитектор фиксирует решение; явное согласование разрешает сразу продолжить implement. Обычный дефект исправляется через регрессионный тест.
7. **Обязательные тесты GREEN → task → остановка.** Разработчик отмечает реально закрытые checkpoints, сохраняет результаты тестов/регрессии, обновляет history и handoff. Статус строки — `Implement на проверке`; пользователь получает конкретный результат и инструкции проверки. Следующий шаг не начинается.
8. **Приёмка реализации.** Пользователь проверяет и даёт замечания либо явно принимает. Замечания остаются в том же шаге. Только после приёмки проставляется `Выполнен` в WBS и поле приёмки task; тесты сами по себе эту отметку не разрешают.
9. **Следующий шаг.** Сохранить точку продолжения и остановиться. Пользователь при необходимости очищает контекст/открывает новую сессию и отдельно запускает следующий шаг, который опять начинается с design. Очистка контекста не удаляет файлы; агент не утверждает, что программно очистил историю.

Создание или обновление самого плана/ADR по прямому запросу пользователя не запускает P1.01. Пользовательская приёмка не означает автоматический Git commit/push. Наличие примеров команд в документах не является командой их выполнить.

### Статусы WBS

| Статус | Смысл |
|---|---|
| `Запланирован` | Шаг не запущен, папка шага ещё не создана |
| `Design` | Архитектор готовит или уточняет документы |
| `Design на согласовании` | Документы готовы; ожидается согласование |
| `Design согласован` | Design принят; сразу запускается implement текущего шага |
| `Implement` | Разработчик выполняет утверждённые checkpoints через TDD |
| `Implement на проверке` | Обязательные проверки пройдены, task обновлён, разработчик остановился |
| `Замечания` | Есть замечания пользователя; стадия и следующий владелец записаны в task/handoff |
| `Блокирован` | Есть конкретное препятствие; причина, необходимое действие и стадия записаны |
| `Выполнен` | Пользователь явно принял реализацию; свидетельство и дата сохранены |

## 4. TDD и состав проверок

**Уточнение пользователя:** отчётность краткая по AGENTS.md. Не копировать логи/отчёты в docs/plan/*/reports без отдельного запроса; результаты Maven остаются в target. В task — краткие свидетельства и итог, в history — что сделано/не сделано. Это уточнение имеет приоритет над прежними требованиями к объёму отчётов.

Для каждого изменяемого поведения: **сначала тест по AC → ожидаемый RED → минимальная реализация → GREEN → refactor → регрессия**. Тесты не дописываются задним числом как замена TDD. Сначала unit; integration — для реальных границ БД/FSM/HTTP; e2e — по необходимости и по мере появления доступного сквозного контура. На раннем инфраструктурном шаге отсутствие UI не мешает начать с подходящих build/contract/integration-проверок.

Минимальный каркас и настройка запуска тестов допустимы для получения исполнимого RED, но не должны заранее реализовать целевое поведение. Ошибка скачивания зависимости/отсутствующий Docker не являются ожидаемым RED бизнес-критерия. Дизайн явно определяет тестируемое поведение и корректную причину падения.

Для БД нужны интеграционные тесты H2 с настоящей persistence и Liquibase XML по ADR-003. Для Feign нужны HTTP-контрактные проверки. Для готового чата e2e проходит вход/сервисы/H2 с persistence/out и, когда доступно, UI. Настоящая Ultra проверяется отдельно от stub; оценки генерации/скорости не подменяются фикстурой.

Обязательный тест, который не запущен или пропущен из-за среды, остаётся открытым/блокирующим. `Н/П` допустимо только для действительно неприменимого пункта с обоснованием; существенное исключение согласуется в design и не выдаётся за GREEN. В task записываются команды полного согласованного набора, exit code, количество тестов/ошибок/пропусков и отчёты. После всех обязательных проверок можно отметить готовность implement и остановиться, но не принимать шаг за пользователя.

## 5. История и продолжение после очистки контекста

[history.md](../../history.md) — дополняемый журнал. Каждая существенная порция работы фиксируется до остановки: дата/время с часовым поясом, фаза/шаг, стадия и роль, изменения/файлы, причина или пользовательское решение, проверки, открытые вопросы и следующая точка продолжения. В нём отражаются создание design/task, их ревизии, согласования, implement/TDD, исправления и приёмка. Не нужно писать строку на каждое нажатие клавиши; изменения не должны теряться между запусками.

Старые записи не переписываются как будто решение всегда было новым: поправки добавляются новой записью. Если точное время старого события неизвестно, это явно отмечается. Не придумывать Git commit, пройденный тест или разрешение пользователя. Секреты и реальные реквизиты в history/отчёты не помещаются.

В новой сессии прочитать `AGENTS.md`, этот индекс, план активной фазы, последнюю history и существующие design/task текущего шага, затем проверить файлы и `git status`. Активен только один шаг и одна стадия; перейти к implement или следующему шагу по одной памяти чата нельзя.
