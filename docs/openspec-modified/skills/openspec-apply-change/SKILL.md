Apply выполняет ИИ по `Apply policy: ai-strict`. В `Spec update mode: document-copies` используется schema v3: один редактируемый `content/<path>.md` и генерируемый `review/<path>.md`. Base и первоначально согласованная версия закреплены в Git. Lite/full не меняет строгость проверок.

Постоянный состав `.spec-copy`: manifest.json, content и review. Согласование результата хранится в manifest.review_approval. С начала записи master появляется application-state.json; он же хранит конечный результат. Планы, решения и конфликты при необходимости фиксируй в change, отчёт выдавай в ответе.

`scripts/spec_review.py` строит и проверяет представление; он не выбирает бизнес-правило, не применяет изменения и не делает commits. Автоматический merge/patch-применитель не используется.

**Input**: имя change, действие `проверить` или `применить`. Полученное поручение на применение конкретного согласованного результата не требует повторного разрешения. Неразрешённый конфликт решает пользователь.

## 1. Разрешённый этап и источники

Прочти change, profile/mode/policy, master root, `_sdd/navigation.md`, manifest и относящиеся к scope связи.

| Статус change | Действие |
|---|---|
| На согласовании | Анализ/просмотр, master не менять |
| Согласовано / В реализации | Анализ и явно запрошенный apply |
| Реализовано | Проверить прежний результат, не воспроизводить поверх новых правил |
| Архивировано | Не применять повторно |
| Неизвестный | Выяснить состояние |

Для schema v1/v2 восстанови достоверные версии и выполни миграцию. Незавершённую попытку сначала восстанови по прежнему протоколу. Миграция представления не является новым бизнес-согласованием или фактом нового apply.

Для v3 перед работой выполни `spec_review.py --root <project-root> check openspec/changes/<name>`: checksum `change_sha256` в manifest должна совпадать с текущим change. При несовпадении сначала актуализируй content по требованиям. Не перезаписывай checksum просто для продолжения apply.

## 2. Намерение и актуальный master

Прочти полные base/approved из Git и действующий master. Проверь hashes, CH-ID и критерии. Change должен совпадать с намерением base → approved. При расхождении не выбирай источник самостоятельно.

Определи разрешённые действия. Проанализируй связанные правила: разные строки не доказывают независимость. Первоначальные base/approved не меняются после релиза.

## 3. Одна рабочая копия и один просмотр

Подготовь итог в **том же content**, исходя из актуального master. Сохрани независимые байты; не создавай proposed/candidate/current/preview. До перезаписи копии первоначальный intent должен быть закреплён в Git.

Проверь весь набор по ai-apply. Закрепи master как review_base; без точной Git-версии сначала нужен checkpoint. При конфликте установи review_status=conflict и запиши описание/варианты в «Открытые вопросы» change. После сверки content с обновлённым change выполни render --save-change-hash. Ни один master не меняется; до начала apply state не создаётся.

При готовности выстави ready, выполни render/check. Review показывает review_base → content; таблица CH-ID в change ведёт на него напрямую. ИИ не редактирует представление вручную. Покажи итог аналитику и зафиксируй реальное решение через acknowledge в manifest.review_approval. Смена результата инвалидирует прежнюю привязку просмотра.

## 4. Проверить или применить

При проверке верни готовность/конфликты и review, не меняя master/бизнес-статус.

Для apply выполни check --ready, затем запись по ai-apply: state до записи, проверка перед каждым файлом, запись байтов content, перечитывание всего результата, check --result. Не формируй новый текст между просмотром и записью. При сбое/внешней правке остановись и восстанавливай только доказанно собственные записи.

Сохрани конечный результат в том же application-state.json schema v3, отдельные receipt/report не создавай. Обнови `_sdd` отдельной операцией. `Реализовано` допустим после всех применимых проверок кода, документов и `_sdd`.

## 5. Legacy

Branch-diff по умолчанию проверяет закреплённые источники. Для explicit AI apply подготовь v3: base из merge-base (three-dot) либо Base SHA (two-dot), content/approved из Analyst SHA. Не копируй весь root поверх master. Для иных форматов требуется отдельное представление/проверка.

Manual-change без достоверной истории не позволяет заявить сохранность параллельных правок: восстанови baseline либо согласуй конкретные действия с текущими документами.

## Output

Сообщи применённые CH-ID, сохранённые параллельные правки, фактические проверки, конфликты/ограничения и ссылки на review, master и состояние применения, если запись начиналась. Строгость проверок не обещает детерминизм ИИ. После завершения следующий шаг — archive.
