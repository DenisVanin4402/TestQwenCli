# Копии документов для аналитика и строгого AI apply

Новые change используют `Spec update mode: document-copies` и `Apply policy: ai-strict`. Исполнитель apply — ИИ-агент. Python-применитель, plan token и автоматический Git merge не входят в workflow.

## Вид документа для аналитика

Копия — обычный Markdown-документ: исходные заголовки, абзацы, таблицы, списки и ссылки сохраняются. Только реальные правки выделяются **красным с «−» и зачёркиванием** для удаления и **зелёным с «+»** для добавления. Замена показывается двумя соседними строками. Не оборачивай весь документ в code block. В нём нет `--- base`, `+++ proposed`, `@@`, номеров hunks, SHA, JSON, CURRENT/BASE/PROPOSED, conflict markers и технических журналов.

Пример изменённого абзаца в `review/workflow/discount.md`:

```html
<p style="color:#b42318;background-color:#fee4e2;padding:2px 5px;border-left:4px solid #d92d20;border-radius:4px;"><strong style="font-size:10px;margin-right:10px;">−</strong> <del>Если сумма заказа &gt; 10000 рублей, предоставляется скидка 5%.</del></p>
<p style="color:#067647;background-color:#dcfae6;padding:2px 5px;border-left:4px solid #079455;border-radius:4px;"><strong style="font-size:10px;margin-right:10px;">+</strong> Если сумма заказа &gt;<span style="background-color:#abefc6;color:#054f31;font-weight:700;">=</span> 10000 рублей, предоставляется скидка 5%.</p>
```

Эти HTML-элементы записываются непосредственно в `.md`, **без** fence вокруг них. Для строк используй компактные отступы `padding:2px 5px`, скругление `border-radius:4px` и знаки −/+ размером `font-size:10px` с `margin-right:10px`, как в примере.

Внутри пары изменённых строк дополнительно выделяй **только изменившиеся символы** более насыщенным фоном и жирным начертанием: удалённые — `<span style="background-color:#fecdca;color:#912018;font-weight:700;">...</span>`, добавленные — `<span style="background-color:#abefc6;color:#054f31;font-weight:700;">...</span>`. Сопоставляй соответствующие слова и значения, затем уточняй изменившиеся символы внутри них. Не выделяй неизменённые соседние символы, слова или целый оператор:

- `>` → `>=`: внутри строки выделен только новый `=`; в старой строке дополнительного выделения нет, поскольку символы не удалялись.
- `10000` → `15000`: в старой строке `1<span style="background-color:#fecdca;color:#912018;font-weight:700;">0</span>000`, в новой — `1<span style="background-color:#abefc6;color:#054f31;font-weight:700;">5</span>000`.
- `>=` → `>`: выделен только удалённый `=` в старой строке; при замене фрагмента выделены старый и новый фрагменты на соответствующих строках.

Полностью добавленной/удалённой строке достаточно общей подсветки: всё её содержимое изменено. Разметка не добавляет символов в текст требования. Сравнивай исходный текст до HTML-экранирования, затем экранируй `<`, `>`, `&` и оборачивай нужные фрагменты в `span`: например, `&gt;` представляет один символ `>`, HTML-сущность нельзя разрывать. Не разрывай составные Unicode-символы. В Markdown-копиях review и preview используй одинаковые правила выделения.

Неизменённая часть остаётся Markdown. Для таблицы выделяй затронутую строку/ячейку и изменившиеся символы внутри неё, сохраняя вид таблицы; при необходимости используй HTML-таблицу вместо ломающегося Markdown. Для изменений заголовков сохраняй их уровень. Для кода/схем подсвети изменённые строки и символы внутри отображения кода без git diff-заголовков.

Все review-копии и preview сохраняются только в `.md` и открываются в Markdown Preview IntelliJ IDEA / VS Code. Цвет задаётся встроенной разметкой непосредственно в Markdown. Чистый Markdown не стандартизует цвет: если просмотрщик очищает HTML/CSS, цвет может исчезнуть. Проверь **отрендеренный** вид в фактическом просмотрщике. Для независимости от цвета всегда сохраняй знаки −/+ и зачёркивание удаления.

## Layout и неизменные источники

```text
openspec/<service>/workflow/discount.md             # актуальный master
openspec/changes/<name>/
  change.md
  .spec-copy/
    index.md                                      # человеческие названия и ссылки
    manifest.json                                 # технические пути, CH-ID и хеши
    base/workflow/discount.md                      # неизменный исходный снимок
    proposed/workflow/discount.md                  # согласованная чистая версия
    review/workflow/discount.md                    # обычный документ с выделением строк
    current/workflow/discount.md                   # master перед конкретной попыткой apply
    candidate/workflow/discount.md                 # чистый результат, подготовленный ИИ
    preview/workflow/discount.md                   # current → candidate в том же визуальном формате
    application-plan.md                           # служебное объяснение соответствия CH-ID
    conflicts.md                                  # понятные конфликты и решения
    application-report.md                         # фактические проверки и результат
    applied.json                                  # фактические пути, хеши до/после и исходы CH-ID
```

Сохраняй исходные имена и вложенные пути, чтобы аналитик открывал `discount.md`, а не `D001.md`. D-ID может оставаться служебным идентификатором в manifest. Каждое требование CH-ID ссылается на одну или несколько review-копий. Контекстные документы без изменений не копируются.

Base фиксируется **до редактирования** и не меняется после merge релиза. Proposed — полная целевая версия относительно base, без цветовой разметки. Review показывает ровно изменения base → proposed. Если видимая копия, чистая версия и change расходятся — исправь рассогласование до согласования/apply. После правки согласованного требования или proposed верни статус `На согласовании`; нельзя просто пересчитать хеши и оставить прежнее согласование.

Согласование охватывает содержание change и связанных копий. Одно изменение оформления при неизменной семантике не требует повторного бизнес-согласования, но соответствие версий должно быть заново проверено. Не показывай служебные хеши внутри копии для аналитика.

## Manifest schema v2

Пример структуры (значения SHA вычисляются из реальных байтов, не генерируются по памяти):

```json
{
  "schema_version": 2,
  "apply_policy": "ai-strict",
  "master_root": "openspec/orders",
  "documents": [
    {
      "id": "D001",
      "path": "workflow/discount.md",
      "operation": "modify",
      "change_ids": ["CH-01"],
      "base": "base/workflow/discount.md",
      "proposed": "proposed/workflow/discount.md",
      "review": "review/workflow/discount.md",
      "base_sha256": "<sha256>",
      "proposed_sha256": "<sha256>",
      "review_sha256": "<sha256>"
    }
  ]
}
```

Пути копий относительно `.spec-copy`, target — относительно master_root. Поле `review` указывает на Markdown-копию. Пути относительные, без `..`, абсолютных путей, symlink/junction и дубликатов назначения. Для add base и его hash равны `null`, для delete proposed и его hash равны `null`; отсутствие отличается от пустого файла. Rename — явно согласованная пара delete/add с проверкой ссылок. Для нескольких сервисов используй отдельные соответствия root, не подменяй root при apply.

Зафиксируй `.spec-copy/.gitattributes` с `* -text`, если Git может преобразовать переводы строк копий. Хеши защищают от незамеченных изменений/устаревшего анализа, а не от намеренной подмены всех файлов. При повреждении base восстанови подтверждённый исходник из истории, не «исправляй» hash по текущему содержимому.

## Подготовка через propose / change-from-diff

1. Выбери lite/full и прочитай релевантные master-документы и связи.
2. Сохрани точные исходные байты затрагиваемых документов в base и вычисли hashes.
3. Сформируй proposed строго по требованиям; подготовь review как обычный документ с цветными правками. Проверь, что нет скрытых правок/случайного переформатирования.
4. Заполни manifest/index и ссылки в change; проверь их открытие. Не меняй master при propose.
5. Аналитик согласует change вместе с видимыми копиями. Реализация использует proposed и CH-ID.

Для Git diff фиксируй SHA: three-dot берёт base из merge-base, two-dot из Base SHA, proposed из Analyst SHA. Читать через Git object database можно без checkout. `.spec-diff/` сохраняет происхождение при необходимости, но технический patch не попадает в копию аналитика. Не игнорируй не-MD файлы из смешанного diff: согласуй отдельное представление и обработку.

## После merge релиза

Пример: base имеет `> 10000` и лимит `1000`, proposed — `>= 10000` и тот же лимит. Текущий master после merge релиза имеет `> 10000` и лимит `1500`. ИИ проверяет, что лимит независим от изменения границы, переносит только `>=` в current и сохраняет `1500`.

Если релиз изменил порог на `15000`, это конфликт бизнес-правила. Даже если правка расположена в другом разделе/документе (например, поменялась валюта или смысл «суммы заказа»), требуется смысловая проверка. ИИ не выводит `>= 15000` без выбора пользователя.

Порядок анализа, записи, повторной проверки и остановки — в [ai-apply.md](ai-apply.md). Строгость означает ограниченный, проверяемый scope и явные решения конфликтов; это не обещание детерминизма ИИ.

## Совместимость

Старые D001.md/schema v1 и результаты прежнего алгоритмического примера можно читать как исторические артефакты. Автоматически применять их прежним скриптом нельзя. Сохрани исходные байты и происхождение, перенеси пути в schema v2, подготовь цветные копии и проверь согласованность требований. Старый applied receipt не переименовывай в результат нового AI apply.
