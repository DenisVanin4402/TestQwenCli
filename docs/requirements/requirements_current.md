[Дизайн](../tasks/task04/impl_design.md) и [задачи](../tasks/task04/tasks.md) ещё на согласовании. Это планируемое расширение, не часть описанного ниже текущего кода.

Модель и адрес задаются конфигурацией; AccessToken из файла не используется. Явные ACL-действия и UI по-прежнему не вызывают LLM. Результаты приёмки — в [tasks.md](../tasks/task03/tasks.md).

[Task01](../tasks/task01/tasks.md) и [task02](../tasks/task02/tasks.md) находятся на валидации: автоматические проверки и независимая валидация выполнены, ручной UI smoke остаётся открытым. Это описание фактической реализации, а не утверждение о завершённой приёмке.

Связанные документы: [техническая спецификация](technical_specification_current.md), [C4 и последовательности](c4/README.md), [действующие ADR](../adr/README.md), [исходные требования этапа](../stages/01_poc/old/requirements.md), [история](../stages/01_poc/old/history.md). ## 1. Назначение и границы

Пользователь выбирает запрос статуса платежа, получает предложение, отдельно подтверждает его или отказывается. После подтверждения агент передаёт запрос внешнему менеджеру операций и завершает свою сессию. Завершение означает принятие запроса временным corr-контрактом и успешное сохранение локального состояния, но не получение банковского статуса платежа.

| В текущем объёме | За пределами реализации |
|---|---|
| Одна зарегистрированная операция STATUS | Исполнение RECALL/DETAILS |
| Локальный профиль ACL 1.6, тестовый чат и синтетический платёж | Настоящая поверхность GA, банковская авторизация, свободный текст, разбор LLM/RAG |
| Технический GigaChat ChatClient и отдельный live smoke | Подключение модели к диалогу, tools, embeddings, память |
| Сохранение FSM, подготовки и согласия в БД | История действий, журнал команд, входной replay/hash |
| Один синхронный вызов временного WorkflowManager | Outbox/УСС, callback, corr-result и автоматические повторы |
| PostgreSQL либо локальная файловая H2 | Автоматический перенос несовместимых снимков и production SLA |

Тестовый UI относится к этапу 2, но уже присутствует в общем приложении и включён в этот срез как способ проверить POC. Браузер обращается к локальному ACL-зеркалу; основной ACL и зеркало используют один сценарий.

Spring StateMachine (SSM) — единственный механизм переходов. Конфигурация и исполнение используют штатный API SSM в `agent-service`; `agent-db` предоставляет семафор, репозитории и native persistence. Заменяемого движка и собственного протокола переходов поверх SSM нет. Прикладная логика остаётся в отдельных классах guards/actions; три бизнес-состояния, внешний ACL и сохранённый формат `status-v3` сохраняются.

## 2. Контекст и идентичности

| ID | Требование текущего сценария |
|---|---|
| CUR-01 | Сессия определяется UUID `Gigachat-Session-Id`. UUID `Request-Id` идентифицирует сообщение и должен совпадать с `message.reply_with`. `conversation_id` служит корреляции внешнего диалога. |
| CUR-02 | Первому допустимому выбору нужны `epkId`, `digitalUserId`, `paymentId`, `paymentNumber`, `paymentDate`, `amount`, `currency`, `recipientName`, `organizationName`. Источник — metadata ACL, а не fixtureId. |
| CUR-03 | Последующие сообщения могут опускать контекст: операция использует сохранённые данные. Явно переданные поля сверяются с исходной привязкой под блокировкой сессии. Несовпадение отклоняется; привязка не перезаписывается. |
| CUR-04 | Известные поля контекста с явным null, пустотой, дубликатом ключа или неразбираемой датой/суммой отклоняются. Неизвестные JSON-поля и неизвестные ключи additional_info не становятся бизнес-контекстом. |

Дата передаётся в ISO-формате, сумма — десятичной строкой, номер платежа — строкой с сохранением ведущих нулей. Проверка наличия реквизитов и их неизменности не доказывает банковские полномочия, существование платежа или допустимость его суммы/валюты.

## 3. Подготовка и отдельное согласие

| ID | Требование текущего сценария |
|---|---|
| CUR-05 | Первый `request/status` создаёт бизнес-сессию и предложение за один рабочий ход. Зарегистрированные операции задаются программной схемой; сейчас доступен только STATUS. |
| CUR-06 | Подготовка сохраняет независимую копию контекста, UUID `preparationId`, номер `preparationNo`, ID сообщения подготовки и снимок подтверждаемых значений. Номер возрастает внутри сессии и не сбрасывается после отказа. |
| CUR-07 | STATUS показывает текст «Запросить статус платежа №…?» и возвращает ровно два параметра `state` типа `CONFIRMATION`: `paymentNumber` и `preparationNo`. Служебный номер не включается в текст сводки. |
| CUR-08 | `accept_propose` должен вернуть подтверждаемые параметры активного предложения и новый Request-Id, отличный от ID его подготовки. Входные данные подтверждения проверяются, но не заменяют сохранённые реквизиты операции. |
| CUR-09 | `preparationNo` обязателен ровно один раз: положительное целое в пределах long. Другой номер даёт `STALE_PREPARATION`. Ошибка формы, пропуск, null, пустота или дубликат дают `INVALID_CONFIRMATION`. |
| CUR-10 | Бизнес-набор подтверждения должен точно соответствовать схеме STATUS. Лишний/пропущенный/повторный ключ запрещён; `paymentNumber` сравнивается как точная строка. Несовпадение даёт `CONFIRMATION_MISMATCH`. Порядок параметров и description на согласие не влияют. |
| CUR-11 | Все guards выполняются последовательно до первого отказа. При отказе guard нет вызова менеджера, записи нового native-снимка или изменения сохранённого согласия/подготовки. |
| CUR-12 | `reject_propose` не требует подтверждаемых параметров: он удаляет активную подготовку и возвращает выбор операции. Исходный контекст и последний номер подготовки сохраняются. Это отказ от предложения агента, не отмена банковского платежа. |

Выбор операции, свободный текст, бездействие, закрытие страницы и создание нового локального диалога не являются согласием. Отказ не требует state, но переданный state всё равно проходит транспортную проверку типа элементов.

## 4. Переходы и результат

| Состояние | Вход | Результат |
|---|---|---|
| Нет сохранённой FSM | Полный корректный request/status | Создать `CHOOSING_REQUEST_TYPE`, затем подготовить → `AWAITING_CONFIRM`. |
| Нет сохранённой FSM | Согласие, отказ или неполный первый выбор | Ошибка; бизнес-сессия не сохраняется. Техническая строка семафора может остаться. |
| `CHOOSING_REQUEST_TYPE` | request/status | Новая подготовка → `AWAITING_CONFIRM`. |
| `CHOOSING_REQUEST_TYPE` | reject_propose | Успешный ответ `NO_ACTIVE_PREPARATION`, остаться на выборе. |
| `CHOOSING_REQUEST_TYPE` | accept_propose | `INVALID_COMMAND`, без операции. |
| `AWAITING_CONFIRM` | Допустимый accept_propose | Согласие → один вызов менеджера → `COMPLETED` после успешного commit. |
| `AWAITING_CONFIRM` | reject_propose с допустимым контекстом | Удалить подготовку → `CHOOSING_REQUEST_TYPE`. |
| `AWAITING_CONFIRM` | Повторный request/status | `INVALID_COMMAND`; состояние и подготовка прежние, corr не вызывается. |
| `COMPLETED` | Новый поддерживаемый ход | `SESSION_COMPLETED`, без новой операции. Нужна новая сессия. |
| Любое | Неподдерживаемая команда, включая restart_status | Отказ на входной границе, без исполнения FSM. |

**Особенность текущего хранения:** событие без подходящего перехода в существующей FSM сохраняет `lastResult`, `lastRequestId` и увеличивает `projectionVersion`. Состояние и подготовка не меняются. Это отличается от отказа выполненного guard, при котором native save отсутствует.

Успешная подготовка возвращает `200/propose`, отказ — `200/inform` с suggestions, успешная отправка — `200/inform` и `metadata.final_message=true`. Ошибки входа, согласия, занятости и завершённой сессии возвращаются как `400/failure`; технические ошибки операции/хранения — `500/failure`. Текст успеха находится в `content.result`, ошибки — в `content.reason`.

Терминальность передаётся, когда обработка установила сохранённое состояние `COMPLETED`. Входной отказ до загрузки FSM не читает БД только ради final_message и не подтверждает завершённость сессии.

## 5. Сохранность и конкурентная работа

| ID | Требование текущего сценария |
|---|---|
| CUR-13 | Постоянный семафор создаётся отдельной транзакцией. Рабочий ход берёт исключительную блокировку NOWAIT до чтения FSM и удерживает её до commit/rollback. Занятость возвращается без очереди и автоматического повтора. |
| CUR-14 | В одной рабочей транзакции выполняются restore/create, событие с синхронным Action, native persist и остановка временной FSM. Ответ с успешным предметным результатом формируется только после commit. |
| CUR-15 | Ошибка Action или хранения откатывает локальные изменения. Семафор остаётся; после сбоя первой инициализации следующий допустимый вход может создать отсутствующую FSM. |
| CUR-16 | Сохранённая сессия восстанавливается после перезапуска сервера. Текущий формат — `status-v3`; несовместимые/повреждённые снимки не пересоздаются и не мигрируют автоматически. |
| CUR-17 | Внутреннее чтение использует блокировку чтения NOWAIT и возвращает сохранённый предметный снимок после завершения транзакции, без формирования ответа renderer. Не отправляет событий и не вызывает corr. Публичного GET сессии нет. |

Конкурентная первая вставка семафора может ожидать разрешения конфликта уникального ключа; NOWAIT относится к рабочей блокировке существующей строки. Конкуренция PostgreSQL проверяется отдельно от H2.

## 6. Внешняя операция и ограничения

`WorkflowManager` принимает тип операции и серверный `OperationContext`, не возвращая банковского результата. Для STATUS временный адаптер выполняет один запрос corr. Его успешный ответ должен содержать `outcome=ACCEPTED` и непустой `reference`; отказ, неверный ответ или транспортный сбой прерывают Action.

Вызов corr происходит **до локального commit**. Внешний эффект может состояться при timeout, потере ответа или последующей ошибке БД. Rollback не компенсирует corr. Автоматических повторов нет, но новый явный POST после rollback может повторно вызвать менеджер. Ни маркер входной идемпотентности, ни переданный corr ключ сами по себе не обеспечивают exactly-once; локальная заглушка не дедуплицирует вызовы.

Ошибка подготовки HTTP-ответа после commit не отменяет сохранение и не запускает Action повторно. Восстановление доставки потерянного ответа библиотекой replay пока отсутствует.

## 7. Тестовый чат

- `/test-ui/` загружает синтетический платёж и начальные suggestions через `GET /local-api/v1/fixtures`.
- Действия идут одним POST в ACL-зеркало; подтверждение возвращает state последнего предложения. Пока запрос выполняется, кнопки недоступны.
- Клиент проверяет conversation_id/in_reply_to и игнорирует поздний ответ старого локального диалога. После ошибки или потери ответа автоматического POST и активных действий нет.
- После обновления страницы начинается новый локальный диалог. История и прежняя серверная сессия через UI не восстанавливаются; это не отменяет сохранность серверной FSM.
- Свободный текст даёт локальное пояснение, а не бизнес-команду. Схема и guards остаются на сервере.
