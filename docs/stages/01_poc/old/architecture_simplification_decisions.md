# Решения по упрощению архитектуры POC

**Назначение документа, уточнено 05.10.2026:** хронология принятых решений и основание рефакторинга. Ответы §12–20 сведены в [действующие ADR](../../../adr/README.md), [требования POC](requirements.md) и [план TO BE](architecture_refactoring_plan.md). Рефакторинг кода и БД выполнен; результаты проверок приведены в [истории этапа](history.md). Ниже сохранены формулировки на момент обсуждения: списки owner/revision/corr-журналов, статусы «не начата» и запрет начинать реализацию не описывают текущее состояние и не отменяют последующего разрешения пользователя. Последующие уточнения собраны в §21.

Дата исходного обсуждения: 04.10.2026. Основание — [критический review](architecture_simplicity_review.md) и ответы пользователя. Здесь фиксируются выбранные варианты, повторная оценка замечаний и последствия для кода. На момент записи ответов реализация ещё не была разрешена. Непринятые предложения обозначены отдельно.

## 1 Механизм переходов

**Принято пользователем:** сохранить Spring Statemachine и сделать её единственным механизмом выбора переходов через guards/actions. Последующее согласованное уточнение (§12): все прикладные actions оформляются синхронными transition `.action(...)` и работают в общей транзакции с сохранением FSM. Бизнес-логика и SQL могут находиться непосредственно в Action. Внешняя операция передаётся через `WorkflowManager.callOperation(Operation operation, OperationContext context)`; реализация менеджера сейчас не входит в работу.

Следствие: предварительное вычисление готового target в `SessionTransitionPolicy` и повторное исполнение этого решения SSM должны быть заменены одним механизмом переходов. Допуск по владельцу, блокировки, корреляция попыток и атомарная запись остаются во внешнем транзакционном протоколе. Штатное хранение SSM сохраняется. Альтернатива удаления SSM не выбрана.

Статус реализации: не начата. При реализации необходимо уточнить ADR-008 и связанные архитектурные документы, устранить повторное восстановление машины внутри одной транзакции и проверить переходы/rollback.

**Уточнение принято (§12):** обязательная связка `Action → отдельный Service` для каждого шага не нужна. Action может выполнять прикладную логику и SQL в общей транзакции. Отдельный сервис выделяется при самостоятельной или повторно используемой ответственности. Физический HTTP-вызов corr относится к будущей реализации WorkflowManager по Transactional Outbox, а не к транзакционной работе Action.

## 2 Формат хранения

**Принято пользователем:** убрать отдельную `FsmBindingEntity`/таблицу binding и четыре независимых номера версии; хранить один `formatId` в `SessionEntity`, проверяемый до десериализации checkpoint. Native machine ID выводится из sessionId. Проверки наличия checkpoint и принадлежности сессии сохраняются.

Статус реализации: не начата. Правило обновления формата и миграция существующих данных зависят от ещё открытого ответа о совместимости сохранённых сессий. Решение уточнит ADR-008 и описание схемы при реализации.

## 3 Журнал внутренних команд

**Принято пользователем:** удалить журнал внутренних FSM-команд и его использование. Дедупликация входных запросов и возврат сохранённого ответа относятся к входной библиотеке идемпотентности. Собственный FSM replay по commandId, сравнение hash повторной команды и сверка ревизии с журналом больше не требуются.

В текущем коде `@Idempotent` остаётся маркером без AOP. Решение не означает, что библиотека уже подключена или входная идемпотентность работает. До подключения библиотеки эта гарантия по-прежнему отсутствует; удаляемый FSM-журнал её и раньше не обеспечивал.

Состояние SSM, expectedRevision и права исполнителя продолжают ограничивать допустимость команды. Журналы отправок/попыток corr сохраняются: они разрешают физический вызов и связывают его с результатом. Повтор уже обработанной внутренней команды теперь может завершаться отказом по актуальному состоянию, владельцу или ревизии; прежний результат по commandId возвращать не обещаем.

Статус реализации: не начата. Решение частично заменяет требования ADR-008/009/012 о сохранении FSM-журнала, но не атомарность native и оставшейся SQL-части.

## 4 История действий агента

**Принято пользователем:** журналирование истории входов, выходов и действий агента нужно позднее; в текущий объём упрощения не входит. Не заменять удаляемый FSM-журнал новым audit-журналом, logging action, listener, очередью или outbox. Выбор места, состава и способа хранения будущей истории остаётся открытым. Наличие обычных диагностических логов не является реализацией этой истории; их удаление не запрошено.

## 5 Повторная оценка замечаний критика

Статусы ниже относятся к решениям, а не к готовности кода. Все замечания повторно сопоставлены с текущими production-потребителями и тестами. Обозначения R/A/D соответствуют [исходному review](architecture_simplicity_review.md).

| Пункт | Актуальность после решений | Уточнённое действие |
|---|---|---|
| R1 — повторный restore | Закрыт направлением §18 | Одна машина на рабочую транзакцию: под семафором восстановить либо создать, выполнить событие и сохранить. Предварительный load вне этой транзакции удаляется; адаптацию ошибок и ответа выполнить в новом пути. |
| R2 — дубли проверок | Частично поглощён переносом переходов в SSM | Удалить повтор `verifyCommandOwner` в одном проходе и внешнюю вторую политику допустимости переходов. Проверки идентичности/попытки/владельца на границах транзакций оставить. Будущие guards SSM не считать дублями только потому, что старые проверки находились в policy. |
| R3 — event и outcome | Проблема актуальна, прежнее решение устарело | Нельзя больше предлагать «вычислять event вместе с target в policy»: target выбирает SSM. Нужен один способ перевести входное намерение/outcome в событие, без возможности передать противоречивую пару event/outcome. Сам SessionEvent нужен SSM. Конкретная форма входного DTO ещё не утверждена. |
| R4 — неиспользуемый payloadHash исходящего DTO | После §12 повторно оценить на границе WorkflowManager | Ранее предлагалось убрать только CorrSubmitInDTO.payloadHash. Если DTO исчезнет вместе со старым путём, отдельная правка теряет предмет; если останется, удалить поле без потребителей. Hash сохранённого payload не удалять автоматически. |
| R5 — широкие catch | Закрыт правилом §16 | Любая ошибка Action откатывает рабочую транзакцию; превращение локального дефекта в успешный/неопределённый corr-результат с последующим retry не сохраняется. Повторы исключены. |
| R6 — эксклюзивный node lock | Закрыт решением §18 | Общий node lock удаляется; используется постоянный семафор конкретной сессии на всю рабочую транзакцию. Новый shared/exclusive-протокол узла не требуется. |
| R7 — повтор lifecycle-валидации | Поглощается заменой старого исполнителя corr по §12 | Ручной afterPropertiesSet() находится в CorrSubmissionService. При удалении заменяемого сервиса отдельное исправление этого вызова не требуется. Если часть сервиса останется, повтор lifecycle-валидации оценить в оставшемся коде. |
| A1 — binding и четыре версии | Выбран вариант упрощения | Один formatId до десериализации, native ID из sessionId, отдельного binding нет. Совместимость старой БД пока не решена. |
| A2 — два механизма переходов | Исходный вариант удаления SSM отклонён; проблема решается иначе | Единственный механизм — SSM guards/actions. Удаляется внешний вычислитель target. SSM, persister, native таблица и необходимая сериализация остаются. |
| A3 — журнал и max ревизии | Принято полное удаление | Больше не выбирать между сохранением журнала и удалением только max. Удаляется весь механизм command replay, но не corr submission/attempt. |
| D1 — обоснование необходимости защиты | Актуален для документации | Отделять нужный инвариант от выбранной реализации. Реестр защит C4 не является списком обязательных к сохранению классов. |
| D2 — порядок restore в S8 | Подтверждена неточность текущей схемы | При следующем обновлении C4 показать проверку formatId до десериализации и принадлежности/типов после неё. До реализации не изображать новый путь как работающий. |
| D3 — скрытая повторная работа в S4 | Подтверждено | Сейчас три restore на обычном ходе; целевое сокращение описывать отдельно от действующей реализации. |
| D4 — hash DTO и «канонический» JSON | Частично снимается удалением command hashing | Межверсионный hash внутренних команд больше не является требованием. Назначение оставшегося payload hash описывать точно; неиспользуемое поле CorrSubmitInDTO остаётся R4. |

## 8 Что нельзя удалять механически

- `FSM_COMMAND_CONFLICT` сейчас используется не только при конфликте hash, но и при неверной принадлежности команды, отправки или результата попытки. Удаляется ветвь replay, а не автоматически все места этого кода ошибки. Названия оставшихся ошибок можно уточнить отдельно.
- `SnapshotCodec` нужен `JpaSessionStore` и `TransitionJournal` для сериализации/чтения/hash payload corr; удаление hash команд не удаляет весь codec.
- `SessionEvent`, граф состояний, guards/actions, SSM persister, native `state_machine` и нужная регистрация типов остаются: пользователь выбрал SSM, а не чистую Java policy вместо неё.
- Проверки завершения события SSM и ошибок actions остаются. Удаление сравнения с заранее вычисленным target не разрешает сохранять результат неуспешного исполнения машины.
- Сопоставление Request-Id с reply_with, версия ACL 1.6, immutable context, отдельное согласие, owner/generation/token, expectedRevision, BEGIN/FINISH попытки, конечный retry и запрет продолжения после ошибки сохранения остаются.
- Последний результат сессии нужен текущему GET/ответу. Отсутствие журнала команд не означает отказ от этого состояния и не требует нового архива результатов.
- INIT гонка и CREATED/EXISTING остаются: две транзакции могут одновременно попытаться создать одну сессию. Это не replay ранее сохранённой команды.

## 11 Приоритет уведомления клиента и восстановление через УСС

Полные [предлагаемые sequence-диаграммы с границами транзакций](corr_outbox_uss_sequence.md) сохранены по запросу пользователя. Они показывают основной путь, восстановление через УСС и доставку результата; наличие схем не означает утверждения открытых контрактов или начала реализации.

**Уточнение пользователя от 04.10.2026:** вызов corr запускает необратимый бизнес-процесс, включающий операцию отмены/изменения платежа и SMS. Предпочтительна ситуация «клиент получил положительный ответ в чате, операция ещё не выполнена», чем выполнение операции без ответа в чате, когда клиент её не ожидает. Существующая УСС (управление сбойными ситуациями) выполняет автоматические повторы, а при невозможности восстановления передаёт ситуацию оператору. Это новый бизнес-приоритет для проектируемого сценария, а не описание возможностей текущего POC запроса статуса.

**Последующий ответ пользователя о доставке:** если ответ успешно отдан ГигаАссистенту, считаем его доставленным клиенту. Критерий выбран; отдельная квитанция доставки/отображения от GA или клиента не требуется. Это принятое бизнес-допущение, а не техническое доказательство прочтения. Commit БД или возврат DTO из сервиса ещё не равны успешной отдаче HTTP-ответа. Конкретный способ фиксации успешной отдачи относится к будущей интеграции канала с разрешением внешней отправки.

**Предыдущая схема обсуждения, пересматривается по §12–13:** квитанции клиента заменены принятым критерием отдачи ответа GA; результаты операций WorkflowManager обратно в агент не требуются. Следующие шаги сохранены как контекст прежнего обсуждения, а не как дополнительные обязательства к новому контракту.

1. В общей транзакции допустить событие, сохранить намерение, неизменный payload/ключ corr, ответ для чата и состояние ожидания подтверждения доставки. Action определяет бизнес-действие; внешнего вызова corr на этом шаге нет.
2. Вернуть ответ в чат. Пока нет согласованного подтверждения уведомления, не разрешать corr и его автоматические повторы через УСС.
3. По подтверждению, связанному с конкретной операцией и сообщением, отдельной транзакцией разрешить отправку. После commit вызвать corr. Результат сохранить новым событием FSM в новой транзакции. Повтор квитанции не должен создавать новую логическую операцию.
4. Незавершённую разрешённую отправку восстанавливать через УСС. Запись операции должна переживать падение процесса до первого вызова или передачи в УСС; способ гарантированного обнаружения/передачи таких записей ещё требует согласования. УСС не должна обходить условие уведомления клиента.

`afterCommit` исходного синхронного HTTP-запроса сам по себе не обеспечивает ответ в чате до corr: callback выполняется до возврата из транзакционного вызова, когда HTTP-ответ ещё может не быть отправлен. Асинхронный запуск также не устанавливает этот порядок. Callback можно рассматривать после фиксации подтверждения уведомления; его выполнение после падения процесса не гарантируется. JPA-записи из callback требуют отдельной транзакции, а регистрация должна происходить на потоке исходной JPA-транзакции, не произвольно внутри reactive Action.

Открыты: интерфейс и гарантии передачи в УСС; распределение повторов между WorkflowManager и УСС; гарантии идемпотентности corr для всей операции, включая SMS, и срок действия ключа. При неизвестном исходе автоматический повтор допустим при подтверждённой безопасности по этому контракту; иначе требуется сверка/оператор. Поздний повтор должен учитывать актуальность отмены/изменения платежа. Принятие corr и фактическое завершение бизнес-процесса различаются внутри будущего WorkflowManager/УСС, но не требуют обратного события в FSM агента (§13).

**Уточнение исполнения Action, проверено 04.10.2026:** transition `.action(...)` и state doAction нельзя обобщать. В отдельном эксперименте с установленной SSM 4.0.2, плоской машиной, JpaTransactionManager и штатным native persister обычный transition Action выполнялся на исходном потоке с тем же JPA-ресурсом. Его SQL-запись и native-состояние сохранялись общим commit и вместе откатывались при принудительном rollback. Регистрация afterCommit непосредственно из transition Action работала; при rollback callback не вызывался. State doAction исполнялся на parallel-потоке без исходной транзакции. Поэтому обязательный вынос SQL/регистрации afterCommit из transition Action не обоснован для проверенной конфигурации. Это уточняет прежнюю осторожную формулировку о reactive callback; асинхронные actions/guards, параллельные регионы и другие переключения потока требуют отдельной проверки. Внешний эффект corr по-прежнему не становится частью rollback БД, а afterCommit не доказывает доставку ответа клиенту. Production-код не менялся.

Детальные состояния, таблицы, фоновые обработчики и протокол УСС этой схемой не утверждены и не реализованы. Позднее принято направление WorkflowManager из §12; оно отмечено в ADR, но не утверждает автоматически все детали предложенного протокола. Общий журнал истории действий по-прежнему отложен. После выбора точного протокола потребуется согласованно обновить подробные требования, ADR, спецификацию и sequence-диаграммы.

## 12 Синхронные transition actions и граница WorkflowManager

- Все прикладные actions выполняются как синхронные transition `.action(...)`. Обработка события, прикладные SQL-изменения и сохранение native FSM участвуют в одной локальной транзакции. Обязательная отдельная бизнес-обёртка для каждого Action не создаётся.
- Action передаёт внешнюю операцию через контракт `WorkflowManager.callOperation(Operation operation, OperationContext context)`. Техническая цель вызова будущего менеджера — транзакционно зарегистрировать внешнюю работу; физическая сеть выполняется после commit.

## 13 Контракт без результата и предложение минимального OperationContext

**Принято пользователем:** операции через WorkflowManager не требуют возврата результата. Контракт: `void callOperation(Operation operation, OperationContext context)`. Агент не ожидает ни синхронного бизнес-результата corr, ни последующего callback результата WorkflowManager. Менеджер и УСС отвечают за исполнение и восстановление после регистрации. FSM агента не должна оставаться в ожидании отсутствующего по контракту результата. Конкретное конечное состояние локального хода и допуск следующих операций относятся к O6.

Отсутствие бизнес-результата не означает молчаливую потерю регистрации: предлагаемая семантика void — успешно зарегистрирована работа в текущей транзакции; ошибка регистрации прерывает транзакцию исключением. Реализация менеджера по-прежнему отложена. Результат этого вызова нельзя трактовать как подтверждение отмены или изменения платежа.

**Состав и правила ниже утверждены пользователем в ответе на оставшийся вопрос 1 (§19). Текущая реализация ограничена STATUS; поля расширения не означают реализацию RECALL/DETAILS.**

| Поле OperationContext | Тип | Необходимость |
|---|---|---|
| operationId | UUID | Постоянная идентичность логической операции и ключ её повторов в corr/УСС. Создаётся один раз, не меняется при техническом повторе. |
| epkId | String | Организация, к платежу которой относится запрос. |
| digitalUserId | String | Пользователь, подтвердивший операцию. |
| paymentId | String | Платёж, по которому выполняется запрос. |
| changes | PaymentDetailsChangesDTO, необязательно | Подтверждённые новые значения только для уточнения реквизитов. |

Предметное расширение контракта предусматривает STATUS, RECALL (запрос отзыва/отмены), DETAILS (уточнение реквизитов). Последующим ответом §19 текущая реализация ограничена STATUS; исполняемые ветви RECALL/DETAILS и их внешние DTO/endpoints заранее не добавляются. Тип операции передаётся отдельным аргументом и не дублируется внутри context.

PaymentDetailsChangesDTO содержит четыре поля из §6.2 базовых требований: `recipientInn`, `recipientAccount`, `recipientName`, `paymentPurpose`, все String. Для DETAILS требуется хотя бы одно новое значение; null отдельного поля означает «не изменять», пустая строка не означает «очистить». Для STATUS/RECALL changes отсутствует. Причину отзыва не добавляем без требования внешнего контракта.

Контекст — зафиксированный снимок подтверждённых данных. Будущий менеджер сохраняет его при регистрации и не перечитывает изменённый черновик для повтора. Отдельные idempotencyKey, commandId/resultCommandId, номер попытки, owner/token/revision, адрес callback и результат операции в него не входят. sessionId/requestId не нужны для выполнения и возврата результата, поскольку обратного результата нет; связь с исходным ходом остаётся у агента по operationId. Если реальный контракт corr потребует дополнительные реквизиты, расширяется предметный DTO, а не универсальный Map произвольных значений.

По просьбе пользователя оставшиеся вопросы задаются последовательно, с объяснением и вариантами. Вопрос 3.1 закрыт последующим ответом ниже; ранее предложенные варианты внутренних retry менеджера не выбраны и больше не требуют решения в рамках агента. По вопросу 4 пользователь выбрал удаление старого пути с временной простой реализацией менеджера (§15); физически сохранённые данные БД этим выбором не удаляются автоматически. Следующим задано уточнение 4.1 о порядке corr относительно commit и ответа GA.

## 14 Единственный вызов менеджера и полная передача ему исполнения

**Прямой ответ пользователя по 3.1:** все операции внутри WorkflowManager управляются самим менеджером, включая УСС. Последующее уточнение: никаких повторов со стороны агента; менеджер вызывается в Action один раз.

Следствия для согласованного направления:

- На одно выполнение синхронного transition Action приходится один `callOperation(operation, context)`. Агент не оборачивает его в retry и не повторяет вызов по таймеру или при неизвестном внешнем исходе.
- Агент не исполняет corr напрямую, не подбирает внешние задания собственным планировщиком, не регистрирует инциденты УСС и не управляет физическими corr-попытками. Всё это относится к отложенной реализации WorkflowManager.
- Менеджер не возвращает агенту результат исполнения; callbacks бизнес-результата, ожидание исхода в FSM и отправка отдельного итогового сообщения для этих операций не нужны.
- Наличие и политика внутренних повторов, устройство outbox и взаимодействие с УСС не выбираются сейчас. Прежние подробные схемы этих механизмов являются контекстом обсуждения, а не задачами реализации агента.
- Один вызов на выполнение Action не заменяет входную идемпотентность при повторной доставке HTTP-команды. Постоянный operationId остаётся идентичностью внешнего намерения; контракт входной библиотеки рассматривается отдельно.

Для полноценного менеджера сохраняется выбранный приоритет: сначала успешная отдача ответа ГигаАссистенту, затем необратимое внешнее исполнение. Техническую связь этого условия с транзакционной регистрацией callOperation ещё предстоит определить при интеграции менеджера; добавлять агенту собственный механизм повторов для этого не требуется. Последующим ответом 4.1 (§15) пользователь разрешил исключение для временного прямого менеджера.

Статус: только фиксация решений; реализация, включая менеджер, не начата.

## 15 Удаление старого пути и временный WorkflowManager

**Прямой ответ пользователя по вопросу 4:** старый путь удаляем, но планируем временную реализацию WorkflowManager. Она выбирает нужный метод corr по типу Operation, преобразует OperationContext в DTO corr и вызывает FeignClient. Повторы не выполняются. Пользователь также указал «без таймаутов»; трактовка транспортных настроек отделена ниже от отсутствия дополнительных таймеров в менеджере.

Это заменяет прежнее ограничение «сейчас только интерфейс без реализации» именно в части будущего плана реализации. **Сейчас продолжается фиксация решений, код не меняется.** Полноценный Transactional Outbox, восстановление через УСС и таймеры регистрации/исполнения всё ещё отложены. Временная реализация не выдаётся за реализацию гарантий outbox/УСС.

Планируемая ответственность временного менеджера:

1. Один вызов из синхронного transition Action; возвращаемый тип void, обратного бизнес-результата в FSM нет.
2. Выбрать операцию corr: статус, отзыв или уточнение; использовать типизированный mapping OperationContext → generated corr DTO согласно ADR-004.
3. Один вызов соответствующего метода Feign-клиента. Никаких retry менеджера, дополнительных локальных циклов, планировщиков и обращений к УСС.
4. Удалить заменённые прямую маршрутизацию corr из оркестратора, CorrSubmissionService, локальные retry и невостребованные обработчики/DTO результатов. Нужные generated-клиент, внешний контракт и mapping переиспользовать, а не удалить вместе со старым сценарием.

**Уточнение 4.1 закрыто прямым ответом пользователя:** «Временно допускаем прямой corr до commit и ответа GA ради простой реализации». Для временного менеджера принят порядок: начало общей JPA-транзакции → синхронный transition Action → WorkflowManager → один Feign-вызов corr → сохранение FSM и commit → ответ GA. Это временное исключение из приоритета «сначала ответ GA, затем необратимый corr», а не изменение целевого порядка полноценного менеджера.

Принятый риск: corr может выполнить необратимое действие, после чего локальная транзакция откатится либо ответ не будет передан GA. Откат БД не отменяет действие corr; временная реализация не добавляет автоматические повторы или восстановление через УСС. Транзакция и её блокировки удерживаются во время сетевого вызова. Код по-прежнему не меняется: фиксируется решение для последующей реализации.

Следующие технические уточнения, которые не должны скрываться реализационными допущениями:

- Вопрос 4.2 закрыт: сохраняем действующие транспортные connect/read timeout Feign (сейчас по 2000 мс). Временный WorkflowManager не добавляет свои таймеры, deadline или повторы. Указание «без таймаутов» относится к отсутствию дополнительных ограничителей в менеджере, а не к отключению транспортных настроек.
- Вопрос объёма закрыт §19: временный менеджер реализует только STATUS через существующий submitStatus. Контракты recall/details отложены; нельзя направить другие операции в submitStatus.
- Вопрос 4.3 закрыт: пользователь выбрал откат и распространил правило на любую ошибку Action, без привязки к corr. Полное правило приведено в §16; O7 закрыт.

## 16 Любая ошибка Action откатывает общую транзакцию

**Прямой ответ пользователя по 4.3:** «ответ 1 без привязки к вызову corr, любая ошибка в экшне откатывает транзакцию».

Любая ошибка синхронного transition Action, включая ошибки прикладной логики, доступа к БД, mapping и WorkflowManager, прерывает обработку и откатывает общую JPA-транзакцию. Откатываются все её изменения, в том числе native-состояние FSM и прикладные записи. Ошибку нельзя поглощать в Action, менеджере или обработчике ошибок SSM с продолжением успешного commit. При реализации необходимо обеспечить доведение ошибки до транзакционной границы и откат независимо от типа исключения; одной записи ошибки в лог недостаточно. Состояние экземпляра SSM после неуспешной обработки не должно использоваться как зафиксированное состояние сессии.

Ответ об ошибке формируется за пределами откатившейся транзакции; положительный ответ не возвращается. Для неизвестного внешнего исхода допустима формулировка «Не удалось подтвердить выполнение операции», без утверждения, что corr ничего не сделал. Автоматических повторов нет. Откат БД не отменяет уже выполненный внешний эффект — временное исключение 4.1 сохраняется.

Это правило ошибок исполнения Action; штатный отказ guard в переходе сам по себе не считается исключением Action. При будущей реализации нужна проверка отката прикладной записи и native FSM при ошибке Action. Сейчас изменяется только документация.

Вопрос 5 (O5/K01) закрыт последующим ответом в §17.

## 17 Идемпотентность только на входе

**Ответ пользователя по вопросу 5: вариант 1.** Оставляем идемпотентность на входной обработке; внутренние `@Idempotent` initialize/apply и ненужные ключи удаляем.

В план удаления входят внутренние аннотации, дополнительные String-аргументы ключей, передача commandId.toString() фасадом и тесты исключительно этих контрактов. Универсальный commandId, его генерация, поля и проверки также удаляются там, где после отказа от FSM-журнала и старого corr-пути не осталось потребителей. Новую внутреннюю дедупликацию или журнал вместо удалённых не вводим.

Входная граница с `@Idempotent` и ключом `sessionId:requestId` сохраняется. Библиотека ещё не подключена, поэтому текущая аннотация сама по себе не предотвращает повторы. OperationId внешней операции не удаляется и не заменяется техническим ключом внутреннего вызова FSM. Решение не отменяет блокировку сессии, бизнес-проверки согласия и принадлежности данных; их назначение отличается от дедупликации.

## 18 Семафор сессии и создание FSM после сбоя

**Принято пользователем:** вариант 1 вопроса 6.1, с отдельной таблицей семафоров. Для одного сессионного идентификатора существует одна запись с уникальным ключом. Запись является общей точкой блокировки для единоличной работы со стейтмашиной. Если семафор создан, а создание FSM завершилось сбоем, следующий запрос захватывает существующий семафор, создаёт отсутствующую FSM и выполняет действие. Если FSM уже сохранена, запрос восстанавливает её и выполняет действие.

Порядок работы:

1. Обеспечить наличие семафора по ключу сессии отдельной короткой транзакцией/autocommit. Для PostgreSQL подходит `INSERT ... ON CONFLICT (session_id) DO NOTHING`: уникальность исключает вторую строку, существующая строка переиспользуется. Это ещё не захват права выполнения. Ключ одинаков для всех операций одной сессии, а не отдельный для каждого requestId или типа операции.
2. Начать рабочую JPA-транзакцию и взять этот семафор через `SELECT ... FOR UPDATE NOWAIT`. При занятой строке вернуть SESSION_BUSY без выполнения Action и без очереди. Блокировка не переносится из autocommit: она приобретается именно внутри рабочей транзакции.
3. Только после захвата прочитать сохранённую FSM. Если native-запись отсутствует — создать новую машину; если существует — восстановить её. Ошибка чтения или десериализации существующего состояния не означает его отсутствия и не разрешает сброс машины.
4. Обработать событие через guards/actions; сохранить native FSM и прикладные изменения в той же рабочей транзакции. Временный WorkflowManager вызывается согласно §15. Любая ошибка Action откатывает рабочую транзакцию согласно §16.
5. При commit/rollback блокировка освобождается. Строку семафора не удалять при завершении хода: она остаётся для последующих запросов. Никакого отдельного флага занятости, ручного снятия владения или восстановления owner после сбоя не требуется для этого протокола.

Если первая рабочая транзакция откатилась, созданной FSM в БД нет, но отдельно закоммиченный семафор остаётся. Следующий запрос проходит тот же алгоритм без специальной команды восстановления. Если FSM уже существовала, после rollback следующий запрос видит её последнее закоммиченное состояние. Это обработка следующего входящего запроса, а не автоматический retry Action или WorkflowManager. Входная библиотека идемпотентности не должна выдавать неуспешную инициализацию за успешно выполненный запрос.

Создание семафора обозначает регистрацию сессии для работы с FSM; оно не доказывает успешную инициализацию FSM и не даёт создателю строки приоритета перед другими запросами. Исключительное право возникает при захвате блокировки. При первой конкурентной вставке возможен короткий конфликт на уникальном индексе; NOWAIT относится к последующему захвату существующего семафора, а не автоматически ко всем SQL-операциям.

В план удаления входят общий node lock, прежние owner/bootGeneration/executionToken и регистрация/восстановление исполнителя без оставшихся потребителей, предварительный load вне общей рабочей транзакции и технические проверки expectedRevision, необходимые только из-за раздельных load/apply. Защита подтверждённых бизнес-данных и проверка formatId сохраняются. Все пути изменения одной FSM обязаны использовать этот же семафор; его связь с ещё не созданной FSM не должна требовать наличия native-записи заранее.

При реализации проверить сохранность семафора после сбоя первой инициализации и успешное создание FSM следующим запросом, восстановление уже существующей FSM и исключение одновременных Actions одной сессии. Код и схема БД сейчас не меняются. Основания SQL-семантики: [блокировки PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS), [INSERT ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html).

## 20 Предметный результат Action и подготовка ответа общим оркестратором

**Прямое уточнение пользователя:** Action готовит только результат своей работы и не знает про ГигаАссистента, способ взаимодействия с ним или содержание ответа. Подготовка ответа, поиск и применение шаблонов выполняются вне FSM/Actions. Общий оркестратор связывает вызовы входящих API с инфраструктурой исполнения, получает результаты и формулирует ответ внешним системам.

Это исправляет ошибочное предложение ассистента перенести тексты из SessionTransitionPolicy в Actions. Бизнес-логика переносится в guards/actions, а тексты и форматирование — в оркестрацию.

- FSM/Action возвращает предметный исход, типизированные данные и состояние сценария. Здесь нет готового текста, templateId, HTTP, ACL, performative или final_message.
- SessionTurnOrchestrator вызывает инфраструктуру исполнения, получает её результат, выбирает нужный шаблон и заполняет его данными возвращённого снимка. Для текущего POC достаточно локальных шаблонов и обычного форматирования; новый универсальный framework, БД шаблонов или LLM не требуются.
- Входной адаптер преобразует подготовленный ответ в контракт своего канала. Для GA AclInputAdapter/AclMapper задают wire-поля и транспортные коды; controller возвращает HTTP-ответ. Оркестратор не импортирует generated ACL DTO и не становится новым controller.
- В ExtendedState сохраняются предметная подготовка, её идентичность, согласие и последний предметный результат. Готовый текст и выбранный шаблон туда не переносятся. Сводка строится вне FSM по снимку именно той подготовки, к которой относится подтверждение; форматирование не перечитывает изменившийся черновик и не выполняет второй переход.
- План TO BE размещает поиск/применение шаблона после завершения рабочей транзакции. Ошибка Action сначала откатывает транзакцию, затем оркестратор готовит ответ об ошибке. Сбой форматирования после commit не отменяет уже зафиксированную операцию и не запускает FSM/WorkflowManager повторно.

Обновлены [архитектура и sequence в плане](architecture_refactoring_plan.md#28-предметный-результат--оркестратор-и-шаблоны--внешний-ответ), шаги переноса бизнес-логики, подготовки ответа и удаления устаревшего кода. По последующему поручению пользователя переработка всех ADR выполнена с учётом этого уточнения. Код, тесты и БД не менялись.

## 22 Стандартная генерация и настройки приложения, 05.10.2026

По указанию пользователя собственные Mustache-шаблоны удалены. Для документации достаточно стандартных summary/description OpenAPI; API и DTO генерируются штатным OpenAPI Generator. Обычный @FeignClient наследует generated-контракт без ручного дублирования HTTP-методов.

Основные переменные приложения задаются в application.yaml и профильных YAML: имя и URL corr, тайм-ауты, режим/сценарий заглушки, код ACL-агента, HTTP-порт/адрес, каталог ответов и формат даты, параметры БД. Java не дублирует значения по умолчанию этих настроек. Ключи контрактов и сериализации, formatId и бизнес-события не являются параметрами окружения.

При переопределении имени corr индивидуальные настройки Feign используют новое имя; запрет повторов и проверка положительных тайм-аутов сохраняются. Правила ADR-001/004/011 и документация генерации приведены к этому решению. Результат проверки фиксируется в истории этапа.
