Бизнес-правила, не затронутые этими заменами, продолжают действовать.

## 1. Назначение, источники и объём

Агент помогает пользователю СберБизнес подготовить и подтвердить запрос по конкретному платёжному документу: запрос статуса (`status`), запрос отзыва (`recall`) или уточнение реквизитов (`details`). Агент также отвечает на предметные вопросы по согласованной базе знаний.

Результат успешного операционного сценария — подтверждённое принятие запроса модулем Invest corr. Это не означает исполнения отзыва, изменения реквизитов или получения окончательного ответа банка.

Документ объединяет обе исторические детализации из `matrix.md` и последующие решения заказчика; исходный файл удалён из текущего дерева. Вопросы, варианты и ответы сохранены в разделе 14 настоящего документа. При расхождении с историческими детализациями действуют требования настоящего документа. Технические решения определяются [индексом ADR](../../../adr/README.md); этот документ задаёт поведение, а не структуру реализации.

Источники интеграционных уточнений:

- [YAML-контракт](../../../api/rest_api_acl_gigaasistant.02.013.02.yml) — существующая основа внешних DTO; имя файла содержит `02.013.02`, `info.version` — `01.013.02`. Это не номер версии ACL в сообщении.
- [Описание ACL 1.6](../../../api/api_contract_details_1.6.md), редакция от 04.09.2026 — текущая семантика протокола.
- [Реестр кодов](../../../api/error_codes.md), редакция от 01.09.2026 — назначение HTTP-статусов и кодов тела, с учётом указанной версии появления кода.
- [Сущности GigaАссистента](../../../api/giga_assistant_entities.md), редакция от 06.04.2026 — ограничения поверхностей, сценариев, саджестов и переходов.
- [Прежнее описание 1.5](../../../api/api_contract_details_1.5.md), редакция от 22.07.2026 — дополнительные правила поверхности, не заменённые однозначным новым описанием.

По указанию заказчика документально разрешённые вопросы закрыты без повторного согласования (§14.9). Целевой профиль — ACL 1.6; его обязательные поля и семантику нельзя ограничивать неполнотой существующего YAML. Противоречивые примеры не становятся правилами: ограничения совместимости перечислены в §13. Выбор поведения, которого нет в источниках, остаётся в §15. Принятые ADR продолжают действовать.

В объём входят API нашего агента, создание/восстановление сессии, три операции, проверка полномочий, внутренняя ФЛК, подтверждение, отмена подготовки, смена операции, справочные ответы, ошибки, повторы, защита от дублей и сообщение ГигаАссистенту о завершении.

За границами находятся разработка окна чата и агента по платежам, реализация платформенного переключения агентов, банковское исполнение запросов, обработка окончательного ответа банка и отправка СМС самим агентом. Приём адресованного нам `proxy` входит в API агента; сам перевод выполняет поверхность. Напоминания и автоматическое завершение по бездействию не требуются. Точные схемы внешних API оформляются отдельно; незаполненные интеграционные условия нельзя считать согласованными контрактами.

| Агент по переписке — invest-pro | Создаёт/загружает свою сессию, определяет событие, применяет правила FSM, проверяет подготовку, получает подтверждение, обращается в Invest corr, возвращает ответ и доступные действия. |
| Модуль полномочий | Возвращает разрешение, бизнес-отказ либо техническую ошибку проверки пользователя/клиента и платежа. |
| Invest corr | Принимает подтверждённые запросы, предоставляет признаки результата и согласованные гарантии идемпотентности. |
| База знаний | Предоставляет согласованные сведения для предметных ответов. Владелец, материалы и актуализация определяются отдельно. |

## 3. Термины и жизненные циклы

| Термин | Определение |
|---|---|
| Зацепка | Управляющий элемент на интерфейсе платёжного документа в приложении СберБизнес. |
| Suggest | Подсказка после ответа агента; может содержать текст или ссылку на действие. Выбор status/recall/details в нашем профиле через suggestions не показывается. |
| Действие GA | Зарегистрированное пользовательское намерение/задача. Наши status/recall/details — три сценарных действия с выбором, подготовкой и отдельным подтверждением. |
| UI-операция GA | Контекстный элемент у конкретного сообщения о документе, запускающий зарегистрированное действие. Для такого отображения предусмотрены message.type и параметры state с type=OPERATION; каталог нашего отображения — §10.4. |
| Внешняя сессия | Диалог клиента в ГигаАссистенте; его интерфейс и история принадлежат внешней системе. |
| Агентский сценарий GA | Удержание диалога на вызванном агенте для многошагового действия. Его завершение не означает закрытия всего внешнего диалога. |
| Сессия нашего агента | Обработка сообщений с одной доверенной привязкой к пользователю и платежу; создаётся при первом API-запросе, если сохранённого состояния ещё нет. |
| Операция / подготовка | Одна попытка подготовить и подтвердить запрос выбранного типа внутри сессии. До успешной отправки сессия может содержать отменённые или неудачные подготовки. |
| Служебный контекст | Исходный платёж, `epkId`, дополнительные данные идентификации, при необходимости организация и маршрутизация. |
| Черновик | Новые значения реквизитов, введённые для текущей подготовки. Они не подменяют исходные данные платежа. |
| Сводка | Тип запроса, данные платежа и необходимые сведения об организации; для уточнения — все передаваемые поля и новые значения. |
| Отмена подготовки | Отказ от ещё не отправленного запроса со сбросом рабочих данных. Не является банковским запросом отзыва платежа. |
| ФЛК | Форматно-логический контроль передаваемых изменений внутри агента. |
| Автоматический повтор | Повтор технического действия в обработке одного сообщения; не является новым выбором пользователя. |
| Пользовательский повтор | После достоверного отказа Invest corr пользователь соглашается заново подготовить операцию. Перед отправкой требуется новое подтверждение сводки. |

Отмена подготовки возвращает к выбору или начинает явно выбранную другую операцию. Она не завершает нашу сессию; для продолжения передаётся `metadata.final_message=false`. Успешное принятие Invest corr сразу завершает нашу сессию в терминальном `COMPLETED`; обычный ответ содержит `metadata.final_message=true`, без отдельного сообщения или вызова. Флаг завершает сценарий вызванного агента: дальнейших вызовов в рамках этой агентской сессии не ожидается, но закрытие всего чата не требуется. Это разрешённая по 1.6 часть Q-12/ACL-06. Доставка потерянного ответа и идентичность следующего сценария остаются внешними условиями Q-08.

## 4. Вход в сценарий и обработка API-запроса

1. Пользователь открывает платёжный документ, нажимает зацепку; ГигаАссистент открывает чат, начальный диалог ведёт агент по платежам.
2. Пользователь выбирает статус, отзыв или уточнение. Выбранный тип и служебный контекст передаются нашему агенту API-запросом через согласованный маршрут.
3. До первого запроса у нашего агента нет экземпляра сессии и её состояния ожидания. Запрос принимается через доверенный шлюз; по `Gigachat-Session-Id` проверяется наличие сохранённой сессии. Для новой сессии нужен полный исходный контекст, для существующей используется сохранённый контекст по §4.1.
4. Если сессии нет, она создаётся с начальным состоянием FSM `CHOOSING_REQUEST_TYPE`. Если сессия есть, её состояние и контекст загружаются. Загрузка сама по себе не повторяет внешние вызовы.
5. Из поступившего сообщения с учётом состояния вычисляется управляющее событие, применяется к FSM; необходимые проверки и вызовы выполняются синхронно. Ответ возвращается ГигаАссистенту.

Начальное состояние существует с момента создания FSM. Оно не означает обязательного отдельного экрана выбора: событие из первого сообщения сразу применяется к нему. При корректно переданном выбранном типе повторно спрашивать этот тип не требуется.

| Данные входа | Требование |
|---|---|
| Идентификатор сессии и маршрутизация | `Gigachat-Session-Id` находит состояние нашей сессии; поля маршрутизации и `conversation_id` используются адаптером для ответа. |
| Выбранный тип при передаче управления | `status`, `recall` или `details`; определяется служебным действием, а не только подписью кнопки. |
| Исходный платёж | При создании сессии передаётся отдельными парами в `metadata.additional_info`; минимальный состав первого прототипа задан в §4.2. Достаточность для реальных полномочий и отправки — Q-09/Q-10. |
| `epkId`, дополнительные данные идентификации | При создании сессии берутся из доверенного контекста шлюза; `epkId` — организация, `digitalUserId` — пользователь. |
| Организация | Передаётся/определяется по доверенному контексту, если нужна для сводки и запроса. |
| Идентификатор сообщения/вызова | `Request-Id` сохраняется при повторной доставке; новое сообщение получает новый ID. |
| Последующие сообщения | `Gigachat-Session-Id`, `Request-Id` и входное действие по §4.1. Повторная передача пользователя, организации и исходного платежа не обязательна. |

Отсутствующий или противоречивый обязательный контекст вызывает контролируемую ошибку без запуска операции и вызова Invest corr. Пользователь, платёж и организация не угадываются из произвольного текста. Создание новой сессии не отменяет проверку доверенности контекста.

Ответ содержит текст и служебные данные, а при выборе status/recall/details — карточку действий (§6.3/§10.4). Сводка передаётся платформенным механизмом подтверждения. Для inform/failure явно заполняется metadata.final_message: false для продолжения, true для завершения агентского сценария. Успех отдельного хода не означает завершения; справочный ответ в активной подготовке сохраняет false. Совместимость false со специальной обработкой ошибок GA остаётся в Q-17.

В одной сессии одновременно выполняется не более одного пользовательского хода. По [ADR-010](../../../adr/0010-session-execution.md) новый вход в занятую сессию отклоняется: HTTP 400, `message.performative=failure`, `message.content.reason="Сессия занята"`. Скрытая очередь пользовательских сообщений не вводится. Отмена не прерывает выполняющуюся проверку/отправку. Сообщение, поступившее после освобождения сессии, оценивается по достигнутому состоянию. Независимые сессии могут обрабатываться параллельно без смешивания данных.

Новое сообщение в завершённую сессию отклоняется: HTTP 400, `message.performative=failure`, `message.content.reason="Обращение к завершённой сессии"`; отображение ошибки — ответственность ГигаАссистента. Завершённая сессия не переоткрывается. Повторная доставка уже обработанного сообщения рассматривается механизмом идемпотентности и не запускает новую операцию.

### 4.1. Профиль ACL для первого этапа

Основа — ACL 1.6 и [существующая YAML-схема](../../../api/rest_api_acl_gigaasistant.02.013.02.yml) с отмеченными в §13 расхождениями. Ниже задан профиль нашего агента; его внешние условия проверяются у владельца канала, а не объявляются гарантированными по локальному решению.

Для первого этапа используется плоский входной `TurnInDTO` с простым переносом данных через MapStruct по ADR-004:

| Поле входа | Источник |
|---|---|
| `sessionId` | Заголовок `Gigachat-Session-Id`, UUID → строка |
| `requestId` | Заголовок `Request-Id`, UUID → строка |
| `epkId` | `metadata.organization.epk_id` |
| `digitalUserId` | `metadata.customer_info.digital_user_id` |
| `performative` | `message.performative` |
| `actionCode` | `message.content.action_code` |
| `text` | `message.content.user_input` |
| `additionalInfo` | `metadata.additional_info`, список внутренних DTO пар ключ–значение |
| `redirect` | `metadata.redirect`, внутренний DTO маршрута для входного `proxy` |
| `availableActions` | `metadata.available_actions`, сообщённые поверхностью доступные действия; привязка к отображению UI-операций подтверждается по Q-08 |

Маршрутизация ответа, поверхность и поля отображения обрабатываются API-адаптером; переносить весь ACL в бизнес-контекст не требуется. По решению заказчика текст первого этапа берётся только из `message.content.user_input`. История `phrases` и `operator_input` не используются как запасной источник текста и не передаются в LLM для восстановления текущей команды.

Оба заголовка ID обязательны для нашего профиля. `sessionId` постоянен в течение сценария по одному платежу; новый сценарий после завершения требует нового ID. `message.conversation_id` не подменяет `sessionId`; адаптер использует его для корреляции ответа. Для пары `(sessionId, requestId)` повтор того же содержимого возвращает сохранённый результат без нового эффекта, другое содержимое с тем же ID вызывает ошибку. Конкурентный вход подчиняется ADR-010. Это дедупликация входного запроса, отдельная от журнала команд FSM по ADR-009.

Для всех поддерживаемых входных перформативов `message.reply_with` — обязательный UUID, равный `Request-Id`; `message.conversation_id` — обязательный UUID внешнего диалога. Ответный `in_reply_to` равен входному `reply_with`. Отсутствие, неверный формат или несовпадение ID не разрешают бизнес-переход: идентификатор не придумывается и не заменяется на `trigger_phrase_id`. Конкретный ответ на повреждённую структуру сообщения относится к транспортной обработке ошибок Q-17. Нормальная корреляция Q-14 закрыта по таблицам заголовков, запроса и ответа 1.6.

Шлюз отвечает за аутентификацию пользователя и корректность исходной идентификации. Агент выполняет бизнес-проверку полномочий по §6.1. Для существующей сессии данные пользователя, организации и платежа берутся из сохранённого контекста; их отсутствие во входе не является ошибкой. Если исходные параметры повторно переданы, они сверяются с сохранёнными: расхождение вызывает ошибку, контекст не перезаписывается. История `content.phrases` не нужна для восстановления состояния и подготовки запроса во внешнюю систему; используются FSM и собственный контекст.

Источник действия выбирается строго по приоритету: `performative` → `action_code` → пользовательский текст. При выбранном старшем источнике младшие не анализируются, в том числе не передаются в LLM для определения действия или изменений. `performative=request` обозначает обычный вход: он разбирается по `action_code`, а при его отсутствии или значении `COMMON` — по тексту. Для `proxy` отдельно проверяются маршрут и выбранное действие по правилу ниже. `COMMON` обозначает обычное текстовое сообщение, а не самостоятельную операцию. `accept_propose` и `reject_propose` определяют подтверждение/отказ с учётом текущего шага; нижние поля игнорируются. Недопустимое для текущего состояния действие не разрешает отправку.

Поддерживаются входные `performative=request`, `accept_propose`, `reject_propose`, `proxy`. По описанию 1.6 первый агент возвращает HTTP 200, код тела `200`, `proxy` и `metadata.redirect`; поверхность вызывает целевого агента также с `proxy`, новым `reply_with` и прежним `conversation_id`. Собственный ID сессии из этого правила не выводится. Входные `inform` и `failure` остаются неподдерживаемыми и вызывают контролируемую ошибку без бизнес-перехода; их приём для текущего сценария источниками не требуется. Ограничение относится к входу: `failure` в ответе поддерживается.

Для входного `proxy` обязательны объект `redirect`, его `source_agent` и `target_agent`; адресат должен соответствовать нашему агенту и маршруту вызова. `target_action` задаёт выбранное действие; если оно одновременно передано в `content.action_code`, значения должны согласовываться, иначе вход отклоняется. Если `target_action` отсутствует, выбранный тип должен быть явно передан в `action_code` согласно нашему профилю передачи. Неизвестный код не угадывается. После проверки маршрута действие применяется к FSM так же, как явно выбранное действие из `request`; сам `proxy` не подтверждает отправку. Платёж пока передаётся отдельными парами `additional_info` по §4.2. Конкретные коды и размещение данных при реальном редиректе относятся к Q-08/Q-09. Прежний запрет `proxy` заменён этим правилом; вопрос о направлении передачи Q-13 закрыт.

Все последующие правила о намерении, вопросах, отказе и изменениях применяются к выбранному источнику. Например, текст «Да, но измените назначение» вызывает новую сводку, только если выбран текстовый источник. При `performative=accept_propose` этот текст игнорируется и обрабатывается подтверждение текущей сводки при выполнении условий FSM.

Общий протокол 1.6 допускает `user_input` или `phrases`, но наш профиль первого этапа намеренно уже: если по приоритету источников выбран текст, нужен непустой `user_input`; при его отсутствии возвращается контролируемая ошибка без бизнес-перехода и вызова LLM. Наличие `phrases` не исправляет такой вход. Для управляющего перформатива/явного кода, не требующего текстового разбора, `user_input` не становится обязательным. Вызывающая сторона должна нормализовать новый текст в это поле; условие подключения перенесено в Q-08. ACL-02/Q-15 закрыт для первого этапа; внешний смысл `action_code` на последующих ходах остаётся в Q-16.

### 4.2. Минимальный исходный контекст платежа

При создании сессии первого прототипа обязательны следующие пары в `metadata.additional_info`. Имена ключей фиксируются для нашего профиля; их соответствие реальному внешнему источнику уточняется по Q-09. По ACL-схеме `value` передаётся строкой.

| Ключ | Содержание |
|---|---|
| `paymentId` | Идентификатор исходного платежа |
| `paymentNumber` | Номер платежа |
| `paymentDate` | Дата платежа |
| `amount` | Сумма платежа |
| `currency` | Валюта платежа |
| `recipientName` | Наименование получателя |
| `organizationName` | Наименование организации |

Остальные исходные реквизиты для первого прототипа необязательны. Этот набор позволяет сформировать содержательную сводку; его достаточность для реального Invest corr не утверждается до согласования Q-10. Форматы значений уточняются по Q-09. Данные сохраняются в контексте сессии, повторная передача в следующих сообщениях не требуется. Исходный `recipientName` не подменяется новым наименованием из черновика уточнения.

### 4.3. Правила ACL 1.6 и поверхности

Правила ниже задают целевой профиль; необходимые уточнения существующего YAML перечислены в §13:

- Добавление неизвестных JSON-полей не должно ломать приём запроса или менять бизнес-поведение. По 1.6 обязательность и значения enum проверяет AI Proxy; отдельную дублирующую реализацию полной валидации протокола у агента не требуется создавать. Десериализация, обработка повреждённого входа и проверки нашего прикладного профиля остаются на границе/в сервисах по ADR-004. Неподдерживаемый перформатив не становится допустимым действием; полномочия, binding платежа и FSM проверяет агент.
- Целевая `message.version` запроса и ответа — `"1.6"`. В ответе `message.sender` берётся из входного `message.receiver`, `message.receiver` — из входного `message.sender`; переданный `conversation_id` сохраняется, `in_reply_to` заполняется по §4.1. Примеры с `"1.0"`/`"1.5"` не используются как версия целевого профиля; его доступность на стенде проверяется по Q-08.
- У обычного успешного ответа: HTTP 200, `performative=inform`, текст в `message.content.result`, строковый `status_code="200"`. У ответа `failure` причина передаётся в `message.content.reason`. HTTP-статус и `content.status_code` — разные поля. Известные сочетания определены в §8.6; продолжение после ошибок и шаблонное подтверждение требуют Q-17/Q-18. Успех API-ответа не означает принятия запроса Invest corr.
- `suggestions.text` — обязательная подпись, `action_code` — действие по нажатию; у текстового suggest код можно не передавать, а `agent_code` для действия того же агента не требуется. Агент возвращает только действия, допустимые в FSM, по бизнес-полномочиям и в переданном `metadata.available_actions`; ни один список не заменяет остальные проверки. Поверхность может удалить саджест с недоступным кодом. Словарь, а также поведение при отсутствующем списке остаются внешним условием Q-08; отсутствие списка не доказывает доступность всех действий.
- Лимиты саджестов применяются только там, где они предусмотрены отдельно (например, «Да/Нет» по §8.3), и не задают представление трёх операций. После сообщения — не более трёх саджестов: CLASSIC до 75 символов, BUTTON до двух слов; режимы не смешиваются. YAML допускает до 300 символов, но профиль отображения строже; коды агента/действия в YAML — до 100 символов.
- В пользовательском ответе не использовать обычные Markdown-ссылки. Если переходы нужны, их заранее регистрируют на странице присутствия, используют только коды из `metadata.available_transitions`, вставляют в текст блок `transition-code`, а в `message.transitions` передают использованные коды и параметры. Для внешнего перехода ссылка должна быть разрешена платформой; обычный переход и переход-источник регистрируются отдельно. Конкретные переходы в MVP автоматически не добавляются.
- Штатные идентификаторы берутся из `metadata.organization` и `metadata.customer_info`; в `additional_info` передаются дополнительные параметры действия, включая согласованные ключи платежа. Значения `additional_info.value` остаются строками. Наличие в описании токенов и дополнительных идентификаторов не делает их обязательными для `TurnInDTO` или достаточными для реального сервиса полномочий.
- Внешний `state` не заменяет сохранённую FSM и не восстанавливает отменённую подготовку. `REDIRECTION` предназначен для параметров перевода, `CONFIRMATION` — для значений шаблона подтверждения, `OPERATION` — для отображения UI-операций. Точный payload платежа/подтверждения остаётся в Q-09/Q-18. Обязательный обмен памятью `MEMORY` не добавляется; если он понадобится, допускается только один элемент этого типа с `key=MEMORY` и строковым `value`.

Основание: таблицы заголовков, запроса и ответа 1.6; реестр кодов; разделы «Сценарное действие», «Саджесты» и «Переход» в сущностях GA. Эти правила не подтверждают сроки ответа, стабильность ID при повторе или отключение старых кнопок.

### 4.4. Поверхность, сценарий и дополнительные данные

Первый этап предназначен для авторизованного текстового чата СберБизнес: `communication_channel=TEXT`, `surface_mode=ASSISTANT`, поверхность чата `surface.code=ASSISTANT`; `surface.type` различает WEB/MOBILE. Встраивание в PRELOGIN не включено: там не передаются идентификаторы и сессионные параметры, а переходы не поддерживаются. GLOBAL_SEARCH также не входит в операционный сценарий: там не должны выводиться переходы и UI-операции. Отсутствие необязательного объекта `surface` само по себе не отменяет обработку корректного запроса доверенного маршрута нашего профиля.

Многошаговый сценарий удерживает пользователя на агенте до завершения или отмены сценария; автоматическая оркестрация на другого агента и генерация платформенных саджестов на это время приостанавливаются. По описанию в сценарном действии передаётся вся история этого действия, в COMMON/обычном активном действии — четыре сообщения. Это не задаёт способ выбора текущей реплики и не заменяет нашу БД. Сопоставление трёх операций и отмены подготовки с зарегистрированными сценарными действиями проверяется по Q-08; наши правила сохранения подготовки/переключения не меняются по догадке.

| Данные протокола | Использование и ограничение |
|---|---|
| `X-Authorization`, `channel_context.efs_session/efs_token/sbbol_csrf_token`, `customer_info.authorized/sfl_connection_number` | Возможные исходные данные для реального сервиса полномочий. Нужный состав и приоритет дубликатов идентификаторов/токенов — Q-09. Эти поля не создают бизнес-разрешение и не добавляются все сразу в доменный DTO. |
| `channel_context.retry_number`, `request_reason.type=SESSION` | Диагностические признаки повтора от поверхности и удержания агента. Не заменяют `Request-Id`, ID сессии или ключ банковской отправки. |
| `phrases.speaker_type=EXPERT` | Поддерживаемое в 1.6 обозначение реплики эксперта. При использовании истории она отделяется от `CUSTOMER` и не считается пользовательским согласием. |
| `suggestions.message_text/is_posted_to_chat`, `message.is_hidden` | Управляют отображением; показанный текст не считается доказательством входного управляющего действия. Сводка и итог операции должны быть видимыми (`is_hidden=false` либо поле отсутствует). Payload клика — Q-16. |

Требуются регистрация типов сообщения, привязка UI-операций к трём сценарным действиям и параметры карточки (§10.4). Эти элементы выбирают операцию, но не подтверждают банковскую отправку. |
| Ответный `metadata.product_contexts` | Необязательные продуктовые сведения для других агентов. `value` должен однозначно передавать структуру и значения; `description` — содержание, ограничения, особенности и актуальность. Не заменяет доверенный входной платёж или контракт Invest corr; обязательная выдача не вводится. |

События отчётности Сберборда формирует/проксирует AI Proxy из запросов и ответов. Раздел 1.6 об этих топиках сам по себе не требует отдельного Kafka-производителя в нашем агенте. При подключении также проверяется допустимый размер HTTP-заголовков: страница описывает случаи превышения стандартного лимита служебными заголовками; конкретная настройка относится к инфраструктуре Q-08, числовой лимит здесь не выдумывается.

## 5. Контекст, обязательность данных и сброс

Распознанные данные пользователя, выбранная операция, её статус и введённые изменения реквизитов хранятся в общем контексте FSM текущей сессии и доступны при переходах между состояниями. «Глобальный контекст» означает общий контекст одного экземпляра сессии, изолированный от других пользователей/сессий. Он сохраняется и восстанавливается вместе с состоянием; для восстановления не нужна присланная история чата. Частичное изменение обновляет только явно переданные поля и сохраняет остальные знания текущей подготовки. Правила явного сброса `RESET` ниже сохраняются.

| Данные | Когда нужны | Правило сохранения |
|---|---|---|
| Исходный платёж, `epkId`, идентификация, привязка к диалогу | Во всей созданной сессии | Не удаляются при отмене, смене, ошибке или завершении операции. |
| Ограничение «только статус» | Если получен бизнес-отказ полномочий | Сохраняется при возврате к выбору и новой подготовке; действует в текущей сессии по данному платежу. |
| Тип операции | С начала подготовки; также для предложения повторить отклонённый запрос | В `CHOOSING_REQUEST_TYPE` активный тип не задан; при сбросе очищается. |
| Идентификатор/версия подготовки | Для привязки событий, проверок и сводки | Новая подготовка не использует подтверждение прежней; устаревшие результаты не применяются. |
| Бизнес-результат проверки полномочий | При первой подготовке `recall`/`details`, требующей проверки | Разрешение или отказ сохраняются на всю сессию; отмена, смена типа и пользовательский повтор их не сбрасывают. Для `status` проверка не вызывается. |
| Изменённые реквизиты и результат ФЛК | Для текущего `details` | Сохраняются при вопросе/исправлении в этой подготовке; сбрасываются при её отмене, смене или запуске подготовки заново. |
| Сводка, её версия и подтверждение | Перед отправкой | Изменение данных аннулирует прежнее согласие. На первом этапе входное подтверждение относится к текущей сводке из контекста, без передаваемого ID сводки; старые кнопки — Q-11. |
| Ожидаемое уточнение | Если задан вопрос о намерении или данных вместо запроса согласия на отправку | Сохраняются предмет вопроса, связь с подготовкой/версией и ожидаемый смысл ответа. Ожидание восстанавливается без внешней истории, снимается при разрешении вопроса и очищается при отмене, смене или перезапуске подготовки. Пока уточнение не разрешено, CONFIRM не разрешает отправку. |
| Счётчики технических попыток | В пределах конкретной проверки/отправки | Не смешиваются между версиями данных и разными действиями. |
| Зафиксированные данные отправки и ключ идемпотентности | После подтверждения, до первого внешнего вызова | Для всех автоматических попыток одного запроса остаются неизменными. Не теряются при неизвестном исходе. |

Отдельное накопление `rejected_suggests` не требуется. Отменённый тип можно выбрать снова; видимость действий определяется текущими полномочиями, FSM и доступностью на поверхности, а не историей отказов агента.

`RESET` означает очистку рабочей подготовки: типа, пользовательских уточнений, результата ФЛК, сводки, подтверждения и ожидаемого уточняющего вопроса. Служебный контекст, бизнес-результат проверки полномочий и установленное ограничение доступа сохраняются. Сброс рабочих данных не означает удаления истории отправок, ключей и сведений о фактическом или неизвестном результате.

История внешнего чата не удаляется и не используется для автоматического восстановления отменённых уточнений. Технические сроки хранения после завершения сессии определяются отдельно.

## 6. Операционные правила

### 6.1. Три операции и полномочия

| Шаг | Статус | Отзыв | Уточнение |
|---|---|---|---|
| Тип | `status` | `recall` | `details` |
| Проверка полномочий сценария | Не вызывается | Обязателен сохранённый результат; при его отсутствии — проверка | То же, результат общий для сессии |
| Подготовка | Сводка запроса статуса | После разрешения — сводка отзыва | После разрешения — ввод изменений, внутренняя ФЛК, сводка |
| Подтверждение | Явное согласие с актуальной сводкой | То же | То же, со всеми передаваемыми изменениями |
| Результат отправки | Принят запрос статуса | Принят запрос отзыва, а не выполнен отзыв | Принят запрос уточнения, а не изменены банковские реквизиты |

`status` создаёт запрос в Invest corr; агент не обещает мгновенно узнать банковский статус из базы знаний. Отсутствие специальной проверки полномочий для статуса не отменяет проверку принадлежности доверенного контекста.

Бизнес-отказ в полномочиях на отзыв или уточнение делает недоступными обе операции. Остаются статус и справочные ответы. Ограничение нельзя обойти текстом, старой кнопкой, отменой или новой подготовкой. Техническая ошибка проверки не устанавливает это ограничение.

Проверка выполняется при первой подготовке отзыва или уточнения, если в сессии ещё нет бизнес-результата. Полученное разрешение или отказ используются во всех последующих подготовках этой сессии, в том числе после отмены, смены операции и достоверного отказа Invest corr. Техническая ошибка не является бизнес-результатом и не кешируется как разрешение/отказ; её повторы регулируются §8.1.

### 6.2. Ввод, сводка и согласие

Пользователь вводит новые реквизиты сообщением в чате; агент извлекает их, не додумывая значения. Допустимо непустое подмножество четырёх полей: ИНН получателя, счёт получателя, наименование получателя, назначение платежа. Неясный ввод вызывает уточняющий вопрос с сохранением шага.

Перед отправкой показывается сводка по платформенному шаблону GA с параметрами `state.type=CONFIRMATION`; выбран вариант ACL-03 А. Базовые проекты трёх шаблонов — §10.3. Первоначальный выбор действия, согласие на повтор подготовки, ответ на уточняющий вопрос и слово «да» внутри цитаты/вопроса не являются подтверждением отправки. Кнопки подтверждения/отказа принадлежат механизму подтверждения GA; их не подменяют саджестами выбора операции.

Отправка разрешена только при однозначном положительном подтверждении текущей сводки и выполнении условий подготовки. Для первого этапа подтверждение относится к сводке из контекста FSM; её ID во входном сообщении не требуется. Агент не отличает подтверждение старой кнопкой от новой, если они передают одинаковое действие; возможность нажатия старой кнопки и её отключение на поверхности остаются в Q-11.

Если выбранный по §4.1 текстовый источник одновременно содержит согласие и изменение подтверждаемых данных, агент изменяет подготавливаемый запрос, выполняет необходимые проверки, показывает новую сводку и снова запрашивает подтверждение. Это сообщение не запускает отправку. Если выбран старший источник (`accept_propose` или код подтверждения), нижестоящий текст с изменениями не анализируется.

### 6.3. Отмена и переключение

Явный отказ от подготовки/подтверждения — «нет», «передумал», «не отправляйте», «давайте другую операцию» — отменяет подготовку. Команда с буквальным текстом `CANCEL` не требуется. Если новый тип не указан, выполняется `RESET` и показываются доступные операции.

Если до отправки пользователь однозначно выбрал другую разрешённую операцию кнопкой или текстом, текущая подготовка сбрасывается, новая начинается сразу на сохранённом исходном контексте. Повторный выбор из меню не нужен; необходимые проверки и подтверждение выполняются для новой подготовки.

Повторный выбор текущего типа во время ввода/подтверждения без отказа или команды начать заново не создаёт дубликат: агент напоминает текущий шаг. После отмены этот тип остаётся доступным, но отменённые уточнения не восстанавливаются.

Явное «Начнём эту операцию заново» на вводе или подтверждении выполняет `RESET` и `START` того же разрешённого типа. Исходный контекст и бизнес-результат полномочий сохраняются, прежние изменения, сводка, согласие и ожидаемое уточнение очищаются. Для `details` начинается новый ввод, для `status`/разрешённого `recall` показывается новая сводка. Отправка по команде перезапуска не выполняется. Это не перезапуск уже отправленного запроса и не способ выйти из `SUBMIT_UNKNOWN`.

В `AWAITING_RETRY_CONFIRM` явный выбор любого разрешённого типа, включая текущий, начинает новую подготовку по S-07. Выбор запрещённого типа очищает рабочую подготовку и возвращает к выбору разрешённых операций по S-10; сохранённый запрет не снимается. Бизнес-правило отказа в доступе не зависит от того, была ли перед этим попытка corr.

Возврат к выбору показывает зарегистрированные действия «Запросить статус», «Запросить отзыв», «Уточнить реквизиты» у сообщения об исходном платеже; они не передаются через `suggestions`, в том числе с `display_mode=BUTTON`. Представление — UI-операции GA по `message.type` и `state.type=OPERATION` (§10.4). При ограничении «только статус» доступно только соответствующее действие. Выбор запускает подготовку, а отправка corr возможна лишь после отдельного подтверждения сводки.

Показанный набор учитывает FSM, бизнес-полномочия и фактическую доступность действий на поверхности. Пустой набор не снимает ограничения; отсутствие `available_actions` не означает разрешения всего. Документы прямо описывают этот список для саджестов, поэтому механизм доступности UI-операций и регистрация вариантов типов сообщения требуют подтверждения GA по Q-08. Нельзя изобретать поле actions или считать, что GA автоматически отфильтрует операции так же, как саджесты.

Отменённое разрешённое действие можно выбрать снова. Платформенные базовые/статичные саджесты не используются вместо меню; их нежелательное появление при пустом `suggestions` должно быть исключено настройками сценария/страницы присутствия по Q-08. Клик по старому меню оценивается по текущей FSM и полномочиям, не восстанавливает отменённые данные и не переоткрывает COMPLETED. Правило действий вместо саджестов относится к трём операциям; ранее согласованные «Да/Нет» на предложение подготовки заново остаются отдельным диалоговым управлением (§8.3).

### 6.4. Вопросы, неоднозначность, бездействие

Вопрос, который не меняет намерение и не отменяет операцию, обрабатывается по базе знаний с сохранением текущего шага и данных. Агент отвечает и напоминает допустимое ожидаемое действие. В `SUBMIT_UNKNOWN` сохраняется неизвестный исход; справка не разрешает продолжение подготовки, новую отправку или отмену до решения Q-05. Вопрос без активной операции не создаёт банковский запрос.

По [ADR-007](../../../adr/0007-llm-responsibilities.md) основной разбор совмещает определение намерения, извлечение данных и выявление справочного вопроса. На одно пользовательское сообщение допускается не более одного уникального промпта с параметрами; только для ответа RAG разрешён второй — по найденным материалам. Если справочный вопрос надёжно определён без LLM, основной разбор можно пропустить и использовать один вызов для ответа. Отдельный классификатор не обязателен; его возможное применение требует проверки на предметных примерах. Поиск подходящей статьи сам по себе не доказывает справочное намерение и не разрешает операцию.

Если подходящих сведений нет, агент сообщает об отсутствии достаточной информации и предлагает уточнить вопрос. При недоступности базы сообщает о техническом сбое. Он не придумывает банковские сроки, условия или статус конкретного платежа. Справочный ответ не заменяет полномочия, подтверждение и вызов Invest corr.

| Сообщение при выбранном текстовом источнике (§4.1) | Поведение |
|---|---|
| «Нет, передумал» | Отменить подготовку. |
| «Нет, лучше запросить статус» | Сбросить прежнюю подготовку и сразу подготовить статус. |
| «Какие реквизиты можно уточнить?» | Ответить по базе знаний, сохранить шаг. |
| «Да, но укажите договор Б» после сводки | Изменить данные, проверить, показать новую сводку и снова подтвердить. |
| «А если я скажу “нет”?» | Рассматривать как вопрос, а не как отказ. |
| «Да» на шаге ввода реквизитов | Уточнить ввод; отправка недопустима. |
| «Да» в ответ на уточняющий вопрос | Отнести к этому вопросу; не считать автоматически подтверждением запроса. |
| Несовместимые намерения или непонятные значения | Уточнить, сохранить незавершённую подготовку, не отправлять. Ясный отказ исключает отправку. |

При бездействии нет напоминаний, автоматического подтверждения, отмены или бизнес-таймера завершения. Закрытие браузера не является гарантированным серверным событием и не подтверждает/не отменяет запрос. Уже начатая обработка следует своим правилам. Технические тайм-ауты внешних вызовов остаются действующими.

Уточняющий вопрос о намерении/данных сохраняется как ожидание из §5. Следующий выбранный текст разбирается вместе с предметом этого ожидания в пределах того же единственного основного LLM-вызова. «Да» или «Нет» относятся к уточнению, а не автоматически к сводке или отмене. Однозначная самостоятельная команда отмены/смены применяется по своему правилу и очищает ожидание. При неясном ответе вопрос уточняется, данные сохраняются. При разрешении вопроса его результат применяется к подготовке/проверке; если данные готовы, сводка показывается заново и требуется отдельное согласие на последующем ходе. Ответ, разрешивший уточнение, не отправляет запрос в этом же ходе. Старший источник действия по §4.1 сохраняет приоритет, но не обходит проверку незавершённого уточнения.

Если один разбор однозначно определил `details` и новые реквизиты, например «Уточни назначение на оплату договора Б», эти данные не теряются при `START(details)`. Они связываются с новой подготовкой как ещё не проверенные; после успешных или сохранённых полномочий переход M-22 применяет их к ФЛК в том же ходе. Повторно просить уже однозначно введённые значения не нужно. При отказе/исчерпанной технической ошибке полномочий подготовка и эти данные очищаются; они не становятся исходными реквизитами платежа. Противоречивые значения требуют уточнения. Речь об одном действии с его данными; сочетание действия/изменения и отдельного справочного вопроса пока требует Q-19.

## 7. Реквизиты и внутренняя ФЛК

| Поле | Согласованное поведение | Необходимо согласовать по Q-06 |
|---|---|---|
| ИНН получателя | Проверяется, если передан; может быть единственным изменением | Допустимые значения, длина, символы, контрольные проверки, отсутствие ИНН. Пример «10 или 12 символов» не является полной утверждённой спецификацией. |
| Счёт получателя | Значение берётся из ввода без догадок; может изменяться отдельно | Виды счетов, формат, длина, символы и зависимые проверки. |
| Наименование получателя | Передаётся указанное новое значение | Длина, символы, пробелы, пустое значение. |
| Назначение платежа | Передаётся новый текст назначения | Длина, символы, обязательные элементы и ограничения целевой системы. |

Проверяются только передаваемые изменения; неизменяемые поля не становятся обязательными без согласованной зависимости. Отсутствующее поле означает «не изменять»; очистка поля не поддерживается автоматически до согласования. Несколько несовместимых значений одного поля требуют уточнения.

Ошибки сообщаются по соответствующим полям, при нескольких ошибках — списком. Ошибка счёта не объясняется сообщением об ИНН. Исправление в той же подготовке заменяет только явно переданные поля в контексте FSM; остальные ранее введённые значения сохраняются. Например, при исправлении только счёта ранее введённый ИНН остаётся в черновике. Непереданное поле не удаляется и не сбрасывается. Перед подтверждением проверяется актуальная версия всего объединённого набора передаваемых изменений.

На первом этапе исключение отдельного поля из черновика не поддерживается. На просьбу «ИНН оставим прежним, поменяйте только счёт» агент объясняет, что нужно отменить подготовку и заново ввести нужные изменения; до явной отмены текущий черновик и шаг сохраняются. Такая просьба сама по себе не удаляет поле, не вызывает `RESET` и не подтверждает отправку. Правило применяется к выбранному текстовому источнику по §4.1.

Ошибочные значения дают `FLK_INVALID`: пользователь исправляет ввод, автоматического технического повтора нет. Технический сбой выполнения проверки даёт `FLK_ERROR`: разрешён один автоматический повтор той же версии данных. ФЛК выполняется внутри агента, а не внешним банковским сервисом.

## 8. Ошибки, повторы и завершение

### 8.1. Проверки до отправки

При технической ошибке полномочий или внутренней ФЛК выполняются первоначальная попытка и один автоматический повтор. После второй неудачи агент сообщает об ошибке, очищает подготовку и возвращается в `CHOOSING_REQUEST_TYPE` с доступными операциями. Сессия остаётся активной; Invest corr не вызывается. Бизнес-отказ полномочий и ошибки пользовательских значений автоматически не повторяются.

### 8.2. Автоматические повторы Invest corr

Подтверждённые данные и ключ идемпотентности фиксируются до отправки. Все автоматические попытки одного запроса используют одинаковые значимые данные и тот же ключ. Количество попыток, интервалы и технические условия задаются системными настройками ретраев; бизнес-лимита «один повтор» для corr нет. Политика конечна: синхронный вызов должен вернуть результат или ошибку.

Повторная доставка пользовательского сообщения/подтверждения не создаёт новую подготовку или новый ключ отправки. Чужие/устаревшие результаты не применяются: проверяются сессия, операция, версия, тип и ожидаемое действие; для отправки — также ключ.

### 8.3. Достоверный отказ и пользовательская подготовка заново

`SUBMIT_REJECTED` означает достоверный отказ, при котором контракт гарантирует, что запрос не принят. Не всякий код ошибки или тайм-аут удовлетворяет этому условию.

1. После достоверного отказа агент показывает «Операция завершилась с ошибкой. Хотите повторить?» и suggest «Да» / «Нет». Сессия остаётся активной в ожидании решения.
2. «Да» запускает подготовку того же типа заново. Прежнее подтверждение не используется. Для статуса формируется новая сводка; для отзыва используется сохранённое разрешение; для уточнения используются сохранённое разрешение, новый ввод изменений и новая ФЛК. Если бизнес-результата полномочий ещё нет, проверка выполняется по §6.1. Затем показывается сводка и запрашивается отдельное подтверждение.
3. «Нет» сбрасывает рабочую подготовку и возвращает сессию в `CHOOSING_REQUEST_TYPE`. Исходный контекст и ограничения сохраняются; показывается меню разрешённых операций с учётом доступности поверхности по §6.3.
4. Если после новой подготовки, подтверждения и отправки получен очередной достоверный отказ, снова задаётся вопрос «Хотите повторить?» с «Да» / «Нет». Отдельного бизнес-лимита таких пользовательских повторов нет.

Подготовка заново отличается от технического повтора прежней отправки: пользователь заново проходит необходимые шаги и подтверждает новую сводку. Новый подтверждённый запрос получает собственную идентичность отправки; его технические повторы сохраняют свой ключ. Конкретный контракт ключей, повторов после достоверного отказа и сроков их действия уточняется в Q-10. Нельзя создавать новый запрос только из-за сетевого повтора или неизвестного исхода.

### 8.4. Успех и неизвестный исход

Только достоверное принятие Invest corr разрешает сообщение «Запрос принят в обработку». Наша сессия сразу переводится в терминальное `COMPLETED`; обычный ответ ГигаАссистенту содержит `metadata.final_message=true`. Отдельное сообщение или вызов завершения не выполняется. По ACL 1.6 завершается агентский сценарий, дальнейшее ведение внешнего чата остаётся у GA. Доставка потерянного финального ответа и идентичность нового сценария — внешние условия Q-08. Ожидание доставки не делает нашу FSM снова активной. В завершённой сессии нет новых операций и справочных ответов.

Если после настроенных технических повторов результат не установлен, текущий синхронный вызов завершается ошибкой, фиксируется `SUBMIT_UNKNOWN`. Запрос при этом мог быть принят или выполнен. Это не достоверный отказ: предложение «Хотите повторить?» из §8.3 к нему не применяется. Не обещаются фоновая сверка, успешная отмена, автоматическая компенсация или новая отправка. Дальнейшие операционные действия остаются в Q-05. Справочный ответ без изменения исхода допустим по общему правилу вопросов.

### 8.5. Технические ошибки разбора LLM

Если выбран текстовый источник и разбор LLM завершился технической ошибкой (включая тайм-аут или результат, не соответствующий ожидаемой структуре), выполняются максимум **три попытки всего: первоначальная и две повторные**. Успешный разбор прекращает повторы. Все попытки относятся к тому же пользовательскому сообщению и неизменному контексту до его применения; промежуточный невалидный результат не изменяет FSM или черновик и не вызывает операционное действие.

Эти попытки составляют один логический вызов по ADR-007: полный промпт и параметры модели между ними не меняются. Технический повтор после сбоя не увеличивает число уникальных вызовов. Новый промпт для исправления JSON, дополнительная классификация или изменение параметров не считаются таким повтором и не дают права на второй вызов вне RAG.

После третьей неудачи сохраняются текущий шаг, выбранная операция и ранее введённые реквизиты. По повторному решению заказчика **HTTP 500 обязателен**: ответ содержит `message.performative=failure`, соответствующий установленной причине код тела по §8.6 и `final_message=false`; в `message.content.reason` сообщается о техническом сбое и о том, что последнее изменение не применено. Для сохранения внешнего сценария HTTP 500 не заменяется на 200/202. Продолжение новой пользовательской попыткой зависит от поведения GA (Q-17), поэтому не гарантируется одним флагом. `RESET`, терминальное завершение нашей FSM и отправка в Invest corr из этого ответа не выводятся. Новая пользовательская попытка получает новый `Request-Id`; повторная доставка прежнего запроса возвращает сохранённый результат. Неоднозначное намерение требует уточнения пользователя, а не технических повторов. Политики LLM, полномочий/ФЛК и corr остаются раздельными и укладываются в срок ответа каналу по Q-08.

ACL-01 закрыт в части выбора: обязательный HTTP 500 подтверждён. Прежнее описание поверхности связывает `500-2` с завершением активного сценария; новый реестр не задаёт реакцию GA и не отменяет её. Фактическое продолжение/повторный вход остаётся внешним условием Q-17; подтверждение HTTP 500 не считается новым решением об очистке черновика или автоматическом завершении нашей FSM.

Политика §8.5 относится к структурированному разбору. Технический сбой отдельной генерации RAG-ответа после успешного поиска — самостоятельный случай Q-20: это не отсутствие материалов и не недоступность базы. Такой сбой не разрешает выдуманный ответ или банковскую отправку. Для чистого справочного вопроса прежние состояние/черновик сохраняются; число попыток, транспортный ответ и судьба изменений в составном ходе должны быть согласованы по Q-19/Q-20. Новая ветвь не считается закрытой существующим AC-43.

### 8.6. Коды ACL и границы повторов

Таблица фиксирует однозначные значения из [реестра кодов](../../../api/error_codes.md). Наличие кода в реестре не добавляет новый бизнес-сценарий и не определяет переход FSM. Текст должен сохранять формулировку реестра с предусмотренными уточнениями. Для ошибок полномочий, отсутствия знаний и продолжения после технического сбоя точное применение в нашем многошаговом сценарии остаётся в Q-17.

| HTTP / `status_code` | Перформатив и текст | Назначение |
|---|---|---|
| 200 / `200` | `inform`, `result` | Обычный успешный ход; фактический результат описывается текстом. Успешная выдача сводки или просьбы исправить реквизиты не означает отправки corr. |
| 202 / `202-1` | `inform`, `result` | Вопрос направлен не тому агенту. |
| 202 / `202-2` | `inform`, `result` | Вопрос относится к компетенции, но агент ещё не умеет на него отвечать. |
| 202 / `202-3` | `inform`, `result` | Полномочия клиента недостаточны; это бизнес-результат, а не техническая недоступность проверки. |
| 202 / `202-4` | `inform`, `result` | Недостаточно данных для проверки полномочий. Не подменяет тайм-аут/ошибку сервиса. |
| 202 / `202-5` | `inform`, `result` | Требуется перевод на оператора; такой маршрут не включается в MVP одним наличием кода. |
| 202 / `202-6`, `202-8` | `inform`, `result` | Для предметного ответа отсутствует `epk_id` либо конкретный необходимый параметр. |
| 202 / `202-7` | `inform`, `result` | Сценарий выполнен, но агент осознанно не формирует подсказку; не универсальная ошибка. |
| 400 / `400-2` | `failure`, `reason` | Ошибка параметров запроса на агента. Нельзя автоматически приравнивать к занятой или завершённой сессии. |
| 500 / `500-2` | `failure`, `reason` | Прочая внутренняя ошибка агента, не покрытая специальными кодами ниже; например, исчерпаны попытки получить структурно корректный результат LLM. |
| 500 / `500-3` | `failure`, `reason` | Нужная смежная система недоступна. |
| 500 / `500-4` | `failure`, `reason` | Агент передал в смежную систему невалидный запрос. |
| 500 / `500-5` | `failure`, `reason` | Отказ в доступе к смежной системе по сертификатам. |
| 500 / `500-7` | `failure`, `reason` | Ответ смежной системы не получен, например истёк тайм-аут; указывается система. |

`202-9` означает запрос консультации эксперта, но источники расходятся по `inform/proxy`, `result/reason` и не заполняют HTTP-статус в строке реестра. Его отправка до согласования не добавляется. `202-10` относится к версии 1.7 и не включается в профиль 1.6. `404-2` остаётся зарегистрированным кодом непредвиденной ошибки; им не заменяют более точный код и не обозначают автоматически отсутствие справочного ответа.

Агент возвращает полноценный ACL-ответ, включая при ошибке: неизвестный шлюзу код 4xx/5xx может быть преобразован в `417-1`, неразбираемое тело — в `422-1`, HTTP 500 без тела — в `500-6`. Эти коды формирует AI Proxy; наш агент не выдаёт их за собственный результат. HTTP 202 из реестра отсутствует в текущем YAML и требует актуализации схемы при включении соответствующих ответов.

Рекомендация `retry` в реестре адресована поверхности, необязательна и не задаёт число попыток нашего LLM, полномочий или Invest corr. Повторная доставка завершённого входного запроса возвращает сохранённый ответ, включая ошибку; новая пользовательская попытка имеет новый ID. Изменение `retry_number` не создаёт новую банковскую отправку. Состав значимых данных для дедупликации и изменения метаданных при повторе подтверждаются по Q-08. Ни `500-7`, ни внешний `504` не доказывают, что Invest corr не принял запрос; Q-05/Q-10 сохраняются.

## 9. Состояния и матрица переходов

### 9.1. Состояния

Названия обозначают логическое поведение. Тип запроса является атрибутом контекста, а не отдельным состоянием. Начальное состояние FSM — `CHOOSING_REQUEST_TYPE`.

| Состояние | Значение | Ожидание / завершение |
|---|---|---|
| `CHOOSING_REQUEST_TYPE` | Нет активной подготовки | Выбор, вопрос или событие первого сообщения. |
| `CHECKING_AUTH` | Проверяются полномочия `recall`/`details`, если бизнес-результата ещё нет в сессии | Внутренний результат текущего синхронного вызова. |
| `AWAITING_DETAILS` | Ввод/исправление реквизитов | Сообщение пользователя. |
| `VALIDATING_DETAILS` | Выполняется внутренняя ФЛК | Внутренний результат текущего вызова. |
| `AWAITING_CONFIRM` | Показана актуальная сводка | Подтверждение, изменение, отказ, выбор или вопрос. |
| `SUBMITTING` | Отправляется подтверждённый запрос | Результат Invest corr с учётом технической политики повторов. |
| `AWAITING_RETRY_CONFIRM` | Получен достоверный отказ Invest corr | Решение, начинать ли подготовку заново; это не подтверждение отправки. |
| `SUBMIT_UNKNOWN` | Вызов завершён ошибкой, факт принятия неизвестен | Не является ожиданием фонового запроса. Операционные переходы отложены в Q-05. |
| `COMPLETED` | Invest corr подтвердил принятие | Терминальное состояние нашей сессии. |

Отдельное устойчивое `FAILED` для согласованных ветвей не требуется: после ошибки проверки выполняется возврат к выбору, после достоверного отказа corr — ожидание решения о повторе. Ошибка операции и `CANCELLED` могут фиксироваться как исходы подготовки без терминального завершения сессии.

### 9.2. Общие условия

`OPEN(type)` — доверенное первое управляющее сообщение, `SELECT(type)` — последующий выбор кнопкой или однозначным текстом. `START(type)` — новая подготовка с сохранённым исходным контекстом по M-01–M-03, со сбросом предыдущих рабочих данных. Это действие, а не дополнительное состояние.

`CONFIRM` относится к текущей сводке из контекста, `RETRY_YES` — только к вопросу о подготовке заново. Они не взаимозаменяемы. Источник входного действия выбирается по §4.1. `AUTH_DENIED` и `FLK_INVALID` — бизнес-результаты; `AUTH_ERROR` и `FLK_ERROR` — технические ошибки. Внутренние события проверяются на соответствие сессии, операции и версии; версия сводки во входном подтверждении не передаётся, различение старых кнопок на первом этапе отсутствует (Q-11).

### 9.3. Подготовка и проверки

| ID | Из | Событие / условие | В | Действие |
|---|---|---|---|---|
| M-01 | `CHOOSING_REQUEST_TYPE` | `OPEN/SELECT(status)`, корректный контекст | `AWAITING_CONFIRM` | Создать подготовку статуса, показать сводку. |
| M-02 | `CHOOSING_REQUEST_TYPE` | `OPEN/SELECT(recall)`, нет ограничения | `CHECKING_AUTH`, либо `AWAITING_CONFIRM` при сохранённом разрешении | Создать подготовку отзыва; проверить полномочия только при отсутствии результата, иначе показать сводку. |
| M-03 | `CHOOSING_REQUEST_TYPE` | `OPEN/SELECT(details)`, нет ограничения | `CHECKING_AUTH`, либо `AWAITING_DETAILS` при сохранённом разрешении | Создать подготовку уточнения, сохранить извлечённые из этого входа новые значения; проверить полномочия только при отсутствии результата. При разрешении применить готовые изменения по M-22, иначе запросить недостающий/неясный ввод. |
| M-04 | Вход / `CHOOSING_REQUEST_TYPE` | Контекст некорректен или тип неизвестен | Без запуска подготовки | Контролируемая ошибка; не угадывать контекст, не вызывать corr. |
| M-05 | `CHOOSING_REQUEST_TYPE` | Выбран отзыв/уточнение при «только статус» | То же | Отказать в запуске, предложить статус. |
| M-06 | `CHECKING_AUTH` | `AUTH_OK`, тип `recall` | `AWAITING_CONFIRM` | Сохранить разрешение на сессию, показать сводку отзыва. |
| M-07 | `CHECKING_AUTH` | `AUTH_OK`, тип `details` | `AWAITING_DETAILS` | Сохранить разрешение на сессию; при готовых изменениях того же входа сразу применить M-22, иначе перечислить четыре поля и запросить изменения/уточнение. |
| M-08 | `CHECKING_AUTH` | `AUTH_DENIED` | `CHOOSING_REQUEST_TYPE` | Сбросить подготовку, установить/сохранить ограничение на отзыв и уточнение, показать статус. |
| M-09 | `CHECKING_AUTH` | Первый `AUTH_ERROR` | То же | Один автоматический повтор. |
| M-10 | `CHECKING_AUTH` | Второй `AUTH_ERROR` | `CHOOSING_REQUEST_TYPE` | Ошибка, `RESET`, доступные операции. Не устанавливать запрет полномочий из-за технического сбоя. |
| M-11 | `AWAITING_DETAILS` | Однозначно распознано хотя бы одно поле | `VALIDATING_DETAILS` | Обновить явно переданные поля черновика, сохранить остальные; сформировать новую версию объединённых изменений и начать ФЛК. |
| M-12 | `AWAITING_DETAILS` | Неясные поля/значения | То же | Уточнить ввод, сохранить подготовку. |
| M-13 | `VALIDATING_DETAILS` | `FLK_OK`, актуальная версия | `AWAITING_CONFIRM` | Показать полную сводку изменений. |
| M-14 | `VALIDATING_DETAILS` | `FLK_INVALID` | `AWAITING_DETAILS` | Ошибки по полям и запрос исправлений. |
| M-15 | `VALIDATING_DETAILS` | Первый `FLK_ERROR` | То же | Один автоматический повтор той же версии. |
| M-16 | `VALIDATING_DETAILS` | Второй `FLK_ERROR` | `CHOOSING_REQUEST_TYPE` | Ошибка, `RESET`, доступные операции. |
| M-17 | `AWAITING_CONFIRM` | `CONFIRM`, актуальная сводка, завершённая подготовка, нет ожидаемого уточнения | `SUBMITTING` | Зафиксировать данные/ключ, отправить запрос. |
| M-18 | `AWAITING_CONFIRM` | Изменение реквизитов текущего `details` из выбранного текстового источника, в том числе вместе с согласием | `VALIDATING_DETAILS` | Аннулировать прежнее согласие, проверить изменения, затем показать новую сводку. |
| M-19 | `AWAITING_CONFIRM` | Неоднозначное решение | То же | Сохранить предмет ожидаемого уточнения, задать вопрос; не отправлять. |
| M-20 | `AWAITING_DETAILS` / `AWAITING_CONFIRM` | Выбранный текстовый источник просит исключить отдельное поле из черновика | То же | Объяснить ограничение первого этапа и предложить отменить подготовку и ввести изменения заново; текущие данные не менять, не отправлять. |
| M-21 | `CHOOSING_REQUEST_TYPE` / `AWAITING_DETAILS` / `AWAITING_CONFIRM` / `AWAITING_RETRY_CONFIRM`, есть сохранённое уточнение | Ответ относится к ожидаемому вопросу | По результату уточнения, без перехода к отправке | Неясный ответ сохраняет ожидание; ясный снимает его и применяет уточнённые намерение/данные к подготовке или ФЛК. Готовая сводка показывается заново; отдельное согласие требуется на следующем ходе. §6.4. |
| M-22 | `AWAITING_DETAILS` | После START/AUTH_OK есть однозначные изменения из того же входа, полномочия разрешены | `VALIDATING_DETAILS` | Применить сохранённые новые значения к этой подготовке, выполнить ФЛК без повторного запроса уже введённых полей. Второй разбор LLM не нужен. |

| ID | Из | Событие / условие | В | Действие |
|---|---|---|---|---|
| S-01 | `SUBMITTING` | Достоверное принятие текущего запроса | `COMPLETED` | Зафиксировать терминальный исход, вернуть сообщение о принятии с `metadata.final_message=true`; агентский сценарий завершён. |
| S-02 | `SUBMITTING` | Достоверный `SUBMIT_REJECTED` | `AWAITING_RETRY_CONFIRM` | Ошибка и «Хотите повторить?» с «Да» / «Нет». |
| S-03 | `SUBMITTING` | Неопределённость, политика разрешает технический повтор | То же | Тот же запрос/ключ в текущем синхронном вызове. |
| S-04 | `SUBMITTING` | Результат неизвестен, политика исчерпана | `SUBMIT_UNKNOWN` | Вернуть ошибку; не считать запрос непринятым и не предлагать обычный повтор. |
| S-05 | `AWAITING_RETRY_CONFIRM` | `RETRY_YES` без изменения типа | По `START(прежний тип)` | Начать подготовку заново, включая проверки и новую сводку; не отправлять по этому «Да». |
| S-06 | `AWAITING_RETRY_CONFIRM` | «Нет» / отказ от повтора | `CHOOSING_REQUEST_TYPE` | `RESET`, показать все разрешённые операции. |
| S-07 | `AWAITING_RETRY_CONFIRM` | Явно выбран разрешённый тип | По `START(type)` | Начать новую подготовку выбранного типа по общему правилу выбора; нужны проверки и подтверждение. |
| S-08 | `AWAITING_RETRY_CONFIRM` | Неясный ответ, нет однозначного выбора/отказа | То же | Уточнить решение, не отправлять. |
| S-09 | `SUBMIT_UNKNOWN` | Новая отправка, отказ, смена или повтор операции | Не согласовано, Q-05 | Не включать новую отправку, компенсацию или успешную отмену как утверждённое поведение. |
| S-10 | `AWAITING_RETRY_CONFIRM` | Однозначно выбран запрещённый тип | `CHOOSING_REQUEST_TYPE` | `RESET`, объяснить ограничение и показать разрешённые действия; исходный контекст, полномочия и история отправок сохранены, corr не вызывается. |
| G-01 | Любое | Повторная доставка обработанного сообщения | Без повторного бизнес-перехода | Вернуть согласованный сохранённый результат через механизм идемпотентности; не повторять эффект как новый. |
| G-02 | Любое | Чужой/устаревший результат | Без изменения | Не применять к текущей подготовке. |
| G-03 | Занятая сессия | Новый конкурентный API-вход | Без перехода по новому сообщению | Отклонить вход по ADR-010; выполняющийся вызов не прерывать. |
| G-04 | `COMPLETED` | Новое сообщение, не повтор доставки | `COMPLETED` | Техническая ошибка API «Обращение к завершённой сессии». |

S-02 действует после любого очередного достоверного отказа без отдельного лимита пользовательских повторов. Переход в `SUBMITTING` возможен только по M-17 после актуального подтверждения. Внутренние `CHECKING_AUTH`, `VALIDATING_DETAILS`, `SUBMITTING` не принимают параллельные пользовательские события. `COMPLETED` не имеет исходящих бизнес-переходов. Неописанное событие не разрешает отправку.

## 10. Шаблоны ответов и действия: проекты на согласование

**Статус:** способ взаимодействия утверждён заказчиком; приведённые ниже тексты, идентификаторы шаблонов, типы сообщений и примеры являются **проектами для его согласования**, ещё не зарегистрированными в GA. Подготовка, согласование и регистрация шаблонов — обязательный этап подготовки требований перед реализацией отображения. Операционные тексты формируются детерминированно, без отдельного вызова LLM по ADR-007.

### 10.1. Разметка из документации и порядок подготовки

Пример найден в [описании 1.5](../../../api/api_contract_details_1.5.md), в конце страницы, таблица «Примеры шаблонов подтверждения», строка «Использование спойлера». В нём используются подстановка двойными фигурными скобками, заголовок, жирный текст, разделитель и спойлер. Короткий фрагмент источника:

~~~markdown
# Отправляем платёж?
---
**Получатель:** {{receiverOrgName}}
::: spoiler [Все реквизиты]
**Плательщик:** {{payerOrgName}}
:::
~~~

Для нашего агента адаптируются разметка и механизм подстановки: предмет подтверждения — запрос статуса/отзыва/уточнения, а не отправка самого платежа. Пример маскирования &MASK;.account на той же странице помечен «пока такого нет»; эту конструкцию не используем. Дополнительные условные операторы/циклы шаблонизатора документом не подтверждены и здесь не вводятся.

Порядок подготовки:

1. Согласовать тексты, обязательные данные, действия и ожидаемый вид каждого ответа по этому разделу.
2. Зафиксировать у GA коды платформенных шаблонов подтверждения, типы карточек и привязки UI-операций на странице присутствия.
3. Подтвердить поле передачи кода шаблона и реальные входы подтверждения/отказа/выбора действия, включая старую кнопку.
4. Проверить подстановку значений, переносы строк, спойлер, видимость всех изменений и доступные действия на подключаемых WEB/MOBILE-поверхностях; сохранить согласованные примеры в требованиях.
5. После утверждения текстов и проверки внешнего контракта использовать их в реализации. Наличие проекта в этом разделе не означает прохождения регистрации или проверки отображения.

Форма подтверждения выбрана окончательно: платформенный шаблон GA и CONFIRMATION. Старое описание указывает поле message.result, которого нет в текущем YAML; в схеме существует message.content.result. Ниже последнее используется **как предлагаемый вариант для проверки Q-18**, а не как исправленный по догадке факт внешнего API. То же относится к обработке propose в 1.6: механизм выбран, его конкретный обмен должен быть подтверждён владельцем GA.

### 10.2. Параметры и общие правила содержания

| Параметр | Источник / назначение |
|---|---|
| paymentId | Доверенный исходный идентификатор платежа; передаётся в контексте UI-операции, в пользовательском тексте не показывается. Не разрешает заменить платёж в существующей сессии. |
| paymentNumber, paymentDate | Номер и дата исходного платежа из §4.2; дата форматируется для отображения без изменения значения. |
| amount, currency | Сумма и валюта исходного платежа, а не стоимость запроса. Форматированные строки для отображения. |
| recipientName | Исходное наименование получателя. Не подменяется новым наименованием из черновика. |
| organizationName | Наименование организации из доверенного исходного контекста. |
| changesText | Сформированный приложением перечень всех включённых в текущий черновик новых значений. Только для подтверждения details, непустой; не свободный ответ LLM. |
| fieldErrorsText | Полный перечень фактически выявленных ошибок ФЛК по полям; без выдуманных правил проверки. |
| clarificationText | Конкретный вопрос о неясном поле/намерении из установленного результата разбора. |
| expectedActionText | Подсказка следующего шага из FSM: ввод изменений, проверка сводки, выбор действия или решение о подготовке заново. Не разрешает отправку сама по себе. |
| requestTypeText | Одно из фиксированных обозначений: «статуса», «на отзыв», «на уточнение реквизитов». |
| failureReasonText | Установленная техническая причина в формулировке реестра §8.6; не произвольное содержимое exception. |

Обязательные смысловые данные сводки — тип запроса, платёж, организация, получатель, сумма и все отправляемые изменения — видимы сразу, вне спойлера. В спойлере размещается только дополнительное пояснение. Исходные реквизиты и изменения явно разделены. Шаблон не обещает отзыв/изменение самого платежа или банковский результат до его получения.

Изменения формируются по фиксированным меткам в порядке: новый ИНН получателя; новый счёт получателя; новое наименование получателя; новое назначение платежа. Отсутствующие в черновике поля полностью исключаются из changesText. При исправлении одного поля включаются также остальные сохранённые изменения; скрывать их нельзя. Не используются пустые строки вида «ИНН: null», необъявленные условные конструкции шаблонизатора или восстановленные из истории значения.

Все state.value передаются строками; переносы строк сериализуются штатным JSON-сериализатором. Данные подставляются как значения: фигурные скобки, Markdown и последовательность ::: внутри пользовательского назначения не должны создавать вложенный шаблон, скрытый блок или новое действие. Подстановку многострочного changesText и обработку специальных символов необходимо подтвердить на стороне GA; неподдержанный способ не заменяется незаметным сокращением изменений. Недостающий обязательный параметр запрещает показ неполной сводки и её подтверждение.

### 10.3. Три платформенных шаблона подтверждения

Названия INVEST_CORR_CONFIRM_*_V1 — предлагаемые коды регистрации, а не полученные от GA идентификаторы. Все три шаблона относятся к AWAITING_CONFIRM. Подтверждение формы приводит к CONFIRM только при выполнении guards FSM; отказ — к отмене подготовки по §6.3. Проект подписей элементов формы: «Отправить запрос» и «Отказаться». Это элементы платформенного подтверждения, а не suggestions.

**T-C01 — INVEST_CORR_CONFIRM_STATUS_V1. Запрос статуса.**

~~~markdown
# Отправить запрос статуса платежа?
---
**Платёж:** №{{paymentNumber}} от {{paymentDate}}
**Организация:** {{organizationName}}
**Получатель:** {{recipientName}}
**Сумма платежа:** {{amount}} {{currency}}
---
Подтвердите отправку запроса статуса этого платежа.
::: spoiler [Что произойдёт после подтверждения]
Запрос будет передан на обработку. Результат запроса поступит после обработки.
:::
~~~

**T-C02 — INVEST_CORR_CONFIRM_RECALL_V1. Запрос отзыва.**

~~~markdown
# Отправить запрос на отзыв платежа?
---
**Платёж:** №{{paymentNumber}} от {{paymentDate}}
**Организация:** {{organizationName}}
**Получатель:** {{recipientName}}
**Сумма платежа:** {{amount}} {{currency}}
---
Подтвердите отправку запроса на отзыв этого платежа.
::: spoiler [Что означает этот запрос]
Отправка запроса не гарантирует отзыв платежа. Результат станет известен после обработки запроса.
:::
~~~

**T-C03 — INVEST_CORR_CONFIRM_DETAILS_V1. Уточнение реквизитов.**

~~~markdown
# Отправить запрос на уточнение реквизитов?
---
**Исходный платёж:** №{{paymentNumber}} от {{paymentDate}}
**Организация:** {{organizationName}}
**Получатель в исходном платеже:** {{recipientName}}
**Сумма платежа:** {{amount}} {{currency}}
---
**Передаваемые изменения:**
{{changesText}}
---
Проверьте все изменения и подтвердите отправку запроса.
::: spoiler [Что означает этот запрос]
На обработку будет передан запрос с перечисленными изменениями. Исходные данные платежа в нашей подготовке сохраняются.
:::
~~~

Пример changesText только для назначения:

~~~text
Новое назначение платежа: Оплата по договору Б от 01.10.2026.
~~~

Пример после ввода нового наименования и назначения, даже если последнее сообщение исправило только назначение:

~~~text
Новое наименование получателя: ООО «Альфа-Сервис».
Новое назначение платежа: Оплата по договору Б от 01.10.2026.
~~~

Новый ИНН и новый счёт при их наличии добавляются отдельными строками с полными подтверждаемыми значениями. Маскирование, которое мешает проверить изменения, не применяется.

**Примеры видимой части трёх подтверждений на одном условном платеже.** Общие данные: платёж №42 от 03.10.2026, ООО «Вектор», исходный получатель ООО «Альфа», 12 500,00 RUB.

| Шаблон | Заголовок и содержание после подстановки | Действие формы |
|---|---|---|
| T-C01 | «Отправить запрос статуса платежа?»; №42 от 03.10.2026; ООО «Вектор»; ООО «Альфа»; 12 500,00 RUB. | Подготовить к отправке именно запрос статуса; отправка только после подтверждения. |
| T-C02 | «Отправить запрос на отзыв платежа?»; те же исходные данные; пояснение об отсутствии гарантии отзыва. | Подтвердить именно запрос отзыва, а не заявить выполненный отзыв. |
| T-C03 | «Отправить запрос на уточнение реквизитов?»; исходный получатель ООО «Альфа»; отдельный видимый блок: новое наименование ООО «Альфа-Сервис», новое назначение «Оплата по договору Б от 01.10.2026». | Подтвердить оба изменения из актуальной сводки, а не только последнее введённое поле. |

### 10.4. Выбор операции через действия GA

По требованию заказчика три бизнес-операции оформляются как зарегистрированные **сценарные действия**. Для их выбора предлагается описанный в сущностях GA механизм **UI-операций у сообщения об исходном платеже**: message.type задаёт зарегистрированный тип карточки, state с type=OPERATION передаёт параметры. Такое применение к карточке исходного платежа и доступность вариантов должны быть подтверждены GA. Обычный текст со списком или suggestions, в том числе BUTTON, не считаются реализацией этого требования.

Проект регистрации действий и их отображения:

| Действие / предлагаемый action_code | Подпись UI-операции | Текст после выбора, если GA показывает его в чате | Событие и эффект |
|---|---|---|---|
| status | Запросить статус | Запросить статус платежа №{{paymentNumber}}. | SELECT(status): подготовка статуса и T-C01; без немедленной отправки. |
| recall | Запросить отзыв | Подготовить запрос на отзыв платежа №{{paymentNumber}}. | SELECT(recall): полномочия, затем T-C02. |
| details | Уточнить реквизиты | Уточнить реквизиты платежа №{{paymentNumber}}. | SELECT(details): полномочия, ввод, ФЛК, затем T-C03. |

Выбор на первом входе может соответствовать OPEN(type), далее — SELECT(type). Подпись не является источником служебного кода; точный вход после клика — Q-16. Названия и привязки action_code для реального GA должны быть зарегистрированы; status/recall/details сохраняют значения нашего профиля.

Проекты типов сообщения:

| message.type | UI-операции | Когда применяется |
|---|---|---|
| INVEST_CORR_PAYMENT_ACTIONS_V1 | status, recall, details | Все три действия разрешены локально и доступны на поверхности. |
| INVEST_CORR_PAYMENT_STATUS_ONLY_V1 | status | Для пользователя доступен только статус. |

Эти два типа покрывают известные полные/ограниченные меню. Если реальная поверхность разрешает другой поднабор, требуется её поддержанный механизм фильтрации или соответствующая зарегистрированная конфигурация; подменять его полным меню нельзя. Произвольный массив actions в ответ ACL не добавляется. Пустой suggestions не считается доказательством, что GA не добавит свои подсказки: отсутствие подменяющих меню саджестов проверяется при настройке сценария.

**T-A01 — карточка для выбора действия.** Текст формирует наш агент; это не код платформенного шаблона подтверждения.

~~~markdown
# Запрос по платежу
**Платёж:** №{{paymentNumber}} от {{paymentDate}}
**Организация:** {{organizationName}}
**Получатель:** {{recipientName}}
**Сумма платежа:** {{amount}} {{currency}}
---
Выберите действие для этого платежа в меню сообщения.
~~~

Для карточки «только статус» последняя строка заменяется на: «Для этого платежа вам доступен запрос статуса. Выберите действие в меню сообщения». Короткая причина возврата к выбору — например, «Подготовка запроса отменена» — выводится перед карточкой. Параметры OPERATION содержат paymentId и необходимые для отображения/вызова данные §10.2; они не восстанавливают отменённый черновик.

В финальном ответе COMPLETED тип карточки с этими действиями не выдаётся: новая операция требует нового входа. Старое меню в истории не разрешает действие вне текущих правил FSM. Подтверждение отправки и меню выбора действия — разные элементы.

### 10.5. Остальные базовые ответы

Все строки — проекты текстов для согласования. Для обычных сообщений текст передаётся в result; для failure — в reason в соответствии с §8.6. Слово «действия» в таблице означает UI-операции §10.4, если явно не указано другое. Точные коды ошибок и поведение канала остаются в Q-17 там, где они не определены.

| ID / ситуация | Проект текста | Следующий шаг / ограничения |
|---|---|---|
| T-I01 — ввод details | «Укажите новые значения: ИНН получателя, счёт получателя, наименование получателя или назначение платежа. Можно изменить одно или несколько полей». | Ожидать user_input, без отправки. |
| T-I02 — неясный ввод | «Нужно уточнение: {{clarificationText}}». | Сохранить подготовку; вопрос должен называть конкретную неоднозначность. |
| T-I03 — неясное согласие | «Не удалось однозначно определить ваше решение. Проверьте сводку и подтвердите отправку либо откажитесь от подготовки». | Сводка не меняется, отправки нет; повторный показ формы не создаёт новое согласие. |
| T-F01 — ФЛК | «Нужно исправить реквизиты:<br>{{fieldErrorsText}}<br>Укажите исправленные значения. Остальные введённые изменения сохранены». | Исправление в текущем details, затем проверка всего черновика. |
| T-P01 — нет полномочий | «Вам доступен только запрос статуса по этому платежу». | Карточка только с действием status; без кодов recall/details в меню. |
| T-CANCEL — отмена подготовки | «Подготовка запроса отменена». | При отсутствии нового выбора — карточка действий; при явном переключении — следующий шаг выбранной операции. |
| T-SWITCH — переключение | «Предыдущая подготовка отменена. Начинаем подготовку запроса {{requestTypeText}}». | Далее ввод или новая сводка; сохранённые полномочия применяются по §6.1. |
| T-CHECK-ERROR — две ошибки проверки | «Сейчас невозможно выполнить проверку. Подготовка запроса сброшена; запрос в банк не отправлен. Можно выбрать доступное действие». | Карточка действий в той же нашей сессии; видимость/продолжение через GA — Q-17. |
| T-RETRY — достоверный отказ corr | «Запрос не принят в обработку. Хотите подготовить его заново? Перед отправкой потребуется новое подтверждение». | Только для гарантированного отказа без принятия. Согласованные диалоговые «Да/Нет» запускают подготовку/возврат к действиям; «Да» не отправляет прежний запрос. |
| T-ACCEPTED — corr принял запрос | «Ваш запрос {{requestTypeText}} по платежу №{{paymentNumber}} принят в обработку. О результатах узнаете в СМС от номера 900». | final_message=true, COMPLETED. СМС обеспечивает внешний процесс; результат самой банковской операции не объявляется. |
| T-UNKNOWN — исход corr неизвестен | «Произошла ошибка при получении результата запроса». | Сохраняется ранее согласованный минимальный текст. Развёрнутый текст и дальнейшие действия отложены по Q-05; «Хотите повторить?» не предлагается. |
| T-KB-EMPTY — сведений нет | «В базе знаний нет достаточной информации для ответа на этот вопрос. Уточните, пожалуйста, вопрос». | Сохранить шаг; при активной подготовке добавить expectedActionText. |
| T-KB-ERROR — база недоступна | «Сейчас не удалось получить справочную информацию». | Сохранить шаг; возможность предложить продолжение зависит от ответа по Q-17. |
| T-LLM-ERROR — три ошибки разбора | «{{failureReasonText}}. Последнее сообщение не применено. Запрос в банк не отправлялся по этому сообщению». | Обязательные HTTP 500/failure; причина по §8.6. Сохранить шаг/черновик; не обещать возврат GA в тот же сценарий. Текст относится к неудачному разбору до эффекта, а не к неизвестному исходу corr. |
| T-BUSY — занятая сессия | «Сессия занята». | HTTP 400/failure; выполняющийся ход продолжается. Не заявлять отсутствие банковской отправки текущим другим ходом. |
| T-COMPLETED — новое сообщение после завершения | «Обращение к завершённой сессии». | HTTP 400/failure; нет новой операции, справки или переоткрытия. |
| T-REMIND — повтор текущего выбора / ответ на справку | «{{expectedActionText}}». | Для AWAITING_DETAILS: «Укажите новые значения реквизитов». Для AWAITING_CONFIRM: «Проверьте сводку и подтвердите отправку либо откажитесь». Для AWAITING_RETRY_CONFIRM: «Подготовить запрос заново?» |
| T-REMOVE-FIELD — исключить одно изменение | «Чтобы убрать отдельное изменение, отмените текущую подготовку и введите нужные изменения заново. Пока текущие данные сохранены». | Сам текст не удаляет поле, не отменяет подготовку и не отправляет запрос. |

T-LLM-ERROR использует, например, «Внутренняя ошибка агента» для 500-2, формулировку недоступности смежной системы для 500-3 либо отсутствия ответа нужной системы для 500-7. Установленную причину нельзя заменять одной универсальной «ошибкой сети». Для смысловых ошибок пользователя технический failure не назначается только потому, что ввод требует уточнения.

### 10.6. Примеры данных и предлагаемых ответов ACL

**Пример подтверждения details**, HTTP 200. Все значения подставляются в T-C03; кнопки формы рисует GA. В этой предложенной форме result содержит код шаблона, а не весь Markdown.

### 10.7. Что согласовать по проектам шаблонов

На предметный аппрув вынесены тексты T-C01–T-C03, карточка T-A01, подписи трёх действий, элементы формы «Отправить запрос»/«Отказаться» и ответы §10.5. Критерии: пользователь отличает платёж от запроса по нему; видит все изменения; отмена и подготовка заново не выглядят отправкой; успех означает только принятие corr.

После предметного аппрува отдельно подтверждаются регистрация кодов/типов, поле шаблона, реальное отображение разметки, ввод user_input, payload кликов и защита старой сводки. Проверки шаблонов должны покрыть непустое подмножество четырёх изменений, сохранённые поля после частичного исправления, специальные символы/многострочный текст, ограниченные действия и завершённую сессию. Это содержательная приёмка и необходимая проверка отображения, а не разрешение увеличивать число LLM-вызовов.

**Аппрув текстов/разметки:** ожидается. **Регистрация и проверка GA:** не выполнены.

## 11. Инварианты и границы реализации

API-интерфейсы и внешние DTO генерируются из OpenAPI YAML Maven-плагином на фазе `generate-sources` по [ADR-004](../../../adr/0004-api-domain-mapstruct.md); внутренние DTO остаются отдельными, преобразования выполняет MapStruct. FSM доступна бизнес-сценариям через прикладной прокси и заменяемый SPI; Spring Statemachine сохраняет и восстанавливает native состояние своим штатным JPA persister внутри адаптера по [ADR-008](../../../adr/0008-replaceable-fsm.md).

Все классы, интерфейсы и тесты должны содержать краткую, ёмкую и точную документацию на русском языке по [ADR-011](../../../adr/0011-russian-code-documentation.md). Соответствие проверяется при реализации и приёмке каждого этапа.

- Любая отправка имеет тип `status`, `recall` или `details`, корректный доверенный контекст и подтверждение актуальной сводки.
- Разрешение модели, ключевое слово или выбор кнопки операции не заменяют проверку полномочий и подтверждение. По [ADR-007](../../../adr/0007-llm-responsibilities.md) LLM структурирует текст, а управление сценарием и банковским действием остаётся в приложении.
- На одно сообщение — не более одного логического вызова LLM, до двух только при необходимости ответа RAG. Логический вызов определяется уникальным полным промптом и параметрами; технические повторы с той же комбинацией учитываются отдельно. Действия, заданные поддерживаемым перформативом/кодом, не требуют LLM; отдельная генерация операционной сводки не вводится.
- Подготовка `recall`/`details` требует успешных полномочий; `details` также требует непустых изменений и успешной ФЛК актуальной версии.
- Согласие вместе с изменениями в выбранном текстовом источнике не вызывает отправку. Нижние источники при выбранном старшем не анализируются по §4.1. «Да» на предложение повторить запускает только подготовку заново.
- Сброс не удаляет исходный контекст, не снимает ограничение доступа и не восстанавливает старое согласие/отменённые изменения из истории.
- Технический повтор одного отправленного запроса использует прежний ключ и данные. Повторная доставка не является новым намерением.
- Успех устанавливается только по достоверному принятию. Неизвестный исход не преобразуется в достоверный отказ ради обычного повтора.
- В одной сессии нет одновременных ходов; итоговое состояние и возвращаемый ответ должны быть согласованы. Persistence и атомарность определяются [ADR-008](../../../adr/0008-replaceable-fsm.md), [ADR-009](../../../adr/0009-atomic-transition-commit.md), защита исполнения — ADR-010.
- `COMPLETED` завершает нашу сессию немедленно. Справка и новые операции в ней не выполняются; новое обращение отклоняется.

Требования к отдельным событиям логирования, метрикам, числовым лимитам, срокам хранения и схемам конфигурации не выдумываются из шаблонных разделов «Нет изменений» исходной Д2. Они относятся к техническим документам и интеграционным контрактам. Число пользовательских повторов и техническая retry-политика — разные правила.

## 12. Критерии приёмки

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| AC-01 | Первое корректное сообщение с выбранным типом, сохранённой сессии нет | Создана FSM с начальным `CHOOSING_REQUEST_TYPE`; событие этого сообщения применено сразу, повторный выбор не запрошен. |
| AC-02 | Сообщение существующей активной сессии, исходные идентификаторы/платёж и история чата не переданы | По `sessionId` загружены FSM и контекст; действие применено к ним. Отсутствие повторного контекста не является ошибкой. Загрузка не повторяет внешние вызовы. |
| AC-03 | Выбран status | Полномочия сценария не проверяются; показана сводка платформенным шаблоном T-C01; до подтверждения corr не вызывается. |
| AC-04 | Выбран recall, полномочия разрешены | Показана сводка платформенным шаблоном T-C02; актуальное подтверждение допускает одну логическую отправку. |
| AC-05 | Выбран details, полномочия разрешены | Запрошены изменения; после ФЛК платформа показывает T-C03 со всеми передаваемыми новыми значениями и отдельными исходными данными. |
| AC-06 | Отказ полномочий на отзыв либо уточнение | Обе операции недоступны, включая текст/старую кнопку; статус доступен. Ограничение сохраняется после сброса и выбора. |

| AC-09 | Ошибки реквизитов | Сообщены причины по соответствующим полям; возврат к исправлению без автоматического технического повтора. |
| AC-10 | После сводки в выбранном текстовом источнике изменены данные, в том числе «Да, но…» | Отправки нет; новая версия проверена и показана; требуется новое подтверждение. |

| AC-12 | Во время ввода явно выбран другой разрешённый тип | Предыдущие уточнения удалены; новая подготовка начата сразу, без повторного выбора меню; нужны собственные проверки/подтверждение. |
| AC-13 | После отмены снова выбран тот же тип | Он доступен; прежние пользовательские изменения не восстановлены. |
| AC-14 | Повторно выбран текущий тип без отказа во время подготовки | Нет дубликата подготовки; напомнен текущий шаг. |
| AC-15 | Предметный вопрос на вводе, подтверждении или предложении повтора | Ответ по базе знаний; шаг/данные сохраняются, запрос не отправляется. |

Отдельные саджесты и переходы соблюдают §4.3. Реальную фильтрацию UI-операций подтверждает Q-08. |
| AC-51 | Некорректные или расходящиеся ID корреляции | Нет бизнес-перехода и отправки corr, ID не восстанавливаются из истории и не придумываются. Формат транспортного ответа согласуется по Q-17. |
| AC-52 | Выбран текстовый источник; есть user_input / только phrases или operator_input | Используется только user_input. При его отсутствии — контролируемая ошибка без перехода, LLM и отправки; для явного управляющего действия текст не требуется искусственно. |
| AC-53 | Подстановка подтверждения details после частичного исправления | После аппрува шаблона в видимой сводке показаны все текущие изменения и отдельный исходный получатель; нет пустых/непереданных полей или нераскрытых параметров. Разметка из пользовательского значения не создаёт скрытый блок/действие. Отправка возможна только после согласия. |
Это критерии поведения, а не требование создавать отдельный тест на каждую строку. Проверки должны быть минимально достаточными и покрывать реальные сценарии, контракты и persistence по правилам проекта.

Для подключения к GA согласуются проекты §10 и оформляется страница присутствия: платформенные шаблоны подтверждения, поверхности, три сценарных действия, типы карточек и UI-операции, необходимые полномочия, отдельно используемые саджесты/переходы. Затем проверяются отображение и входы действий/подтверждения. Обязательный материал подключения — репрезентативная тестовая корзина XLSX/CSV с одним столбцом вопросов. Корзина передаётся для приёмки GA; по каждому согласованному вопросу проверяется предметная корректность ответа относительно контрольного ожидания. Владелец, материалы и контрольные ответы — Q-07. 50–150 вопросов рекомендованы, допускается меньше без искусственных вариантов; это не число обязательных автотестов и не требование разрабатывать экспортёр.

### 14.8. Лимит логических вызовов LLM

03.10.2026 заказчик потребовал не более одного вызова LLM на пользовательский запрос, с возможностью второго для справочного ответа RAG, и уточнил: «под вызовом понимаю уникальный промпт и параметры, повтор фейла не относится к этому». Принято в ADR-007 и §6.4/§8.5/§11. Прежнее правило трёх технических попыток разбора сохраняется. Возможность классификации без LLM описана в ADR-007; отдельный классификатор не выбран и не добавлен в обязательный объём MVP.

## 15. Оставшиеся решения и внешние условия

Все три выбора ACL-01–ACL-03 разрешены ответами заказчика (§14.10); повторный опрос не требуется. На предметный аппрув подготовлены проекты шаблонов §10. Открыты внешние контракты ниже и ранее отложенный Q-05; они не подменяются утверждением текстов или выбором предполагаемого поведения API.

### 15.1. Q-05 — ранее отложенный неизвестный результат Invest corr

Сохраняется прежний статус: отложен заказчиком для отдельного обсуждения с бизнесом. Подтверждены конечное ожидание по системной политике, возврат ошибки, сохранение данных и признание того, что запрос мог быть принят/выполнен. Новые документы канала не определяют банковский результат.

Остаются открыты: точное пояснение пользователю; допустимость дальнейших операций и повторов; необходимость сверки, её исполнитель и интерфейс; уведомление о позднем результате; различение неизвестной отправки и нового намерения; срок гарантий идемпотентности и устранение расхождения между показанной ошибкой и выполнением. Обычное предложение «Хотите повторить?» после достоверного отказа эти вопросы не закрывает. Новое решение по Q-05 в рамках настоящей сверки не принято.

Выбор заказчика фиксирует требования нашего продукта. Он не подтверждает неизвестные гарантии внешней системы; при несовместимости сначала устанавливается факт, затем рассматривается минимальное необходимое изменение.

### 15.3. Следующий предметный аппрув — проекты ответов

Решения о HTTP 500, user_input и платформенном подтверждении получены и повторно не предлагаются к выбору. Предмет согласования теперь конкретный: тексты/разметка T-C01–T-C03, карточка T-A01 и три действия, прочие ответы §10.5. Все проекты приведены вместе с параметрами, состояниями, примерами и ограничениями; готовность описана в §10.7.

После утверждения внести ответ заказчика в §14 и сменить статус только одобренных шаблонов. Различать «текст утверждён», «зарегистрировано в GA» и «обмен/отображение проверены». Отсутствующий внешний контракт Q-08/Q-11/Q-16/Q-18 не закрывается одним аппрувом содержания.

### 15.4. Q-19 — действие вместе со справочным вопросом

Вопрос относится только к выбранному текстовому источнику. Если действие задано старшим источником, нижний текст по-прежнему игнорируется; это правило не пересматривается.

Как обрабатывать «Поменяй назначение на договор Б и расскажи, сколько занимает уточнение»? Вариант А: выполнить подготовку/ФЛК и ответить на вопрос в одном ходе; тогда нужно определить, сохраняется ли новое назначение при сбое справочной части. Вариант Б: попросить разделить задачи и явно определить, что именно из текущего сообщения сохранено, но ещё не применено. Это влияет на число пользовательских шагов и риск незаметного частичного выполнения. Обычное «Уточни назначение на договор Б» без отдельного вопроса уже разрешено M-22 и повторного решения не требует.

Отдельно требуется правило для «Да, отправляйте, и сколько это займёт?» на сводке: считать ли это однозначным согласием с независимым вопросом или сначала ответить и запросить отдельное подтверждение. Пока правило не выбрано, этот составной случай не объявляется принятым сценарием отправки. Прежние запреты согласия в цитате/вопросе и согласия вместе с изменениями сохраняются.

### 15.5. Q-20 — технический сбой второго вызова LLM

Материалы найдены, но генерация справочного ответа завершилась тайм-аутом. Использовать ли для неё те же три попытки всего, что для разбора, или одну попытку без технического повтора? В первом случае повышается шанс получить ответ, но расходуется больше общего deadline; во втором ошибка возвращается быстрее. Технические повторы сохраняют полный промпт и параметры и не разрешают третью уникальную генерацию. Решение об обязательном HTTP 500 после исчерпания обработки ошибки LLM не предлагается отменять; соответствие причины коду и реакция поверхности проверяются по Q-17.

Для чистого вопроса прежняя подготовка сохраняется. Для составного сообщения нужно решить вместе с Q-19, применяются ли уже извлечённые изменения при неуспешной справке и как это явно объясняется в ответе. Нельзя выдать сбой генерации за отсутствие знаний или молча заявить, что весь ход не применён, если часть изменений сохранена. До согласования эта ветвь RAG не считается полностью принятой.
