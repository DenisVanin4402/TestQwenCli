# История этапа 1 POC

История фиксирует выполненную работу по [ADR-015](../../../adr/0015-stage-history-and-agent-responsibilities.md). Проект архитектуры и наличие тестового плана не подтверждают готовность реализации.

## 04.10.2026 — архитектурная подготовка

Пользователь поручил начать этап с отдельным архитектором и исполнителями под управлением одного оркестратора, затем уточнил: до реализации нужен проработанный архитектурный документ. Текущая работа ограничена подготовкой и проверкой этой основы.

| Ответственный | Область |
|---|---|
| `/root` — оркестратор | Постановка задач, согласование областей работы, индекс этапов, история и итоговая проверка документов. |
| `poc_architect` — архитектор | [Архитектура](architecture.md): границы, сценарии, данные, транзакции, FSM, конкуренция, интеграция и задания исполнителям; [заключение](architecture_review.md). |
| `poc_review` — независимый ревьюер | Сверка проекта с действующими ADR и требованиями; проверка существенных гарантий и ограничений. |
| `poc_spec_sync` — исполнитель документации | Синхронизация [требований](requirements.md) и [техспецификации](technical_specification.md) с уже принятыми решениями. |

Выявлены устаревшие положения о самостоятельном локальном POST, входном `InputRequest`/replay, общем deadline исходящей отправки и недостаточной приёмке PostgreSQL. Основа синхронизации — явные уточнения ADR-012/013/018 и действующие ADR-003/017; новые ADR не принимаются. Журнал команд FSM, занятость, проверка владельца и неизменная идентичность corr сохраняются.

Исходное состояние: Maven-каркас из восьми модулей, `AgentApplication`, package-info и профиль `bootstrap`; прикладной код этапа не реализован. Maven и тесты приложения в рамках документационной подготовки не запускаются.

**Результат:** архитектор подготовил архитектурный документ и заключение; исполнитель синхронизировал требования и техспецификацию. Описаны слои и зависимости, ACL/MapStruct, внутренние модели, схема данных, native SSM, атомарный commit, owner/token, повторы corr, аварийные окна и задачи T0–T5 с владельцами. Индекс этапов обновлён. При независимом review уточнены порядок проверки журнала команд, гонка создания сессии, обработка session lock contention и ранняя подготовка сборочной инфраструктуры.

**Проверки:** независимое содержательное review итогового комплекта не выявило блокирующих дефектов. Архитектор сверил native SSM API с локальными артефактами через `javap`. Проверка шести документов, 52 локальных ссылок и шести JSON-примеров прошла без ошибок; `git diff --check` успешен. Код, POM и исходная ACL YAML не менялись.

**Ограничения:** пригодность проекта к реализации не подтверждает runtime. Общий rollback SSM/JPA, PostgreSQL LOB/блокировки и запуск JAR должны быть фактически проверены на T1/T5. Входной replay/конфликт Request-Id ждёт библиотеки; банковский corr, восстановление неизвестного результата, тексты и старые подтверждения сохраняют открытые вопросы. Следующий предусмотренный шаг — реализация по подготовленной архитектуре с ранней проверкой persistence.

## 04.10.2026 — реализация и уточнение хранения

После команды пользователя продолжить назначены исполнители: `poc_persistence` — model/db, `poc_core` — service/api-out, `poc_acl` — api-in/ui-back; оркестратор ведёт POM, common, main и приёмку. Архитектор отдельно проверяет изменения схемы и границ. Ниже сохранены промежуточные результаты; итоговая проверка приведена в следующем разделе.

Пользователь уточнил требования ко всему существующему и будущему коду: самодостаточные русские описания, отсутствие `var` в production Java и пояснения значимых шагов внутри длинных методов и алгоритмов. Уточнения внесены в ADR-011/014 и документы этапа.

Вопрос пользователя об `ExtendedState` выявил лишнее разделение первого прохода: штатный контекст SSM содержал только служебные значения, а данные сценария сохранялись отдельно. Архитектор уточнил ADR-008/009, архитектуру и спецификацию: контекст платежа, текущий черновик, сводка и согласие сохраняются штатным persister. Отдельные журналы команд, отправок и попыток, а также записи владельца нужны для ограничений уникальности и конкурентного доступа.

Ранние проверки: generation трёх OpenAPI выполнена; RED для ядра и адаптеров зафиксирован до реализации. Первый H2 запуск дошёл до миграций, но выявил несовпадение CLOB/VARCHAR в mapping. После уточнения архитектуры отдельный native roundtrip сначала выявил необходимость регистрации типов штатному Kryo; после настройки регистрации прошёл (1 тест). Новая машина восстанавливает UUID, даты/время, сумму, enum и три DTO, включая сводку с native LOB больше 64 КБ. Собственный сериализатор checkpoint не создаётся.

Адресные проверки: service — 16, corr stub/Feign — 5, ACL — 10, helper API — 2 теста без ошибок. Выявлено повторное чтение после отказа NOWAIT; отдельная регрессия прошла RED/GREEN после исправления busy-path. После main RED реализованы wiring, регистрация узла до HTTP-готовности и явные профили БД; `DatabaseProfilesTest` прошёл 4 случая отказа несовместимого запуска.

Новый `SessionPersistenceTest` прошёл 6 случаев на H2: восстановление, журнал команд, общий rollback после native save, ответ без перехода, несовместимость формата, неизменная отправка/попытки и отсечение прежнего запуска. `PocHttpIntegrationTest` прошёл 2 связанных сценария через настоящий HTTP с H2/Liquibase/JPA/SSM: выбор/отмена/согласие/принятие/завершённость и отклонение неверной корреляции/подмены контекста. На этом шаге PostgreSQL, запуск/аварии JVM и итоговый `verify` ещё не выполнялись. Maven-результаты находятся в `target`.

## 04.10.2026 — итоговая проверка реализации

`mvn spotless:apply -q` и `mvn clean verify` завершились успешно. Чистая сборка сгенерировала три API и MapStruct, собрала исполняемый JAR и прошла Spotless. Всего 51 проверка без ошибок и пропусков: H2 persistence/native — 8, service — 17, ACL — 10, corr — 5, helper API — 2, профили и настоящий HTTP — 6, отдельные JVM — 3.

Два аварийных сценария завершили JVM перед внешним эффектом и после принятия запроса до записи ответа. После restart сохранены native контекст, ключ и payload; исполнение помечено прерванным, GET и повторный вход не создают отправку. Отдельный JAR прошёл запуск, сохранение сводки, restart с той же файловой БД и завершение после согласия. В persistence дополнительно проверены откат первого initialize, несовместимые native metadata и сохранение OWNED соседнего узла.

Архитектурное review не выявило блокирующих дефектов слоёв и выбранного хранения. `SessionChanges` удалён: текущие данные сценария находятся в ExtendedState, `TransitionJournal` обслуживает только независимые журналы и права исполнения. Production Java не содержит `var`; описания DTO, enum, методов, OpenAPI и значимых алгоритмов уточнены по требованиям пользователя.

На отдельной локальной PostgreSQL 17 выполнена команда `mvn -o -pl agent-db -am test-compile failsafe:integration-test failsafe:verify -Pintegration-tests '-Dit.test=Postgres*IT' '-Dfailsafe.failIfNoSpecifiedTests=false' -q` с параметрами тестовой БД в `POC_TEST_POSTGRES_*`. Native LOB — 1 проверка, persistence/транзакции/уникальности/NOWAIT/конкурентное initialize — 11: все 12 без ошибок и пропусков. Предшествующая попытка внутри песочницы не дошла до тестов из-за недоступного Maven-кэша; разрешённый запуск вне песочницы прошёл. Ошибки SQL уникальности и NOWAIT в журнале ожидаемы: ими проверяются контролируемые отказы, сами тесты успешны.

**Итог:** реализация и обязательная приёмка POC завершены в согласованном объёме; 51 проверка общей чистой сборки и 12 PostgreSQL-проверок — всего 63. После успешного общего `verify` исходники не изменялись; отдельная PostgreSQL-проверка дополнила приёмку без повторного запуска уже прошедших сценариев.

Согласованные ограничения сохраняются: входная HTTP-идемпотентность ждёт библиотеки; настоящий банковский corr, GA/LLM и разрешение неизвестного банковского результата не входят в этот POC. Логи и XML-отчёты находятся только в `target`.

## 04.10.2026 — отдельный аргумент ключа идемпотентности

Пользователь выявил неверный `keyParameterIndex`: маркер `SessionTurnOrchestrator.handle` ссылался на DTO вместо самого ключа. Архитектор подтвердил такое же замечание для `SsmFsmEngine.initialize/apply`. Оркестратор назначил `poc_core` исправление входной границы и ACL, `poc_persistence` — SPI/реализацию FSM и передачу ключа фасадом; ADR-012, его индекс, архитектура и спецификация уточнены.

Согласованы сигнатуры `handle(input, idempotencyKey)`, `initialize(context, command, idempotencyKey)` и `apply(command, idempotencyKey)` с индексами 1, 2 и 1. ACL составляет ключ `sessionId:requestId` из проверенных канонических UUID, фасад FSM передаёт строковый `commandId`. Собственные AOP или replay не добавляются. Регрессия входной сигнатуры сначала завершилась RED: отдельного String-параметра не было.

## 04.10.2026 — проверка transition Action и общей JPA-транзакции

По уточняющему вопросу пользователя сравнили transition `.action(...)` со state doAction на фактически установленной SSM 4.0.2. В изолированном эксперименте с H2, JpaTransactionManager и штатным persister transition Action работал на исходном потоке с тем же JPA-ресурсом; doAction — на parallel-потоке без транзакции. Проверены commit и принудительный rollback: SQL-запись Action и native-состояние сохранялись либо откатывались вместе. afterCommit, зарегистрированный непосредственно из transition Action, выполнялся только при commit.

Уточнены [документ решений](architecture_simplification_decisions.md) и [sequence](corr_outbox_uss_sequence.md): reactive API не запрещает SQL и transaction synchronization внутри обычного transition Action в проверенной плоской конфигурации. Диагностический исходник размещён только в agent-db/target; production-код, постоянный набор тестов и ADR не менялись. Maven не запускался.
