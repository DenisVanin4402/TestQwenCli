# Требования к этапу 1 POC запроса статуса

**Уточнение этапа UI от 05.10.2026:** исходящие действия передаются suggestions, подтверждение — propose/state CONFIRMATION. GET сессии удалён, внутреннее чтение сохраняется для проверки persistence. Прежние требования UI-восстановления заменены [ADR-020](../../../adr/0020-acl-chat-actions.md).

**Редакция:** 05.10.2026. **Статус:** требования реализованы после согласованного упрощения; результаты и границы проверок приведены в [истории](history.md). Этот текст заменяет прежний POC с журналами команд, попытками corr и состояниями ожидания его результата.

## 1. Назначение и источники

POC показывает подготовку запроса статуса одного платежа, отдельное согласие, вызов операции и завершение агентской сессии. Агент не получает фактический банковский статус и результат внутренних процессов corr.

Основания: [действующие ADR](../../../adr/README.md), [хронология решений пользователя](architecture_simplification_decisions.md), [план рефакторинга](architecture_refactoring_plan.md) и [техническая спецификация](technical_specification.md). План и спецификация актуализированы по итогам обсуждения; [архив](README.md) содержит только прежние варианты. [Исходные требования](base_requirements.md) сохраняют бизнес-контекст и историю AC; старый протокол исполнения не переносится из них в новую реализацию.

Далее следуют [UI](../../02_test_ui/requirements.md), [MVP](../../03_mvp/requirements.md) и [GA](../../04_ga/requirements.md). Проверка stub отдельно от готовности реальных интеграций.

## 2. Объём

Входит: только STATUS, усечённый ACL 1.6, helper GET, SSM с native JPA persister, сохранение/восстановление сессии, семафор, отдельное согласие, временный WorkflowManager с одним вызовом corr, локальные шаблоны ответа вне FSM.

Не входят: рабочие RECALL/DETAILS, LLM/RAG, полная поверхность GA, журналы/история действий, outbox/УСС, повторы corr, callback или поздний ответ менеджера, миграция старых данных. Входная библиотека идемпотентности не подключена; маркер не обеспечивает runtime replay.

## 3. Исходные данные и подготовка

Первому допустимому входу нужны epkId, digitalUserId и семь полей платежа: paymentId, paymentNumber, paymentDate, amount, currency, recipientName, organizationName. Организация/пользователь поступают из ACL metadata, поля платежа — из additional_info. Синтетические данные локального профиля не доказывают реальные банковские полномочия. FixtureId и каталог UI не проникают в ядро.

Сессия определяется Gigachat-Session-Id, вход — Request-Id, совпадающим с message.reply_with; conversation_id служит внешней корреляции. Последующие пропуски контекста дополняются из сохранённых данных под блокировкой. Явно переданные значения сверяются с привязкой; подмена её не перезаписывает.

Подготовка содержит снимок данных, идентичность и согласие именно на неё. В ExtendedState сохраняются предметные данные и последний предметный результат; готовая сводка, templateId и ACL-ответ не сохраняются. Новая подготовка требует нового согласия. OperationContext утверждён в ADR-006; для STATUS changes отсутствует.

## 4. Бизнес-поведение

| Требование | Действующее поведение |
|---|---|
| POC-БТ-01 — подготовка | Первый request/status с полным контекстом создаёт отсутствующую FSM и подготовку за один рабочий ход; повторный выбор не запрашивается. Другие операции не подменяются статусом. |
| POC-БТ-02 — согласие | Выбор не является согласием. В ожидании подтверждения допустимы только подтверждение и отказ. Повторный выбор status отклоняется без изменения подготовки и без отправки операции. |
| POC-БТ-03 — отказ | Отказ очищает подготовку и возвращает выбор. Новый выбор status после отказа создаёт новое предложение, требующее отдельного согласия. Исходная принадлежность сохраняется. Самостоятельной команды перезапуска нет. |
| POC-БТ-04 — операция | Подтверждающий Action один раз вызывает void WorkflowManager с operationId и подтверждённым контекстом. Нет внутреннего commandId, журнала и агентских повторов. |
| POC-БТ-05 — завершение | Успешное выполнение Action и commit дают COMPLETED. Новые операции в той же сессии запрещены. Это не возврат фактического статуса платежа или результата банковского процесса. |
| POC-БТ-06 — ошибка | Любая ошибка Action откатывает все локальные изменения хода, включая native FSM. Ответ об ошибке готовится после rollback. Штатный отказ guard не запускает corr. |
| POC-БТ-07 — неопределённый внешний эффект | Corr мог выполниться до локального сбоя. Ошибка не утверждает «операция точно не выполнена»; нет автоматического retry, SUBMIT_UNKNOWN или ожидания corr-result. Риск временно принят. |
| POC-БТ-08 — конкуренция/восстановление | Постоянный семафор, рабочий FOR UPDATE NOWAIT, SESSION_BUSY без очереди. После сбоя инициализации следующий допустимый вход использует семафор и создаёт отсутствующую FSM. |
| POC-БТ-09 — бездействие | Бездействие/закрытие страницы не подтверждают, не отменяют и не отправляют операцию. GET не выполняет переход. |

По согласованной task01 сводка показывает операцию и её подтверждаемые поля: для STATUS — номер платежа. В state CONFIRMATION возвращаются paymentNumber и служебный preparationNo; полный доверенный контекст остаётся на сервере. SessionTurnOrchestrator вызывает renderer после транзакции по возвращённому снимку. Тексты остаются проектом T-C01 до предметного утверждения.

## 5. Состояния и переходы

SSM guards/actions — единственное место выбора перехода. Адаптер передаёт намерение, оркестратор не вычисляет targetState.

| Состояние / вход | Результат |
|---|---|
| Нет native FSM; корректный первый status | Создать CHOOSING_REQUEST_TYPE и выполнить выбор → AWAITING_CONFIRM. |
| CHOOSING_REQUEST_TYPE; status | Подготовка → AWAITING_CONFIRM. |
| AWAITING_CONFIRM; request с status | 400/failure, недопустимое событие; состояние и подготовка сохраняются, corr не вызывается. |
| AWAITING_CONFIRM; accept_propose | Проверить согласие/данные, один WorkflowManager, после успешного commit → COMPLETED. |
| AWAITING_CONFIRM; reject_propose | Очистить подготовку → CHOOSING_REQUEST_TYPE. |
| Любое состояние; request с удалённым restart_status | 400/failure на входной границе, без изменения FSM и вызова corr. |
| CHOOSING_REQUEST_TYPE; reject_propose | Нет активной подготовки, без отправки. |
| Нет актуального предложения; accept_propose | Контролируемый отказ без corr. |
| COMPLETED; новый пользовательский ход | Ошибка завершённой сессии; нового перехода/операции нет. |
| Ошибка Action | Rollback, остаётся последнее закоммиченное состояние. |
| Семафор занят | SESSION_BUSY; конкурентный Action не запускается. |

SUBMITTING, AWAITING_RETRY_CONFIRM, SUBMIT_UNKNOWN, RETRY_YES/NO и SUBMIT_ACCEPTED/REJECTED/UNCERTAIN сняты. Они не являются будущими обязательными состояниями или событиями.

## 6. Ответ и гарантии

После commit оркестратор формирует содержание, адаптер — ACL. Успешный финал: HTTP 200, content.status_code="200", performative=inform, metadata.final_message=true. Завершается агентская сессия. Основания — [коды](../../../api/error_codes.md) и [ACL 1.6](../../../api/api_contract_details_1.6.md).

Транзакция не включает формирование/доставку внешнего ответа. Сбой ответа после commit не запускает повтор Action. Временный прямой corr выполняется до commit и GA; rollback его не отменяет. Передача ответа GA считается доставкой клиенту, однако порядок «ответ перед corr» относится к будущему полноценному менеджеру.

## 7. Приёмка и трассировка прежних пунктов

Реализованный путь описан в [C4](c4_architecture.md); выполненный план перенесён в [архив](README.md). Заменённый код подлежит физическому удалению. Минимальные TDD, HTTP, PostgreSQL, native LOB/rollback и JAR-проверки заданы ADR-017; приложение не собирается ради правки документации.

| Прежние сценарии/строки | Статус после пересмотра |
|---|---|
| UC-01, UC-02, UC-05, UC-07, UC-10 | Сохраняются: подготовка/согласие, отказ, восстановление, busy и недопустимое намерение — по новой матрице §5. Самостоятельный перезапуск STATUS удалён по решению пользователя. |
| UC-03, UC-09 | Сняты ветви новой подготовки после corr-result. Обычный отказ и новый выбор после него остаются. |
| UC-04 / P-18 | Входной replay/conflict отложен до библиотеки; не считается проверенным. |
| UC-06 | Проверка ошибки одного вызова и rollback, без повторов и SUBMIT_UNKNOWN. |
| UC-08 | Заменён проверкой семафора после сбоя и восстановления последнего commit. Гарантии восстановления банковского исхода нет. |
| P-01–P-21 в прежней матрице | Заменены матрицей §5; внутренние результаты, command replay и retry-ветки не являются AC новой реализации. |
| Исходные AC о сохранности, согласии, busy, terminal | Сохраняются в применимой STATUS-части с новой границей транзакции. |
| Исходные AC о журналах, попытках/сверке corr, owner/revision | Сняты с агента; работа будущего менеджера — отдельная задача. Общая exactly-once при HTTP-повторе не заявляется. |

## 8. Оставшиеся внешние зависимости

Реальный corr-контракт и поле operationId, предметные тексты, подключение входной библиотеки, полный GA и внутренний протокол Outbox/УСС требуют своей интеграции. Они не блокируют документацию/рефакторинг POC со временным STATUS-адаптером и не разрешают возвращать удалённую функциональность. Старый Q-05 о восстановлении corr внутри агента закрыт передачей ответственности менеджеру.
