## 1. Назначение и границы

Чат позволяет аналитику пройти POC статуса тестового платежа: выбрать действие, проверить сводку, подтвердить либо отклонить и увидеть результат. HTML/CSS/JavaScript находятся в agent-ui; серверные маршруты и каталог — в agent-ui-back. Вычисление FSM, полномочий, ФЛК, corr и банковского результата остаётся на сервере.

Базовый запуск локальный, с синтетическими данными. Аккаунты, административная панель, полноценный GA и свободный текст относятся к последующим этапам. WorkflowManager не возвращает бизнес-результат; успешный commit завершает сессию, ошибка не доказывает отсутствие внешнего эффекта.

## 2. Требования к экрану

### UI-БТ-01. Платёж и новый диалог

Карточка показывает организацию, номер, дату, сумму, валюту и получателя серверного fixture. Начальные саджесты приходят с каталогом в формате ACL. Пользователь не вводит доверенные epkId/digitalUserId.

«Новый диалог» создаёт новый UUID, но не отменяет внешнее действие старого и не является безопасным повтором после потери ответа.

### UI-БТ-02. Чат и корреляция

Действия пользователя и ответы приложения выводятся последовательно. Только последний актуальный ответ содержит действующие кнопки; старая история не интерактивна. Поздний ответ A не меняет сообщения, кнопки и занятость нового диалога B. Ответ проверяется по conversation_id и in_reply_to.

Внизу есть текстовое поле и кнопка «Отправить». Пока ввод текста вызывает локальное пояснение об отсутствии поддержки, без HTTP-вызова. Набранное согласие не заменяет кнопку подтверждения.

### UI-БТ-03. Действия ACL

Выбор операции отображается из suggestions: text задаёт подпись, action_code передаётся в message.content, display_mode задаёт вид BUTTON/CLASSIC. Поддерживается status. После отказа сервер возвращает новый саджест выбора.

Propose запрашивает согласие: по task06 UI показывает «Подтвердить»/«Отклонить» только при наличии явных серверных саджестов и отправляет accept_propose/reject_propose. Один performative не создаёт кнопки. Терминальный ответ и техническая ошибка не оставляют действий; предметный INVALID_COMMAND может содержать навигацию. Нет retry corr, restart_status и локальной таблицы бизнес-доступности.

### UI-БТ-04. Сводка

Содержание сводки и подтверждаемые реквизиты формирует агент; state содержит параметры CONFIRMATION. По согласованной архитектуре [task01](../../tasks/task01/arch_design.md) STATUS согласует paymentNumber и возвращает общий служебный preparationNo. UI передаёт оба поля при accept_propose; сервер проверяет их по активной подготовке. Свой набор задаётся для каждой операции программно. reject_propose этого набора не требует и не отменяет банковский платёж. Для локального профиля сводка приходит готовым текстом в content.result; регистрация шаблонов GA не заявляется.

Текст ответа и реквизиты выводятся безопасно, без выполнения HTML. Null, отсутствующие значения и незаполненные шаблонные выражения не показываются.

### UI-БТ-05. Обработка

Во время запроса показывается ожидание, повторный клик не создаёт дополнительного POST. Новый диалог не прерывает уже выполняющийся серверный ход. Нет скрытой очереди сообщений.

### UI-БТ-06. Ошибки доставки

Читается тело HTTP-ошибки, включая content.reason при 500. Сетевой сбой означает, что результат не получен, а запрос мог быть выполнен. Нет автоматической повторной доставки и отдельного GET результата.

### UI-БТ-07. Перезагрузка и закрытие

История живёт только на странице. Перезагрузка открывает новый локальный диалог без POST; старая серверная сессия не восстанавливается через браузер. Закрытие страницы не отправляет отказ. Это заменяет прежнее требование GET-восстановления по поручению пользователя.

### UI-БТ-08. Диагностика

Явно показан режим stub/real. Компактный блок содержит sessionId, requestId и HTTP-код без секретов. Универсальной настройки интеграций на экране нет.

## 3. Обмен

- GET /local-api/v1/fixtures — единственный вспомогательный API: платёж, metadata, код агента, режим и начальные suggestions.
- POST /local-api/api/v1/ai/agents/{agent_code} — зеркало ACL в agent-ui-back.
- Основной POST /api/v1/ai/agents/{agent_code} использует тот же контракт и адаптер; браузер обращается к зеркалу.
- GET сессии удалён. AvailableCommands/projectionVersion не являются UI-протоколом.

Каждый клик получает новый Request-Id, равный reply_with. Состояние интерфейса строится из ACL-ответа. Входящий state не заменяет сохранённые на сервере реквизиты.

## 4. Сценарии и приёмка

| Сценарий | Результат |
|---|---|
| UI-UC-01 — статус | Саджест → propose/сводка → отдельное согласие → финальный inform. |
| UI-UC-02/03 — отказ и новый выбор | Отказ → inform с suggestions → новый propose без старого согласия. |
| UI-UC-04 — двойной клик | Один POST; только актуальные кнопки активны. |
| UI-UC-05 — потеря ответа | Понятная неопределённость; ни GET, ни повторного POST. |
| UI-UC-06 — перезагрузка | Новый диалог без автоматического бизнес-входа. |
| UI-UC-07 — свободный текст | Пока только локальное пояснение; обработка появится в MVP. |
| UI-UC-08 — поздний ответ | Ответ старого диалога не меняет новый. |
| UI-UC-09 — небезопасный текст | Разметка показывается как данные, а не элементы управления. |

UI.1–UI.3 включают текущий чат, действия, ошибки и защиту доставки. UI.4 — расширение MVP. Минимум проверок: HTTP обоих входов и отсутствие удалённого API, клиентские тесты доставки и ручная проверка чата в браузере. Полный архив и backend-журнал не требуются.

Общий стенд, зарегистрированные коды/шаблоны GA и окончательные продуктовые тексты остаются отдельными вопросами, не блокирующими локальный тестовый профиль.

Поведенческие требования task01 проверены автоматизированно при реализации [task02](../../tasks/task02/tasks.md): одинаковый допуск/отказ основного ACL и зеркала, отсутствие внешнего вызова при неверном согласии и точный возврат state браузером. Ручная проверка чата и независимая валидация task02 отмечаются отдельно по фактическому результату.
