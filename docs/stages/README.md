# Этапы реализации invest-pro

06.10.2026 выбран вариант A [task05](../tasks/task05/arch_design.md): справка поверх STATUS по полному тексту знаний во втором LLM-вызове, вне транзакции; составной ввод разделять, справку выполнять одной попыткой. На confirmation свободный ввод запрещён. [Знания](../tasks/task05/knowledge.md) и [промпты с вопросами](../tasks/task05/prompt_design.md) подготовлены для обсуждения. Полнота MVP остаётся отдельно; к дизайну реализации и задачам пока не переходили.

05.10.2026 выбрана архитектура A [task04](../tasks/task04/arch_design.md): текстовый выбор STATUS через GigaChat до транзакции и прямое шаблонное уточнение без FSM при отсутствии команды. JSON-модель, YAML-промпты и прогон до 10 сообщений с TP/TN/FP/FN входят в доработку. [Дизайн](../tasks/task04/impl_design.md) и [задачи](../tasks/task04/tasks.md) согласованы; реализация проходит проверку. Извлечение реквизитов и RAG остаются будущими расширениями.

05.10.2026 пользователь выбрал вариант A [task03 — реальный клиент GigaChat через Spring AI](../tasks/task03/arch_design.md): штатная автоконфигурация в текущем этапе POC/тестового UI. [Дизайн реализации](../tasks/task03/impl_design.md) и [задачи](../tasks/task03/tasks.md) явно согласованы 05.10.2026. Клиент реализован, [приёмка и независимая валидация](../tasks/task03/validation.md) завершены; последующее решение task04 добавляет текстовый выбор STATUS.

05.10.2026 начата [task02](../tasks/task02/arch_design.md): прямое использование SSM и сокращение внутренних моделей без потери поведения. Дизайн реализации и задачи согласованы; выполняются реализация и проверки с сохранением отдельных guards/actions.

Каждая папка содержит требования своего этапа. Подэтапы и открытые вопросы находятся внутри соответствующего документа; технические спецификации размещаются рядом с требованиями по мере подготовки.

Новые короткие доработки регистрируются отдельно в [docs/tasks](../tasks/tasks.md): варианты архитектуры → выбор → дизайн реализации и задачи → явное согласование обоих документов → реализация → проверка отдельным валидатором-архитектором. Документы этапов сохраняют требования и актуализируются при принятии затрагивающих их решений.

На 05.10.2026 код и схема БД POC переработаны по действующим ADR: один путь FSM/WorkflowManager, удаление старого runtime, ответ после commit. [План](01_poc/old/architecture_refactoring_plan.md) и [спецификация](01_poc/old/technical_specification.md) возвращены из архива и уточнены по итогам обсуждения; [хронология решений](01_poc/old/architecture_simplification_decisions.md) сохраняет основания рефакторинга. В [архиве](01_poc/old/README.md) остаются прежнее ревью и схема будущего corr/Outbox. [Ревью кода и исправления](01_poc/old/code_smells_review.md) фиксирует согласованные замечания, а [история этапа](01_poc/old/history.md) — фактические результаты и ограничения приёмки. Исходные AC отменённых corr/replay/owner-веток сохраняются как историческая трассировка, не как будущий объём реализации.

Общий источник и история решений сохранены в [основных требованиях](01_poc/old/base_requirements.md). Принятые технические ограничения — в [индексе ADR](../adr/README.md). Полное распределение исходных критериев приёмки и переходов находится в §11 документа этапа GA.

Требования определяют поведение и границы этапа; архитектура закрепляет ответственность слоёв, данные и гарантии выполнения, а техническая спецификация уточняет контракты и приёмку. Наличие документа не означает готовности кода. Несогласованные внешние контракты и продуктовые решения сохраняют открытый статус; локальный контракт прототипа не заменяет контракт банка.
