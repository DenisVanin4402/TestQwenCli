## Критерии приёмки

| AC | Проверяемый результат | Работы |
|---|---|---|
| AC1 | request/accept_propose/reject_propose явно отображаются в SELECT/CONFIRM/CANCEL; выбор операции — из каталога, CONFIRM — из подготовки. | T1, T2, T5 |
| AC2 | STATUS возвращает ровно paymentNumber + preparationNo; один источник схемы используется при подготовке и сравнении. | T3, T5 |
| AC3 | Старое/искажённое/неполное согласие не меняет подготовку и не вызывает WorkflowManager. | T3–T5 |
| AC4 | Несколько guards исполняются последовательно до первого отказа; action вызывается SSM после всех проверок. | T2–T4 |
| AC5 | Общие guards в guard.common, actions отдельно; вся их логика в определяющих классах. | T3, T7 |
| AC6 | Новый набор существующих полей задаётся регистрацией; нет второго движка, EventChecks и веток конкретной операции в инфраструктуре/mapper. | T2, T3, T7 |
| AC7 | Номер монотонен в сессии, переживает CANCEL и restart; old format не принимается за новый. | T4, T6 |
| AC8 | Сохранены транзакция, блокировки, rollback, один lifecycle FSM и отсутствие retry. | T4, T7 |
| AC9 | Оба ACL-входа одинаковы; UI возвращает state, не решает бизнес-правила; только fixture вне контракта. | T5, T6 |
| AC10 | Есть явные согласования, необходимые проверки и отдельная независимая валидация плана/факта. | Согласование, T7 |
