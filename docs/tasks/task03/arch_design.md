# Task03. Реальный клиент GigaChat через Spring AI

**Дата:** 05.10.2026. **Статус:** Завершена.

## Запрос и принятые ограничения

Пользователь поручил добавить реального клиента GigaChat через Spring AI в текущий этап POC/тестового UI. Выбор библиотеки закреплён [ADR-001](../../adr/0001-outbound-clients-and-stubs.md). **05.10.2026 выбран вариант A; затем пользователь явно согласовал impl_design.md и tasks.md: «подтверждаю, можно релаизовывать».** Приняты штатная автоконфигурация и описанные ниже границы клиента.

## Исходное состояние до task03

**Уточнение пользователя 05.10.2026:** Authorization Key и поле AccessToken размещаются в локальном `.env`. Пользователь выбрал «Authorization Key → OAuth; AccessToken не используется». SDK получает/обновляет токен в памяти; запись токена в файл и авторизация готовым токеном не реализуются. По отдельному запросу уже подготовлены `.env`, `.env.example`, исключение из Git и инструкция штатного импорта. Это не согласование реализации самого клиента.

- [Parent POM](../../../pom.xml) задаёт Java 21, Spring Boot 3.5.15, Spring AI 1.1.2 и GigaChat starter 1.1.2. [agent-api-out](../../../agent-api-out/pom.xml) уже подключает starter.
- [Пакет gigachat](../../../agent-api-out/src/main/java/ru/sberbank/pprb/agent/gigachat/package-info.java) содержит только описание будущего адаптера. Клиента приложения и вызова модели нет.
- [application.yaml](../../../agent-main/src/main/resources/application.yaml) и [application-bootstrap.yaml](../../../agent-main/src/main/resources/application-bootstrap.yaml) исключают `GigaChatAutoConfiguration`.
- Текущий ACL принимает явные действия; текст в UI вызывает локальное пояснение. Операционные ответы формируются шаблонами. Это зафиксировано в [требованиях](../../requirements/requirements_current.md) и [спецификации](../../requirements/technical_specification_current.md).
- Рабочее дерево содержит изменения task01/task02; эта доработка не закрывает их приёмку.

## Принятые границы

Добавить работоспособный синхронный клиент: передача system/user сообщений, получение текста, настройки модели, доступа и тайм-аутов, явное включение реального режима и проверка фактического запроса. Использовать штатные `ChatModel`/`ChatClient` Spring AI; не создавать собственный HTTP/OAuth-клиент.

Клиент размещается в `agent-api-out`, настройки запуска — в `agent-main`. В обычном локальном запуске и bootstrap модель не создаётся и credentials не нужны. Включение GigaChat независимо от профиля БД и режима corr. Ошибочная конфигурация включённого клиента останавливает запуск, без скрытого перехода на заглушку. Секреты поступают извне; TLS проверяется, тайм-ауты конечны.

Принятый объём — клиент, доступный для вызова из Java, и явно запускаемый интеграционный smoke. Новый HTTP endpoint, изменение UI/ACL, распознавание намерений, память диалога, RAG, tools и влияние LLM на FSM в него не входят. Это требует отдельного расширения объёма, если пользователь ожидает сразу текстовый диалог. Модель по умолчанию — предусмотренная ADR-007 GigaChat Ultra; конкретный идентификатор задаётся конфигурацией и проверяется при реальном smoke.

## Варианты подключения

| Вариант | Устройство | Отличия |
|---|---|---|
| **A — штатная автоконфигурация, принят** | Явный режим включает библиотечную автоконфигурацию GigaChat и создаёт `ChatClient` на её chat-модели. Неиспользуемые возможности отключены. | Меньше собственного wiring, библиотека управляет авторизацией и транспортом. Для SDK 1.1.2 уточнена необходимость удаления безусловного определения embedding-bean до инициализации; подробнее в impl_design.md. |
| B — явная конфигурация библиотечных компонентов | Автоконфигурация GigaChat остаётся исключённой; условная конфигурация приложения создаёт библиотечные API/model и `ChatClient`. | Точечный контроль создаваемых компонентов, но больше кода и привязки к конструкторам SDK. HTTP и обновление токена всё равно выполняет библиотека. |

**Принят вариант A.** Он использует уже подключённый starter и соответствует требованию минимального кода. Отдельный прикладной порт и обёртка только для перенаправления `prompt → response` сейчас не нужны; контракт структурированного разбора появится вместе с его потребителем. Вариант B оставлен для сравнения и не реализуется.

Для этой технической интеграции принят один запрос генерации без автоматических повторов. Политика ADR-007 «исходный вызов + два повтора» относится к будущему структурированному разбору; она не переносится на corr. При подключении разбора потребуется единый бюджет попыток без умножения библиотечных и прикладных retries.

## Совместимость и вопросы для дизайна реализации

[Документация библиотеки](https://github.com/ai-forever/spring-ai-gigachat#совместимость-версий-и-ветки) разделяет линейки: 1.1.x для Boot 3.4/3.5 и Spring AI 1.x; 2.x для Boot 4 и Spring AI 2.x. Предлагается сохранить закреплённые версии проекта. Это проверка заявленной совместимости, а не результат сборки интеграции.

При подготовке [дизайна реализации](impl_design.md) прочитаны metadata и API локальных JAR 1.1.2: условия автоконфигурации, настройки TLS/тайм-аутов, получение и обновление токена, retry и синхронный advisor. Это статическая проверка библиотеки, не выполненные интеграционные тесты. Для первого подключения используется Authorization Key и настраиваемый scope; корпоративный mTLS не входит в задачу. Ключи в документы и репозиторий не помещаются.

## Критерии приёмки

1. Включённый клиент вызывает GigaChat через Spring AI и возвращает непустой текст для синтетического запроса. Реальный smoke запускается отдельно с внешними credentials; без него реальная связность не считается проверенной.
2. Контрактная проверка с локальным HTTP-сервером подтверждает библиотечный обмен авторизации/генерации, передачу сообщений и настроек; мок одного `ChatClient` не заменяет эту проверку.
3. HTTP-ошибка, timeout и пустой ответ не становятся успешным результатом или ответом заглушки. Один вызов генерации не вызывает скрытые повторные генерации; получение токена учитывается отдельно.
4. При выключенной интеграции локальный POC и bootstrap запускаются без credentials и запросов к GigaChat. При включённой — обязательные настройки проверяются при запуске.
5. Профили БД и corr сохраняют независимость; явные ACL-действия выполняются без LLM. Поведение подтверждения, FSM и шаблонных ответов сохраняется.
6. В README описаны включение, настройки, доверие TLS и запуск smoke. Код, YAML и диагностические сообщения не раскрывают ключи/токены.

## Результат

Согласованные [impl_design.md](impl_design.md) и [tasks.md](tasks.md) выполнены; фактические проверки и ограничения отмечены в tasks.md. Технический клиент перенесён в текущий этап, текстовый разбор остаётся отдельной работой. Независимая [валидация](validation.md) пройдена.
