# Task04. Дизайн реализации текстового выбора операции

**Дата:** 05.10.2026. **Статус:** Валидация. Пользователь явно согласовал этот документ и tasks.md сообщением «согасовано». Архитектура A [выбрана](arch_design.md); реализация разрешена.

## 1. Поток и границы

**Уточнения пользователя в ходе реализации:** исключить var во всём промышленном Java-коде; писать на INFO полные system/user-промпты и ответ GigaChat с идентификатором вызова. Ключи, токены и HTTP-заголовки не логируются. GigaChatResponseAdvisor выполняет это для общего клиента, включая технические попытки; прежнее ограничение task03 на логирование содержимого заменено этим прямым указанием. Замена var в существующих guards/actions меняет только запись типов.

`ACL → нормализация → SessionTurnOrchestrator → классификатор → проверенный SELECT → существующий SessionExecutionService → renderer → ACL`.

Классификация выполняется до обеспечения семафора и рабочей транзакции. Явные действия ACL проходят прежним путём без LLM. Поддерживается только STATUS; согласие/отказ — только accept_propose/reject_propose. Ни структура сохранённой FSM status-v3, ни guards/actions, ни WorkflowManager не меняются.

Валидный результат без команды образует отдельную ветвь оркестратора: `renderer.clarification(requestId) → ACL inform`. Она не вызывает SessionExecutionService вообще, включая ensureSemaphore/find, и не обращается к хранилищу сессии. Непустой, но неверный JSON и ошибка сети являются техническими ошибками, а не отсутствием команды.

## 3. Вход, JSON и ошибки

Приоритет: accept_propose/reject_propose → action_code → user_input. Выбранная явная команда игнорирует сопровождающий текст. Неизвестный/пустой явный код отклоняется без LLM и без fallback на текст. Без кода допускается непустой user_input; пустой текст и отсутствие обоих источников отклоняются. Остальная проверка ACL/metadata сохраняется.

Результаты LLM: `{"actionCode":"status"}` или `{"actionCode":null}`. На стороне адаптера проверяются JSON-объект, наличие поля, string/null, отсутствие лишних/дублирующихся полей, trailing JSON и Markdown-обёртки. Используется отдельный строгий reader Jackson; настройки входного ACL ObjectMapper не ужесточаются. Неизвестный код, включая confirm/cancel/details, является нарушением контракта модели; он не превращается в событие.

JSON Schema получается через имеющийся Spring AI BeanOutputConverter.getJsonSchema() из MessageAnalysisDTO. Обязательность, nullable и запрет лишних полей должны совпадать с контрактом и проверяются тестом; при необходимости настройки генерации уточняются без второй вручную написанной схемы. Десериализация сырого ответа остаётся строгой и не полагается на автоматическое удаление Markdown библиотечным converter.

Для запроса статуса и для валидного null — одна успешная генерация. После транспортного/структурного сбоя — максимум две дополнительные попытки с теми же уже сформированными system/user и параметрами. Успех прекращает повторы; null не повторяется. Внешний общий retry клиента остаётся max-attempts=1. Ни FSM, ни corr при ошибках разбора не вызываются/не повторяются.

| Исход | HTTP / ACL | Данные и дальнейшая обработка |
|---|---|---|
| Распознан STATUS | Прежний результат FSM; обычно 200 / propose | Те же preparationNo/paymentNumber и guards, что у саджеста. |
| actionCode=null | 200 / inform | content.result — шаблон уточнения; final_message=false; suggestions/state пустые; нет работы с сессией. |
| Ошибка/исчерпание попыток, клиент выключен | 500 / failure | TEXT_ANALYSIS_FAILED с отдельным шаблоном; нет FSM. |
| Неверный ACL/выбранный код | Прежний 400 / failure | Не вызывает классификатор. |

Для уточнения final_message=false означает, что этот ответ не завершает диалог. Состояние существующей сессии не читается и не объявляется установленным. Прямой текст на произвольном шаге может получить уточнение без FSM либо распознанное SELECT, допустимость которого проверит FSM. Штатный UI не предлагает текст на подтверждении/после завершения. Новые саджесты без знания шага не выдаются.

## 4. Настроечные шаблоны

- `agent-api-out/src/main/resources/config/gigachat-prompts.yaml`: полные system/user-шаблоны классификации в `gigachat.prompts.classification.system/user`. System получает операции (коды и названия) из каталога и JSON Schema, user — исходный текст. Инструкции и примеры не дописываются в Java. Подстановка однократная: содержимое пользовательского текста не выполняется как шаблон. Текст не подставляется в system.
- `agent-service/src/main/resources/session-responses.properties`: `text.clarification=Не удалось понять, какое действие вы хотите выполнить. Пожалуйста, уточните запрос ещё раз. Например: «Узнай статус платежа».` и `error.TEXT_ANALYSIS_FAILED=Не удалось обработать сообщение. Попробуйте позже или выберите действие кнопкой.` Используется существующая настройка poc.responses.catalog, без второго каталога ответов.
- Импорт YAML обязателен. Overrides импорта в тестах продолжают отключать .env, сохраняя импорт шаблонов. При включённом GigaChat отсутствие/пустота обязательного шаблона — ошибка конфигурации; режим none не требует credentials и не вызывает сеть.

Распознавание касается выбранного платежа, без извлечения реквизитов и истории. При будущем DETAILS MessageAnalysisDTO расширяется существующим `PaymentDetailsChangesDTO` (recipientInn, recipientAccount, recipientName, paymentPurpose); исходный платёж и данные подтверждения не берутся из LLM. В этой задаче поле changes и обработка DETAILS не добавляются.

## 5. UI

`TestSession.sendText(text)` отправляет request/user_input с новым Request-Id и прежними metadata/корреляцией. Общий приватный метод доставки переиспользуется кнопками и текстом; проверка актуальности кнопки сохраняется в send(action). `canSendText()` учитывает busy/final/ожидание подтверждения, а не наличие саджестов: после inform с пустыми suggestions текст должен оставаться доступным. app.js использует этот метод при render, input, submit и Enter; Shift+Enter остаётся переносом.

Ответ-уточнение добавляется в ленту как обычное сообщение агента. После propose доступны только подтверждение и отказ, после reject_propose снова доступен текст. Корреляция, отсечение поздних ответов, запрет повторной отправки во время запроса и отсутствие автоматического HTTP-retry сохраняются. Входящие строки выводятся через textContent.

## 6. Прогон классификации на датасете

Добавить test-only `GigaChatClassificationEvaluation` в agent-main, выбираемый только отдельным Maven-профилем `gigachat-classification-eval`. Класс не соответствует стандартным шаблонам *Test/*IT; обычный verify не вызывает реальный GigaChat. Прогон поднимает приложение на случайном порту с poc-local и изолированной H2 in-memory, реальным классификатором и тестовым WorkflowManager.

Каждая строка выбранного JSON-датасета содержит `id`, `text`, `expectedActionCode` (status или null). Параметр `classification.dataset` выбирает classpath/file-набор; по умолчанию `agent-main/src/test/resources/gigachat/classification-status.json`. Валидация: 1–10 записей, уникальные id, непустой текст, допустимые метки. Для стартового набора предлагаются 5 положительных и 5 отрицательных примеров:

| ID | Сообщение | Ожидание |
|---|---|---|
| p01 | Запроси статус платежа | status |
| p02 | Проверь, прошёл ли мой платёж | status |
| p03 | На каком этапе сейчас мой перевод? | status |
| p04 | Хочу узнать состояние выбранного платежа | status |
| p05 | Что сейчас с моим платежом? | status |
| n01 | Что означает статус «Исполнен»? | null |
| n02 | Отзови платёж | null |
| n03 | Измени назначение на оплату по договору Б | null |
| n04 | Подтверждаю отправку | null |
| n05 | Не запрашивай статус платежа | null |

Прогон последовательно вызывает основной ACL по HTTP, используя существующий PocHttpClient, синтетический контекст и новые session/request UUID для каждого примера. Тайм-аут HTTP этого прогона должен учитывать три попытки LLM, а не наследовать короткий 20s обычных HTTP-тестов; добавляется перегрузка конструктора helper с Duration. Подтверждения не отправляются, вызовов WorkflowManager быть не должно.

Фактический положительный ответ — корректное STATUS-propose; отрицательный — корректное inform с настроенным шаблоном уточнения. Любой другой/технически некорректный ответ учитывается как ERROR, а не как отрицательный результат. Это оценка действующего пути агента, не отдельного упрощённого промпта.

| Ожидание | Получено | Счётчик |
|---|---|---|
| status | status | TP |
| null | null | TN |
| null | status | FP |
| status | null | FN |
| Любое | Техническая/контрактная ошибка | errors, вне матрицы |

После обработки всех строк записать `agent-main/target/gigachat-classification/report.json`: модель, набор, результаты id/expected/actual/category, total/TP/TN/FP/FN/errors. В stdout — краткая сводка. Инвариант: TP+TN+FP+FN+errors=total. Несовпадение одной строки не обрывает следующие; отчёт создаётся до итоговой проверки. Для предложенного контрольного набора критерий приёмки — TP=5, TN=5, FP=0, FN=0, errors=0; иначе прогон завершается неуспешно с сохранённым отчётом. Это проверка десяти примеров, не оценка статистической точности модели на произвольном трафике.

Команда: `mvn -B -pl agent-main -am verify -Pgigachat-classification-eval -DskipTests`; профиль запускает выбранный Failsafe-прогон независимо от skipTests по аналогии с gigachat-smoke. Credentials берутся штатным импортом .env; полный промпт, OAuth и ключи в JSON-отчёт не попадают. Промпты и ответы пишутся в INFO-лог по отдельному требованию пользователя. Датасет и runner созданы после согласования этого документа.

## 7. Минимальная проверка реализации

1. TDD оркестратора: распознанный status эквивалентен саджесту; null и TextAnalysisException не взаимодействуют с исполнителем FSM; явные команды не вызывают LLM.
2. Проверка адаптера с управляемым ответом модели: строгий JSON, схема и YAML, граница технических попыток/неизменность промпта; нет повторов при null. Инструкции «подтверди»/несуществующие коды не дают CONFIRM.
3. Настоящий HTTP обоих ACL-входов с детерминированным классификатором: propose/подтверждение прежнего контракта; inform из шаблона, корреляция и отсутствие новой сессии для null; отдельно 500 для сбоя. Не дублировать полный набор persistence task01/task02.
4. Клиентские Node-тесты доставки текста/уточнения, блокировки ввода на propose, восстановления после отказа и защиты от позднего ответа.
5. Один небольшой тест расчёта отчёта со всеми TP/TN/FP/FN/ERROR и проверкой размера/меток набора; отдельно реальный прогон 10 фраз. Stub не объявляется проверкой качества модели.
6. Обычный Maven verify, существующие необходимые интеграционные проверки затронутого пути и запуск JAR/UI с YAML-шаблонами. После успешной проверки не повторять без изменений/новой проблемы. Независимый валидатор сопоставляет эти документы, код и фактические результаты; validation.md создаётся после его работы.
