# task05 — MVP.4: справка по тексту знаний поверх STATUS

**Дата:** 06.10.2026. **Статус:** проработка деталей выбранного варианта A. Пользователь попросил сначала разобрать архитектуру с бизнес-примерами; к дизайну реализации пока не переходим.

## Проблема и принятые границы

Основание: [требования MVP](../../stages/03_mvp/requirements.md), MVP-БТ-05/06, §6.4, вопросы MVP-Q-03/07/08.

**Пользователь выбрал 06.10.2026:**

- RAG поверх текущего STATUS; полнота MVP.1–MVP.3 и всей матрицы MVP.4 остаётся отдельной работой.
- Знания — текст на 2–3 страницы в промпте. Первый вызов LLM классифицирует запрос и необходимость RAG; второй ищет ответ в переданном тексте знаний и формирует справку. Отдельный поисковый сервис, embeddings и векторная БД не требуются.
- Вариант A: LLM вне транзакции, короткие чтения состояния.
- Команду и самостоятельный вопрос в одном сообщении попросить разделить; ничего из сообщения не применять.
- Второй LLM-вызов — одна попытка. Для первого разбора сохраняются три попытки всего.
- Текст знаний подготовить из требований, включив комиссию, сроки, назначение услуги и доступные сведения. Неизвестные значения не выдумывать.
- **На confirmation свободный ввод запрещён.** Прежнее предложение разрешить там справку отменено; доступны только штатные подтверждение/отказ.

Справка доступна до выбора STATUS и после отказа от подготовки. Нужно отличать отсутствие сведений от технического сбоя. RECALL, DETAILS, полномочия, ФЛК, память уточнений, входной replay и подключение настоящей поверхности GA не добавляются. Подтверждение/отказ — только accept_propose/reject_propose. Эта задача не закрывает весь MVP.4.

Ниже раскрыт выбранный подход. Конкретные сообщения, JSON и пограничные случаи — **детализация для обсуждения**, а не реализованное поведение. По [AGENTS.md](../../../AGENTS.md) impl_design.md и tasks.md будут представлены позднее и отдельно согласованы перед изменением кода.

## Глоссарий

| Термин | Значение в этой задаче |
|---|---|
| Услуга / STATUS | Подготовка и отправка запроса статуса выбранного платежа. Отправка обращения не означает зачисление денег. |
| Справка / RAG | Ответ по тексту знаний. Здесь весь небольшой текст сразу включается во второй промпт; внешнего поиска нет. |
| LLM / GigaChat | Модель, классифицирующая текст и отвечающая на вопросы. Она не принимает согласие и не вызывает банковскую операцию. |
| Промпт | Инструкции и данные запроса к модели. System задаёт правила и знания; user содержит сообщение клиента. |
| Логический вызов / попытка | Один полный промпт с параметрами / одно его фактическое выполнение. Повтор того же промпта после сбоя — новая попытка, не новый логический вызов. |
| Сессия / ход | Диалог с одним исходным платежом / одно сообщение или нажатие кнопки с отдельным Request-Id. |
| FSM / SSM | Машина состояний / библиотека Spring StateMachine. Определяет допустимость действий на текущем шаге. |
| Шаг выбора | CHOOSING_REQUEST_TYPE: подготовки нет, можно спросить или выбрать STATUS. До первой команды сохранённой FSM может ещё не существовать. |
| Подготовка / сводка | Серверный черновик запроса / его показ, например «Запросить статус платежа №125?». Это ещё не отправка. |
| Confirmation | AWAITING_CONFIRM: сводка показана, доступны «Подтвердить» и «Отклонить»; текст отправлять нельзя. |
| COMPLETED | Обращение закончено. Старую сессию нельзя продолжить вопросом или новой операцией. |
| preparationNo | Номер подготовки в сессии: защищает от подтверждения старой сводки после отмены и новой подготовки. |
| Снимок / projectionVersion | Прочитанные состояние, контекст и подготовка / существующий счётчик их изменений. Позволяет заметить изменение за время ожидания LLM. |
| Транзакция / commit | Граница согласованного чтения или изменения данных / фиксация изменений в БД. Ожидание LLM находится вне этой границы. |
| Семафор / NOWAIT | Существующая строка сессии, блокируемая БД для согласованного доступа / отказ при занятой строке без очереди на блокировку. |
| ACL / performative | Формат сообщений чата / тип сообщения: request, propose, accept_propose, reject_propose, inform, failure. |
| action_code / user_input | Код кнопки, например status / свободный текст. Разные источники намерения, не два действия в ходе. |
| WorkflowManager / corr | Путь передачи подтверждённого запроса во внешнюю обработку; справка его не вызывает. |
| Корреляция | Связь ответа с сессией и сообщением по conversation_id и in_reply_to. |

## Варианты исполнения справки

Источник знаний во всех вариантах одинаков: полный согласованный текст в промпте второго вызова.

| Вариант | Устройство | Отличия |
|---|---|---|
| A — вне транзакции, короткие чтения | Прочитать снимок, выполнить LLM без блокировки БД, перед справочным ответом сверить актуальность снимка. | **Выбран.** Использует существующий find; нет событий и сохранения ответа. Нужна обработка конкурентного изменения. |
| B — под блокировкой чтения | Получить снимок и справку в одной транзакции с блокировкой сессии. | Проще согласованность; ожидание LLM удерживает соединение и блокирует подтверждение/отказ. Отсутствующая сессия всё равно требует отдельного пути. |
| C — событие SSM | Добавить событие вопроса и сохраняемый исход обработки. | Новые события/исходы и запись на вопрос. LLM внутри Action удерживает транзакцию; вынос наружу снова требует согласования снимка. История справки этой задаче не нужна. |

## Вариант A подробно

### 1. Выбрать один источник действия

**Бизнес-смысл:** нажатая кнопка имеет однозначное значение. Сопроводительный текст не должен тайно добавлять вторую операцию.

Приоритет прежний: управляющий performative → action_code → user_input. Если выбран старший источник, младшие не анализируются. Неизвестный явный код отклоняется, а не угадывается по подписи. Пустой выбранный текст не отправляется модели.

| Ситуация | Поведение |
|---|---|
| Нажато «Запросить статус». | SELECT STATUS в существующую FSM, без LLM. |
| Нажато «Подтвердить», рядом передан текст «А сколько стоит?». | Обработка именно подтверждения по guards; текст не создаёт справку. Штатный UI такого смешанного ввода не формирует. |
| На выборе написано «Да». | Это не согласие. Разбор приводит к просьбе уточнить намерение. |
| Написано «Запроси статус и объясни стоимость». | Текстовый составной ввод: попросить два отдельных сообщения; не готовить STATUS и не вызывать справочный ответ. |

### 2. Проверить, можно ли сейчас принимать текст

**Бизнес-смысл:** сначала убедиться, что диалог допускает вопрос. Это серверная проверка, даже если клиентская кнопка уже отключена.

Коротко читаем снимок: прочитали, завершили транзакцию, освободили блокировку. Переданную привязку проверяем на соответствие сохранённому контексту; чужие/изменённые данные не используются для выдачи действий.

| Ситуация на сервере | Результат |
|---|---|
| Сессии ещё нет, вопрос «Для чего услуга?». | Вопрос допустим; справка не создаёт семафор или запись FSM. |
| Шаг выбора после «Отклонить». | Можно спросить о комиссии, сроках, назначении услуги. |
| AWAITING_CONFIRM, прямой HTTP-запрос «Сколько стоит?» в обход UI. | HTTP 400 без классификации, справки и записи. Предлагаемый смысл: «Сначала подтвердите или отклоните подготовленный запрос». |
| COMPLETED. | Терминальный отказ без LLM; нужен новый диалог. |
| Другое сообщение заняло сессию. | SESSION_BUSY без очереди на повтор и без LLM. |
| БД недоступна или снимок повреждён. | Техническая ошибка. Нельзя принять это за новый пустой диалог. |

Чтобы спросить после появления сводки, пользователь нажимает «Отклонить», возвращается на выбор и задаёт вопрос. Подготовка отменяется; после справки её нужно создать и подтвердить заново. Скрытой «приостановки подтверждения» нет.

### 3. Первым вызовом определить смысл сообщения

**Бизнес-смысл:** вопрос об услуге не запускает услугу; просьба проверить выбранный платёж не получает общую статью вместо подготовки STATUS.

Классификатор получает текущий текст и каталог операций, без истории и банковских реквизитов. Возвращает проверяемый структурированный результат. Названия JSON-полей будут зафиксированы позже; здесь важны четыре исхода:

| Исход | Пример | Дальнейшее действие |
|---|---|---|
| Команда STATUS | «Проверь, прошёл ли мой платёж». | Подготовка STATUS и отдельное подтверждение. |
| Справка | «Для чего услуга?», «Какая комиссия?», «Как запросить статус?». | Второй вызов по знаниям. |
| Составной ввод | «Запроси статус и расскажи о сроках». | Шаблон с просьбой разделить; обе части не выполняются. |
| Неясный ввод | «Сделай это», «Да», команда неподдерживаемой операции. | Уточнить; не запускать операцию и не угадывать из истории. |

Несколько **справочных** вопросов допустимы: «Для чего услуга и сколько стоит?» — один справочный запрос. Несовместимы действие и самостоятельный вопрос, а не любое наличие союза «и». «Могу ли я запросить статус?» — общий вопрос о возможности; «Можешь проверить мой платёж?» — просьба подготовить STATUS.

Технический сбой/невалидный JSON допускает до трёх одинаковых попыток первого разбора. Валидное «неясно» не повторяется: проблема в смысле сообщения, не в работе модели.

### 4. Выполнить ровно выбранную ветвь

**Бизнес-смысл:** у вопроса и банковского действия разные последствия.

Для команды используется прежняя FSM: она проверяет реальный шаг на момент исполнения, готовит сводку и ждёт отдельного согласия. Первый снимок не разрешает обходить guards. Второго LLM-вызова для команды нет.

Для справки второй вызов получает исходный вопрос и **весь** текст знаний. GigaChat в одном запросе выбирает подходящие разделы и отвечает. Отдельного поиска, перефразирования, ранжирования или вызова «проверь ответ» нет.

**Пример:** «Что я узнаю через услугу?» → классификация справки → ответ о назначении и результате → сообщение пользователю; ни подготовка, ни WorkflowManager не вызываются. «Узнай статус» → классификация команды → сводка; справочные знания не запрашиваются.

Команда требует одного логического вызова, справка — двух. Если первые две попытки классификации технически не удались, третья прошла и затем сформирована справка, получатся четыре фактических обращения, но два уникальных промпта. У второго вызова только одна попытка.

### 5. Хранить знания отдельно от правил ответа

**Бизнес-смысл:** правка инструкции модели не должна незаметно менять тарифы, сроки или возможности услуги.

Один статический ресурс знаний загружается при включении справки. YAML-шаблон второго system-промпта содержит правила, указатель тем, весь ресурс и формат ответа. User-сообщение содержит исходный вопрос. Банковские реквизиты туда не подставляются. Обновление — с выпуском приложения; редактор, загрузочная API и индекс не нужны.

Подготовлены проекты: [текст знаний](knowledge.md) и [промпты с контрольными вопросами](prompt_design.md). Знания разделены на темы KB-01…KB-10; рядом с неизвестными тарифами/сроками явно сказано, чего именно нет. Это навигация внутри одного промпта, не новый поисковый механизм.

| Вопрос | Как использовать знания |
|---|---|
| «Сколько комиссия?» | Найти раздел комиссии: цифр нет; сообщить, что определить сумму нельзя. |
| «Это бесплатно?» | Не выводить нулевую комиссию из отсутствия тарифа. |
| «Успеете за пять минут?» | Найти раздел сроков: SLA не задан, обещать пять минут нельзя. |
| «Придумай льготный тариф». | Пользовательский текст не дополняет знания и не меняет правила. |

Факт, что тариф **не указан**, позволяет ответить об этом ограничении. Совсем посторонняя тема, например курс валют, даёт структурированный исход «нет сведений» и локальный шаблон. Невалидный ответ второго вызова — техническая ошибка, не «нет сведений». Строгая форма проверяется приложением; достоверность содержания — предметным корпусом.

### 6. Проверить, не изменился ли шаг за время ожидания

**Бизнес-смысл:** другой запрос с тем же sessionId может успеть подготовить или отправить обращение. Справочный ответ не должен открыть текстовый ввод поверх подтверждения.

Перед выдачей справки снова коротко читаем сессию. Та же проверка нужна для успешного шаблонного уточнения/разделения, если первый вызов занял время и ответ возвращает доступные действия. Сравниваем наличие снимка и существующую projectionVersion. Содержание знаний не зависит от платежа, но **доступные действия и возможность текста зависят от шага**. Новые счётчики, таблицы и долговременная блокировка не вводятся.

| Было до LLM → стало после | Предлагаемый ответ |
|---|---|
| Выбор → тот же выбор и версия. | Справка и STATUS. |
| Сессии нет → по-прежнему нет. | Справка без создания сессии. |
| Выбор/нет сессии → confirmation. | Отбросить справку, показать актуальную сводку propose с пояснением об изменении шага; текст заблокировать. Это не справка на confirmation и не новая подготовка. |
| Выбор → COMPLETED. | Отказ о завершении, без справки и новых действий. |
| Версия изменилась, но снова выбор: другой запрос успел подготовить и отменить. | Отбросить справку; пояснить изменение, вернуть актуальное меню. Вопрос можно задать заново. |
| Снимок занят/не читается. | Ошибка busy/БД; не выдавать старые действия, не повторять автоматически LLM. |

Штатный UI отправляет по одному запросу. Эта проверка нужна для конкурентных API-входов с **одним** sessionId; независимые диалоги друг другу не мешают. Последнее чтение фиксирует момент актуальности ответа, но не блокирует сессию до доставки. Следующие команды всё равно проверяются сервером.

### 7. Справкой не менять банковский процесс

**Бизнес-смысл:** чтение условий не создаёт заявку, согласие или скрытую команду на будущее.

Не меняются состояние, preparationNo, платёжные данные, сохранённый результат последнего действия и его Request-Id, projectionVersion. Не сохраняются справочный текст, отложенная команда и готовый ACL-ответ. Сообщение в видимой ленте не является записью бизнес-состояния.

**Пример:** после «Отклонить» пользователь спрашивает «Можно потом запросить заново?». Ответ разъясняет возможность; подготовка возникает только после отдельного выбора STATUS. Сообщение «Запроси и расскажи» не оставляет команду, которая сработает на следующее «Да».

Корреляция справки относится к текущему вопросу: если последней банковской командой была отмена с Request-Id=X, а вопрос пришёл с Y, ответ адресуется Y. В сохранённой FSM последней командой остаётся X.

### 8. Показать ответ и сохранить ограничения UI

**Бизнес-смысл:** на выборе можно спрашивать; при подтверждении нужно принять решение по сводке.

| Состояние/ответ | Что видит пользователь |
|---|---|
| Справка на выборе | inform: ответ, доступный STATUS и активное текстовое поле. |
| Разделение/уточнение на выборе | inform: просьба уточнить/разделить, STATUS и активный текст. |
| Подготовка STATUS | propose: сводка, «Подтвердить», «Отклонить»; текстовое поле и отправка отключены. |
| Прямой текст в confirmation | HTTP 400; FSM не меняется, LLM не вызывается. Штатный UI такой вход не отправляет. |
| Отказ кнопкой | Подготовка отменена прежним путём; снова доступны выбор и вопросы. |

**Бизнес-последовательность:** вопрос о комиссии → ответ → выбор STATUS → сводка → желание узнать сроки → «Отклонить» → вопрос о сроках → ответ → новый выбор и новое отдельное подтверждение. Дополнительный шаг следует из выбранного запрета свободного ввода на confirmation.

Публичный GET сессии, восстановление согласия из браузерного хранилища и отдельный endpoint справки не добавляются. Основной ACL и локальное зеркало используют одно поведение.

### 9. Различать нехватку знаний, сбой и новую попытку пользователя

**Бизнес-смысл:** «в знаниях нет ответа» и «сервис не смог ответить» — разные ситуации. Ни одна не означает отправку или отмену банковского запроса.

Без подходящих сведений возвращается HTTP 200 с честным ограничением или шаблоном. После трёх неудачных попыток разбора — HTTP 500 / failure. После единственной неудачной попытки справки — тоже HTTP 500, но с отдельной причиной; нет повторной генерации. Пример текста: «Не удалось получить справку. Попробуйте позже».

Отсутствующий/пустой/нечитаемый ресурс знаний при включённой справке — ошибка конфигурации при старте, без фиктивного наполнения. При выключенном GigaChat кнопочный STATUS запускается без этого требования. Удалённой базы здесь нет: её недоступность из общих требований конкретизируется как ошибка загрузки ресурса; недоступность самой модели остаётся runtime-ошибкой.

После адресованного нетерминального **сбоя справки на выборе** можно отправить новый текст с новым Request-Id. Это новая попытка по решению пользователя. Нельзя распространить правило на любую ошибку: сбой подтверждения не разблокирует текст и не вызывает повторную отправку. Ошибка не переводит UI в шаг выбора сама по себе; текущий запрет сохраняется. При потере/несовпадении ответа UI не повторяет POST и не восстанавливает старые кнопки.

Без push/GET интерфейс не может мгновенно узнать о чужом конкурентном запросе. Поэтому запрет UI относится к последнему достоверному ответу, а окончательный запрет обработки текста — к серверному шагу. Если после ошибки пользователь отправит текст, а сервер уже окажется на confirmation, пункт 2 отклонит его до LLM. Введение постоянной синхронизации экрана этой задачей не требуется.

**Изменение относительно task04:** текст начинает читать сессию; уточнение «без чтения FSM» заменяется ответом с учётом шага. Запрет текста на confirmation сохраняется и проверяется сервером до LLM. Рабочая транзакция и guards подтверждения остаются по ADR-009/010/021.

## Сводка решений по составному вводу и ошибкам

| Случай | Предлагаемое поведение |
|---|---|
| Команда + самостоятельный вопрос, Q-19 | **Выбрано:** попросить разделить; ничего не применять и не хранить отложенную команду. |
| Согласие + вопрос | На confirmation любой свободный текст отклоняется до LLM. На выборе текстовое согласие не создаёт CONFIRM; предложение выполнить действие вместе с вопросом требует разделения. |
| Ответ отсутствует в корректном тексте знаний | Второй вызов сообщает недостаток сведений; HTTP 200 с локальным шаблоном и действиями текущего шага. Это не техническая ошибка. |
| Сбой второго вызова / невалидный результат, Q-20 | **Выбрано:** одна попытка, затем HTTP 500 / failure с отдельной причиной и final_message=false, если сессия не завершилась конкурентно; бизнес-данные справкой не меняются. |
| Сбой первого разбора | Уже принятые три попытки всего, затем HTTP 500. Общий ChatClient/corr не получает автоматических повторов. |
| Ресурс знаний отсутствует, пуст или не читается при включённой справке | Явная ошибка конфигурации при запуске, без подмены выдуманной базой/stub. При выключенном GigaChat запуск кнопочного STATUS остаётся доступным. |

При статическом ресурсе **нет отдельной удалённой базы**, которая может стать недоступной в ходе запроса. Исходное требование недоступности источника адаптируется к проверке загрузки конфигурации; недоступность самой LLM остаётся runtime-ошибкой. Это ограничение выбранного пользователем способа хранения, а не закрытая проверка внешнего поискового сервиса.

Лимит: один уникальный промпт для разбора; второй только для справки по знаниям. Переформулирование поиска, генеративное ранжирование и исправление ответа новым промптом не вводятся.

## Материалы и предметная приёмка

По поручению пользователя подготовлены [знания](knowledge.md) и [промпты с вопросами и ожиданиями](prompt_design.md). Они остаются проектами для содержательного обсуждения. Комиссия, сроки, назначение услуги, доступные сведения и связанные темы включены. В требованиях нет числового тарифа/SLA, поэтому эти ответы честно обозначают отсутствие данных. Расшифровки банковских статусов и условия отзыва также не выдумываются.

Контрольные примеры: справка о подтверждении; вопрос без сведений в тексте; просьба проверить фактический платёж; цитата команды; составной ввод; попытка заставить модель ответить вне знаний. Ожидания задаются согласованным содержанием. Рабочий протокол и предметное качество реального GigaChat принимаются отдельно; наличие инструкции в промпте не доказывает достоверность ответов.

## Критерии приёмки

1. Справка работает до первой операции и после отмены. На confirmation UI не отправляет текст, сервер отклоняет его до LLM; в COMPLETED тоже нет LLM. Вопрос после появления сводки требует сначала отказа от подготовки.
2. Первый вызов выделяет необходимость справки, второй ищет/отвечает по полному тексту знаний. Недостаток информации и технический сбой различаются. Нет выдуманного фактического статуса, ложного согласия и вызовов WorkflowManager на справочных ветвях.
3. Команды, вопросы, неоднозначность и составной ввод следуют выбранным правилам. Явный ACL-вход обходится без LLM. Проверяются строгие результаты, число промптов и попыток.
4. Вопрос не создаёт отсутствующую FSM и не записывает существующую; после восстановления confirmation сервер сохраняет запрет текста. Конкурентное изменение не возвращает старые действия или свободный ввод на confirmation. PostgreSQL подтверждает короткие чтения/NOWAIT и отсутствие блокировки во время LLM.
5. Основной ACL и зеркало дают одинаковое поведение. UI допускает следующий текст после нетерминальной ошибки справки на выборе, но не разблокирует confirmation; не повторяет POST и не принимает чужой/старый ответ.
6. Минимальные TDD-проверки поведения, HTTP/persistence и JS дополняются smoke приложения и согласованными примерами реального GigaChat. Отдельный валидатор-архитектор сопоставляет реализацию с документами; фактические результаты и ограничения фиксируются в validation.md.

## Решения и дальнейшее согласование

Принято: **A; RAG поверх STATUS; знания целиком во втором промпте; составной ввод разделять; одна попытка справки; запрет текста на confirmation**. Проекты знаний и промптов подготовлены из требований. Принятые положения отражаются в ADR-007/010/020 и документах этапов; они не означают готовность кода.

Сейчас обсуждаются девять пунктов выше и проекты текстов. По прямому поручению пользователя **к impl_design.md, tasks.md и реализации пока не переходим**. После обсуждения представим оба документа для отдельного явного согласования. Выбор A не считается разрешением на реализацию.
