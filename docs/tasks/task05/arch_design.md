# task05 — MVP.4: справка по тексту знаний поверх STATUS

**Дата:** 06.10.2026. **Статус:** выбранный вариант A реализован; [валидация](validation.md) пройдена. 06.10.2026 пользователь явно согласовал [impl_design.md](impl_design.md) и [tasks.md]. По последнему решению пользователя запрет справки после завершения пока только клиентский.

## Проблема и принятые границы

Основание: [требования MVP](../../stages/03_mvp/requirements.md), MVP-БТ-05/06, §6.4, вопросы MVP-Q-03/07/08.

**Пользователь выбрал 06.10.2026:**

- RAG поверх текущего STATUS; полнота MVP.1–MVP.3 и всей матрицы MVP.4 остаётся отдельной работой.
- Знания — текст на 2–3 страницы в промпте. Первый вызов LLM классифицирует запрос и необходимость RAG; второй ищет ответ в переданном тексте знаний и формирует справку. Отдельный поисковый сервис, embeddings и векторная БД не требуются.
- Вариант A уточнён: LLM вне транзакции; перед выдачей справки сессию не читаем и её версию не сверяем. Справочный путь не меняет сессию.
- Если классифицированы действие и вопрос либо несколько изменений состояния, ничего не выполнять и попросить выбрать одно действие. Несколько чисто справочных вопросов в сообщении допустимы.
- Если одновременно пришли кнопка/управляющее действие и непустой user_input, ничего не выполнять и попросить выбрать один источник. Прежний приоритет кнопки над текстом заменён этим правилом.
- Второй LLM-вызов — одна попытка. Для первого разбора сохраняются три попытки всего.
- Текст знаний подготовить из требований, включив комиссию, сроки, назначение услуги и доступные сведения. Неизвестные значения не выдумывать.
- **На confirmation текстовое поле активно.** Можно задать справочный вопрос без отказа от подготовки; прежний запрет ввода отменён последним уточнением пользователя.
- По пункту 2 дополнительных ограничений пока не выбираем: справка по умолчанию доступна в любом нетерминальном состоянии. По последнему решению запрет после завершения пока только клиентский.

Справка доступна до выбора STATUS, на confirmation и после отказа от подготовки; после завершения UI блокирует текст; сервер пока не проверяет терминальность справочного запроса. Нужно отличать отсутствие сведений от технического сбоя. RECALL, DETAILS, полномочия, ФЛК, память уточнений, входной replay и подключение настоящей поверхности GA не добавляются. Подтверждение/отказ — только accept_propose/reject_propose. Эта задача не закрывает весь MVP.4.

Ниже раскрыт выбранный подход. Конкретный контракт согласован в impl_design.md; результаты проверок отмечаются в tasks.md.

## Глоссарий

| Термин | Значение в этой задаче |
|---|---|
| Услуга / STATUS | Подготовка и отправка запроса статуса выбранного платежа. Отправка обращения не означает зачисление денег. |
| Справка / RAG | Ответ по тексту знаний. Здесь весь небольшой текст сразу включается во второй промпт; внешнего поиска нет. |
| LLM / GigaChat | Модель, классифицирующая текст и отвечающая на вопросы. Она не принимает согласие и не вызывает банковскую операцию. |
| Промпт | Инструкции и данные запроса к модели. System задаёт правила и знания; user содержит сообщение клиента. |
| Логический вызов / попытка | Один полный промпт с параметрами / одно его фактическое выполнение. Повтор того же промпта после сбоя — новая попытка, не новый логический вызов. |
| Сессия / ход | Диалог с одним исходным платежом / одно сообщение или нажатие кнопки с отдельным Request-Id. |
| FSM / SSM | Машина состояний / библиотека Spring StateMachine. Определяет допустимость действий на текущем шаге. |
| Шаг выбора | CHOOSING_REQUEST_TYPE: подготовки нет, можно спросить или выбрать STATUS. До первой команды сохранённой FSM может ещё не существовать. |
| Подготовка / сводка | Серверный черновик запроса / его показ, например «Запросить статус платежа №125?». Это ещё не отправка. |
| Confirmation | AWAITING_CONFIRM: сводка показана, доступны «Подтвердить», «Отклонить» и текстовое поле для вопроса. Справка не заменяет согласие. |
| COMPLETED | Обращение закончено. UI закрывает ввод; сервер запрещает новые операции, но справочный ACL-вход пока не проверяет состояние. |
| preparationNo | Номер подготовки в сессии: защищает от подтверждения старой сводки после отмены и новой подготовки. |
| Снимок / projectionVersion | Прочитанные бизнес-данные / существующий счётчик изменений. Справочный путь не перечитывает снимок перед ответом и не использует счётчик для проверки актуальности. |
| Транзакция / commit | Граница согласованного чтения или изменения данных / фиксация изменений в БД. Ожидание LLM находится вне этой границы. |
| Семафор / NOWAIT | Существующая строка сессии, блокируемая БД для согласованного доступа / отказ при занятой строке без очереди на блокировку. |
| ACL / performative | Формат сообщений чата / тип сообщения: request, propose, accept_propose, reject_propose, inform, failure. |
| action_code / user_input | Код кнопки, например status / свободный текст. Это поля протокола, в отличие от смыслов, выделяемых классификатором внутри текста. |
| Изменение состояния / справочный смысл | Намерение подготовить, подтвердить, отменить и т. п. / вопрос об услуге без действия. Несколько первых или их смесь со справкой требуют выбора одного действия. |
| WorkflowManager / corr | Путь передачи подтверждённого запроса во внешнюю обработку; справка его не вызывает. |
| Корреляция | Связь ответа с сессией и сообщением по conversation_id и in_reply_to. |

## Варианты исполнения справки

Источник знаний во всех вариантах одинаков: полный согласованный текст в промпте второго вызова.

| Вариант | Устройство | Отличия |
|---|---|---|
| A — вне транзакции, справка независимо от FSM | Выполнить классификацию и справку вне транзакции. Перед ответом сессию не читать. | **Выбран с уточнением.** Нет событий/записи/проверки версии для справки. Терминальный запрет пока только в UI. |
| B — под блокировкой чтения | Получить снимок и справку в одной транзакции с блокировкой сессии. | Проще согласованность; ожидание LLM удерживает соединение и блокирует подтверждение/отказ. Отсутствующая сессия всё равно требует отдельного пути. |
| C — событие SSM | Добавить событие вопроса и сохраняемый исход обработки. | Новые события/исходы и запись на вопрос. LLM внутри Action удерживает транзакцию; вынос наружу снова требует согласования снимка. История справки этой задаче не нужна. |

## Вариант A подробно

### 1. Выполнять одно действие за раз

**Бизнес-смысл:** если в тексте несколько действий, агент не выбирает удобное из них и не выполняет часть сообщения. Пользователь должен уточнить одно действие. Несколько вопросов по справке не требуют такого разделения.

| Сообщение | Поведение |
|---|---|
| «Запроси статус и объясни комиссию». | Действие + вопрос: ничего не выполнять, не создавать подготовку и не генерировать справку. |
| «Отмени подготовку и снова запроси статус». | Несколько изменений состояния: ни одно не выполнять. |
| «Запроси статус и сразу подтверди». | Подготовка + подтверждение: ничего не выполнять; текст не становится согласием. |
| «Для чего услуга, сколько стоит и какие сроки?» | Только справочные вопросы: один классификационный и один справочный вызов. |
| «Запроси статус» без иных смыслов. | Одна команда: прежний путь подготовки и отдельного подтверждения. |
| «Какая комиссия?» при открытой сводке. | Справка; подготовка и её номер не меняются. |
| Одновременно accept_propose и user_input «Какая комиссия?». | Ничего не подтверждать и не отвечать справкой; попросить выбрать кнопку или текст. Конфликт определяется до LLM. |
| Одновременно action_code=status и непустой user_input, даже «Запроси статус». | Попросить выбрать один источник; совпадение предполагаемого смысла не разрешает смешанный вход. |

Предлагаемый ответ на несколько действий: «Пожалуйста, выберите одно действие за раз. Уточните, что выполнить сейчас». Компоненты сообщения не сохраняются как отложенные команды. Повтор одной просьбы другими словами сам по себе не считается несколькими действиями.

**Различаем два понятия:** конфликт источников ACL виден по полям запроса до LLM; несколько смыслов единственного текстового источника выявляет классификатор. Пользователь выбрал отказ от выполнения в обоих случаях. Единственная кнопка по-прежнему работает без LLM. Управляющее действие вместе с отдельным action_code также не образует одну команду; стандартный performative=request для кнопки action_code сам по себе не является вторым действием.

Подпись кнопки/message_text для отображения не считается отдельно введённым user_input. Два источника определяются по реально переданным управляющим полям и непустому текстовому входу, а не по наличию подписи в ленте. Проект ответа: «Пожалуйста, выберите одно действие за раз: нажмите кнопку или отправьте текст отдельно».

### 2. Доступность справки — клиентский запрет

06.10.2026 пользователь выбрал: **«только клиентский запрет пока»**. Справка доступна до выбора, при открытой сводке и после отказа. После успешной подтверждённой операции и commit сервер возвращает COMPLETED/final_message=true; UI блокирует кнопки и текст. Поздний информационный ответ не открывает диалог.

Предложение читать существующую FSM перед вторым LLM-вызовом отклонено. Справка не читает сессию до или после модели. Прямой ACL-вопрос в COMPLETED пока получает справочный ответ; это принятое ограничение task05. Операционные guards сохраняют серверный запрет новых операций.

### 3. Первым вызовом определить смысл сообщения

**Бизнес-смысл:** модель либо выделяет одну команду, либо справочный запрос, либо просит пользователя уточнить один смысл. Она не ранжирует несколько желаний пользователя и не выбирает одно самостоятельно.

| Исход | Пример | Дальнейшее действие |
|---|---|---|
| Одна команда STATUS | «Проверь, прошёл ли мой платёж». | Обычная подготовка STATUS; отдельное подтверждение обязательно. |
| Справка, один или несколько вопросов | «Для чего услуга и сколько стоит?». | Второй вызов по всему тексту знаний. |
| Несколько действий или действие с вопросом | «Запроси статус и отзови платёж», «Запроси и объясни сроки». | Попросить выбрать одно действие; ничего из сообщения не применять. |
| Несколько возможных смыслов / непонятный ввод | «Сделай это», «Да», неоднозначная просьба. | Попросить детализировать один смысл; никаких действий и справочной генерации. |

Несколько ясных справочных вопросов — разрешённое исключение из правила «один смысл». «Как запросить статус?» — справка; «Можешь проверить мой платёж?» — просьба подготовить STATUS. Наличие вопросительного знака само по себе маршрут не определяет.

Классификатор использует текущий текст и каталог, без истории и банковских реквизитов. Итог проверяется приложением. Валидная неоднозначность не повторяется; невалидный JSON/технический сбой допускает до трёх одинаковых попыток первого разбора.

### 4. Выполнить ровно выбранную ветвь

**Бизнес-смысл:** у вопроса и банковского действия разные последствия.

Для команды используется прежняя FSM: она проверяет реальный шаг на момент исполнения, готовит сводку и ждёт отдельного согласия. Справочный путь не разрешает обходить guards. Второго LLM-вызова для команды нет.

Для справки второй вызов получает исходный вопрос и **весь** текст знаний. GigaChat в одном запросе выбирает подходящие разделы и отвечает. Отдельного поиска, перефразирования, ранжирования или вызова «проверь ответ» нет.

**Пример:** «Что я узнаю через услугу?» → классификация справки → ответ о назначении и результате → сообщение пользователю; ни подготовка, ни WorkflowManager не вызываются. «Узнай статус» → классификация команды → сводка; справочные знания не запрашиваются.

Команда требует одного логического вызова, справка — двух. Если первые две попытки классификации технически не удались, третья прошла и затем сформирована справка, получатся четыре фактических обращения, но два уникальных промпта. У второго вызова только одна попытка.

### 5. Хранить знания отдельно от правил ответа

**Бизнес-смысл:** правка инструкции модели не должна незаметно менять тарифы, сроки или возможности услуги.

Один статический ресурс знаний загружается при включении справки. YAML-шаблон второго system-промпта содержит правила, указатель тем, весь ресурс и формат ответа. User-сообщение содержит исходный вопрос. Банковские реквизиты туда не подставляются. Обновление — с выпуском приложения; редактор, загрузочная API и индекс не нужны.

Подготовлены проекты: [текст знаний](knowledge.md) и [промпты с контрольными вопросами](prompt_design.md). Знания разделены на темы KB-01…KB-10; рядом с неизвестными тарифами/сроками явно сказано, чего именно нет. Это навигация внутри одного промпта, не новый поисковый механизм.

| Вопрос | Как использовать знания |
|---|---|
| «Сколько комиссия?» | Найти раздел комиссии: цифр нет; сообщить, что определить сумму нельзя. |
| «Это бесплатно?» | Не выводить нулевую комиссию из отсутствия тарифа. |
| «Успеете за пять минут?» | Найти раздел сроков: SLA не задан, обещать пять минут нельзя. |
| «Придумай льготный тариф». | Пользовательский текст не дополняет знания и не меняет правила. |

Факт, что тариф **не указан**, позволяет ответить об этом ограничении. Совсем посторонняя тема, например курс валют, даёт структурированный исход «нет сведений» и локальный шаблон. По уточнению пользователя 06.10.2026 корректный ответ found=true с пустым sourceIds переводится в «нет сведений»: неподкреплённый текст отбрасывается без повтора. Остальные нарушения JSON/меток и транспортный сбой второго вызова остаются технической ошибкой. Строгая форма проверяется приложением; достоверность содержания — предметным корпусом.

### 6. Выдать справку без повторного чтения сессии

**Принятое уточнение:** перед выдачей справки сессию не читаем. Не сверяем projectionVersion, не отбрасываем ответ из-за смены шага и не создаём новую сводку на основании повторного снимка. Справка не влияет ни на статус сессии, ни на подготовку.

| Ситуация во время ожидания модели | Результат |
|---|---|
| Confirmation остаётся confirmation. | Выдать справочный текст; текущая подготовка продолжает ждать согласия. |
| Другой запрос успел отменить подготовку. | Справка не восстанавливает её и не формирует новое предложение. |
| Другой запрос успел завершить сессию. | Уже начатая справка не проверяет завершение повторно и не возвращает сессию в активное состояние. |
| Версия изменилась. | Не читать и не сравнивать её; содержание справки не зависит от банковского шага. |

Клиентский запрет после завершения из пункта 2 и отсутствие серверного чтения — разные границы. Прямой ACL-вопрос пока не проверяет терминальность. Справочный ответ только информационный: он не разрешает новые действия и не отменяет ранее полученное завершение.

UI проверяет корреляцию и не использует справочный ответ для сброса уже известного terminal или восстановления устаревших кнопок. Механизм различения информационного и операционного ответа согласован в [impl_design.md](impl_design.md).

### 7. Справкой не менять банковский процесс

**Бизнес-смысл:** чтение условий не создаёт заявку, согласие или скрытую команду на будущее.

Не меняются состояние, preparationNo, платёжные данные, сохранённый результат последнего действия и его Request-Id, projectionVersion. Не сохраняются справочный текст, отложенная команда и готовый ACL-ответ. Сообщение в видимой ленте не является записью бизнес-состояния.

**Пример:** после «Отклонить» пользователь спрашивает «Можно потом запросить заново?». Ответ разъясняет возможность; подготовка возникает только после отдельного выбора STATUS. Сообщение «Запроси и расскажи» не оставляет команду, которая сработает на следующее «Да».

Корреляция справки относится к текущему вопросу: если последней банковской командой была отмена с Request-Id=X, а вопрос пришёл с Y, ответ адресуется Y. В сохранённой FSM последней командой остаётся X.

### 8. Оставить текстовое поле активным рядом с подтверждением

**Бизнес-смысл:** пользователь может выяснить условия услуги перед согласием, не отменяя подготовленное обращение.

| Ситуация | Что видит пользователь |
|---|---|
| Шаг выбора | Меню STATUS и активное поле для текста. |
| Открыта сводка confirmation | Сводка, «Подтвердить», «Отклонить» и активное поле. |
| Задан один или несколько справочных вопросов | Информационный ответ; показанная подготовка и возможность отдельно подтвердить/отклонить сохраняются. |
| Текст содержит несколько действий или неоднозначность | Просьба уточнить одно; подготовка не меняется. |
| Справка завершилась технической ошибкой | Сообщение об ошибке; бизнес-шаг не отменяется и не подтверждается. |
| Сессия уже завершена и это известно UI | Завершение сохраняется; поздняя справка не открывает ввод заново. |

**Пример:** выбор STATUS → сводка → «Сколько стоит и какие сроки?» → справочный ответ → «Подтвердить» той же подготовки. Повторный выбор операции и новый preparationNo из-за вопроса не нужны.

В исходном UI до task05 текст на confirmation был запрещён, а обычный inform очищал параметры и кнопки подтверждения. Справка должна оставлять текущую активную подготовку доступной без повторного чтения/записи FSM и без нового propose. Способ выразить это в ACL и отобразить в текущем диалоге согласован в impl_design.md; «сохранить активную подготовку» не означает восстановление согласия из истории браузера.

Публичный GET, автоматические POST-повторы и подтверждение текстом не добавляются. Допустимость каждой последующей операции по-прежнему проверяет сервер.

### 9. Различать нехватку знаний, сбой и новую попытку пользователя

**Бизнес-смысл:** отсутствие ответа в знаниях и технический сбой — разные ситуации. Ни одна не отправляет и не отменяет банковский запрос.

Недостаток сведений даёт HTTP 200 с честным ограничением или шаблоном. Ошибка разбора после трёх попыток даёт HTTP 500 / failure. Ошибка справки на единственной попытке — HTTP 500 с отдельной причиной, без повторной генерации. Пример: «Не удалось получить справку. Попробуйте позже».

Отсутствующий/пустой/нечитаемый ресурс знаний при включённой справке — ошибка конфигурации при старте. При выключенном GigaChat кнопочный STATUS работает без этого требования. Удалённой базы знаний нет; её недоступность из общих требований конкретизируется как ошибка загрузки ресурса. Недоступность модели остаётся ошибкой во время работы.

После адресованного нетерминального сбоя справки можно задать вопрос снова с новым Request-Id, в том числе при активном confirmation. Это новая пользовательская попытка, не автоматический повтор. Ошибка справки не стирает подготовку и не переносит диалог на выбор; ошибка подтверждения не трактуется как ошибка справки и не порождает повтор банковской отправки.

При потере/несовпадении ответа UI не повторяет POST и не восстанавливает недостоверные действия. Информационный ответ или его ошибка не сбрасывают известное завершение диалога. Отдельное получение/повторное чтение серверного шага ради справки не добавляется.

**Изменения относительно task04:** свободный ввод разрешается на confirmation; разбор различает справку и несколько смыслов. Перед справочным ответом нет чтения FSM или проверки версии. Запрет справки после завершения пока только клиентский. Рабочая транзакция бизнес-операций и guards подтверждения сохраняются.

## Сводка принятых правил

| Случай | Поведение |
|---|---|
| Изменение состояния + вопрос; несколько изменений состояния | Ничего не выполнять, попросить выбрать одно действие. |
| Кнопка/управляющее действие + непустой user_input | Ничего не выполнять, без LLM попросить выбрать один источник. |
| Неоднозначные смыслы | Попросить детализировать один; не выбирать самостоятельно. |
| Несколько чисто справочных вопросов | Один справочный маршрут и один второй вызов LLM. |
| Справка на confirmation | Допустима; подготовка, её номер и статус сессии не меняются. |
| Сведения отсутствуют | HTTP 200 с ограничением/шаблоном, без выдуманных значений. |
| Второй вызов технически не удался | Одна попытка, HTTP 500; это не отсутствие знаний. |
| Состояние изменилось во время справки | Не перечитывать сессию, не проверять версию, не возвращать старое бизнес-состояние. |

Лимит: первый промпт — классификация (до трёх одинаковых попыток), второй — только справка (одна попытка). Отдельные генеративные поиск, ранжирование, исправление/проверка ответа не вводятся.

## Материалы и предметная приёмка

По поручению пользователя подготовлены [знания](knowledge.md) и [промпты с вопросами и ожиданиями](prompt_design.md). Они согласованы как часть дизайна реализации. Комиссия, сроки, назначение услуги, доступные сведения и связанные темы включены. В требованиях нет числового тарифа/SLA, поэтому эти ответы честно обозначают отсутствие данных. Расшифровки банковских статусов и условия отзыва также не выдумываются.

Контрольные примеры: справка о подтверждении; вопрос без сведений в тексте; просьба проверить фактический платёж; цитата команды; составной ввод; попытка заставить модель ответить вне знаний. Ожидания задаются согласованным содержанием. Рабочий протокол и предметное качество реального GigaChat принимаются отдельно; наличие инструкции в промпте не доказывает достоверность ответов.

## Критерии приёмки

1. Текстовое поле активно при confirmation. Справка допустима во всех нетерминальных состояниях, не требует отказа от подготовки; после завершения действует только клиентский запрет по пункту 2.
2. Единственная кнопка идёт в прежнюю FSM без LLM. Кнопка вместе с непустым текстом ничего не выполняет и просит выбрать источник. Действие с вопросом, несколько действий и неоднозначные смыслы единственного текста ничего не применяют; агент просит выбрать/уточнить одно. Несколько справочных вопросов допустимы.
3. Классификация и справка используют максимум два уникальных промпта. Первый вызов — до трёх попыток, второй — одна. Недостаток знаний и технический сбой различаются.
4. Справка не создаёт/не записывает FSM, не вызывает WorkflowManager и не читает сессию повторно перед ответом. Нет сравнения projectionVersion и отбрасывания справки из-за изменения шага.
5. ACL и UI сохраняют доступность активного подтверждения после справки/уточнения. Информационный ответ не восстанавливает отменённую подготовку и не сбрасывает известное завершение. Корреляция проверяется, автоматических POST-повторов нет.
6. Минимальные TDD-проверки и smoke выполняются после разрешения на код. Приёмка реального GigaChat использует согласованные вопросы; результат отдельного валидатора-архитектора фиксируется в validation.md.
