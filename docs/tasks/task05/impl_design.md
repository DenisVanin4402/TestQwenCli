## 1. Путь обработки

1. `AclInputAdapter`/`AclMapper` проверяют envelope и форму входа. Затем определяют конфликт источников: управляющий performative (`accept_propose`/`reject_propose`), присутствующий `action_code`, непустой `user_input`. Два и более источника дают просьбу выбрать один, без LLM/FSM. Обычный `request` и подпись кнопки не считаются отдельными источниками. Ошибки формы ACL сохраняют приоритет над содержательной обработкой.
2. Единственная кнопка проходит существующий путь. Неизвестный/пустой явный код остаётся ошибкой без fallback на текст. Единственный текст классифицируется до семафора и транзакции.
3. `COMMAND` преобразуется в прежний `SELECT`; допустимость проверяют существующие guards. `MIXED`/`UNCLEAR` возвращают локальный текст без работы с сессией.
4. `REFERENCE` вызывает справочный порт с исходным вопросом, без истории/платёжных данных. По согласованному ограничению терминальность проверяет только UI.
5. Справка использует один вызов LLM вне транзакции. После него сессия не читается, версия не сверяется, события и записи отсутствуют. Ответ коррелирует с текущим вопросом.

## 3. JSON, знания и ошибки

Первый ответ содержит ровно два обязательных поля:

```json
{"route":"COMMAND","actionCode":"status"}
```

Для `REFERENCE/MIXED/UNCLEAR` `actionCode` строго null; для COMMAND — непустой код из переданного каталога. Старый JSON только с actionCode больше не принимается. Неизвестный маршрут, неподходящий тип, лишние/дублирующиеся поля, Markdown и trailing JSON — сбой попытки. Валидный MIXED/UNCLEAR не повторяется. Схема выводится из DTO через существующий BeanOutputConverter; закрытость объекта, required и nullable уточняются так же, как в текущем классификаторе. Строгий reader локален адаптеру; глобальный ACL ObjectMapper не меняется.

Второй ответ содержит ровно `found`, `answer`, `sourceIds`:

```json
{"found":true,"answer":"В материалах комиссия не указана.","sourceIds":["KB-03"]}
```

При found=true нужны непустой answer и массив уникальных строк sourceIds, каждая из которых соответствует заголовку KB-раздела загруженного ресурса. **Уточнение пользователя 06.10.2026:** корректный ответ с found=true и пустым sourceIds не выдаётся как технический сбой. Адаптер отбрасывает неподкреплённый текст и возвращает found=false, answer=null, sourceIds=[]; UI получает HTTP 200 и локальное «В доступных материалах нет сведений по этому вопросу». Повтор LLM не добавляется. При исходном found=false допустимы только answer=null и sourceIds=[]. Все поля обязательны, типы строгие; остальная проверка JSON аналогична классификатору. Схема выводится из ReferenceAnswerDTO, условные ограничения проверяются адаптером. Остальные нарушения контракта или транспортная ошибка дают ReferenceAnswerException после единственной попытки. Метки проверяют принадлежность корпусу, но не доказывают достоверность текста; их не показываем пользователю и не сохраняем в FSM.

`agent-api-out/src/main/resources/knowledge/status-reference.md` содержит согласованные KB-01…KB-10 из knowledge.md, без служебного вступления и таблицы оснований. Полный ресурс включается в каждый справочный промпт. При включённой модели отсутствие, пустота, ошибка чтения или дубли меток — ошибка старта. Нет отдельной загрузочной API или поискового индекса. YAML `config/gigachat-prompts.yaml` получает справочные system/user-шаблоны из prompt_design.md; смысловых инструкций в Java нет. User — исходный текст, без повторной обработки как шаблона. Общие ChatClient/advisor и политика INFO-логирования task04 сохраняются; общий клиент не получает retry.

| Исход | HTTP / ACL | Текст |
|---|---|---|
| Конфликт источников | 200 / inform | `text.input-source-conflict`: «Пожалуйста, выберите одно действие за раз: нажмите кнопку или отправьте текст отдельно». |
| MIXED | 200 / inform | `text.multiple-actions`: «Пожалуйста, выберите одно действие за раз. Уточните, что выполнить сейчас». |
| UNCLEAR | 200 / inform | `text.clarification`: «Не удалось понять запрос. Уточните одно действие или задайте вопрос об услуге». |
| found=true | 200 / inform | Проверенный answer, включая честное отсутствие тарифа/SLA. |
| found=false | 200 / inform | `text.reference-not-found`: «В доступных материалах нет сведений по этому вопросу». |
| Сбой справки | 500 / failure | `error.REFERENCE_FAILED`: «Не удалось получить справку. Попробуйте позже». |
| Сбой классификации | 500 / failure | Существующий TEXT_ANALYSIS_FAILED; не выдавать его за UNCLEAR. |
| COMMAND / кнопка | Прежний контракт | Ответ по фактическому результату FSM. |

Renderer проверяет обязательные новые шаблоны при загрузке. В режиме none обычный текст заканчивается прежним TEXT_ANALYSIS_FAILED до справочного порта. Неполный/невалидный ACL сохраняет прежний 400, без модели. Прямой справочный ACL-вход не проверяет COMPLETED; ошибки чтения сессии на этом пути не возникают.

## 4. Отличие информационного ответа в ACL

Используется имеющийся в исходном ACL контейнер `metadata.additional_info` с одной парой `key=response_mode`, `value=information`. В локальном YAML добавить его в AclOutputMetadata с обычными полями key/value по исходному `additionalInfo`. Это семантика локального профиля; поддержка настоящей поверхности GA не заявляется.

`AclMapper.toMetadata` получает TurnOutDTO и ставит метку только для закрытого набора кодов: INPUT_SOURCE_CONFLICT, MULTIPLE_ACTIONS, CLARIFICATION_REQUIRED, TEXT_ANALYSIS_FAILED, REFERENCE_ANSWER, REFERENCE_NOT_FOUND, REFERENCE_FAILED. Отдельный флаг в TurnOutDTO не нужен. Информационный ответ передаёт пустые suggestions/state, final_message=false; false означает, что ответ сам не завершает диалог, а не результат чтения состояния сессии. Новое propose не формируется. Семантику описать в OpenAPI.

Ответы FSM и ошибки формы метки не получают. Нельзя считать любой inform/failure информационным: inform после отмены меняет кнопки, а ошибка подтверждения может сопровождаться неопределённым внешним эффектом. Корреляция и HTTP-статус остаются прежними на основном ACL и зеркале. Метка ничего не разрешает серверным guards и не даёт серверной гарантии запрета справки после завершения.

## 5. Поведение UI

`canSendText()` проверяет busy/final, без запрета awaitingConfirmation. `deliver()` сохраняет текущие actions/aclState/awaitingConfirmation на время запроса; busy скрывает доступ к кнопкам. Отправка текста не отправляет подтверждение, отправка кнопки не прикладывает черновик текста.

По уточнению пользователя 06.10.2026 поле и отправка заблокированы на время ожидания. После корректного успешного ACL-ответа отправленный текст очищается; ошибка оставляет его в поле. Поздний ответ другого диалога не очищает новый черновик. При фокусе темнеет общая рамка формы ввода и кнопки; коричневая обводка textarea убрана.

После проверки conversation_id/in_reply_to:

- `final_message=true` всегда закрывает ввод и очищает действия. Известный final монотонен: поздний false не открывает диалог.
- Адресованный ответ с response_mode=information только добавляет текст/ошибку в ленту. Не заменяет подготовку или кнопки и не восстанавливает снимок старых actions. После busy=false остаются текущие подтверждение/отказ либо меню выбора; повторный вопрос получает новый Request-Id.
- Адресованная ACL-ошибка показывается один раз в ленте, без копии в плашке над вводом. Плашка используется при потере, повреждении или неверной корреляции ответа.
- Операционный ответ заменяет действия по прежнему контракту propose/inform; ошибки операции снимают доступ к действиям по прежним правилам. Данные прошлого propose не становятся новыми реквизитами подтверждения.
- Потеря ответа, ошибка JSON или корреляции не дают права сохранить активные кнопки: снять действия/aclState/awaitingConfirmation, показать существующее сообщение неопределённости. Автоматического POST/GET и восстановления из sessionStorage нет.

Отдельные вкладки не синхронизируются. Если другая вкладка отменила подготовку, текущая не узнает этого из справки; серверные guards отклонят старое согласие. В текущем экземпляре UI информационный ответ никогда не возвращает уже удалённые кнопки. Вывод answer — через существующий textContent.
