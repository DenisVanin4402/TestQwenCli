# task06 — Возврат к операции после справки, уточнения и недопустимой команды

**Дата:** 07.10.2026. **Статус:** Валидация; браузерная приёмка открыта. Пользователь выбрал A, затем явно согласовал [impl_design.md](impl_design.md) и [tasks.md](tasks.md): «начинаем реализацию задач … task06 — документы подтверждаю». Конкретизация R1 и границ очистки принята вместе с дизайном.

## Проблема и требования пользователя

После справочного ответа, непонятного ввода или недопустимой команды нужен явный путь продолжения диалога. UI показывает только те кнопки, которые явно передал backend.

1. На активном нетерминальном шаге после справки, сообщения «Не удалось понять запрос. Уточните одно действие или задайте вопрос об услуге» и отказа в недопустимом переходе через пустую строку вывести **«Хотите продолжить предыдущую операцию?»** и ровно два саджеста: **«Да»**, **«Нет»**. Для недопустимой команды вопрос выводится сразу после отказа; отдельный справочный запрос не нужен. Опечатки исходных сообщений исправлены.
2. **«Да»**: прочитать актуальное состояние FSM и показать сообщение текущего шага, как при входе в него. Это возврат к операции, не согласие на её выполнение.
3. **«Нет»**: очистить память текущей операции, вернуть FSM в начальное состояние и показать доступные операции с серверными саджестами.
4. UI не создаёт кнопки саджестов самостоятельно и не подставляет отсутствующие кнопки.
5. Дополнительный ответ пользователя от 06.10.2026: **только до завершения, как сейчас**. После завершения поле ввода остаётся заблокированным.
6. Последнее уточнение пользователя: **на начальном шаге вопрос о продолжении и «Да»/«Нет» не показывать**. Под справочным/уточняющим сообщением и отказом в недопустимой команде вывести доступные операции. Отсутствующая FSM соответствует начальному выбору, а не существующей предыдущей операции.
7. Учесть расширение MVP: состояния относятся к трём категориям — **инициирующее, промежуточные, терминальное**. Правило навигации определяется категорией, а не сравнением только с тремя нынешними состояниями. Новые шаги подготовки должны подключаться без изменения общей логики «Да»/«Нет».

Эти требования, архитектура A и конкретный контракт дизайна реализации приняты пользователем; реализация разрешена явным согласованием обоих документов 07.10.2026.

Объём — существующий STATUS, справочный и уточняющий маршруты task05, ответы на недопустимые команды, основной ACL и его зеркало, тестовый UI; модель состояний дополняется явной категорией. Ввод DETAILS/RECALL и новые бизнес-шаги пока не реализуются. Их расширение учитывается по [требованиям MVP](../../stages/03_mvp/requirements.md): в частности, `AWAITING_DETAILS` — промежуточный шаг подготовки с ожиданием ввода. Доставка через настоящую поверхность GA остаётся отдельной задачей.

### Три категории состояний

| Категория | Состояния | Навигация после справки/уточнения/недопустимой команды |
|---|---|---|
| Инициирующее (`INITIAL`) | Сейчас `CHOOSING_REQUEST_TYPE`; отсутствие FSM имеет ту же семантику для представления | Только доступные операции, без вопроса и «Да»/«Нет». |
| Промежуточные (`INTERMEDIATE`) | Сейчас `AWAITING_CONFIRM`; в MVP также `AWAITING_DETAILS` и другие шаги подготовки | Вопрос о продолжении и «Да»/«Нет». «Да» показывает именно текущий шаг; «Нет» отменяет текущую подготовку и возвращает к началу. |
| Терминальное (`TERMINAL`) | Сейчас `COMPLETED` | Нет продолжения и доступных операций; завершение не снимается. |

Категория — метаданные конкретного состояния, не отдельное состояние FSM и не сохранённый дублирующий признак сессии. По категории выбирается общая навигация; конкретные данные/текст продолжения и допустимый переход отмены принадлежат шагу. На будущем `AWAITING_DETAILS` «Да» возвращает запрос ввода с сохранёнными изменениями, а не сводку подтверждения. Новое состояние обязано явно задать категорию, представление и необходимые переходы; неизвестный шаг нельзя автоматически считать подтверждением или стартом.

Синхронные внутренние `CHECKING_AUTH`/`VALIDATING_DETAILS` из MVP, если будут введены, также промежуточные, но сами по себе не становятся точками ожидания пользовательского ответа. Текущий протокол читает согласованный снимок после транзакции либо сообщает занятость; чтение не прерывает выполняемую проверку и не запускает её повторно.

**Вывод:** одного enum состояния недостаточно: он не содержит номер платежа и значения сводки. Но **состояния вместе с сохранённым ExtendedState достаточно** для текущего STATUS. Текст уже строится вне actions. Хранить готовый ответ ради продолжения не требуется.

Нужна небольшая отдельная логика представления текущего шага: существующий `render` выбирает текст по `lastResult`. После недопустимой команды там может быть `INVALID_COMMAND`, хотя FSM всё ещё ждёт подтверждения. Продолжение должно повторно показать сводку активной подготовки, а не эту ошибку. Повторный `SELECT`, вход в состояние с выполнением actions и вызов WorkflowManager для показа сообщения не подходят.

## Рассмотренные варианты архитектуры

| Вариант | Устройство | Отличия |
|---|---|---|
| **A. Представление текущего шага по снимку — выбран** | По «Да» прочитать сохранённую FSM; сформировать сообщение по её текущему `state` и предметным данным, используя существующие шаблоны. | Использует уже сохранённые данные; нет повторного действия и хранения текста. Восстанавливает смысл текущего шага, но не обещает побайтовый повтор старого текста после изменения шаблонов. |
| **B. Сохранённое представление шага** | Сохранять связанный с шагом ответ: текст, описание кнопок и подтверждаемые значения; по «Да» читать его вместе с FSM. | Нужен для точного повтора исторического/невоспроизводимого ответа. Добавляет дублирование данных, правила обновления и атомарного сохранения представления. Требует пересмотра ADR-004/008/009; сейчас такой необходимости нет. |

**Принят A.** «Как будто вошли в шаг» трактуется как повторное представление шага без исполнения перехода. Для будущего шага понадобятся его предметные данные и шаблон; это не основание заранее сохранять тексты всех ответов. B не выбран.

Backend должен знать актуальный шаг **уже при формировании справочного/уточняющего ответа**, а не только по клику «Да». Прежнее предложение вообще не читать FSM на этих маршрутах отменено в этой области. По выбранному A используется снимок текущего хода либо короткое внутреннее чтение после LLM; связанные ADR уточнены, код реализован, автоматические проверки пройдены; браузерная приёмка открыта.

## Поведение выбранного варианта A

### Продолжение после INVALID_COMMAND — рассмотренные варианты текста

`INVALID_COMMAND` — исход недопустимой команды, а не шаг FSM. Например: выбрали STATUS → `AWAITING_CONFIRM`; снова выбрали STATUS → переход не выполнен, `lastResult=INVALID_COMMAND`, прежняя подготовка остаётся. Последующая справка также не меняет шаг и подготовку.

По последнему уточнению общий вопрос и серверные «Да»/«Нет» появляются уже в самом отказе на активном шаге; если затем задан справочный вопрос, справка также получает эту пару. На начальном шаге оба сообщения получают доступные операции. Для клика «Да» ранее рассмотрены два варианта текста:

| Вариант | Ответ по «Да» при сохранённом INVALID_COMMAND | Отличие |
|---|---|---|
| **R1. Показать текущий шаг — рекомендуется** | На `AWAITING_CONFIRM` снова показать сводку и явные кнопки подтверждения/отказа; на выборе — меню операций. | Последняя ошибка уже была показана и не мешает продолжению. Ответ определяется текущими состоянием и данными. |
| **R2. Напомнить об ошибке и показать текущий шаг** | Например: «Предыдущая команда недоступна на этом шаге. Запросить статус платежа №123?» и кнопки подтверждения/отказа. | Дополнительно объясняет, почему прежняя команда не выполнена; нужны текст и условие по `lastResult`. Поскольку показ не записывает FSM, напоминание может повторяться при следующих продолжениях до нового бизнес-хода. |

В обоих вариантах «Да» не повторяет отклонённую команду и не выполняет операцию. «Нет» явно отменяет текущую подготовку и возвращает меню по общему правилу. Сам по себе `INVALID_COMMAND` не является причиной очищать подготовку. Если FSM отсутствует или уже завершена, применяются пограничные случаи таблицы ниже.

Прямой повтор только последнего ответа через существующий `render(lastResult)` снова покажет ошибку и не вернёт пользователя к сообщению текущего шага. В согласованный impl_design включён R1 как прямое применение A: сообщение текущего шага без повторения ошибки. R2 остаётся рассмотренной альтернативой и не входит в план; этот выбор текста согласован вместе с дизайном 07.10.2026.

### Справка, уточнения и управляющие саджесты

Единое правило предлагается применить к справке и отсутствию сведений (`REFERENCE_ANSWER`/`REFERENCE_NOT_FOUND`), непонятному вводу (`CLARIFICATION_REQUIRED`), уточнению одного действия/источника (`MULTIPLE_ACTIONS`/`INPUT_SOURCE_CONFLICT`) и недопустимой команде (`INVALID_COMMAND`). Технические сбои LLM, хранения или исполнения операции в эту группу не входят.

| Текущий шаг | Что backend добавляет к такому сообщению |
|---|---|
| `INITIAL` или FSM отсутствует | Доступные операции в `suggestions`. Вопроса о продолжении и кнопок «Да»/«Нет» нет. |
| `INTERMEDIATE` | `\n\nХотите продолжить предыдущую операцию?` и ровно «Да»/«Нет». Кнопки конкретного шага сразу не показываются. |
| `TERMINAL`, в том числе при смене шага во время обработки | Вопроса и действий нет; ответ отмечает завершённость, UI не открывает ввод заново. |

Текст исходной справки/уточнения/отказа сохраняется. Строка продолжения и кнопки формируются приложением, без дополнительного LLM-вызова. Например, на подтверждении: «Не удалось понять запрос. Уточните одно действие или задайте вопрос об услуге», пустая строка, «Хотите продолжить предыдущую операцию?» и «Да»/«Нет».

**Предлагаемый способ чтения:** классификация и справка остаются вне транзакции. Если текущий ход уже вернул согласованный снимок FSM (например, с `INVALID_COMMAND`), использовать его. На маршрутах без такого снимка после LLM/уточнения получить его существующим внутренним `find` в короткой транзакции. При предметном отказе без снимка чтение выполняется после завершения транзакции отказа. Блокировка не удерживается во время LLM; публичный GET и передача состояния из UI не добавляются. Отсутствие FSM даёт начальные саджесты без создания записи; ошибка/занятость чтения не подменяются стартовым меню или предположением об активной операции.

Справка и уточнение по-прежнему не отправляют события и не меняют подготовку, результат или версию FSM. Существующая обработка недопустимой команды может сохранить её исход; добавление вопроса и кнопок не создаёт второго перехода или записи. Серверное чтение нужно для представления текущего шага; новый запрет обращения к LLM в завершённой сессии до классификации этой задачей не вводится.

«Да»/«Нет» передаются как два явных управляющих `action_code` через существующий ACL POST, без LLM. Они не являются `accept_propose`/`reject_propose`; клик «Да» никогда не отправляет банковский запрос. Текстовые «да/нет» не добавляются как новый способ управления. Отдельное состояние ожидания ответа на справку не нужно: смысл клика задан кодом. Каждый новый справочный/уточняющий ответ получает кнопки по тому же правилу с учётом актуального шага.

### «Да»: показать текущий шаг

| Состояние на момент клика | Ответ |
|---|---|
| `AWAITING_CONFIRM` | Актуальная сводка прежней подготовки, прежний `preparationNo`, подтверждаемые параметры и явно переданные backend кнопки подтверждения/отказа. Операция ещё требует отдельного согласия. |
| Другое `INTERMEDIATE` при расширении MVP | Представление конкретного шага по его сохранённым данным. Например, `AWAITING_DETAILS` просит ввести/уточнить реквизиты и сохраняет уже введённые значения. Это контракт расширения, не реализация DETAILS в task06. |
| `CHOOSING_REQUEST_TYPE` | Приглашение выбрать операцию и текущие саджесты каталога. Старое сообщение об отмене/ошибке не повторяется. |
| Сохранённой FSM нет | «Предыдущая операция не выбрана. Выберите действие» и начальные саджесты. FSM ради показа не создаётся. |
| `COMPLETED` при устаревшем клике | Завершённый ответ без действий. Завершение не снимается и внешняя операция не повторяется. |

По клику состояние читается заново: оно могло измениться после показа «Да»/«Нет». Чтение — существующий внутренний путь с короткой транзакцией и блокировкой. Результат отражает согласованный снимок на момент чтения; последующие действия снова проверяет сервер. Ответ связывается с **новым** Request-Id клика, не с сохранённым `lastRequestId`. Ни `preparationNo`, ни сохранённый результат, ни версия FSM из-за показа не меняются. Повреждение/занятость хранилища возвращают ошибку, а не притворяются отсутствием операции. Строки таблицы про начальный шаг/отсутствующую FSM нужны для устаревших кликов: новые ответы на старте «Да»/«Нет» уже не предлагают.

### «Нет»: очистить текущую операцию и вернуться к выбору

Предлагается понимать «очищение памяти» как очистку **данных текущей операции**: подготовки, подтверждаемых значений и согласия, а при появлении новых шагов — также их временного ввода. Исходный платёж, принадлежность пользователю/организации, идентификатор сессии и монотонный счётчик подготовок сохраняются. Это соответствует существующему сбросу MVP-БТ-04 и не позволяет старому подтверждению совпасть с новой подготовкой.

Сброс существующей FSM категории `INTERMEDIATE` выполняется через SSM под действующим семафором и в одной транзакции. Сейчас используется существующая семантика CANCEL; при добавлении промежуточного шага регистрируются его отмена и очистка данных, общая навигация не меняется. Категория сама не разрешает переход в обход guards. Ответ с начальным меню выдаётся после commit. Инициирующее состояние остаётся на выборе; если FSM ещё нет, возвращается начальное меню без создания пустой сессии. Сбрасывать состояние категории `TERMINAL` устаревшим кликом нельзя.

Эта граница очистки принята в составе дизайна реализации 07.10.2026. Буквальное удаление также исходного контекста и счётчиков потребовало бы отдельного решения о новой сессии и повторной передаче исходных данных.

### Backend — единственный источник кнопок

Каждый принятый ответ задаёт полный актуальный набор кнопок. Отсутствующие или пустые `suggestions` означают отсутствие кнопок; старые действия из предыдущего сообщения не переносятся. После справки/уточнения/недопустимой команды на активном шаге видны только «Да»/«Нет», на начальном — доступные операции. Параметры старой сводки не используются UI для самостоятельного восстановления подтверждения; по «Да» они приходят заново с сервера.

Правило распространяется и на `propose`: backend явно описывает «Подтвердить»/«Отклонить», UI не создаёт их только по performative. Сохраняются отдельные `accept_propose`/`reject_propose` и серверная проверка состава/номера подготовки. В дизайне реализации нужно определить минимальное явное описание действия кнопки в общем ACL-профиле: существующая `AclSuggestion` содержит `action_code`, но не performative отправляемого сообщения. Нельзя незаметно заменить подтверждение обычным `request/status` или приписать локальное расширение исходному контракту GA.

Backend и UI должны поддержать явные саджесты также в предметном отказе `INVALID_COMMAND`: текущие ограничения «на ошибке саджестов нет» этому не соответствуют. Наличие таких кнопок не превращает отказ в успешное выполнение операции. Конкретные поля/коды ответа определяются в дизайне реализации. Если backend не прислал кнопки, UI их не показывает; при техническом сбое и недостоверной корреляции навигация не выдумывается. Свободный ввод остаётся доступным до завершения. Начальные кнопки по-прежнему поступают из серверного fixture. Корреляция, запрет повторного клика во время запроса и отсутствие автоматического POST-повтора сохраняются.

## Критерии приёмки

1. На подтверждении справка (включая отсутствие сведений), непонятный ввод, уточнение одного действия/источника и недопустимая команда заканчиваются точной строкой через пустую строку; backend передаёт ровно «Да»/«Нет». Отказ в команде получает вопрос сразу, без дополнительной справки. На начальном шаге и без FSM те же сообщения получают только доступные операции, без вопроса и «Да»/«Нет». UI не оставляет старых кнопок.
2. «Да» после справки на подтверждении возвращает актуальную сводку и явные кнопки с прежними значениями и номером подготовки, без записи FSM, LLM, повторной подготовки и WorkflowManager. Согласие требуется отдельным кликом.
3. Продолжение после сохранённого `INVALID_COMMAND` показывает текущий шаг, а не последнюю ошибку. Восстановление работает после перезапуска приложения, без памяти браузера; ответ коррелирует с новым кликом.
4. «Нет» удаляет данные текущей операции и атомарно возвращает к начальному шагу. Исходный контекст и счётчик сохраняются; новая подготовка получает новый номер, старое подтверждение не принимается. WorkflowManager не вызывается.
5. При отсутствии FSM и на начальном шаге устаревшие клики «Да»/«Нет» дают меню доступных операций, не исполняя бизнес-операцию. Отсутствие FSM отличается от ошибки её чтения. Сам справочный/уточняющий ответ отсутствующую FSM не создаёт.
6. Кнопки справки/уточнения определяются серверным снимком: после LLM либо по снимку текущего хода. LLM не удерживает блокировку/транзакцию FSM. При изменении состояния между сообщением и кликом используется актуальный серверный снимок. Устаревший клик не открывает завершённую сессию. Запрет ввода после завершения сохраняется.
7. При пустых/отсутствующих `suggestions`, в том числе на `propose`, `information` и ошибке, кнопок нет. Явные навигационные саджесты предметного отказа отображаются; UI не подавляет их только из-за `failure`/HTTP-ошибки. Полученные кнопки подтверждения отправляют прежние управляющие performative и актуальный `state`. Оба ACL-входа ведут себя одинаково.
8. Ошибка чтения/сброса не выдаётся за успешное продолжение/начальное меню. Потеря ответа не вызывает автоматического повтора. Проверки — минимальные TDD для нового поведения, persistence/HTTP и клиентские проверки по этим сценариям, затем отдельная архитектурная валидация.
9. Общая навигация и терминальность зависят от явной категории состояния. Существующие три состояния сохраняют поведение; новый промежуточный шаг требует своего представления/данных и перехода отмены, но не изменения правил навигации. Нет fallback неизвестного шага в подтверждение/меню, нет новых бизнес-состояний или фиктивных состояний для тестов в task06.
