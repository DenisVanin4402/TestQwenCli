# task06 — Дизайн реализации

**Дата:** 07.10.2026. **Статус:** согласован, реализован; Валидация, браузерная приёмка открыта. Пользователь явно подтвердил этот документ и [tasks.md](tasks.md): «начинаем реализацию задач … task06 — документы подтверждаю». Архитектура A и конкретизация поведения ниже приняты.

## 1. Поведение и границы

Один способ представления текущего шага по `SessionSnapshotDTO`, без повторного события, хранения текста, нового бизнес-состояния FSM или дополнительного поля native-снимка. По уточнению пользователя состояния имеют три явные категории: инициирующее, промежуточные и терминальное. По «Да» используется R1: сообщение текущего шага без повторения последней ошибки. По «Нет» очищается подготовка, сохраняются контекст сессии и монотонный номер подготовок. Это конкретизация A, представленная в составе этого документа на согласование.

Для `REFERENCE_ANSWER`, `REFERENCE_NOT_FOUND`, `CLARIFICATION_REQUIRED`, `MULTIPLE_ACTIONS`, `INPUT_SOURCE_CONFLICT`, `INVALID_COMMAND` применяется общая таблица:

| Снимок | Оформление исходного сообщения |
|---|---|
| Нет FSM или категория `INITIAL` | Доступные операции, без вопроса и «Да»/«Нет». |
| Категория `INTERMEDIATE` | Исходный текст + `\n\nХотите продолжить предыдущую операцию?`; ровно «Да»/«Нет», без параметров подтверждения. |
| Категория `TERMINAL` | Исходный текст, без вопроса/действий, `terminal=true`. |

Справка и уточнения не меняют FSM. `INVALID_COMMAND` получает навигацию сразу, независимо от того, был ли исход сохранён исполнителем или возвращён исключением допуска. Ошибки формы, подтверждения, контекста, технические ошибки и неизвестный `action_code` автоматически не включаются в эту группу.

## 2. Вход и явные кнопки

Основной ACL и зеркало продолжают использовать один `AclInputAdapter`/`AclMapper`; новых HTTP-маршрутов нет.

| Кнопка | Явный саджест backend | Вход по клику |
|---|---|---|
| Операция | `text` из каталога, `action_code=status`, `performative=request` | Прежний `request/content.action_code=status`. |
| Да | `text=Да`, `action_code=resume_operation`, `performative=request` | Только `request/content.action_code=resume_operation`. |
| Нет | `text=Нет`, `action_code=reset_operation`, `performative=request` | Только `request/content.action_code=reset_operation`. |
| Подтвердить | `text=Подтвердить`, `performative=accept_propose`, без `action_code` | `accept_propose` и полученный `state`. |
| Отклонить | `text=Отклонить`, `performative=reject_propose`, без `action_code` | `reject_propose`; `state` необязателен. |

В `agent-api-in/src/main/resources/openapi/acl-poc.yaml` расширить общую `AclSuggestion` необязательным `performative` с enum `request/accept_propose/reject_propose`. Это **расширение локального профиля**, не заявление о поддержке этого поля поверхностью GA. Backend выдаёт поле у всех новых саджестов; отсутствие поля у старого саджеста с `action_code` означает прежний `request`. Нельзя создавать кнопку при отсутствии самого саджеста. Для `request` нужен непустой `action_code`; для подтверждения/отказа он отсутствует. `guid`, `display_mode=BUTTON`, `message_text`, `is_posted_to_chat` сохраняются.

Зеркало/fixture используют существующий `$ref` на общую схему. Generated Java обновляется только Maven-генерацией, вручную не редактируется. `state[]` типа CONFIRMATION по-прежнему несёт `paymentNumber`/`preparationNo`; новые управляющие кнопки его не принимают как согласие.

`AclInputAdapter.handle` распознаёт два навигационных кода до поиска бизнес-операции. `AclMapper.toInput` переносит навигацию в отдельное поле входа. Навигационная кнопка с текстом либо с `accept_propose/reject_propose` остаётся конфликтом источников: не выполняется ни одно действие, LLM не вызывается. Неизвестный код остаётся `UNSUPPORTED_COMMAND`, не становится текстом. Навигация не включается в каталог операций для LLM; текстовые «да/нет» не становятся согласием или навигационной командой.

## 3. Модели и представление

| Файл / класс | Изменение |
|---|---|
| `agent-model/.../enums/SessionStateCategory.java` — новый | Ровно `INITIAL`, `INTERMEDIATE`, `TERMINAL`. Категория управляет представлением и навигацией, не заменяет разрешения/guards FSM. |
| `SessionState` | Обязательное `final SessionStateCategory category`, конструктор и `getCategory()`. Нынешние константы: `CHOOSING_REQUEST_TYPE(INITIAL)`, `AWAITING_CONFIRM(INTERMEDIATE)`, `COMPLETED(TERMINAL)`. Имена/порядок констант не меняются, новые шаги сейчас не добавляются. Нет вычисления категории как «всё остальное — промежуточное». |
| `agent-model/.../enums/NavigationAction.java` — новый | `RESUME`/`RESET`, фиксированные коды `resume_operation`/`reset_operation` и их разрешение. Это вход оркестратора, не событие SSM. |
| `SessionTurnInDTO` | Необязательное `navigationAction`. `event` остаётся для `SELECT/CONFIRM/CANCEL`; одновременные независимые намерения не допускаются. |
| `agent-model/.../dto/turn/TurnSuggestionDTO.java` — новый | `text`, необязательный `actionCode`, `kind`. |
| `agent-model/.../enums/SuggestionKind.java` — новый | `COMMAND`, `CONFIRM`, `CANCEL`; граница ACL переводит их в соответствующий performative. В модели нет generated/wire DTO. |
| `TurnOutDTO` | Заменить `availableOperations` единым `List<TurnSuggestionDTO> suggestions`, по умолчанию пустым. Подтверждение и терминальность остаются отдельными данными. |
| `ResultCode` | Добавить успешный `OPERATION_CHOICE_REQUIRED` для показа стартового меню без выдуманного отказа/отмены. Константы `TurnOutcome`, `SessionState`, `SessionEvent` не расширяются; в SessionState добавляются только метаданные категории. |
| `SessionResponseRenderer` | `render(snapshot)` сохраняет обычные исходы; добавить `renderCurrent(snapshot, requestId)`, `withNavigation(output, snapshot)` и общий `operationSuggestions(state)`. Общая навигация/terminal — по категории, представление промежуточного шага — по конкретному state. Отсутствующий снимок явно допустим для текущего меню/навигации. |
| `session-responses.properties` | Вопрос продолжения, начальное меню, отсутствие предыдущей операции и подписи четырёх управляющих кнопок. Новые ключи проверяются при старте, как существующие шаблоны. |

`renderCurrent` сначала различает категории. `INITIAL` даёт `OPERATION_CHOICE_REQUIRED`, `TERMINAL` — завершённый ответ (`SESSION_COMPLETED` для текущего COMPLETED). Для `INTERMEDIATE` отдельный `renderIntermediate(snapshot, requestId)` выбирает представление конкретного шага: сейчас AWAITING_CONFIRM использует прежний `CONFIRMATION_REQUIRED` и общий метод сводки/параметров. Другой промежуточный шаг не получает эту сводку автоматически; отсутствие реализации его представления — ошибка без кнопок, а не fallback. При отсутствии FSM по «Да»: «Предыдущая операция не выбрана. Выберите действие». В ответе всегда новый Request-Id. Входной снимок не мутирует; временно переписывать его `lastResult` ради старого renderer нельзя.

**Расширение:** при добавлении, например, `AWAITING_DETAILS(INTERMEDIATE)` из [плана MVP](../../stages/03_mvp/requirements.md) нужно добавить его предметные данные, проверку сохранённого снимка, шаблон/ветку представления шага и CANCEL-переход с очисткой этих данных. По «Да» возвращается запрос ввода с уже сохранёнными изменениями, а не confirm-сводка. `withNavigation`, ACL и UI сохраняют общие правила без добавления в них проверки нового enum. Достаточно обычного метода/явного разбора конкретных шагов внутри renderer; реестр стратегий, иерархия Java-классов для каждого состояния и новый движок не вводятся. Бизнес-переходы по-прежнему регистрируются в SSM.

Признак terminal в представлении/навигации и проверка терминальности перед навигационным сбросом используют `state.getCategory()`. `OperationCatalog.choices` в текущем POC выдаёт каталог для `INITIAL`, а не только по сравнению с CHOOSING_REQUEST_TYPE; выбор разрешённых операций при будущем расширении остаётся предметным правилом. Проверки конкретных переходов и целостности данных нельзя механически заменить одной категорией: например, AWAITING_DETAILS ещё не имеет готового confirmation snapshot. Нынешние проверки persistence сохраняются, а при реализации нового шага уточняются вместе с ним.

`withNavigation` применяется только к кодам §1, сохраняет исходный код/вид результата и текст, добавляет навигацию по категории; выполняется один раз и не содержит списка промежуточных enum. Подготовка и подтверждение в этих ответах не выдаются. Обычный `propose`, включая результат «Да» именно на AWAITING_CONFIRM, получает от renderer две явные кнопки подтверждения/отказа. «Да» на другом промежуточном шаге возвращает его собственное представление и явно доступные действия.

`AclMapper.suggestions` структурно переносит готовый список, включая `INVALID_COMMAND` с `failure`. Существующий запрет любых саджестов при `ResultKind.ERROR` удаляется: допустимый набор уже определён renderer. Терминальные ответы всегда без кнопок. `toMetadata` может сохранить `response_mode=information` как характеристику ответа; она больше не означает сохранение старых действий UI. В `AclInputAdapter.status` добавить новый `OPERATION_CHOICE_REQUIRED` как 200; HTTP-коды прежних исходов не меняются: `INVALID_COMMAND` — 400/failure с `reason` и навигацией; новое меню — 200/inform.

`LocalHelperController.getFixtures` получает начальные саджесты через тот же `SessionResponseRenderer.operationSuggestions(CHOOSING_REQUEST_TYPE)` и общий ACL mapper; `FixtureMapper` переносит новый performative из общей схемы. Отдельный список операций или текстов в UI не создаётся. Регистрация бизнес-кодов не должна пересекаться с двумя фиксированными навигационными кодами; эту проверку добавить к существующей `SessionStateMachineConfiguration.verifyDefinitions`.

## 4. Чтение, оркестрация и сброс

`SessionTurnOrchestrator.handle` сохраняет приоритеты: ошибка формы → конфликт источников → явная навигация/бизнес-команда → текст. Конфликт получает только оформленный по §1 ответ, без выполнения входов.

- Справка и классификация выполняются вне транзакции. После успешного информационного результата вызвать существующий `fsm.find(sessionId)` и оформить ответ по полученному снимку. Чтение не создаёт строку семафора/native FSM. Не сравнивать старую версию, не повторять LLM при смене шага.
- Если обычный `fsm.process` вернул снимок с `INVALID_COMMAND`, передать его в `withNavigation` без повторного чтения. Если `INVALID_COMMAND` пришёл исключением без снимка, читать после выхода из откатившейся транзакции. Технические ошибки не запускают дополнительное чтение.
- `RESUME`: только согласованное чтение и `renderCurrent`; ни `ensureSemaphore`, ни `process/sendEvent/persist`, ни WorkflowManager/LLM не вызываются.
- `RESET`: вызвать новый `SessionExecutionService.cancelIfPresent(input)` в одной рабочей транзакции, затем сформировать начальное меню/терминальный ответ после её завершения. До сброса отдельный `find` не выполняется.

`cancelIfPresent` возвращает `Optional<SessionSnapshotDTO>`: захватить существующий семафор через `getAndLock` (FOR UPDATE NOWAIT); если строки/native FSM нет — пустой результат без создания. Для существующей FSM переиспользовать восстановление, проверку формата и `processLocked`. На `TERMINAL` вернуть снимок без события/записи; на `INITIAL` вернуть начальный шаг без события/записи. На `INTERMEDIATE` направить `CANCEL` по зарегистрированным guards/actions и сохранить в той же транзакции. Сейчас это прежний переход AWAITING_CONFIRM → CHOOSING_REQUEST_TYPE с `CancelPreparationAction`; обычный reject_propose на выборе сохраняет существующий `ReportNoPreparationAction`. Новый промежуточный шаг добавляет свой CANCEL-переход, а не ветку оркестратора. Категория не разрешает принудительно установить начальный state в обход SSM; если переход не принят, начальное меню как успех не выдаётся. Общее восстановление не дублируется вторым экземпляром машины.

Проверка переданного контекста сохраняется и на новых путях. В `ContextConsistencyGuard` выделить публичный чистый `matches(PaymentContextInDTO, TrustedPaymentContextDTO)` из существующего сравнения; `evaluate` использует его. При чтении для навигации оркестратор проверяет явно переданные поля этим же методом; сброс проверяет их под захваченной блокировкой до применения команды/возврата терминального снимка. Несовпадение даёт `CONTEXT_MISMATCH`, без сводки и кнопок. Новый сервис авторизации или требование полного metadata для последующих ходов не добавляются.

Категория получается из метаданных enum и отдельно не записывается в ExtendedState/DTO снимка. Формат ExtendedState, `formatId`, таблицы и миграции остаются прежними; совместимость добавления метаданных enum подтверждается существующим тестом чтения сохранённого native-снимка. «Да», справка и уточнение не меняют native-байты, номер, исход или версию. «Нет» на промежуточном шаге удаляет данные текущей подготовки/согласие, но сохраняет исходный контекст, sessionId и `lastPreparationNo`; следующий SELECT получает новый номер. Уже выполненную внешнюю операцию сброс не отменяет.

Внутренние синхронные CHECKING_AUTH/VALIDATING_DETAILS из плана MVP относятся к INTERMEDIATE, если будут добавлены. В task06 их нет. Категория не создаёт для них пользовательскую паузу: запрос читает зафиксированный снимок после завершения транзакции либо получает SESSION_BUSY, не прерывая Action и не повторяя проверку.

## 5. Ошибки и конкуренция

| Случай | Поведение |
|---|---|
| FSM отсутствует | Начальное меню, без создания пустой FSM. Это допустимый результат только успешного чтения/проверки отсутствия. |
| Смена шага во время LLM | Кнопки по снимку после LLM; при завершении `final_message=true`, действий нет. Сам справочный текст не отбрасывается ради смены версии. |
| Смена шага после показа кнопок | «Да» читает заново; «Нет» читает/отменяет под блокировкой. Устаревшие клики на выборе дают меню, на завершении — терминальный ответ без повторной операции. |
| Занятость/повреждение/сбой чтения | Существующий `SESSION_BUSY`/`STORAGE_UNAVAILABLE`, без вопроса и кнопок. Успешно сгенерированная справка при невозможности определить навигацию заменяется этим техническим ответом; LLM не повторяется. |
| Ошибка действия/сохранения сброса | Rollback, прежняя подготовка сохраняется при известном откате; ответ с существующей причиной без обещания успешного сброса. |
| Ошибка LLM или подтверждения | Прежний код и текст, без автоматической навигации. Нельзя считать эту ошибку отсутствием операции. |

Снимок согласован на момент чтения; это не обещание, что шаг не изменится до доставки. Нет нового протокола версий, pending-флага, истории кнопок, автоматического retry или нового события «показать шаг». Запрет ввода после завершения остаётся клиентским; дополнительное чтение до LLM ради его серверного запрета не вводится.

## 6. UI

В `agent-ui/src/main/resources/test-ui/session.js`:

- `suggestions(items)` принимает только явные корректные элементы backend и их performative; при отсутствии performative у элемента с кодом используется прежний `request`. Некорректный элемент/неизвестный тип не порождает кнопку.
- `deliver` после проверки корреляции заменяет весь набор действий саджестами текущего ответа. Удаляет прежние `aclState` и `awaitingConfirmation`; новые параметры устанавливает только из текущего успешного `propose`. `information` не сохраняет старые кнопки. `final_message=true` всегда очищает действия и блокирует ввод.
- Полученный 400/failure может иметь явные навигационные саджесты; они отображаются, а текст остаётся ошибкой. Не создавать подтверждение по одному `propose`. Подтверждающие саджесты принимаются только вместе с успешным текущим `propose` и его параметрами.
- `send` передаёт action_code только для `request`; подтверждение — через `accept_propose` с новым полученным `state`. Старые ссылки на кнопки, двойной клик, потеря/несовпадение ответа и поздний ответ другого диалога сохраняют текущую защиту. Автоматических GET/POST-повторов нет.

`app.js` использует существующий вывод списка; менять его только при необходимости для явного типа кнопки. Дизайн страницы и поведение текстового поля task05 не перерабатываются.

## 7. Необходимая проверка

TDD для новой навигации; адаптировать существующие проверки task05, которые ожидают отсутствие чтения или сохранение старых кнопок. Минимальные сценарии и команды — в [tasks.md](tasks.md). Используются stub LLM для маршрутов и синхронизации конкурентных сценариев; промпты/справочный адаптер не меняются, повторный реальный GigaChat evaluation не требуется. Проверить оба ACL-входа, native persistence/rollback, реальные NOWAIT на PostgreSQL, продолжение после рестарта JAR и UI в браузере. После реализации — отдельный валидатор-архитектор; этот документ не является результатом валидации.
