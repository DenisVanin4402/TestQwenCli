## 1. Карточка и контракт

В `agent-model/.../dto/turn` добавить `ConfirmationViewDTO(title, fields, question)` и `ConfirmationDisplayFieldDTO(label, value)`. Значения — готовые строки, поля — упорядоченный список. `TurnOutDTO.confirmationView` необязателен и используется только для представления подтверждения STATUS; это не данные согласия.

В `agent-api-in/src/main/resources/openapi/acl-poc.yaml` добавить необязательный `AclOutputContent.confirmation_view` и схемы `AclConfirmationView`/`AclConfirmationDisplayField`. Внутри объекта обязательны непустые `title`, `question`, непустой список `fields` с непустыми `label`/`value`. Пример дополнения к существующему `result`:

```json
{
  "confirmation_view": {
    "title": "Запрос статуса платежа",
    "fields": [
      {"label": "Номер платежа", "value": "00042"},
      {"label": "Организация", "value": "ООО «Пример»"},
      {"label": "Дата платежа", "value": "03.10.2026"},
      {"label": "Получатель", "value": "ООО «Получатель»"}
    ],
    "question": "Отправить запрос статуса этого платежа?"
  }
}
```

`result` остаётся полным текстом: заголовок, пустая строка, строки «Подпись: значение», пустая строка и вопрос. Старый клиент использует его; новый UI отображает карточку вместо дублирующего текста. В inform/failure карточки нет. Это расширение локального профиля, не утверждение о поддержке поля внешней поверхностью GA.

`AclMapper.toContent` получает `TurnOutDTO`, MapStruct переносит вложенные поля; ветви result/reason/status_code сохраняются. Один mapper обслуживает основной ACL и зеркало. Generated-классы создаются стандартной генерацией, вручную не правятся. Входящие `state[]`, `accept_propose` и guards не меняются.

## 2. Формирование представления

В `SessionResponseRenderer.renderOutcome` сформировать view только для STATUS/CONFIRMATION_REQUIRED; `renderCurrent` использует тот же путь. Номер — из `preparation.confirmationSnapshot`; организация, дата и получатель — из `preparation.context`. Порядок фиксирован по AC; дату форматирует существующий formatter. Никакого чтения fixture/нового metadata или LLM.

В `session-responses.properties` определить подписи/заголовок карточки. `status.proposal` становится вопросом «Отправить запрос статуса этого платежа?» без аргументов. Текстовое представление собирается из готового view, поэтому четыре значения не дублируются в отдельном шаблоне. Схему `confirmationFields` ради отображения не расширять; для прочих регистраций сохраняется существующее представление. Новые обязательные строки проверяются при старте вместе с каталогом. Native-снимок, PreparationDTO и Liquibase не меняются.

Заменить только `INVALID_COMMAND.message` на «Сейчас это действие недоступно. Есть незавершённая операция.». `error.INVALID_COMMAND` остаётся отдельным текстом guard-отказа. `withNavigation` по-прежнему добавляет вопрос и «Да»/«Нет» на активном шаге.

## 3. Тестовый UI

`session.js`: после проверки корреляции сохранять валидную `confirmation_view` в конкретном сообщении истории только при успешном propose. Отсутствующий/неполный объект не мешает показать `result`. ## 4. Знания и ответ о возможностях

Заменить `agent-api-out/src/main/resources/knowledge/status-reference.md` содержанием разделов KB-01…KB-10 из knowledge.md. Удалить старые статьи и примеры про отсутствие комиссий, сроков и возможностей. По уточнению пользователя наименование — «Банк», стиль — профессиональная банковская справка для обычных клиентов, комиссия по RUB — 50 рублей. Оговорки о вымышленных/учебных/демонстрационных условиях из знаний и ответов убрать. Документ task05 остаётся историей прежнего набора, с указанием замены в текущих документах этапа.

Чтобы перечень операций следовал реальной регистрации:

- `ReferenceAnswerProvider.answer(String question, List<OperationSpecDTO> operations)` принимает каталог; `SessionTurnOrchestrator` передаёт `operations.registeredOperations()` в ветке REFERENCE.
- `GigaChatReferenceAnswerProvider` формирует короткий раздел **KB-00. Зарегистрированные операции** из переданных `title`/`actionCode`. Это дополнение к KNOWLEDGE, с допустимой меткой KB-00; статический ресурс не может определять эту зарезервированную метку. Список вычисляется из аргумента вызова, без отдельного реестра, записи в БД или перечисления всех значений enum Operation.
- В промпте указать: KB-00 — единственный источник перечня операций; пользователь видит названия, а не actionCode. Это перечень возможностей агента, текущие кнопки и допустимость действия определяет приложение.
- KB-02 — перечень тем справки. На «Что делает агент?», «Что ты можешь?», «Какие операции доступны?» ответ явно содержит **операции и справку**. На текущей регистрации пример: «Могу подготовить запрос статуса выбранного платежа и после вашего подтверждения передать его на обработку. Также могу рассказать о комиссии, сроках обработки, графике работы Банка, валютах и порядке оформления обращения». Это образец смысла, не требование дословного вывода LLM. Правило двух частей задаётся в промпте; статьи содержат справочные сведения, а не инструкции по формированию ответа.

В `gigachat-prompts.yaml`:

1. Классификация: явно привести оба вопроса о возможностях как REFERENCE; запрос фактического статуса остаётся COMMAND, команда вместе со справкой — MIXED. Убрать жёсткое «Сейчас зарегистрирован STATUS»; каталог остаётся источником команд.
2. Справка: обновить указатель KB-00…KB-10, пример комиссии и инструкцию о возможностях; удалить требования перечислять неизвестные тарифы/недоступные данные и отвечать об отсутствии чисел.
3. Для комиссий/сроков/валют использовать условия из знаний и говорить от имени Банка простым профессиональным языком. Не добавлять оговорки об учебном, демонстрационном или вымышленном характере условий. В примере комиссии по RUB — 50 рублей за обращение, независимо от суммы платежа. Несколько справочных тем отвечаются вместе. Вопрос без источника даёт found=false; не добавлять к каждому успешному ответу список ограничений.
4. Сохранить ответ только по источникам, проверку `found/answer/sourceIds`, запрет принимать текст вопроса за источник или согласие, одну попытку справки и существующие попытки классификации. Новая настройка каталога и изменение `GigaChatReferenceProperties` не требуются: KB-00 входит в имеющийся блок KNOWLEDGE.

Уточнение по реальному прогону: user-промпты явно ставят задачу классификации/справки и передают клиентский текст внутри блока данных; это предотвращает стандартный ответ модели о себе вместо JSON на «Что ты можешь?». Число вызовов и строгий контракт не меняются.

Обновить реализации/заглушки provider и места вызова в тестах/evaluation под новую сигнатуру. Нет нового MessageRoute, ResultCode, события FSM, отдельного сервиса возможностей, поиска или embeddings.

## 5. Ошибки и совместимость

Пустой ресурс/отсутствие KB-разделов, повторная метка или статическая KB-00 — ошибка конфигурации при старте. Некорректный ответ модели остаётся REFERENCE_FAILED/HTTP 500; валидный ответ без меток источников — REFERENCE_NOT_FOUND, неизвестная метка — нарушение контракта/REFERENCE_FAILED. Исчерпанная ошибка классификации сохраняет TEXT_ANALYSIS_FAILED. Чистая справка и описание возможностей не создают/изменяют FSM; последующее чтение/навигация task06 сохраняются.

Некорректный view на клиенте приводит к показу полноценного result, без повторного POST. Успешное согласие использует прежний state даже при отсутствии карточки. Старый совместимый снимок строит view по уже сохранённому контексту; представление не записывается обратно. Отдельного слоя миграции/персистентного формата не требуется.
