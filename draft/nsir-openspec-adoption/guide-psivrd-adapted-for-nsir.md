# OpenSpec Guide для команды НСиР

Адаптация подхода команды ПСиВРД под folder-based SDD/OpenSpec framework, `docs-hub`, сервисную архитектуру НСиР и смешанный формат работы аналитиков: ручные правки документов, `openspec-explore` и `openspec-propose`.

Исходная управленческая логика взята из гайда ПСиВРД в `docs/sdd-explore/guide-default-openspec(masterspec-as-a-single-file).html`, но single-file master-spec допущения заменены на текущую folder-based модель НСиР.

## 1. Формат пилота

Пилот нужен не для того, чтобы сразу перевести всю документацию НСиР в идеальное состояние. Цель пилота - проверить на реальных задачах, помогает ли SDD/OpenSpec быстрее и надежнее проходить путь:

```text
идея / Jira
  -> понимание текущего поведения
  -> согласованное изменение
  -> технический план
  -> код и тесты
  -> актуальная документация
```

### Границы пилота

На первом этапе не распространяем процесс на все сервисы и все типы задач. Берем ограниченный набор:

- один основной сервис, например `invest-dkz`;
- одну сквозную область НСиР;
- 2-3 задачи разной формы:
  - изменение workflow;
  - изменение интеграции или модели;
  - изменение фронтового поведения;
  - небольшое изменение справочника или настройки.

### Что считаем хорошим результатом

Хороший результат пилота - не количество сгенерированных Markdown-файлов, а снижение потерь смысла между аналитикой, разработкой и приемкой.

Команда должна получить:

- понятную структуру `docs-hub`;
- понятный способ работы аналитиков с Git и AI-агентом;
- рабочие `change.md`, которые разработчик может брать без устной расшифровки;
- `design.md` и `tasks.md`, которые не противоречат аналитике;
- проверяемые критерии приемки и автотесты там, где они нужны.

## 2. Почему ПСиВРД-гайд важен, но не переносится буквально

В гайде ПСиВРД полезны:

- объяснение SDD простым языком;
- роль `change.md` как инкремента к спецификации;
- разделение `change.md`, `design.md`, `tasks.md`;
- review gates;
- DoR/DoD;
- метрики пилота;
- мысль, что SDD - это командный процесс, а не одиночный vibe coding.

Для НСиР нужно изменить базовые допущения:

| В ПСиВРД-гайде | В НСиР |
|---|---|
| Сильный акцент на восстановление single-file baseline/spec. | Master specification - папка документов, контрактов и диаграмм. |
| Confluence сверяется с кодом при brownfield-восстановлении. | Confluence сначала мигрирует в `docs-hub`, затем Git становится рабочим источником. |
| Основной OpenSpec-flow идет через `propose` и `apply-change`. | Есть три равноправных входа: `explore`, `propose`, `change-from-diff`. |
| `apply-change` обновляет baseline. | Для branch-diff чаще нужен verify source, потому что документы уже изменены в ветке аналитика. |
| Есть QA как отдельная роль. | Отдельных тестировщиков нет: приемку делают аналитики, автотесты делает разработка. |

## 3. Термины

| Термин | Смысл для НСиР |
|---|---|
| SDD | Подход, где изменение сначала становится понятной спецификацией, затем проектируется и реализуется. |
| OpenSpec | Набор правил и skills для работы со спецификациями, changes, design, tasks и archive. |
| Master specification | Актуальная документация сервиса или области в виде папки документов. |
| `_sdd` | Навигационный слой для агента: manifest, navigation, coverage, stale-files. |
| `openspec-explore` | Read-only исследование документации и кода. Используется для понимания текущего состояния и зоны влияния. |
| `openspec-propose` | Создание `change.md` через интервью, master-spec context и исследование. |
| `openspec-change-from-diff` | Создание `change.md` из diff ветки аналитика и базовой ветки. |
| `change.md` | Аналитическое описание "что и зачем меняем". |
| `design.md` | Технический проект "как реализуем". |
| `tasks.md` | Исполняемый план реализации и проверки. |
| Branch-diff | Режим, где аналитик сначала меняет документы в Git, а агент строит change по diff. |
| Manual-change | Режим, где change сначала формируется как предложение, а документы обновляются явно позже. |
| Verify source | Проверка, что master-spec документы уже содержат согласованные изменения. |

## 4. Три режима работы аналитика

НСиР не должен сводить работу аналитика только к ручной правке Markdown-файлов. У аналитика есть три нормальных режима.

### Режим 1. Explore

Используется, когда аналитик хочет понять текущую область до изменения:

- как сейчас описан workflow;
- какие документы связаны с сущностью;
- какие интеграции затронуты;
- какие места в коде подтверждают или опровергают документацию;
- где есть gaps и противоречия.

`explore` не создает change и не меняет файлы без отдельного решения. Это режим исследования.

Пример запроса:

```text
Работаем по OpenSpec explore.
Нужно исследовать область обработки входящего УЭСИД по НСиР для сервиса invest-dkz.

Найди:
- релевантные workflow-документы;
- модели данных;
- интеграции;
- фронтовые документы;
- места в коде, если они доступны;
- gaps и противоречия.

Ничего не меняй, подготовь карту контекста и вопросы аналитику.
```

Результат:

- карта релевантных документов;
- список затронутых сущностей и процессов;
- open questions;
- рекомендации: идти в `propose`, править docs branch или обновить `_sdd`.

### Режим 2. Propose

Используется, когда аналитик еще не внес правки в документы, но хочет вместе с агентом сформировать изменение.

Это удобно:

- для новых требований;
- для неясных задач;
- для аналитиков, которым проще обсуждать задачу в чате;
- для быстрых черновиков перед ручной правкой документов.

Пример запроса:

```text
Работаем по OpenSpec propose для сервиса invest-dkz.
Нужно оформить change по NSIR-245.

Суть: при получении уточняющего ответа из внешней системы нужно изменить обработку невыясненной суммы и дальнейший workflow расследования.

Сначала задай вопросы по скоупу и источникам.
Используй master-spec документы, explore при необходимости и не переходи к design без моего подтверждения.
Spec update mode: manual-change.
```

Результат:

- `openspec/changes/<change-name>/change.md`;
- статус `На согласовании`;
- источники master specification;
- open questions;
- критерии приемки.

После согласования можно:

- обновить master-spec документы вручную;
- открыть docs PR;
- создать `design.md` и `tasks.md`.

### Режим 3. Ручная правка документов + change-from-diff

Используется, когда аналитик знает, какие страницы нужно поменять, и хочет сохранить привычный сценарий Confluence-цветов.

Отличие: вместо цветов в Confluence используется ветка и Git diff.

Шаги:

1. Аналитик создает ветку `analysis/NSIR-245-short-name`.
2. Меняет несколько документов в `docs-hub`.
3. Коммитит изменения.
4. Агент создает `change.md` по diff.

Пример запроса:

```text
Создай change из diff master specification.
service=invest-dkz
base_ref=release/2026-07
analyst_ref=analysis/NSIR-245-short-name
change_name=nsir-245-short-name
diff_mode=three-dot

Важно:
- не делай checkout веток;
- анализируй added/modified/deleted/renamed документы;
- используй manifest и related context;
- сформируй не patch-summary, а полноценный change.md.
```

Результат:

- `change.md` со статусом `На согласовании`;
- `.spec-diff/` с metadata diff;
- источники изменения;
- context files;
- рекомендации по design/tasks.

## 5. Как выбрать режим

| Ситуация | Режим |
|---|---|
| Аналитик не уверен, где описан процесс. | `explore` |
| Нужно быстро понять влияние изменения. | `explore` |
| Требование есть, но документы еще не меняли. | `propose` |
| Нужно сформировать change через интервью. | `propose` |
| Аналитик уже изменил несколько документов. | `change-from-diff` |
| Нужно сохранить привычную модель "несколько страниц под Jira". | `change-from-diff` |
| Документация устарела или manifest не видит новые файлы. | `init-master-spec refresh` |
| Change согласован, нужен технический план. | `design` |
| Есть tasks, пора кодить. | `implement` |
| Реализация готова, документы были изменены в analyst branch. | `verify source` |
| Реализация готова, документы еще не обновлены. | `apply-change` как manual gateway |

## 6. Артефакты

### Master specification

Master specification в НСиР - это папка документов:

```text
docs-hub/
  invest-dkz/
    workflow/
    integrations/
    model/
    dictionaries/
    openapi/
    settings/
    frontend/
  common/
    cross-service-processes/
    glossary/
```

Навигационный слой:

```text
openspec/<service>/_sdd/
  manifest.yaml
  navigation.md
  coverage.md
  stale-files.md
```

### Change package

```text
openspec/changes/<change-name>/
  change.md
  design.md
  tasks.md
  .research/
  .spec-diff/
```

Назначение:

| Артефакт | Роль |
|---|---|
| `change.md` | Аналитический инкремент. Что и зачем меняем. |
| `.research/` | Результаты read-only исследования. |
| `.spec-diff/` | Metadata веточного diff для branch-diff режима. |
| `design.md` | Техническое решение. |
| `tasks.md` | Исполняемый план разработки и проверки. |

## 7. Роли

| Роль | Ответственность |
|---|---|
| Аналитик | Исследует область, меняет документы или запускает propose, ревьюит `change.md`, принимает результат. |
| Разработчик | Делает design/tasks, реализует код, добавляет автотесты, связывает code PR с change. |
| Владелец продукта | Подтверждает бизнес-ценность, приоритет, границы и критерии приемки. |
| Tech lead | Проверяет архитектуру, интеграции, миграции, Docker/OpenShift, риски. |
| AI-агент | Помогает читать, структурировать и реализовывать, но не принимает решения за команду. |

Отдельной роли тестировщика нет. Поэтому тестовые обязанности явно распределяются:

- аналитик отвечает за приемочные сценарии;
- разработчик отвечает за автотесты;
- tech lead проверяет достаточность технической верификации для рискованных изменений.

## 8. Флоу работы команды

### Flow 1. Исследование области через explore

| Шаг | Кто | Что происходит | Результат |
|---|---|---|---|
| 1 | Аналитик | Формулирует область исследования. | Есть тема и сервис. |
| 2 | Агент | Читает `_sdd/navigation.md` и `manifest.yaml`. | Выбран контекст. |
| 3 | Агент | Выполняет read-only анализ docs/code. | Карта области. |
| 4 | Аналитик | Проверяет gaps и вопросы. | Решение: propose, docs branch или refresh. |

### Flow 2. Новый change через propose

| Шаг | Кто | Что происходит | Результат |
|---|---|---|---|
| 1 | Аналитик | Описывает задачу обычным языком. | Начальное требование. |
| 2 | Агент | Проводит интервью и читает master spec. | Уточненный scope. |
| 3 | Агент | При необходимости делает explore зоны изменения. | Подтвержденный контекст. |
| 4 | Агент | Создает `change.md`. | Change на согласовании. |
| 5 | Аналитик/PO | Ревьюит и согласует. | Статус `Согласовано`. |
| 6 | Разработчик | Создает `design.md` и `tasks.md`. | Готовность к реализации. |

### Flow 3. Change из ветки аналитика

| Шаг | Кто | Что происходит | Результат |
|---|---|---|---|
| 1 | Аналитик | Создает ветку от base ref. | `analysis/<jira>-...` |
| 2 | Аналитик | Меняет документы master specification. | Docs diff. |
| 3 | Агент | Выполняет `change-from-diff`. | `change.md` + `.spec-diff/`. |
| 4 | Команда | Ревьюит смысл change. | `Согласовано` или доработка docs. |
| 5 | Разработчик | Создает design/tasks и реализует. | Code PR. |
| 6 | Агент/разработчик | Проверяет source в analyst ref. | Change `Реализовано`. |

### Flow 4. Реализация

| Шаг | Кто | Что происходит |
|---|---|---|
| 1 | Разработчик | Читает `change.md`, `design.md`, `tasks.md`. |
| 2 | Разработчик/агент | Выполняет tasks последовательно. |
| 3 | Разработчик | Добавляет или обновляет тесты. |
| 4 | Разработчик | Проверяет Docker/OpenShift/config, если затронуты. |
| 5 | Аналитик | Выполняет приемку по критериям. |
| 6 | Команда | Закрывает verify/apply и archive. |

## 9. Source of truth

### Переходное состояние

До полного переезда:

- Confluence остается входным источником;
- код и тесты помогают проверить фактическое поведение;
- `docs-hub` постепенно становится рабочей копией аналитики;
- gaps фиксируются явно.

### Целевое состояние

После миграции:

- `docs-hub` хранит согласованное поведение;
- Jira хранит задачу, статус, приоритет и ссылки;
- code repos реализуют согласованное поведение;
- OpenSpec artifacts связывают Jira, docs, design, tasks, code и tests.

Формула:

```text
Jira отвечает за "что делаем и статус".
docs-hub отвечает за "как должна работать система".
code repo отвечает за "как это реализовано".
OpenSpec change отвечает за "как изменение прошло от смысла до реализации".
```

## 10. Review gates

### Gate 1. Explore review

Используется, если работа начиналась с исследования.

Проверяем:

- агент нашел правильные документы;
- gaps не скрыты;
- связанные сервисы и интеграции не потеряны;
- понятно, нужно ли переходить к `propose` или docs branch.

### Gate 2. Change review

Проверяем:

- понятна цель;
- scope ограничен;
- источники указаны;
- влияние на сервисы, интеграции, БД, фронт и конфигурацию описано;
- критерии приемки проверяемы;
- open questions видны;
- `change.md` не содержит технический план реализации.

### Gate 3. Design review

Проверяем:

- техническое решение соответствует change;
- учтены code repos;
- учтены миграции, OpenShift, Docker, наблюдаемость;
- есть план тестов;
- tasks исполняемы.

### Gate 4. Code review

Проверяем:

- код соответствует `change.md` и `design.md`;
- тесты обновлены;
- PR связан с Jira и change;
- нет скрытого расширения scope.

### Gate 5. Source/apply review

Для branch-diff:

- analyst ref существует;
- diff summary совпадает с `.spec-diff`;
- master-spec документы содержат согласованные изменения;
- `_sdd` не stale или refresh запланирован.

Для manual-change:

- документы master specification обновлены;
- `_sdd` refreshed;
- change можно перевести в `Реализовано`.

## 11. DoR / DoD

### Ready для разработки

- Есть Jira.
- Есть `change.md`.
- Change в статусе `Согласовано`.
- Указан `Spec update mode`.
- Есть sources master specification.
- Есть критерии приемки.
- Для сложного изменения есть `design.md` и `tasks.md`.
- Нет блокирующих open questions.

### Done

- Все tasks выполнены.
- Code PR merged или готов к merge по правилам команды.
- Тесты запущены или причина отсутствия тестов зафиксирована.
- Аналитик подтвердил приемку.
- Master-spec source проверен или обновлен.
- Change переведен в `Реализовано`.
- Change архивирован.

## 12. Метрики пилота

| Метрика | Что показывает |
|---|---|
| Time to first useful draft | Как быстро появляется пригодный `change.md` или карта explore. |
| Prompt iterations | Сколько уточнений понадобилось агенту. |
| Missing context count | Сколько затронутых документов/сервисов не нашли до реализации. |
| Change review rework | Сколько раз change возвращался на доработку. |
| Test coverage delta | Появились ли тесты по change. |
| Spec drift incidents | Разошлись ли docs и code после merge. |
| Analyst Git friction | Где аналитики блокируются на Git/Bitbucket. |
| AI draft acceptance rate | Какая часть результата агента принята после review. |

## 13. Безопасные правила

1. Агент сначала читает, потом предлагает, потом меняет.
2. `explore` всегда read-only.
3. `change.md` описывает что и зачем, а не как кодить.
4. Нельзя начинать реализацию при статусе `На согласовании`.
5. Для branch-diff агент не делает `git fetch`, `git pull`, `git checkout base_ref` или `git checkout analyst_ref`.
6. Для folder-based master spec автоматический merge по умолчанию не используется.
7. Если агент нашел проблему вне scope, это open question или follow-up, а не скрытое расширение задачи.
8. Секреты, персональные данные и production-конфигурации не передаются агенту без отдельного разрешения.

## 14. Что показывать на вводной встрече

За 60-90 минут важно показать не весь фреймворк, а три входа:

1. `explore`: аналитик просит исследовать область и получает карту контекста.
2. `propose`: аналитик формирует новый change через интервью.
3. `change-from-diff`: аналитик меняет документы в ветке, агент делает change из diff.

После этого показать общий хвост:

```text
review change
  -> design.md
  -> tasks.md
  -> implementation
  -> tests
  -> verify/apply
  -> archive
```

## 15. Главный смысл для НСиР

SDD/OpenSpec не заменяет Confluence одним большим Markdown и не заставляет аналитика становиться разработчиком.

Для НСиР это способ:

- сохранить сильную сторону текущего процесса: аналитик работает с предметной документацией;
- добавить Git traceability вместо цветовых выделений;
- дать разработчику не набор разрозненных страниц, а согласованный change;
- сделать тесты и приемку частью задачи, а не последним ручным этапом;
- поддерживать документацию актуальной после реализации.
