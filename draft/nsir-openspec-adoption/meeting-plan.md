# План вводной встречи по SDD/OpenSpec для НСиР

## Цель встречи

За 60-90 минут команда должна понять не "что такое OpenSpec вообще", а как именно НСиР будет работать с документацией и изменениями после переезда из Confluence в `docs-hub`.

Ожидаемый результат встречи:

- аналитики понимают, как привычная модель "несколько страниц под одну Jira-задачу" переносится в Git;
- аналитики понимают, что могут работать не только через ручную правку документов, но и через `explore` и `propose`;
- разработчики понимают, где брать согласованное описание изменения и как превращать его в `design.md` и `tasks.md`;
- владелец продукта понимает, где смотреть смысл изменения, критерии приемки и статус;
- команда согласует пилотные правила: какие задачи берем первыми, кто ревьюит, что считается готовностью.

## Подготовка до встречи

Минимально нужно подготовить:

1. Один пример сервиса или области: например `invest-dkz`, `invest-pay` или общая сквозная область НСиР.
2. Один демонстрационный Jira-кейс: изменение workflow, интеграции, справочника, доменной модели или фронтового поведения.
3. Один пример запроса для `explore`: область, по которой агент должен найти документы, gaps и вопросы.
4. Один пример запроса для `propose`: задача, которую агент оформит через интервью.
5. Ветка/пример в `docs-hub`, где изменены 2-5 Markdown-файлов master specification.
6. Локальные refs для демо branch-diff:

```text
base_ref=<базовая ветка или ref>
analyst_ref=<ветка с правками аналитика>
service=<service-name>
change_name=<jira-key>-<short-name>
```

7. Локально доступный AI-агент с SDD/OpenSpec skills.
8. Резервный вариант: показать уже созданный пример из `docs/sdd-explore/history.md`, если live demo не пойдет.

## Демо-сценарий

### Шаг 1. Показать текущую проблему

Коротко показать старую модель:

- Jira-задача;
- несколько страниц Confluence;
- изменения выделены цветом;
- разработчик вручную ищет, какие куски относятся к задаче;
- после реализации трудно проверить, что документация и код снова синхронны.

Не нужно критиковать Confluence. Важно сказать: сильная сторона текущего процесса - аналитик меняет предметную документацию, а не пишет техническую спецификацию с нуля. Эту сильную сторону сохраняем.

### Шаг 2. Показать новую структуру

```text
docs-hub/
  <service-name>/
    workflow/
    integrations/
    model/
    dictionaries/
    openapi/
    settings/
    frontend/
  common/
    cross-service-processes/
    glossary/
  openspec/
    <service-name>/
      _sdd/
        manifest.yaml
        navigation.md
        coverage.md
        stale-files.md
    changes/
      <change-name>/
        change.md
        design.md
        tasks.md
        .spec-diff/
```

Пояснение: фактическая документация может лежать в привычном дереве `docs-hub/<service-name>/...`, а OpenSpec-слой хранит change-артефакты и навигацию для агента. Важно, чтобы команда договорилась о едином master-spec root и не смешивала разные схемы внутри одного сервиса.

### Шаг 3. Показать `explore` как первый режим аналитика

Формулировка для агента:

```text
Работаем по OpenSpec explore.
Нужно исследовать область обработки входящего УЭСИД по НСиР для сервиса invest-dkz.
Найди релевантные workflow, модели, интеграции, фронтовые документы, gaps и открытые вопросы.
Ничего не меняй.
```

Что показать:

- аналитик может использовать агента как исследователя, не меняя документы;
- результатом является карта контекста и вопросы, а не код;
- после explore можно перейти к `propose` или ручной правке документов.

### Шаг 4. Показать `propose` как второй режим аналитика

Формулировка:

```text
Работаем по OpenSpec propose для сервиса invest-dkz.
Нужно оформить change по NSIR-123.
Суть: <краткое описание изменения>.
Сначала задай вопросы по скоупу и источникам, затем подготовь change.md.
```

Что показать:

- аналитик может не начинать с Git-правок;
- агент проводит интервью и читает master-spec context;
- `change.md` появляется до технического дизайна.

### Шаг 5. Сгенерировать `change.md` из diff

Формулировка для агента:

```text
Создай change из diff master specification.
service=invest-dkz
base_ref=release/2026-07
analyst_ref=analysis/NSIR-123-update-product-type
change_name=nsir-123-update-product-type
diff_mode=three-dot
```

Что показать:

- агент не делает checkout веток;
- агент читает diff только по master-spec root;
- агент использует manifest и context files;
- в `change.md` появляется не механический patch, а смысл изменения: что меняется, зачем, какие модели, workflow, интеграции, критерии приемки.

### Шаг 6. Показать review `change.md`

Команда смотрит:

- понятна ли бизнес-цель;
- все ли затронутые документы учтены;
- есть ли open questions;
- можно ли это отдавать в разработку;
- нужны ли изменения автотестов и ручной приемки аналитика.

Статус после ревью: `Согласовано`.

### Шаг 7. Создать `design.md` и `tasks.md`

Формулировка:

```text
Подготовь design.md и tasks.md для change nsir-123-update-product-type.
Учитывай service-based архитектуру, Docker/OpenShift, интеграции и автотесты.
```

Что показать:

- `design.md` - инженерное решение, не замена аналитики;
- `tasks.md` - исполняемый чеклист для разработчика;
- задачи должны быть мелкими и проверяемыми;
- для branch-diff финальный `apply-change` не обязателен, потому что master-spec уже изменена в ветке аналитика. Нужен verify.

### Шаг 8. Показать финальную трассировку

```text
Jira NSIR-123
  -> docs-hub branch analysis/NSIR-123-update-product-type
  -> docs PR
  -> openspec/changes/nsir-123-update-product-type/change.md
  -> code branch feature/NSIR-123-update-product-type
  -> code PR
  -> tests
  -> acceptance
  -> archive
```

## Что важно проговорить вслух

1. OpenSpec не заменяет аналитика. Он структурирует изменение и снижает потерю контекста.
2. `change.md` не должен содержать технический план реализации. Он отвечает на "что и зачем".
3. `design.md` и `tasks.md` появляются после согласования change.
4. Для НСиР есть три рабочих входа: `explore`, `propose`, `change-from-diff`.
5. Branch-diff сохраняет привычку аналитика менять несколько документов под Jira, но не отменяет `explore` и `propose`.
6. Если аналитик пока не готов работать с Git, можно стартовать через `propose`, парную работу с разработчиком или web UI Bitbucket.
7. Отсутствие тестировщиков компенсируется не ручным героизмом, а явными критериями приемки и автотестами в `tasks.md`.

## Частые вопросы на встрече

**Нужно ли аналитикам учить Git глубоко?**

Нет. Для пилота достаточно: создать ветку, изменить файлы, открыть PR, прочитать diff, ответить на комментарии. CLI не обязателен, можно начинать с Bitbucket UI.

**Что делать с цветами из Confluence?**

В Git цвет заменяется diff. Если к одной Jira меняется несколько страниц, они меняются в одной ветке и одном PR. Дополнительно в начале каждого измененного документа можно оставить короткий блок "Изменения по NSIR-123", если это помогает ревью.

**Где живет истина - Jira, docs-hub или код?**

Jira хранит задачу и статус работы. `docs-hub` хранит согласованное поведение системы. Код должен реализовать согласованное поведение. Если код и docs расходятся, это отдельный gap или change.

**Почему нельзя просто дать разработчику Confluence/Markdown diff?**

Можно, но тогда каждый разработчик заново интерпретирует изменения. `change.md` превращает набор правок в проверяемое требование с источниками, влиянием, критериями и open questions.

## После встречи

1. Выбрать 1 простую и 1 среднюю пилотную задачу.
2. Назначить аналитика, разработчика и reviewer-а по каждой.
3. Для каждой задачи выбрать режим старта: `explore`, `propose` или `change-from-diff`.
4. Создать ветки в `docs-hub`, если выбран branch-diff.
5. Договориться, что первые 2-3 задачи делаются парно: аналитик + разработчик + агент.
6. Через неделю провести короткий разбор: что сработало, что нужно упростить.
