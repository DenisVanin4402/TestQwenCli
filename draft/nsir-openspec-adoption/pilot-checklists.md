# Чеклисты пилота SDD/OpenSpec для НСиР

## 1. Старт пилота

Перед стартом:

- [ ] Выбраны 1-2 сервиса для пилота.
- [ ] Выбран 1 сквозной процесс, если нужно проверить multi-service сценарий.
- [ ] В `docs-hub` заведена базовая структура документации.
- [ ] Для пилотных сервисов создан или запланирован `_sdd`.
- [ ] Команда договорилась о branch naming.
- [ ] Команда договорилась, где лежат active changes.
- [ ] Команда договорилась, когда начинать с `explore`, когда с `propose`, а когда с ручной docs branch.
- [ ] Определен способ связи docs PR и code PR.
- [ ] Выбраны 2-3 реальные Jira-задачи разной сложности.
- [ ] Назначены аналитик, разработчик и reviewer по каждой задаче.

## 2. Definition of Ready для change

Change можно брать в design/разработку, если:

- [ ] Есть Jira-задача или понятный бизнес-запрос.
- [ ] Определен сервис или сквозная область.
- [ ] Есть `change.md`.
- [ ] `change.md` содержит master-spec root и manifest.
- [ ] Указан `Spec update mode`: `branch-diff` или `manual-change`.
- [ ] Для branch-diff указаны `base_ref`, `analyst_ref`, `diff_mode`.
- [ ] В sources указаны все важные master-spec documents.
- [ ] Понятна бизнес-цель.
- [ ] Scope не размыт.
- [ ] Есть критерии приемки.
- [ ] Open questions не блокируют разработку или явно вынесены в follow-up.
- [ ] Аналитик поставил статус `Согласовано`.

## 2А. Definition of Ready для explore

Explore можно запускать, если:

- [ ] Понятна область исследования: сервис, процесс, сущность, интеграция или Jira.
- [ ] Задан режим read-only.
- [ ] Понятно, что нужно получить: карта документов, влияние, gaps, вопросы, code references.
- [ ] Указано, можно ли смотреть code repo или только `docs-hub`.
- [ ] Аналитик готов после результата выбрать следующий шаг: `propose`, docs branch, refresh `_sdd` или follow-up.

## 3. Definition of Ready для реализации

Код можно начинать, если:

- [ ] Change в статусе `Согласовано` или `В реализации`.
- [ ] Для сложного изменения есть `design.md`.
- [ ] Есть `tasks.md`.
- [ ] В `tasks.md` есть задачи на тесты.
- [ ] Понятны затронутые code repos.
- [ ] Понятны изменения БД, миграции, конфигурации, OpenShift, если они есть.
- [ ] Понятна приемка аналитика.
- [ ] Риски и rollback описаны или явно не требуются.

## 4. Definition of Done

Change можно считать реализованным, если:

- [ ] Все рабочие задачи в `tasks.md` выполнены.
- [ ] Кодовые PR связаны с Jira и change.
- [ ] Релевантные unit/integration/e2e тесты пройдены.
- [ ] Если тесты не запускались, причина явно зафиксирована.
- [ ] Аналитик выполнил приемку или подтвердил критерии на тестовом контуре.
- [ ] Для branch-diff выполнен verify master-spec source.
- [ ] Для manual-change документы master specification обновлены и `_sdd` refreshed.
- [ ] Change переведен в `Реализовано`.
- [ ] Change архивирован после завершения.

## 5. Review checklist для `change.md`

- [ ] В `change.md` нет технического плана реализации.
- [ ] Есть цель изменения.
- [ ] Есть инициатор или ссылка на Jira.
- [ ] Есть список затронутых компонентов.
- [ ] Описаны изменения бизнес-логики.
- [ ] Описаны изменения workflow/FSM, если затронуты.
- [ ] Описаны изменения моделей данных, если затронуты.
- [ ] Описаны изменения интеграций/API, если затронуты.
- [ ] Описаны изменения фронта, если затронуты.
- [ ] Описаны ошибки, валидации, роли/доступы, если затронуты.
- [ ] Описана миграция и обратная совместимость, если нужна.
- [ ] Есть критерии приемки.
- [ ] Для незатронутых разделов явно указано `Нет изменений.`
- [ ] Open questions видны.

## 5А. Review checklist для explore-результата

- [ ] Найдены ключевые master-spec documents.
- [ ] Найдены связанные workflow, модели, справочники и интеграции.
- [ ] Фронтовые документы проверены, если сценарий пользовательский.
- [ ] Code references указаны, если код был доступен.
- [ ] Gaps и противоречия не скрыты.
- [ ] Есть рекомендации следующего шага.
- [ ] Агент не изменил файлы в read-only режиме.

## 6. Review checklist для `design.md`

- [ ] Design ссылается на `change.md`.
- [ ] Design ссылается на master-spec documents.
- [ ] Названы code repos и модули.
- [ ] Описан технический подход.
- [ ] Описаны изменения БД/миграций.
- [ ] Описаны изменения API/интеграций.
- [ ] Описаны изменения конфигурации, Docker/OpenShift.
- [ ] Описаны изменения мониторинга/логирования, если нужны.
- [ ] Указаны риски.
- [ ] Указан rollback или причина, почему он не нужен.
- [ ] Нет выдуманных технологий.

## 7. Review checklist для `tasks.md`

- [ ] Tasks разбиты на небольшие исполняемые шаги.
- [ ] Есть отдельные секции по backend/frontend/integration/config/tests, если применимо.
- [ ] Есть задача на обновление автотестов.
- [ ] Есть задача на приемочный сценарий аналитика.
- [ ] Есть задача на проверку master-spec source.
- [ ] Для branch-diff нет требования обязательного final apply-change.
- [ ] Чекбоксы можно выполнять последовательно.
- [ ] Нет задач, которые требуют неявного продуктового решения.

## 8. Чеклист аналитика при правке docs-hub

- [ ] Ветка создана от правильной базовой ветки.
- [ ] Jira key есть в имени ветки или commit message.
- [ ] Изменены все документы, которые заменяли бы Confluence-цвета.
- [ ] Новые термины добавлены в glossary или доменную модель.
- [ ] Изменения в workflow согласованы с моделями и интеграциями.
- [ ] Изменения фронта согласованы с фронтовой документацией.
- [ ] Удаленные документы удалены осознанно.
- [ ] PR открыт и готов к diff review.
- [ ] После правок запрошен refresh `_sdd`, если manifest стал stale.

## 9. Чеклист разработчика перед кодом

- [ ] Прочитан `change.md`.
- [ ] Прочитан `design.md`, если есть.
- [ ] Прочитан `tasks.md`.
- [ ] Понятен `Spec update mode`.
- [ ] Понятны затронутые docs sources.
- [ ] Понятны критерии приемки.
- [ ] Понятны тесты, которые нужно добавить.
- [ ] В code PR будет ссылка на change/design/tasks.

## 10. Метрики пилота

Минимальные метрики на 2-4 недели:

| Метрика | Как считать | Зачем |
|---|---|---|
| Time to first change draft | Время от старта Jira до первого `change.md`. | Понять, ускоряет ли процесс подготовку требований. |
| Change review rework | Число возвратов `change.md` на доработку. | Проверить качество первичного анализа. |
| Missing context count | Сколько раз при реализации не хватило docs/code контекста. | Улучшать manifest/navigation. |
| Test coverage delta | Добавлены ли тесты по change. | Не потерять качество без тестировщиков. |
| Spec drift incidents | Сколько раз код и docs разошлись после merge. | Проверить, работает ли verify/archive. |
| Analyst Git friction | Сколько раз аналитик блокировался на Git/Bitbucket. | Понять, где нужны шаблоны или обучение. |

## 11. План внедрения на 4 недели

### Неделя 1. Подготовка

- [ ] Провести вводную.
- [ ] Выбрать сервисы пилота.
- [ ] Перенести минимально нужную документацию.
- [ ] Создать `_sdd`.
- [ ] Выбрать первую простую задачу.

### Неделя 2. Первые рабочие режимы

- [ ] Провести один `explore` по выбранной области.
- [ ] Провести один `propose` или branch-diff по реальной Jira.
- [ ] Если выбран branch-diff, аналитик меняет docs в ветке.
- [ ] Агент создает `change.md` из propose или diff.
- [ ] Команда ревьюит change.
- [ ] Разработчик создает `design.md`/`tasks.md`.
- [ ] Фиксируются первые проблемы процесса.

### Неделя 3. Реализация и приемка

- [ ] Реализовать первую задачу в code repo.
- [ ] Обновить автотесты.
- [ ] Провести приемку аналитика.
- [ ] Проверить master-spec source.
- [ ] Архивировать change.

### Неделя 4. Расширение

- [ ] Провести второй change, желательно сложнее или сквозной.
- [ ] Сравнить branch-diff и propose сценарии.
- [ ] Обновить гайд по итогам пилота.
- [ ] Принять решение, какие gates обязательны.

## 12. Риски и меры

| Риск | Симптом | Что делать |
|---|---|---|
| Аналитикам сложно работать с Git | PR не открываются, refs не готовы, правки идут мимо docs-hub. | Начать с Bitbucket UI, парной работы и короткого Git cheat sheet. |
| Агент делает механический пересказ diff | `change.md` не содержит смысла и критериев. | Требовать context files через manifest и review `change.md` по чеклисту. |
| Manifest устаревает | Агент не видит новые документы. | Refresh `_sdd` после крупных docs PR и перед важными changes. |
| Разработчики игнорируют `tasks.md` | Реализация расходится с design. | Сделать ссылку на tasks обязательной в code PR. |
| Нет автотестов | Приемка держится только на ручной проверке аналитика. | В DoD требовать тест или явное обоснование отсутствия теста. |
| Сквозной процесс распадается по сервисам | Каждый PR проверяет только свой кусок. | Для cross-service changes делать общий change и отдельные tasks по сервисам. |
| Документация противоречит коду | Споры в реализации, неясная приемка. | Фиксировать gap, не скрывать, решать через PO/аналитика и follow-up. |

## 13. Минимальные правила, которые стоит сделать обязательными

1. Любая неясная область начинается с `explore` или явного отказа от него.
2. Любой нетривиальный change должен иметь `change.md`.
3. Нельзя начинать реализацию, если change в статусе `На согласовании`.
4. Для branch-diff агент не делает checkout base/analyst веток.
5. Code PR должен ссылаться на Jira и change.
6. В `tasks.md` должны быть тесты или причина их отсутствия.
7. Перед archive должен быть verify master-spec source или manual apply.
8. Gaps и open questions не скрываются.
