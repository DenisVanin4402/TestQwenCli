# Рабочий гайд НСиР по SDD/OpenSpec

## 1. Для чего это команде

Команда НСиР ведет несколько основных сервисов, интеграции, бизнес-процессы, сервисную архитектуру, Docker/OpenShift контуры и фронтовую документацию. Сейчас значительная часть смысла живет в Confluence, а изменение по одной Jira-задаче часто размазано по нескольким страницам и выделено цветом.

Новая модель сохраняет предметный способ работы аналитиков, но переносит источник истины в Git:

- вместо Confluence-страниц - Markdown/контракты/диаграммы в `docs-hub`;
- вместо цветовых выделений - ветка, commit, diff и PR;
- вместо устного "смотри эти места" - `change.md` с источниками, влиянием и критериями приемки;
- вместо ручной передачи разработчику - `design.md` и `tasks.md`, которые связывают аналитику, код и тесты.

Главная цель - не добавить бюрократию. Цель - сделать так, чтобы изменение было понятно, ревьюируемо, реализуемо и проверяемо.

## 2. Базовые термины

| Термин | Что означает в НСиР |
|---|---|
| `docs-hub` | Git-репозиторий с аналитической, системной и фронтовой документацией по сервисам и сквозным процессам. |
| Master specification | Актуальное описание поведения сервиса или области. Это папка документов, а не один файл. |
| `_sdd` | Служебный навигационный слой для агента: manifest, navigation, coverage, stale-files. |
| `change.md` | Аналитическое описание изменения: что меняется, зачем, какие источники, влияние, критерии. |
| `design.md` | Технический проект реализации согласованного change. |
| `tasks.md` | Исполняемый план для разработчика и агента. |
| Explore | Режим исследования: агент читает документы и код read-only, строит карту контекста, gaps и вопросы. |
| Propose | Режим формулирования change через интервью с аналитиком и чтение master specification. |
| Branch-diff | Режим сохранения привычной работы аналитика: аналитик меняет master specification в ветке, агент строит `change.md` из Git diff. |
| Manual-change | Режим, когда требования сначала формулируются в `change.md`, а документы master specification обновляются явно позже. |
| Verify source | Проверка, что изменения master specification действительно присутствуют в ветке аналитика и соответствуют change. |

## 3. Целевая структура `docs-hub`

Рекомендуемая структура для сервисной документации:

```text
docs-hub/
  invest-dkz/
    workflow/
    integrations/
    model/
    dictionaries/
    openapi/
    settings/
    frontend/
  invest-pay/
    workflow/
    integrations/
    model/
    dictionaries/
    openapi/
  common/
    cross-service-processes/
    glossary/
    architecture/
  openspec/
    <service-or-domain>/
      _sdd/
        manifest.yaml
        navigation.md
        coverage.md
        stale-files.md
    changes/
      <change-name>/
        change.md
        design.md
        tasks.md
        .spec-diff/
```

Если команда решит хранить сами документы прямо под `docs-hub/openspec/<service>/`, это тоже допустимо. Важно не физическое имя папки, а правила:

1. У каждого сервиса или общей области есть один согласованный master-spec root.
2. `_sdd/manifest.yaml` описывает реальные документы и их связи.
3. `openspec/changes/` хранит активные изменения.
4. `openspec/changes/archive/` хранит завершенную историю.
5. `changes`, `archive`, `_sdd`, `_system` не используются как имена сервисов.

В примерах `docs-hub/...` показывает расположение в общем ландшафте репозиториев. Если агент запущен из корня самого репозитория `docs-hub`, пути обычно указываются без префикса `docs-hub/`: например `invest-dkz/...` и `openspec/changes/...`.

## 4. Что переносим из Confluence

Переносить нужно не оформление страниц, а структуру знания:

- сервисы и их назначение;
- интеграции сервиса;
- доменную модель;
- справочники;
- workflow и состояния;
- API/OpenAPI;
- настройки и эксплуатационные параметры;
- фронтовые сценарии, экраны, валидации;
- сквозные процессы между сервисами;
- известные ограничения, gaps и спорные места.

Цветовые выделения Confluence не переносятся как механизм управления изменением. Их заменяют:

- ветка аналитика;
- commit message с Jira key;
- Git diff;
- PR review;
- `change.md` как нормализованное описание изменения.

## 5. Роли

| Роль | Ответственность |
|---|---|
| Аналитик | Меняет master-spec документы, формулирует смысл изменения, ревьюит `change.md`, проверяет приемку. |
| Разработчик | Генерирует или дополняет `change.md`, создает `design.md`/`tasks.md`, реализует код, обновляет автотесты. |
| Владелец продукта | Подтверждает бизнес-смысл, приоритет, границы изменения и критерии приемки. |
| Tech lead / senior developer | Проверяет технический дизайн, миграции, влияние на сервисную архитектуру, Docker/OpenShift и интеграции. |
| Автотесты / разработчик тестов | Закрывает проверяемые критерии автотестами, если отдельной роли нет - ответственность остается у разработчика задачи. |
| AI-агент | Помогает читать docs/code, генерировать artifacts и выполнять tasks, но не принимает продуктовых решений за команду. |

## 6. Три режима работы аналитика

Аналитик НСиР может входить в SDD/OpenSpec-процесс тремя способами. Эти режимы не конкурируют, а закрывают разные рабочие ситуации.

| Режим | Когда использовать | Что получается |
|---|---|---|
| `explore` | Нужно разобраться в текущей области, найти документы, код, gaps и вопросы. | Карта контекста без изменения файлов. |
| `propose` | Есть идея или задача, но документы еще не изменены. | `change.md` через интервью и чтение master specification. |
| `change-from-diff` | Аналитик уже изменил несколько документов в ветке. | `change.md` из Git diff и `.spec-diff/` metadata. |

### 6.1. Explore

`explore` - безопасный read-only режим. Он нужен до change, когда область неочевидна или документация может противоречить коду.

Пример:

```text
Работаем по OpenSpec explore.
Исследуй область обработки входящего УЭСИД по сервису invest-dkz.
Найди workflow, модели, интеграции, фронтовые документы, gaps и вопросы.
Ничего не меняй.
```

После explore аналитик выбирает следующий шаг: оформить `propose`, вручную изменить документы в ветке или обновить `_sdd`.

### 6.2. Propose

`propose` нужен, когда аналитик хочет сформировать change вместе с агентом, а не начинать с ручных правок Markdown.

Пример:

```text
Работаем по OpenSpec propose для сервиса invest-dkz.
Нужно оформить change по NSIR-123.
Суть: <краткое описание изменения>.
Сначала задай вопросы по скоупу и источникам.
```

`propose` создает `change.md`, но не должен сразу переходить к `design.md` и коду.

### 6.3. Change-from-diff

`change-from-diff` сохраняет привычный сценарий Confluence-цветов: аналитик меняет несколько документов под Jira, только теперь эти изменения видны как Git diff.

Пример:

```text
Создай change из diff master specification.
service=invest-dkz
base_ref=release/2026-07
analyst_ref=analysis/NSIR-123-short-name
change_name=nsir-123-short-name
diff_mode=three-dot
```

Этот режим не делает checkout веток и не требует финального automatic apply-change по умолчанию.

## 7. Основной lifecycle для НСиР

### 7.1. Инициализация документации сервиса

Выполняется один раз на сервис или при крупном refresh.

1. Документация сервиса переносится в `docs-hub`.
2. Агент запускает `openspec-init-master-spec`.
3. Появляются или обновляются:

```text
_sdd/manifest.yaml
_sdd/navigation.md
_sdd/coverage.md
_sdd/stale-files.md
```

4. Команда ревьюит coverage gaps.
5. После этого сервис можно использовать как master specification.

Фраза агенту:

```text
Инициализируй master spec для invest-dkz.
Документы сервиса лежат в docs-hub/invest-dkz.
Собери manifest, navigation и coverage для работы SDD/OpenSpec.
```

### 7.2. Изменение требований через branch-diff

Это ключевой сценарий для задач, где аналитик уже понимает, какие документы нужно изменить, и хочет сохранить привычную модель "несколько страниц под одну Jira".

1. В Jira появляется задача, например `NSIR-123`.
2. Аналитик создает ветку в `docs-hub`, например `analysis/NSIR-123-product-type`.
3. Аналитик меняет все нужные документы: workflow, model, integration, frontend, справочники.
4. Аналитик коммитит изменения и открывает PR или передает ref разработчику.
5. Разработчик в своей рабочей ветке запускает `openspec-change-from-diff`.
6. Агент создает:

```text
openspec/changes/nsir-123-product-type/change.md
openspec/changes/nsir-123-product-type/.spec-diff/
```

7. Аналитик и разработчик ревьюят `change.md`.
8. После согласования статус меняется на `Согласовано`.
9. Разработчик запускает `openspec-design` и получает `design.md` + `tasks.md`.
10. Код реализуется в code repo.
11. После реализации выполняется verify: master-spec изменения уже есть в analyst ref, финальный автоматический merge в документы не требуется.
12. Change архивируется.

Фраза агенту:

```text
Создай change из diff master specification.
service=invest-dkz
base_ref=release/2026-07
analyst_ref=analysis/NSIR-123-product-type
change_name=nsir-123-product-type
diff_mode=three-dot
```

### 7.3. Изменение через propose

Этот режим нужен, если аналитик еще не правил документы, но хочет вместе с агентом сформировать change. Для НСиР это не временный fallback, а нормальный режим работы для новых или неясных требований.

1. Аналитик или разработчик описывает задачу в чате.
2. Агент читает `_sdd/navigation.md`, `_sdd/manifest.yaml` и релевантные документы.
3. Агент проводит короткое интервью.
4. Агент создает `change.md` со статусом `На согласовании`.
5. После ревью документы master specification обновляются явно в режиме `manual-change`.

Этот режим удобен для первых недель пилота, для новых требований и для задач, где сначала нужно договориться о смысле, а уже затем править master specification.

### 7.4. Реализация в отдельных code repos

Так как код сервисов лежит в отдельных репозиториях, нужно явно связывать docs и code:

1. В code branch указывать Jira key и change name.
2. В PR code repo добавлять ссылку на:
   - docs-hub branch/PR;
   - `openspec/changes/<change-name>/change.md`;
   - `design.md` и `tasks.md`, если они лежат в docs-hub.
3. Если `tasks.md` ведется рядом с change в docs-hub, разработчик отмечает выполнение там или синхронизирует статус в комментарии PR.
4. Если реализация изменила технический подход, сначала обновляется `design.md`, затем код.

Минимальный блок в code PR:

```md
## SDD/OpenSpec

- Jira: NSIR-123
- Change: docs-hub/openspec/changes/nsir-123-product-type/change.md
- Design: docs-hub/openspec/changes/nsir-123-product-type/design.md
- Tasks: docs-hub/openspec/changes/nsir-123-product-type/tasks.md
- Spec update mode: branch-diff
- Docs branch: analysis/NSIR-123-product-type
```

## 8. Статусы change

| Статус | Кто ставит | Когда |
|---|---|---|
| `На согласовании` | Агент при создании `change.md` | Change создан и идет на ревью. |
| `Согласовано` | Аналитик вручную | Смысл, scope и критерии подтверждены. |
| `В реализации` | Агент или разработчик | Началась работа по `tasks.md`. |
| `Реализовано` | Разработчик после проверки | Код, тесты и master-spec source проверены. |
| `Архивировано` | Агент при archive | Change перенесен в архив. |

Обратные переходы выполняются только вручную. Если change надо переделать, это должно быть видно в истории PR.

## 9. Правила для Jira

Одна Jira-задача должна ссылаться на:

- docs-hub ветку или PR;
- active change path;
- code PR, когда он появился;
- критерии приемки;
- тестовую проверку или автотесты.

Рекомендуемые имена:

```text
docs branch: analysis/NSIR-123-short-name
change name: nsir-123-short-name
code branch: feature/NSIR-123-short-name
```

Если одна Jira затрагивает несколько сервисов, есть два варианта:

1. Один cross-service change в `openspec/changes/<change-name>/`, если изменение сквозное и реализуется как один инкремент.
2. Несколько service changes, если задачи реально независимы и идут в разных PR.

Выбор фиксируется в Jira и `change.md`.

## 10. Review gates

### Gate 1. После `change.md`

Проверяем:

- понятна бизнес-цель;
- указаны все измененные master-spec documents;
- не спрятаны open questions;
- есть влияние на сервисы, интеграции, модели, фронт и конфигурацию;
- есть критерии приемки;
- нет технического плана реализации внутри `change.md`.

### Gate 2. После `design.md` и `tasks.md`

Проверяем:

- техническое решение соответствует change;
- затронуты нужные code repos;
- учтены Docker/OpenShift, конфигурация, миграции, мониторинг;
- tasks достаточно мелкие;
- есть задачи на тесты;
- есть verify master-spec source.

### Gate 3. Перед merge code PR

Проверяем:

- код соответствует `change.md` и `design.md`;
- автотесты добавлены или причина отсутствия явно зафиксирована;
- аналитик понимает, как принимать изменение;
- нет неучтенных расхождений с master specification.

### Gate 4. Перед archive

Проверяем:

- change в статусе `Реализовано`;
- source docs проверены;
- tasks закрыты;
- ссылки на Jira/docs/code PR сохранены.

## 11. Тестирование без отдельной роли тестировщика

Для НСиР каждый change должен иметь проверяемые критерии:

- что проверяет аналитик вручную;
- какие автотесты добавляет разработчик;
- какие интеграционные проверки нужны;
- какие регрессионные зоны затронуты;
- что проверяется в Docker/OpenShift окружении.

В `tasks.md` должны быть отдельные пункты:

```md
- [ ] Добавить или обновить unit-тесты бизнес-правила.
- [ ] Добавить интеграционный тест по измененному workflow.
- [ ] Проверить OpenAPI/контракт, если затронут endpoint.
- [ ] Подготовить сценарий приемки аналитика.
- [ ] Проверить конфигурацию для Docker/OpenShift, если затронуты параметры.
```

Если автотест невозможен или нецелесообразен, причина фиксируется в PR и `tasks.md`.

## 12. Работа с фронтовой документацией

Фронтовая документация является частью master specification, если изменение влияет на:

- экран;
- форму;
- валидацию;
- маршрутизацию;
- роли и доступы;
- тексты ошибок;
- доступность действия в зависимости от статуса workflow.

Для фронта в `change.md` должны быть:

- пользовательский сценарий;
- измененные элементы экрана;
- правила видимости и валидации;
- критерии приемки;
- ссылка на макет, если он есть.

Если фронтовая документация живет отдельно, ее путь должен быть в manifest и sources change.

## 13. Работа со сквозными процессами

Сквозной процесс не должен теряться между сервисами.

Если change затрагивает несколько сервисов:

1. В `change.md` должен быть раздел влияния по каждому сервису.
2. В sources должны быть и service docs, и общий cross-service документ.
3. В `design.md` должны быть отдельные решения по каждому code repo.
4. В `tasks.md` должны быть явно разделены backend, integration, frontend, config, tests.
5. Приемка должна проверять полный бизнес-процесс, а не только один endpoint.

## 14. Правила работы с AI-агентом

Агенту можно поручать:

- собрать manifest/navigation/coverage;
- найти релевантные документы;
- создать `change.md`;
- сделать технический дизайн;
- разбить работу на tasks;
- помочь реализовать tasks;
- проверить diff и consistency;
- подготовить summary для PR.

Агенту нельзя молча поручать:

- принимать продуктовые решения;
- расширять scope задачи;
- удалять требования из master specification;
- делать checkout чужих веток в branch-diff workflow;
- автоматически сливать произвольные folder-based docs;
- скрывать gaps или противоречия.

Правило: если агент нашел связанную проблему вне scope, она фиксируется как open question или follow-up Jira/change.

## 15. Что делать при противоречиях

Если документация, код и ожидание аналитика расходятся:

1. Не выбирать удобную версию молча.
2. Зафиксировать противоречие в `change.md` или `coverage.md`.
3. Уточнить у аналитика/владельца продукта.
4. Если решение влияет на scope, обновить `change.md`.
5. Если проблема отдельная, создать follow-up.

## 16. Минимальный пилотный процесс

Для первых 2-4 недель не нужно пытаться покрыть все сервисы.

Минимум:

1. Выбрать 1 сервис и 1 сквозной процесс.
2. Перенести достаточно документации, чтобы выполнить 2 реальные задачи.
3. Сгенерировать `_sdd`.
4. Провести 1 исследование через `explore`.
5. Провести 1 change через branch-diff.
6. Провести 1 change через propose для сравнения.
7. Зафиксировать трудозатраты, проблемы и качество результата.
8. После пилота решить, какие правила становятся обязательными.

## 17. Антипаттерны

- Перенести Confluence в Markdown, но продолжить работать "цветами" без веток и PR.
- Создавать один огромный master Markdown на сервис.
- Делать `change.md` как копию diff без анализа контекста.
- Начинать кодить до согласования change.
- Считать `tasks.md` бюрократией и не обновлять его по ходу реализации.
- Не добавлять тесты, потому что "аналитик потом проверит".
- Архивировать change, когда master specification и код не синхронизированы.
- Использовать AI-агента как замену ревью.
