SDD/OpenSpec framework

Master specification как папка документов

Обновленный workflow сохраняет дисциплину SDD, но больше не заставляет команду собирать всю спецификацию в один огромный Markdown. Existing docs становятся source of truth, а `_sdd` дает агенту карту чтения.

foldersource of truth лежит в `openspec/<service>/`
manifestагент выбирает документы без чтения всего дерева
diff`change.md` можно создать из ветки аналитика
Карта процесса source -> change -> code
01

Документы сервиса лежат в привычной структуре: workflow, integrations, API, data, security.

02

`openspec-init-master-spec` создает `_sdd`: manifest, navigation, coverage, stale-files.

03

04

`design.md` и `tasks.md` превращают требования в реализуемый инженерный план.

05

После реализации выполняется verify master spec, а не неявный merge в один файл.

01
Зачем меняем старую модель

Один большой Markdown больше не является центром framework

Для больших сервисов single-file master spec плохо масштабируется: документ становится тяжелым, агенту сложно выбирать контекст, а команда вынуждена переносить уже существующую документацию в искусственный формат.

БольПрактический эффектРешение
Монструозный specОбновлять и ревьюить один файл становится дорого.Master specification становится папкой документов.
Существующие материалыWorkflow, API, DBML, схемы и интеграции уже живут в разных файлах.Framework подключает текущую структуру вместо переписывания.
Слабая навигация для агентаАгент читает лишнее или пропускает связи.`_sdd/manifest.yaml` и `_sdd/navigation.md` дают карту чтения.
Аналитик меняет docs заранееПовторное интервью не нужно, но нужен `change.md`.`openspec-change-from-diff` строит change из git diff.
02
Целевая модель

Source of truth - `openspec/<service-name>/`

Master specification сервиса - это папка с документацией команды. Внутри может быть произвольная структура, которая отражает реальную работу проекта.

openspec/
  <service-name>/
    _sdd/
      manifest.yaml
      navigation.md
      coverage.md
      stale-files.md
    workflow/
    integrations/
    api/
    data/
    security/
    ...
  changes/
    <change-name>/
      change.md
      design.md
      tasks.md
      .spec-diff/
      .research/
    archive/

Главное различие

`_sdd` не является бизнес-требованием. Это навигационный слой, который помогает агенту и человеку быстро найти содержательные master-spec documents.

03
Принципы

Framework разделяет смысл, проектирование и исполнение

Source of truth

Текущее поведение описывает master-spec folder, а не один сгенерированный файл.

Delta-first

`change.md` фиксирует, что и зачем меняется, включая источники и критерии приемки.

Engineering layer

`design.md` и `tasks.md` отделяют технический план от аналитического change.

Targeted reads

Агент читает navigation, manifest и релевантные документы, а не все дерево подряд.

Explicit gaps

Противоречия попадают в open questions, а не решаются молча удобной версией.

Verify over merge

Для branch-diff финальный шаг - проверка source-of-truth docs в analyst ref.

05
Lifecycle

Нормальный путь от документации к реализации

teach

Понять workflow, выбрать следующий skill и не вернуться к single-file mental model.

init

Создать или обновить `_sdd` для master-spec folder.

change

Сформировать `change.md` через `propose` или `change-from-diff`.

review

Человек согласует смысл change и переводит статус в `Согласовано`.

design

Подготовить технический проект и источник требований.

tasks

Разбить реализацию на проверяемые шаги.

verify

Проверить код, tests, master spec source и архивировать change.

06
Два режима изменения

`manual-change` и `branch-diff` закрывают разные ситуации

Manual-change

Требование формируется через интервью, Jira или обсуждение. Агент читает master spec, задает вопросы и создает `change.md`.

идея -> propose -> change.md
  -> review -> design -> tasks
  -> code -> update docs -> refresh _sdd

Branch-diff

Аналитик уже изменил master-spec documents в своей ветке. Агент создает `change.md` из diff двух локальных refs.

base_ref ... analyst_ref
  -> git diff -- openspec/<service>/
  -> .spec-diff/ + change.md
  -> design -> tasks -> code -> verify
07
Правила чтения

Manifest делает чтение документации управляемым

  1. Сначала читать `_sdd/navigation.md`.
  2. Затем читать `_sdd/manifest.yaml`.
  3. Проверить `_sdd/stale-files.md`.
  4. Выбрать документы по `tags`, `entities`, `integrations`, `endpoints`, `events`, `related_files`, `depends_on`, `read_priority`.
  5. Если manifest отсутствует или stale, предложить `openspec-init-master-spec`.

Не скрывать противоречия

Если документы расходятся, агент фиксирует open question или gap. Он не выбирает удобную версию молча.

08
Branch-diff guardrails

Diff строится через git, но без переключения веток

Разрешено

git rev-parse --verify <base_ref>
git rev-parse --verify <analyst_ref>
git merge-base <base_ref> <analyst_ref>
git diff --name-status --find-renames <base_ref>...<analyst_ref> -- openspec/<service>/
git show <ref>:<path>

Запрещено автоматически

git fetch
git pull
git checkout <base_ref>
git checkout <analyst_ref>

Default semantics

По умолчанию используется three-dot diff: `git diff <base_ref>...<analyst_ref> -- openspec/<service>/`. Two-dot допустим только по явному выбору пользователя.

10
Quality gates

Готовность определяется артефактами и проверками

Definition of Ready

  • Есть `_sdd/manifest.yaml` и `_sdd/navigation.md`.
  • `change.md` создан и содержит sources.
  • Выбран `Spec update mode`.
  • Gaps и open questions явно видны.
  • Change согласован человеком.
  • Для сложного изменения есть `design.md` и `tasks.md`.

Definition of Done

  • Tasks выполнены или исключения согласованы.
  • Кодовые PR прошли review.
  • Тесты, сборка и линтер выполнены или есть причина.
  • Master spec обновлен или подтвержден в `Analyst ref`.
  • Change переведен в `Реализовано` и архивирован.

Следующий блок

Детализация сценариев

Этот гайд намеренно останавливается на границе сценариев. Дальше стоит раскрывать отдельные walkthrough:

  • инициализация master spec;
  • создание `change.md` через `propose`;
  • создание `change.md` через `change-from-diff`;
  • переход к `design.md` и `tasks.md`;
  • реализация и verify master spec;
  • архивирование change.

Граница текущего материала

Разделы до этого места дают рамку framework. Подробные пошаговые сценарии лучше делать отдельным блоком, чтобы не смешивать концепцию, правила безопасности и walkthrough.
