## 1. Предпосылки доработки openspec под свои нужды
1. Команда НСиР развивает проект уже 3+ года, за это время скопилась обширная документация в confluence по 10 сервисам и библиотекам
2. Подход работы в команде - аналитики дорабатывают конфлюенс - вносят изменения в существующую документацию (помечают изменения цветом) - разработчики на основе изменений дорабатывают код
3. Актуальность документации коду очень высокая. Без изменения документации код не имеет права быть изменен (кроме багов)
4. Формат документации в конфлюенсе - разбитая на разделы структура по каждому сервису (интеграции, справочники, доменная модель, бизнес-сервисы, описания фронта и действий)

Терминология: 
 - Мастер-спецификация - структурированный набор документов, описывающих поведение системы, которое в реализовано в настоящий момент
 - Новая Feature, Доработка - изменение документов мастер-спецификации (с пометкой), описывающие новое поведение системы или корректировку существующего
  

Нарисовать схематичную диаграмму процесса разработки: Аналитик -> Изменение файлов в Confluence (цвет) -> передача в разработку -> снятие цветовой раскраски после реализации
Нарисовать схему мастер-спецификации: Сервис (Под ним стрелочками)
   - Бизнес-процессов (80+ шт, 5+ шагов в каждом)
   - Интеграции (15+)
   - Справочники (50+)
   - Формы UI (30+)
   - Алгоритмы обработки действий UI (80+)

## 2. Задача перевода документации в MD формат 
1. Задача по переводу аналитики в md формат в bitbucket/git встала еще до внедрения OenSpec. Понимали, что это основа для внедрения подхода sdd.
2. Был попробован реверс инжиниринг из кода - получался не очень (сложно сделать уровень абстракции который есть в конфлюенсе - привязка к решению имплементации слишком явная, вместо описания алгоритмов и структур данных)
3. Был попробован перевод Confluence (собственные скиллы для этого, перевод через агента) в md - получилось лучше. Аналитиков устроило. 
4. Для пилотного сервиса работы с дебиторско-кредиторской задолженностью провели полный перевод аналитики в структурированный md формат
   4.1 создали отдельный git-репозиторий для хранения всей документации проекта в md (docs-hub) 
   4.1 после конвертации в Confluence получили структурированную папку с md файлами (~100 документов md)
   4.2 Структура разбита на технологические составляющие: в корне имя сервиса invest-dkz, внутри подпапки - dbml - схема бд as is, dictionaries - справочники - каждый в своем файле, model - доменная модель которая хранится в бд, workflow - бизнес сервисы (18 шт) , integrations- описания алгоритмов интеграции, openapi- формализованное описание интеграций, settings-настройки

## 3. Работа с OpenSpec
1. Подход OpenSpec показался перспективным. Посмотрели, подходит ли он для нашей ситуации.
2. Обнаружили, что с нашей существующей структурированной документацией в явном виде не получится работать:
   - Работа с OpenSpec в исходном виде подразумевает реверс инжиниринг - создание мастер спецификации из кода
   - Для большого проекта один или несколько больших Markdown-файлов по бизнес-капабилити становится узким местом.
   - Плохо масштабируется на существующую enterprise-документацию. 
   - Сложнее работать с OpenAPI/YAML/диаграммами/dbml артефактами как с равноправными частями master spec.

## 4. Адаптация под наши требования
1. Новый путь: подключаем в OpenSpec нашу сложную структуру аналитики как мастер-спецификацию и далее работаем по стандартному процессу
    - пользователь кладет документацию в openspec/<service>/, запускает openspec-init-master-spec;
    - агент создает папку _sdd где хранит информацию о структуре мастер-спецификации и использует ее при работе остальных этапов
2. Новый путь: аналитик может не делать change.md через анкетирование(propose), а просто меняет один или несколько файлов прямо в мастер спецификации, и потом change.md создается автоматом из diff
3. Остальные этапы остаются без изменений: propose -> review/approve -> design -> implement -> apply/verify -> archive 

## 5. Схематично
### Стандартная схема openspec:
```text
init -> propose -> review/approve -> design -> implement -> apply/verify -> archive
```

  init - инициализация мастер-спецификации доменной области через реверс-инжиниринг (один md)
  propose - 
  ...

### 6. Адаптированная схема
6.1. Инициализация и создание change.md через Propose
     - есть не подключенный сервис к OpenSpec (аналитика переведена в md формат и структурированно лежит в git)
     - аналитик запускает инициализацию мастер-спецификации из документации сервиса
     - делает изменение через 
   
```text
init-master-spec -> propose -> review/approve -> design -> implement -> apply/verify -> archive
```

init-master-spec - инициализация - подключение существующей структурированной мастер-спецификации сервиса 
[дописать]
...

6.2. Создание change.md через Propose
    
```text
propose -> review/approve -> design -> implement -> apply/verify -> archive
```

6.3. Cоздание change.md через Change-from-diff
 - Аналитик создает свою ветку в git и меняет файлы прямо в мастер-спецификации
 - Запускает создание дельта-спецификации (change.md) из разницы веток в гите.   

```text
 сhange-from-diff -> review/approve -> design -> implement -> apply/verify -> archive
```
