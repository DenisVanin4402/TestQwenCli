# Предметная модель и данные


Прочитай [стандарт](../reversa-analysis/references/standard.md). Вход — карта capability, используемые сценарии и источники; выход — общая предметная модель, определения, логические данные и применимые справочники.

## Содержательная работа

- Различай предметный объект, его идентичность, состояние, событие и производное представление. Например, «заказ» и «сводка по заказам» не обязаны быть двумя сохраняемыми сущностями.
- Для сущности зафиксируй определение, границы жизненного цикла, обязательные и необязательные свойства, единицы, точность, диапазоны, допустимые значения и правила отсутствия данных.
- Для отношений зафиксируй кратности, обязательность и инварианты. Не переноси физический внешний ключ в ER-модель без предметного смысла. Показатель «ровно N» уточняй текстом, если нотация схемы не выражает его точно.
- Для справочника укажи код и смысл значения, правила выбора, владельца ведения/источник актуальности, неизвестные и устаревшие значения. Неполный список маркируй неполным. Не придумывай административный интерфейс ведения по наличию таблицы.
- Для вычисляемых полей сослаться на алгоритм; формулу не дублировать в нескольких местах. Для сквозных сущностей определить одно каноническое описание.

Используй [модель](../reversa-analysis/assets/templates/domain.md), [логические данные](../reversa-analysis/assets/templates/data.md), [глоссарий](../reversa-analysis/assets/templates/glossary.md), [справочник](../reversa-analysis/assets/templates/reference.md). Схемы — встроенные Mermaid erDiagram/flowchart по [правилам диаграмм](../reversa-analysis/references/diagrams.md).

Проверяй согласованность понятий между данными, процессами и правилами. Имена полей внешнего сообщения оставляй, когда они нужны для понимания контракта. Внутренние классы, ORM, таблицы хранения и индексы переноси в приложение доказательств. При конфликте источников зафиксируй обе версии и вопрос, не выбирай молча удобную.
